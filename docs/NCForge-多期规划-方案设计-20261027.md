## 3. 一期架构

```
┌───────────────── NCForge（Tauri 2）─────────────────┐
│ 前端：Monaco 编辑器 + 文件树 + 面板（问题/日志/SVN/补丁/SQL） │
│ Rust 后端：文件读写与编码、文件监听、进程管理、配置        │
└────────┬────────────────────────────────┬────────────────────┘
         │                                │
   jdt.ls 0.57.0（ufjdk 1.8）        nc-core（Java 进程，ufjdk 1.8 运行）
   补全/跳转/引用/调用层级         classpath 生成 │ ecj 3.17 增量编译 │ SVNKit
                                    JDBC 只读查询 │ CFR 反编译 │ 补丁打包
         │                                │
         └──── 1909home + C:\work\aier 源码 + 测试库 aier260824 ────┘
```

- **nc-core 用 Java**：ecj、SVNKit、Oracle JDBC、CFR 都是 Java 库，现有 nc-db / NcSvn / 补丁工具代码可直接复用。前端通过 Rust 后端与它用 JSON 通信。JDBC 驱动直接用 NC home 的 `driver\oracle_11g`，不另带。
- **不带 JDK**：nc-core 与 jdt.ls 都用 NC home 里的 ufjdk 1.8 启动，每台开发机天然就有。
- **nc-core 同时提供 CLI**：一期只给工作台用；二期原样注册给 cc-bridge，远程 Claude 和按钮走同一引擎。
- **文件系统就是工作区**：没有 Eclipse 那样的 workspace 缓存，外部修改（包括远程 Claude 经桥的修改）由文件监听即时反映。

- 首次启动引导：自动发现 NC home 与源码目录。**同事的 NC home 目录名不一定叫 1909home，按内容识别不按名字**：同时满足「`startup.bat` 含 `nc.bs.mw.start.NCStarter`」「有 `modules`/`ierp`/`middleware`」「有 `ufjdk`」才算。查找顺序：Eclipse 工作区里 UAP Studio 配置的 NC home（存放位置 M0 核实）→ 各盘常见位置 → 手动选择；多个候选时列出版本与 jar 数供选择。

- 设置页：NC home、工程、数据库连接（默认只读）、内存上限。

### 附 A：jdt.ls 选型依据（2026-10-27 实测 + 官方 CHANGELOG）

| 版本 | 内核 | 运行要求 | 压缩包 / 解压 | 结论 |
|---|---|---|---|---|
| 1.64.0（最新） | — | Java 21 | 50MB / 52MB，另需精简 JRE21 约 40MB / 62MB | 要多带 JDK，不用 |
| **0.57.0**（2020-06） | jdt.core 3.22 | **Java 8**（已用 Java 8 实启，补全/定义/引用/重命名均正常声明） | 53.5MB / 55MB | **采用** |
| 0.59.0 起 | — | Java 11 | — | 不可用 |
| 0.35.0（2019-03） | jdt.core 3.17（与 eclipsehy 同内核） | Java 8 | 38.9MB / 40MB | 未采用，见下 |

选 0.57 而不选 0.35 的原因（均来自官方 CHANGELOG）：
- Windows 空闲时占 CPU（0.36 修复）；重新编译后补全缓存被清、补全变慢（0.37）；Windows 文件刷新慢（0.38）；jar 未变也频繁刷新 classpath（0.41）。
- **处理新建/重命名文件时会改写磁盘文件（0.56 修复）**——对 GBK 文件安全至关重要。
- 补全结果上限（0.49），7283 个 jar 下尤其需要；参数提示、查找实现的多处修复（0.38–0.49）。
- 新增调用层级（0.49）、跳到父类实现（0.43）、生成 getter/setter/构造器/toString（0.37–0.40）、移动/内联/重命名包等重构（0.42–0.55）、语义高亮（0.54）。
- 0.35 唯一优势是与 Eclipse 同内核，但编译本就用 ecj 3.17，该优势不再重要。
- 代价：0.57 已停止维护，遇到问题只能自行规避；NC 代码为 Java 8 语法且长期不变，可接受。

内存：jdt.ls 预计 1–2G（M0 实测），与现在 Eclipse 的 2G 上限相当。用工作台取代 Eclipse 后总内存基本持平。

## 附 C：M0 验证结果（2026-10-27，进行中）

验证脚本与原始结果在 `D:\AItool\aiwork\nc-workbench-m0\`（只读源码，输出写在该目录内）。

| # | 验证项 | 结果 |
|---|---|---|
| 2 | ecj 产物与 Eclipse 一致 | **通过**：用 eclipsehy 的 jdt.core 3.17 在 ufjdk 1.8 上编译，7 个模块共 379 个无编译错误的类，**377 个字节完全一致**（另 2 个在 gl 模块，差约 120 字节，原因待查） |

| 4 | 还原中间件启动参数 | 未做 |

**ecj 选型修正**
- 采用 **eclipsehy 的 jdt.core 3.17**，不用 NC home 自带的 `ecj-4.6.1.jar`：后者在同样两个模块上只有 17/30 字节一致。
- 必须加 **`-preserveAllLocals`**：Eclipse 默认保留未使用的局部变量（如 `catch (Exception var4)`），ecj 命令行默认会优化掉。完整参数：`-1.8 -g -nowarn -proc:none -preserveAllLocals`。
- jdt.core 的 jar 单独放在 classpath 里即可运行，入口类 `org.eclipse.jdt.internal.compiler.batch.Main`。
- 逐文件指定编码的写法是 `X.java[GBK]`（不带 `-encoding`）。
- 比对口径：只比对源文件本身没有编译错误的类（用 `-proceedOnError` 编译后排除有错误的）。各模块都有 10%–50% 的源文件因为引用了不在 NC home 里的类（如 `nc.itf.gsp.*`）而报错，这是工程环境的差异，不是编译器的差异，但意味着 M3 要把工程环境完整复现。

**classpath 的重大发现（影响 M1/M3/M4）**
- newar 的 `.classpath` 里没有写具体 jar，引用的是 UAP Studio 提供的 9 个「库容器」（`nc.uap.mde.library.container/Product_Common_Library` 等）。工作台要自己复现容器包含哪些 jar 及顺序；现有 `nc-compile` 技能生成的 `.nc-compile/classpath.args`（7205 条）可作参考。
- **把 7205 个 jar 全放进 classpath 不可用**：ecj 跑了近 3 分钟仍未出结果（CPU 几乎空闲，耗在打开 jar 上）。按需挑 jar（类名索引 58 万条 + import 静态推断）后，单模块编译只需 3–13 秒。工作台的 M3 必须采用这个思路。
- 按需挑 jar 时**顺序要按原 classpath 排列**；不要用「按简单类名猜 jar」的兜底，实测会引入错误版本、越补越乱。
- 把其他模块的 src 目录全部作为 `-sourcepath` 会让 ecj 连带编译被引用的源码，错误滚雪球，不可取；跨模块依赖应走各模块已编译的 `classes` 目录。
- `.settings/org.eclipse.core.resources.prefs` 记录了逐文件的编码（`encoding//ic/src/.../InsertBP.java=GBK`），工作台打开文件时应优先读它。

**源码编码/换行实测（共 13,778 个文件，114MB）**

| 项 | 数量 |
|---|---|
| GBK | 11,175（81%），解码再编码全部原样还原，无 U+FFFD |
| UTF-8（含中文） | 436（3%） |
| 纯 ASCII | 2,160（16%） |
| 纯 CRLF / 纯 LF | 13,260 / 191 |
| **混合换行（CRLF + LF/CR）** | **303**（2.2%） |
| 孤立 CR | 6 |
| 无结尾换行 | 2,433（18%） |
| 带 UTF-8 BOM | 2 |
| 既不是 UTF-8 也解不了 GBK | 7（实际是 `.metadata` 和语言包 properties） |

M2 编辑器的保存策略据此定为：
- 按文件原编码编码；BOM 有就保留；无结尾换行的保持无结尾换行。
- **混合换行文件（约 2%）不能依赖编辑器的统一换行**（Monaco 会按主导换行统一，这是已知行为，待 M2 实测确认）：保存时逐行比对原文件，未改动的行沿用原来的行尾，新增的行用主导换行。
- 无法解码的文件（极少）只读打开，不允许保存。

### 验证 2 补充:gl 里 2 个「不一致」的类查清了(2026-10-27)

结论:**不是 ecj 的问题,是 Eclipse 的产物里中文字符串常量是乱码。** ecj 3.17 与 Eclipse 的字节一致性实际是 379/379(排除这 2 个是 Eclipse 自己编错)。

- 证据:`VoucherBO.java`、`GLVoucherService4Fip.java` 两个源文件是合法 UTF-8、不是合法 GBK;`.settings/org.eclipse.core.resources.prefs` 里没有给它们登记 UTF-8,Eclipse 按工程默认 GBK 读,于是常量池里 `"接口"`(接口)变成了 `"鎺ュ彛"`(鎺ュ彛)。我方(逐文件探测编码,标 `[UTF-8]`)产物是正确的。
- 差异只在含中文的字符串常量;其余字节码逐条一致(javap 反汇编 18993 行仅这些行不同)。
- 影响面(只读扫描 newar 各模块 src):合法 UTF-8 且含非 ASCII 的 .java 共 78 个,其中 **53 个未在 Eclipse 偏好登记为 UTF-8**(uapbd 37、ic 5、pu 5、ct 2、gl 2、price 1、scmpub 1)。这些文件只要含中文字符串字面量,用 Eclipse 编出来的 class 里就是乱码(注释里的中文不受影响)。
- 是否已上线乱码:未核实。`gl/classes` 里的两个 class 是 2026-10-23 在本机 Eclipse 编的,线上补丁怎么编的要另查。

对工作台设计的含义(M3 编译):
1. 默认按「文件内容探测」决定编码(UTF-8 合法且有非 ASCII 则 UTF-8,否则 GBK),比 Eclipse 更正确。
2. 对「合法 UTF-8 但未在 Eclipse 偏好登记」的文件,编译时给出提示:该文件在 Eclipse 里会被按 GBK 编出乱码,避免用户拿 Eclipse 产物和工作台产物对比时困惑。
3. 编码登记(偏好文件)要在工作台里可视化与可编辑,否则用户在 Eclipse 与工作台之间切换会互相覆盖。
