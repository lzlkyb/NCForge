# 跨模块 Ctrl+点击「工作区源码优先」修复（2026-11-17）

用户报告：从别的类 Ctrl+点击 `DeliveryVO.java`，应该优先跳工作区里的源码，没有才回落 jar；
实际直接显示 jar（反编译/签名桩）里的内容。

## 1. 根因：不是前端排序，是影子工程只链一个模块

🔴 **最先设想的那条路是错的**。第一反应是「jdt.ls 返回了 file: 与 jdt:// 两条，前端没把工作区那条前置」。
逐层 grep 后否定：`navigationTargets.ts`、`langConvert.ts::toTargets`、`langProviders.ts::provideDefinition`
确实全都保序不排序，但**根本排不出第二条** —— jdt.ls 只给一条。

证据链（全部当场取证，不是推理）：

| 证据 | 内容 |
| --- | --- |
| `shadow.rs:357` | 注释写死「源码链接：**只链当前模块**，切模块时摘掉旧的」 |
| `shadow.rs:366-370` | `src_dirs` 只由 `spec.module` 拼出，`SRC_DIRS = ["src/public","src/client","src/private"]` |
| 实测影子目录 | `{config_dir}/lang/shadow` 下只有一个 junction：`ic → C:\work\aier\newar\ic`（另有历史 `aert.orphan-20261107-171104`） |
| 实测 `.classpath` | `kind="src"` 仅 3 条，全是 `ic/src/{public,client,private}`；`kind="lib"` 819 条 |
| `DeliveryVO` 归属 | `so/src/public/nc/vo/so/m4331/entity/DeliveryVO.java`（**so 模块**，389 个源文件） |
| `so` 在 classpath 里的形态 | 只有 `C:/work/aier/newar/out/so` 这个 **class 目录**（`kind="lib"`），**没有源码目录** |

结论：jdt.ls 眼里 `DeliveryVO` 只有字节码，`textDocument/definition` 只返回**一条 `jdt://`**。
前端加排序无效，必须在「知道源码在哪」的那一层动手。

工作区规模实测：**59 个有源码的模块 / 7522 个 `.java`**（`uapbd` 2451、`ic` 999、`pu` 879、`so` 389…）。

## 2. 为什么选「结果改写」而不是「链全部模块」

| | A 跳转结果按索引改写（**已采用**） | B 影子工程链全部源码模块 |
| --- | --- | --- |
| 做法 | jdt.ls 返回 `jdt://` 时解出 FQCN，查工作区类型索引，命中就换成真实 `.java` + 声明行列 | 59 个模块全建 junction，`src_dirs` 全量进 classpath |
| 改动面 | 新增 1 个纯逻辑模块 + `lang_request` 一处接入；**前端零改动** | `shadow.rs` 链接/清扫重写、`lang.rs` 单模块 URI 映射（`shadow_uri_of`/`rel_under`/`swap_prefix`）全改 |
| 代价 | 一次索引查表（已预热，毫秒级） | jdt.ls 索引量 999 → 7522 文件，冷启动与内存显著上涨（未实测） |
| 风险 | 索引未建好/未命中一律回落原行为，不会更差 | 触碰 URI 双向映射高风险区，补全/诊断/DAP 全依赖它 |
| 红利 | 定义/引用/实现一并受益 | 跨模块补全与诊断也变准 |

决策（用户 2026-11-17 拍板）：**先 A 再评估 B**。B 作为独立评估项，需先有冷启动实测数据。

架构一致性：`commands/type_search_cmds.rs:100-101` 搜类时早就是「工作区命中就把 jar 同名类滤掉」，
本次只是把同一口径用到跳转链路。

否则「跳定义对了、查引用还是 class」）。

### 3.1 三条硬约束

1. 🔴 **只改 `jdt://`**。`file://` 目标一个字不动 —— jdt.ls 解析到源码比索引准（索引不解析继承与局部变量）。
2. 🔴 **未命中原样回落**。索引没建好（`shared_opt` 返回 `None`）、类不在工作区、URI 形态不认 —— 全部保留原结果。
3. 🔴 **不重排、不增删条目**。Monaco 取第一条直接跳，顺序变了就是行为变了。

### 3.2 优先级与稳定性

同名类分布多模块时：**当前模块 > 路径字典序 > 行号**。当前模块优先是因为用户正在那儿干活；
其余按字典序只为**结果稳定**，不代表哪个更"对"。

### 3.3 嵌套类的已知近似

索引按「包 + **简单名**」记录（`build_state::typed_declarations` 的正则只取声明处标识符，不带外层），
所以 `p.Outer$Inner` 在索引里是 `p.Inner`。`exact` 先全等找，找不到再按「包 + 末段简单名」回落一次。

⚠️ 这条回落**可能选错同包内另一个外层的同名嵌套类**。取路径+行号最小的那条保证稳定；
真跳错了用户一眼能看出来，而完全不改写就必然停在反编译桩上。**宁可给出稳定的近似，也不静默不修**。

🔴 **两次「红灯没亮」都是我的测试/结论有问题，不是代码有问题**：

1. 拆掉 `starts_with("jdt://")` 守卫后 13 测试**全绿** —— 因为 `parse_jdt_uri` 本身就挡住非 jdt 地址，
   守卫是冗余的；且原夹具用的 `A.java`/`B.java` 索引里根本没有，查表返回空，守卫失效与否看不出差别。
   ⇒ 改用**索引里真有**的 `DeliveryVO` 做 `file://` 夹具，并补 `file_uri_never_rewritten_even_when_index_hits`。
2. 把嵌套回落的 `split_once('$')` 改成 `rsplit_once('$')` 后**全绿** —— 逐一枚举输入后发现
   **两种写法等价**（`$` 段里不含点号，包名推导结果相同）。我原先写在注释里的「rsplit 会算错包名」是**错的**，
   已就地更正为「等价，取第一个只是读起来直白」。
