# 自动编译：调研、实证与方案

> 2026-11-04 · 结论先行：**照搬 Eclipse 的引擎做不到（jdt.ls 承担不了），照搬它的「结果」可以（保存即出 class）**。
> 落地方式是 ecj 单文件编译，而不是整工程 jdt.ls 增量构建。
>
> 实测环境：Windows 10 / 32 GB / 工作区 `C:\work\aier\newar`（7377 个 .java）/ NC home `D:\ncc\1909home`（13 GB、12738 个 jar）/ jdt.ls 0.57 / JDK 1.8（`ufjdk`）。

---

## 1. 问题从哪来

现在的编译是**全手动**的，而且粒度很粗：

- 命令面板 / 文件树右键「编译模块 X」→ 走 `compile.rs`，**整个模块的全部源文件**丢给 ecj；
- 「编译全部模块」→ 按依赖顺序把所有模块逐个整编；
- 保存文件不会触发任何编译。

Eclipse 里改一个文件按 Ctrl+S，class 就出来了。用户提的正是这一点：**为什么我们要手动点**。

---

## 2. 先纠正一个我自己的错误前提

我上一轮说过「shadow-bin 是单工程单输出，表达不了模块布局，所以只能两层」。**这句话是错的**。

实测 `C:\work\aier\newar`：

```
.project      1 个   <name>ar</name>，buildSpec = javabuilder + nc.uap.mde.ModuleBuilder
.classpath    1 个   237 行
```

`.classpath` 里有 223 个 `kind="src"` 条目，全部属于**同一个工程**：

```xml
<classpathentry kind="src" output="aert/classes" path="aert/src/public"/>   ← 149 条自带 output
<classpathentry kind="src" path="pubapp/src/public"/>                        ← 74 条没有 output
<classpathentry kind="con" path="nc.uap.mde.library.container/*"/>           ← 9 个私有容器
```

`output` 是 **per-src 属性**，JDT 原生支持。所以「模块」在 Eclipse 眼里只是**输出路径的分组**，编译单位是 IProject，覆盖全部 7377 个 java 文件。**Eclipse 并没有「按模块增量编译」这回事**——它一次增量就管整个工程，靠依赖图把受影响的那几个 CU 挑出来重编。

## 3. 探针：能不能让 jdt.ls 干这活

探针脚本：`desktop/scripts/_probe-jdtls-build.mjs`，五个模式
（`micro | full | incr | manual | junction`），全程用临时 workspace，不动用户的开发实例。

### 3.1 per-src `output` 生效吗 —— 生效

小工程两个 src 目录分别配 `output=modA/classes`、`output=modB/classes`：

| 检查项 | 结果 |
|---|---|
| `modA/classes/pkga/A.class` | ✅ 生成 |
| `modB/classes/pkgb/B.class` | ✅ 生成 |
| 全局输出 `bin-default/` | 空 |
| `.classpath` 是否被 jdt.ls 改写 | 没有 |

jdt.ls 完全尊重 per-src output。这条路本身是通的。

### 3.2 关键坑：`java/buildWorkspace` 不是 executeCommand 命令

第一版探针发的是：

```js
{ command: "java/buildWorkspace", arguments: [true] }   // 走 workspace/executeCommand
```

结果 `No delegateCommandHandler for java/buildWorkspace`。我据此得出「0.57 不支持」的结论，**也是错的**。

去 GitHub 核对（lsp-java / nvim-jdtls）：

```elisp
(lsp-request-async "java/buildWorkspace" (lsp-json-bool full))   ; 第一个参数是方法名
```

它是 **`JavaProtocolExtensions` 的自定义 JSON-RPC 请求方法**，不是 LSP 命令，所以 `plugin.xml` 的 command 列表里永远查不到它。改成：

```js
await client.request("java/buildWorkspace", full);   // full = true 全量 / false 增量
```

0.57 **完全支持**：

| 场景 | 耗时 |
|---|---|
| 小工程首次 `buildWorkspace(true)` | 243 ms |
| 小工程改文件后 `buildWorkspace(false)` | 98 ms，class 真的重建了 |

参数语义来自 `BuildWorkspaceHandler`：`forceReBuild ? FULL_BUILD : INCREMENTAL_BUILD`。

### 3.3 整工程规模下的实测

影子工程用 junction 把 newar 的 109 个顶层目录链进来，`.classpath` 的 output 改写到影子内的 `_out/`（**不碰用户的 `<module>/classes`**）。

| 项 | 实测 |
|---|---|
| 整工程 import（重启到 ServiceReady） | **152.3 s** |
| 整工程全量 build（autobuild） | 12 分 22 秒（import 4m02 + build 8m11），产物 21526 个 class |
| 整工程手动全量 `buildWorkspace(true)` | **150.7 s**（返回 2 = WITHERROR，因为没挂 jar） |
| 无变更增量 `buildWorkspace(false)` | 35 ms |
| 改一个文件后增量 | 35 ms，**但 class mtime 没变（没重编）** |
| 内存峰值 | 936 MB（Xmx 2560） |

junction 对照实验（真实目录 vs junction 目录各改一个文件）：**junction 侧也是 true，能重编**。
所以整工程那次没重编不是 junction 本身，怀疑是跨盘 junction（影子在 D:、源码在 C:）导致 URI 解析不一致——没继续挖，因为下面的结论已经足够。

### 3.4 为什么这条路被否掉

不是「没命令」，是 **jdt.ls 每次启动都重建 workspace**。Eclipse 能秒级增量，靠两样东西：

1. 进程长期驻留（内存里的资源树与依赖图）；
2. `lastBuildState` 持久化（下次启动接着用）。

jdt.ls 把这两样都吃掉了：每次 initialize 全量 reconcile，152 秒起步。**换成整工程影子 = 每次打开应用多等 2.5 分钟**，不可接受。

顺带挖到一条有用的事实：vscode-java#451 —— Eclipse 工程每次启动都全量构建，根因是 `didChangeConfiguration()` 里做了 CLEAN_BUILD；0.57 字节码证实修法是「只有 `configureJVMs()` 返回 true 才全量」。**客户端每次启动都发 didChangeConfiguration 且 settings 有差异，就会白等一次全量。**

## 4. 方案：只学 Eclipse 的「结果」

保留现状：jdt.ls 继续做**单模块影子的索引 / 跳转 / 诊断**，`autobuild` 保持关闭（它只写 `shadow-bin`，写不到 NC 的 `<module>/classes`）。

自动编译改走 **ecj 单文件**：

| 层 | 谁做 | 何时 | 产物 |
|---|---|---|---|
| 索引 / 诊断 | jdt.ls 单模块影子 | 打开文件时 | `shadow-bin`（一次性的） |
| 产物 | ecj，**只编保存的那个文件** | 保存后 700ms 防抖 | `<模块>/classes`（与 Eclipse 同一个位置） |
| 产物兜底 | ecj 整模块 / 全模块 | 手动「编译模块」「编译全部」 | 同上 |

为什么不是「保存后整模块编」：模块动辄 2000+ 文件，一次几十秒，保存一次编一次等于编辑器卡死。
为什么不是「保存后 jdt.ls 增量」：见 §3.4。

### 4.1 实测：单文件编译 1.1 秒

`compile.rs::single_file_compile_live`（`#[ignore]`，真机快照）跑的就是这条路径：
`gl/src/private/nc/bs/gl/busirecon/BusiReconBO.java`，`seed_jars` 空（最坏情况，靠 import 现挑）。

```
模块 gl · 1 个源文件 · 按 import 挑出 16 个 jar
第 1 轮编译（16 个 jar）…
单文件编译：1149 ms · 16 个 jar · 1 轮 · 0 错误
```

1.1 秒里 JVM 启动占大头（约 0.9 s），ecj 真正编一个类是几十毫秒。所以：

- 保存后等 1 秒左右出 class，**和 Eclipse 的体感接近**；
- 想再快只能上常驻 daemon（见 §6），本轮不做；
- 挑出的 jar 只有 16 个（单模块整编是几十到上百），这也是它快的原因之一。

### 4.2 一条必须说明的代价

**单文件编译发现不了跨文件的签名变更。** 改了 `A.foo()` 的参数，只重编 `A.java`，引用它的 `B.class` 还是旧字节码——编译不报错，运行期 `NoSuchMethodError`。

Eclipse 靠依赖图解决这件事，我们没有（jdt.ls 的依赖图拿不到，自己建要到 P3）。所以：

- 自动编译**只做单文件**，定位是「语法错误 / 拼写错误 / import 缺失」的第一道网；
- 改签名、改继承、动接口这类改动，仍然手动「编译模块」；
- 界面上要明说，不能让用户以为「保存没报错 = 一切都对」。

### 4.3 与现有编译的关系

- 自动编译结果**合并进同一个 `compileResult`**：只替换该文件的问题条目，其它文件的历史问题保留。
  不这么做的话，保存一次就把你上一轮整模块编译的 20 条错误全清了，用户会以为都修好了。
- 自动编译**不投送元数据**（投送是 upm 相关，与单个 class 无关），也不触发重启。
- 自动编译**抢不到编译闸就静默跳过**（用户正在手动编译），不弹错。
- 自动编译**不自动打开底部面板**——每次保存都弹面板是骚扰；状态栏的编译 chip 会更新，问题面板按需去看。

### 4.4 开关

配置项 `auto_compile`（默认开），设置 → 任务页。「默认开」的理由：这就是用户要的行为；关掉的场景是低配机器或大批量替换时嫌吵。

首次自动编译会触发类索引构建（10~100 秒，之后走 `class-index.bin` 缓存）。这段时间状态栏显示「编译中…」，不阻塞编辑。

## 5. 落地清单

后端：

- `config.rs` 加 `auto_compile: bool`（默认 true）；`commands/system.rs::ConfigPatch` 加同名字段。
- `commands/compile_cmds.rs` 新增 `compile_file(path)`：
  - 复用 `resolve_module`；只收 `.java`；
  - `CompileSlot` 拿不到 → 返回 `Ok(None)`（跳过，不报错）；
  - `CompileJob { files: Some(vec![file]), .. }`，`out_dir` 仍是 `<模块>/classes`；
  - 不更新模块 seed（单文件挑出的 jar 是子集，覆盖整模块 seed 会让下次整编多跑几轮）；
  - 不投送元数据。

前端：

- `lib/autoCompile.ts`：`isAutoCompileTarget` / `mergeFileResult`（纯逻辑，单测）；
- `lib/autoCompileQueue.ts`：模块级防抖队列（700 ms），`useFileSave` 保存成功后入队，`useModuleCompile` 消费；
- `lib/compile.ts::compileFile`；
- 命令面板新增「编译当前文件」。

## 6. 后续（本轮不做）

- **依赖图 + 受影响文件集合**：真正的 Eclipse 语义。要自己解析 `.java` 的引用关系建图，
  与 jdt.ls 的 `workspace/symbol` 或自建索引配合。这是 P3 的活。
- **常驻 daemon**：像 rust-analyzer / Ristretto 那样常驻一个 JVM，省掉每次 ~1 s 的启动开销。
  `nc_index` 目前是每次编译进程内复用，跨次仍要重建。
- **编译诊断接 Monaco**：现在问题面板有，编辑器里没有波浪线（jdt.ls 的诊断只在打开的文件上）。

## 7. 探针脚本说明

`desktop/scripts/_probe-jdtls-build.mjs`（与 `_probe.mjs` 同类，不进安装包）：

```bash
node scripts/_probe-jdtls-build.mjs micro      # per-src output 是否生效
node scripts/_probe-jdtls-build.mjs manual     # java/buildWorkspace 能不能调、增量多久
node scripts/_probe-jdtls-build.mjs junction   # junction 链进来的源码会不会被漏掉
node scripts/_probe-jdtls-build.mjs full [mod] # 整工程影子（单模块 / 全量）
node scripts/_probe-jdtls-build.mjs incr <root> <data> <cfg>   # 二次启动 + 增量
```

⚠️ **探针会在 `D:\tmp\ncf-probe\<root>` 里建 junction 指回真实源码。绝不要对那个目录做递归删除**
（`fs.rmSync(recursive)` / `rm -rf` 会沿 junction 删进 `C:\work\aier\newar`）。清理只能用
`[System.IO.Directory]::Delete(path, $false)` 逐个非递归摘除。脚本本身已经改成一次性目录 + 不递归删根。
