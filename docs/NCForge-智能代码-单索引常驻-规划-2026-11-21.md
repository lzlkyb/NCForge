## 1. 决策与依据

| | 内容 |
|---|---|
| 决策 | 影子工程改为 **flat 形态**：1 个 Eclipse project + 全部源码模块的源根；jdt.ls **一次导入、常驻**，不再因跳模块重启 |
| 依据 | 用户明确「看代码时每个模块来回跳，跳过去还要等智能代码准备」不可接受 |
| 为什么现在能做 | flat 的代价是**一次性**的：导入 128.8s（现状 16.1s），内存 996MB（现状 921MB）。而现状的代价是**每次跳转** 10~40s。来回 N 次就亏 N 次 |
| 为什么不做 multi | 导入 280.2s、造影子 **554s**、1079MB，且收益与 flat 相同（都落源码）。multi 唯一优势是 project 隔离，为 1 个跨模块同名类付 2.2 倍导入 + 9 分钟造影子，不划算 |
| 不变的事 | 跨**工作区**（换工程）仍要重建，这一点行业软件也一样 |

## 2. 目标态

```
一个工作区 = 一个 jdt.ls 进程 = 一个 Eclipse project = 全部源码模块的源根
```

- 打开工作区 → 建/复用 flat 影子工程 → jdt.ls 导入一次 → 索引落盘
- 打开任意模块的 `.java`：**不再调 `lang_start`**，直接用现有会话
- 跳定义 / 查引用 / 补全 / 诊断：全部命中同一份索引，毫秒级
- 关闭软件再打开同一工作区：命中落盘缓存（warm），不再全量重建

## 2.5 与行业软件的逐条对照（2026-11-21 复核）

「对齐行业」要落到具体机制，不能只说「一个索引常驻」。下面把 IDEA / Eclipse-JDT / rust-analyzer
的共性拆成 6 条，逐条标明本规划是**照做**、**有理由偏离**，还是**漏了**。

### 骨架：三条照做

| 行业共性 | IDEA | Eclipse / JDT | rust-analyzer | 本规划 |
|---|---|---|---|---|
| 一个工作区 = 一个索引空间 | project + modules | workspace + projects | 单一 Index | flat 单 project ✅ |
| 引擎常驻，跳转不重建 | ✅ | ✅ | ✅ | ✅ S3 |
| 索引落盘 + 版本失效重建 | ✅ | ✅（`.index`） | ✅ | ✅ `data_dir` + `DATA_LAYOUT` |

### 偏离一：模块边界（有理由，但代价要认）

行业三家都**保留**模块边界：IDEA 的 module、Eclipse 的 project 各有自己的 `.classpath`。
本规划把 53 个模块压成一个 project，等于放弃这个边界。

理由不是「省时间」，而是 **NC 的模块本来就不构成 classpath 边界**：jar 统一从 NC home 收
（`eclipse_cp.rs:96` 注释：*jar 由 `middleware_classpath` 从 NC home 收*），模块之间只有
「源码互相引用」和「各自的 out/bin」。multi 那 280s 导入 / 554s 造影子，成本来自 53 次
OSGi bootstrap，不是来自 classpath 复杂度 —— 也就是说 multi 付了模块化的钱，却拿不到模块化的收益。

代价（必须写进已知差异）：
- 模块归属只能靠路径推断，jdt.ls 侧没有原生的「这个类属于哪个模块」
- 1 个跨模块同名 FQCN 要按字典序选一个

> 🔴 **2026-11-21 实测修正：这不是「偏离」，NC 官方本来就是 flat。**
> 本机 `C:\work\aier\newar\.project` 的工程名是 `ar`，**整个 NC 开发区就是一个 project**；
> 63 个模块**没有任何模块级 `.project`**；`.classpath` 是 223 条 `kind="src"` 覆盖 63 个模块的源根。
> 6 个 NC 启动配置的 `PROJECT_ATTR` 全部是 `newar`。
> ⇒ 结论反过来：**multi 才是偏离官方的做法**，flat 同时对齐行业与 NC 实施标准。
> 证据见 `NCForge-本地Eclipse-NC开发环境实测-2026-11-21.md` §2。
>
> 🔴 **2026-11-21 二次修正：`output` 不能照抄官方的路径。**
> 官方写 `output="gl/classes"`，我们的源根是 **junction**（`shadow/gl` → `ws/gl`），
> 照抄会让产物经 junction 写进 `C:\work\aier\newar\gl\classes` —— 违反「jdt.ls 不写用户文件」红线
> （`OUTPUT_DIR = shadow-bin` 就是为此存在）。
>
> 正确做法：**撤掉有源码模块的 class 目录**（这是必须的）+ src 的 `output` 指向**影子内**（可选）。
> 官方 `.classpath` 里 `kind="lib"` 是 **0 条**，本来就没有任何 classes 条目 ——
> 所以「撤 classes」与官方形态一致，不是权宜之计。
> `output` 只影响产物落点；我们 autobuild 关、不编译，所以它指向 `shadow-bin/<模块>` 即可，
> 既保留模块隔离（万一将来开 autobuild），又不碰用户目录。

### 偏离二：索引期间可用性（不是对齐，是工程替代）

IDEA / rust-analyzer 都是**后台索引 + 降级可用**（dumb mode：能编辑、能跳同类，全库功能禁用），
所以冷启动不阻塞。**jdt.ls 的 import 是同步阻塞的**，架构上做不到这件事。本规划的 S4「双进程
双阶段」是用工程手段绕过：先起 single 服务当前模块，flat 后台 ready 后接管。

效果上的确接近（冷启动即可干活），但机制不同，不能算对齐。要真对齐得换引擎（或不使用 jdt.ls 的
import，改走 `workspace/didChangeWatchedFiles` 渐进喂给它），那是另一个量级的方案。

### 缺口三条（本规划原来漏了，现已补进阶段）

| # | 缺口 | 查证 | 影响 |
|---|---|---|---|
| 1 | **增量更新没兜住** | `lang_notify` 是通用透传（`lang_cmds.rs:1005`），技术上能发；但前端只发 `didOpen`/`didChange`（`lang.ts:231/242/250`），**从未发 `didSave`，也没有 `workspace/didChangeWatchedFiles`**，后端同样没有 | 现在靠「切模块重启 + 重新导入」顺带吸收磁盘变化；**flat 不再重启后，外部改动（SVN 更新、Eclipse 里改）永远进不了索引**。而行业的核心恰恰是「建好之后永不重建，每次只增量」—— 这条现在是空的，已加 **S2.5** |
| 2 | 索引期间跳转不可用 | 全等 2 分钟，期间补全/跳转全废 | 行业是渐进可用。S4 只解决「能编辑」，不解决「能跳转」。列为已知限制，不做（换引擎才根治） |
| 3 | 预建 / 共享索引没提 | IDEA Shared Indexes、rust-analyzer 磁盘缓存分发 | NC 是「同一套代码库分发到多个实施现场」的形态，装完即带索引的收益比通用 IDE 更大。列为后续可选 **S6** |
| 4 | **完整工作流的「运行」没进视野** | 本机 Eclipse 用 `nc.uap.mde.launch` 跑 `nc.starter.test.JStarter`，`WORKING_DIRECTORY=${FIELD_NC_HOME}`，`-Dnc.runMode=develop` | 见下 |

> **缺口 4 展开**：本机 100 个 launch 配置里 16 个是 `nc.uap.mde.launch`。运行 NC 的官方口径是
> 「跑 `JStarter` 的 main + 工作目录 = NC home + `-Dnc.runMode=develop` 让客户端读本地 classes」，
> classpath 由 `nc.uap.mde.MiddlewareClasspathProvider` 现算。
> ⇒ 这意味着**编译产物布局必须与官方一致**（`<模块>/classes`），否则「编完直接跑」不成立。
> 本轮不新增「运行」功能，但 S1 的 output 改动必须满足这个前提，S5 用 ModuleBuilder 语义验收。

### 一个待核实的前提（已按实测降级）

~~`select_jars` 是按当前模块的源文件 import 精选，flat 之后 jar 集变成 53 个模块的并集，
最坏情况全部 jar 进 classpath，会拖慢解析。~~

**2026-11-21 实测修正**：官方 `.classpath` 里 `kind="lib"` 是 **0 条**，jar 全由 9 个
`nc.uap.mde.library.container/*` 自定义 container 动态解析 ⇒ 「全量库」在 Eclipse 里就是常态，
「jar 并集撑爆 classpath」的担忧**降级**（不是伪问题，但预期风险小得多）。

新问题变成另一半：**jdt.ls 用不了这 9 个 container**（自定义 container 要插件注册
`classpathContainerInitializer`，我们的独立分发没有用友插件）⇒ 必须展开成 `kind="lib"` 列表。
展开时按官方这 9 个维度分类（Ant / Product_Common / Middleware / Framework / Module_Public /
Module_Client / Module_Private / Module_Lang / Generated_EJB），比现在只按 import 精选更接近官方语义。

**S0 仍要量「展开后的 jar 条数与总字节」+ 该 classpath 下的导入耗时**，但不再作为「可能推翻 flat」的风险项。

## 2.6 S0 之后的方案再评估（2026-11-21）

### 实测堵死了一条路：import 期间零响应

`initialize` 返回后立刻 didOpen 探针，每 3 秒问一次 `definition`，**8 次全部 8 秒超时**，
第一次拿到源码结果就是 `ServiceReady` 的同一秒（107.4s / 3 模块 1384 文件）。

⇒ jdt.ls 的请求处理器在 import 期间**阻塞等待 job 完成**，不是「返回空」。这是设计，不是配置。
⇒ **「单实例 + 边导边用」不可能**，除非改 jdt.ls 源码。

### 三条路只剩两条

用户日常跨 **10 个以上**模块（2026-11-21 确认）⇒ LRU 常驻 2~3 个模块不适用。

| | A. 自建 flat + 双进程 | B. 桥接本机 Eclipse |
|---|---|---|
| 启动等待 | 46s 可编辑，**后台 3~6 分钟**后才跨模块可跳 | **0**（Eclipse 早已索引完） |
| 内存峰值 | ~1.7GB（single + flat 两个 JVM） | 不增加（复用 Eclipse 进程） |
| 跨 10+ 模块跳转 | 零等待（全量索引） | 零等待（全量索引） |
| 依赖 | 只要 NC home | **必须装 Eclipse + 用友插件 + 打开该 workspace** |
| 增量 | 要自己推 `didChangeWatchedFiles`（S2.5） | Eclipse 自己维护，不用管 |
| 工作量 | **7 天**（S1~S5，且含 URI 映射重写） | **2~3 天**（Eclipse 插件 + HTTP 端点 + 前端接入） |
| 风险 | warm 无效已实测；双进程切换状态复杂 | Eclipse 版本兼容、插件开发、双进程状态同步 |

### 为什么 B 突然变得有吸引力

IDEA/Eclipse 不慢，是因为**索引持久 + 增量 + UI 与索引解耦**；jdt.ls 把同样的工作量放进了同步 import，
所以我们感受到的是「3 分钟不能动」。B 直接复用 Eclipse 已经做好的那三件事：
本机 1018MB / 6136 个 `.index` 从 2021 年用到 2026，一次没重建过。

**代价是依赖性**：nc-workbench 如果必须靠 Eclipse 才能跳转，就失去了「不装 IDE 也能干活」的定位。
但 NC 实施人员本来 100% 装着 Eclipse（本机就是），所以「Eclipse 开着就桥接、没开就退回 single」
是一个可行的混合形态，而不是纯依赖。

### 建议顺序

1. **先花半天验 B 通不通**：写一个最小 Eclipse 插件，用 `SearchEngine` 做一次 `definition`，
   通过 HTTP 返回。通了就把 B 作为主路线；不通再回 A。
2. B 通之前**不动 S1**（flat 的影子生成改造）。A 的 7 天投入不应该在方案未定时开始。



| 环节 | 现状 | 目标 |
|---|---|---|
| 影子工程源根 | `shadow.rs:366` 只拼 `spec.module` 的 `SRC_DIRS` | 拼**全部有源码模块**的 `SRC_DIRS` |
| junction | `ensure_link` 只链当前模块（`shadow.rs:352`） | 每个模块一条，`sweep_shadow` 只摘「不在清单里的」 |
| class 目录 / 输出 | `project_class_dirs` 剔除当前模块自己的产物 | **剔除全部有源码模块**的产物（官方 `.classpath` 里本来就没有它们）；src 的 output 指向 `shadow-bin/<模块>`，**不能**写 `<模块>/classes`（junction 会写进用户目录） |
| 切模块 | `lang_cmds.rs:349` 「切模块 = 重启」：`shutdown()` + 重新 `launch()` | 同工作区内**不重启**；只有工作区根 / NC home / jdt.ls 变化才重启 |

| 前端触发 | `lang.ts:604 ensureLang` 打开 .java 就按模块调 `lang_start` | 只在服务**未启动**时调；模块变化不再触发 |
| 状态文案 | 每切模块都「正在准备…」 | 只在首次建索引时出现 |

## 4. 改动面（按依赖顺序）

### 4.1 `shadow.rs` — flat 生成

- `generate()`：`src_dirs` 从「当前模块」扩到「有源码模块清单」，用现有 `SRC_DIRS` 过滤存在性
- **每条 src 的 `output` 指向 `shadow-bin/<模块>`**（不写 `<模块>/classes`）。
  🔴 源根是 junction，`output="gl/classes"` 会写进用户工作区；官方那种写法在我们这里不可用。
  我们 autobuild 关、不编译，所以 output 只是给 JDT 一个「产物落点」声明，落影子内即可
- junction：为每个模块 `ensure_link`（探针 `tests/shadow_scale_live.rs:build_flat` 已验证这条路径可行）
- `sweep_shadow`：签名从「保留 module」改为「保留清单」（`&[String]`）。**必须保证失效 junction 被摘掉**，否则模块改结构后残留链接会让 jdt.ls 看到不存在的源根
- `own_output_dirs`：**扩到「全部有源码模块」** —— 这是必须的（原规划正确，我 2026-11-21 中途误判过一次，已改正）。
  官方 `.classpath` 里 `kind="lib"` = 0 条，本来就不含 classes；我们现状是 single 模式必须给它，flat 之后要撤掉
- 🔴 **`select_jars` 只调一次**：`select_jars(&index, &all_files)`（S0 实测 94.9s）。
  **不要按模块循环**（258s，同样结果）。结果按「NC home 指纹 + 模块清单」缓存到 `classpath.cache`，
  内容不变不重算
- 🔴 **源根按「真有 `.java`」筛**：S0 实测 59 个目录含 `SRC_DIRS`，其中只有 53 个真有源文件；
  按目录判会生成 6 个空源根，jdt.ls 报 classpath 警告
- 模块清单从哪来：**默认全工作区** —— 扫工作区根下「含 `src/public` / `src/client` / `src/private` 之一」的一级目录（实测 53 个 / 7522 `.java`）。**不要用 `eclipse_cp::graph().projects`**：那是**依赖闭包**，只覆盖主工程链到的模块，而用户跳的恰恰是闭包外的模块 —— 这正是要修的问题。另留 `lang.shadowModules = "all" | "closure"` 两档，S0 量出闭包规模后由现场决定。**单测钉住**「`.svn` / `bin` / `out` / `classes` 之类不算模块」

### 4.2 `lang.rs` — N 对前缀

- `LangSession`：`real_prefix` / `shadow_prefix` 两个 String → `Vec<(String, String)>`
- `shadow_uri_of`：按最长前缀匹配，命中不了才报「文件不在任何已链模块内」
- `to_server` / `from_server` / `swap_path_fields`（DAP）：依次应用全部前缀对
- 🔴 硬约束：**多对依次替换不能把上一步输出喂给下一步**（既有测试 `swap_prefix_only_touches_string_heads` 钉的是 `gl`/`gl2` 碰撞，必须继续绿）

### 4.3 `commands/lang_cmds.rs` — 生命周期去模块化

- `start_blocking` 的 `same` 判断：从「模块相同」改为「工作区根 + NC home + jdt.ls 目录相同」
- `data_dir_for`：key 去掉 `module`；`DATA_LAYOUT` 加一（旧缓存自然失效）
- `LangStatus.module` 保留（UI 仍显示当前文件属于哪个模块），但**不再驱动重启**
- 开关：新增配置 `lang.shadowMode = "flat" | "single"`，默认 `flat`。`single` 保留为回滚路径

### 4.4 前端 `lib/lang.ts`

- `ensureLang(path)`：删掉「模块不同就重启」的判断，只保留「未启动才启动」
- 模块切换不再走 `lang_start`；`startLangNow` / `restartLang` 保留（手动入口）
- `LangBadge` 文案：区分「首次建索引（约 2 分钟）」与「补全准备中」

### 4.5 编译链路（不改，但要核对）

`compile.rs` / `compile_file` 仍按模块收集源文件——编译是真按模块的，与索引的工程模型无关。**不动**，但要在 S5 回归「自动编译仍然只编当前模块」。

## 5. 阶段计划

### S0 · 前置测量（0.5 天，不改生产代码）

必须先把这三个数测出来，否则 S4 的首屏策略是猜的：

| 测什么 | 怎么测 | 用途 |
|---|---|---|
| flat **warm**（同工作区第二次起） | 扩 `shadow_scale_live.rs`：同一 data 目录跑两次 | 决定首屏要不要做双阶段 |
| flat 在真实 53 模块下的 **jar 精选 + 编码扫描耗时** | 计时 `select_jars` + `detect_encoding` 全量文件 | 决定要不要限制扫描范围 |
| flat 的**诊断噪声** | 统计 `publishDiagnostics` 条数与 CPU 占用 | 决定要不要按模块过滤诊断 |
| **全量 vs 依赖闭包** | `all`（工作区全部有源码模块）与 `closure`（`eclipse_cp::graph().projects`）各跑一次 | 决定默认档位；闭包若小很多且覆盖够，可以用更便宜的档 |
| **jar 并集规模** | 53 个模块的 `select_jars` 结果取并集，比条数与总字节；再用并集 classpath 导入一次计时 | 预算是 128.8s 之外还要加多少；若并集暴增则考虑「按模块分档的 jar 子集」 |
| **增量是否真的生效** | 导入完成后用外部命令改一个 `.java`（模拟 SVN 更新），不重启，观察 30s 内 definition 是否指向新位置 | 决定 S2.5 是否必须自己推 `didChangeWatchedFiles`，还是 jdt.ls 能自己感知 junction 变化 |

**验收**：`desktop/target/perf/shadow-scale.md` 里出现 flat warm 一行；三个数写进本文档附录。

### S0 实测结果（2026-11-21，本机 `C:\work\aier\newar`）

离线部分（不启 jdt.ls，探针 `tests/shadow_s0_offline.rs`）：

| 项 | 实测 |
|---|---|
| 模块 | **59** 个目录含 `SRC_DIRS`，其中 **53** 个真有 `.java` |
| 规模 | **7419** 个 `.java` / **62.0 MB** 源码 |
| 依赖闭包 `graph()` | **1** 个工程（`newar` 自己）—— 闭包完全覆盖不到模块 |
| `ClassIndex` | 4367 jar / 516601 类 / **63.14s**（冷，有缓存时接近 0） |
| `select_jars` 全量**一次** | **94.86s** → 并集 **1162** 条 jar / 92KB classpath |
| `select_jars` **逐模块循环** | **258.16s**（53 次重复解码，同样结果） |
| 基线 `ic` 单模块 | 563 条 jar / 24.4s |

**四个直接结论：**

1. 🔴 **造影子成本被严重低估**。原以为「flat 造影子 11s」，实际是 `select_jars` 94.86s + `ClassIndex` 63s（冷）
   ⇒ **冷启动 ≈ 95s（选 jar）+ 129s（导入）≈ 3.7 分钟**，比「11s + 129s」糟得多。
2. 🔴 **必须一次调 `select_jars(&index, &all_files)`，不能按模块循环**：258s → 95s，同样的结果。
   S1 实现里如果写成 `for m in modules { select_jars(module_files) }` 再取并集，等于白花 2.7 倍时间。
3. 🔴 **jar 并集必须缓存**（按 `NC home 指纹 + 模块清单` 做 key）。否则每次打开工作区都付 95s，
   而 92KB / 1162 条的 classpath 内容其实很少变。
4. **源根要按「真有 `.java`」筛**（59 → 53）。按目录判会生成 6 个空源根，jdt.ls 会报 classpath 警告。

在线部分（启 jdt.ls，探针 `tests/shadow_scale_live.rs`）：

| 项 | 实测 | 含义 |
|---|---|---|
| 真实目录的增量 | 改文件**不发通知**，10s 后 definition 已更新（行 2 → 4） | jdt.ls 能感知自己工程内的**真实目录**变化 |
| **junction 源根的增量** | 改真实文件后 12s，definition **仍停在行 2**（不穿透）；显式推 `didChangeWatchedFiles`（**junction 侧 URI**）后 10s 变成行 4 | 🔴 **生产形态不穿透，S2.5 必须自推**；URI 用 shadow 路径 |
| **flat cold 导入** | **154s / 187s / 355s**（三次同配置，见下） | 波动 2.3 倍，I/O 主导，不能承诺固定时长 |
| **flat warm（同一 data）** | cold 354.7s → warm **359.1s**，峰值 973MB → **296MB** | 🔴 **缓存命中了（内存降 70%）但时间没省** |

#### 🔴 warm 无效是本轮最重要的负面结论

同一 `-data` / `-configuration` 目录跑第二次：峰值内存从 973MB 掉到 296MB —— **说明缓存确实被读到了**；
但 ServiceReady 是 354.7s → 359.1s，**一点没快**。

⇒ 瓶颈不在「解析 AST」，而在 **jdt.ls 启动时的全量扫描 + 建立 JavaModel + 校验外部改动**，
这部分成本是 `O(文件数)`，缓存救不了。

直接后果：

1. **每次启动（含关软件再开）都要付 3~6 分钟**，不是「只有第一次」。
2. **S4 的双进程不是可选项，是必须**（否则用户开软件先干等 3 分钟）。
3. **S6 预建索引分发基本失效** —— 它省的是「解析」，而这里瓶颈不在解析。
4. 三次同配置差 2.3 倍（154 / 187 / 355），说明**磁盘 I/O 占大头**：机器刚跑完大量编译时最慢。
   对外文案不能写「约 2 分钟」，只能说「首次 3~6 分钟，取决于磁盘」。

> **这条动摇了「单实例 flat」的可行性**。需要在 S1 之前先做一个产品决策：
> 接受「每次启动后台烧 3~6 分钟 + 双进程」，还是换方案（见 §6.1 新增风险项）。

> 🔴 S0 的「增量」一项是**阻塞项**：如果 jdt.ls 在 junction 路径下完全感知不到真实文件变化，
> 那 flat 模式必须自带 `didChangeWatchedFiles` 推送，否则「不重启」会从优点变成缺陷
> （索引永远停在导入那一刻）。这条测出来才能定 S2.5 的工作量。

### S1 · 影子工程改 flat（1.5 天）

- 4.1 全部改动 + 单测（模块清单识别、sweep 摘链、每条 src 的 output 正确）
- 不改 `lang.rs`：此时 jdt.ls 已经能全量索引，但 URI 映射还是单前缀 → 跨模块文件仍打不开，属**中间态**

**验收**：源根数 = **真有 `.java`** 的模块数 × 实际存在的 `SRC_DIRS`；
每条 `kind="src"` 的 `output` 指向 `shadow-bin/<模块>`（**不是** `<模块>/classes`）；
`.classpath` 里不含任何「有源码模块」的 classes / out 条目（无源码模块保留）；
junction 数 = 参与模块数；
🔴 **`generate` 前后真实工作区的文件数与 mtime 不变**（证明没经 junction 写用户目录 —— 这是红线）；
`select_jars` 在一次调用内完成；连续两次 `generate` 第二次 `changed=false`。

### S2 · URI 映射 N 对（1 天）

- 4.2 全部改动

### S2.5 · 文档同步与增量（1 天，flat 的成败关键）

flat 之后不再重启引擎，**磁盘变化必须靠通知喂给 jdt.ls**，否则索引冻结在导入那一刻。

- **编辑器内改动**：前端保存后补发 `textDocument/didSave`（现在只有 `didChange`，只更新内存文档）。
  路径必须走 `shadow_uri_of`，不能发真实路径
- **编辑器外改动**（SVN 更新、Eclipse 里改、外部脚本）：新增 `workspace/didChangeWatchedFiles` 推送。
  触发点挂在文件树刷新 / SVN 更新完成之后，按「变更文件清单」批量发，不逐文件
- 🔴 **junction 的监视语义：已实测，不穿透**（2026-11-21，S0）。
  同一份 jdt.ls：普通目录源根改文件 10s 内 definition 自动更新；**junction 源根改真实文件，12s 后仍停在旧行**；
  推 `didChangeWatchedFiles`（**junction 侧 URI**）后 10s 才更新。
  ⇒ **不能依赖 jdt.ls 自动感知**，必须由我们全权推送。且 URI 用 `shadow_uri_of(真实路径)` 的结果
  （junction 侧）——实测这一路有效。
  > 真实路径那一档**没有单独验证**。理论上它不在任何源根内、会被 jdt.ls 丢弃，但本轮没测，
  > 实现时按「只用 shadow URI」写即可，不必去验证反向。
  > ⚠️ 顺带纠正一条早期判断：`probe-src`（普通目录）那次「自动感知成功」不能代表生产，
  > 生产每个模块根都是 junction —— 两者的差别恰好就是这次测出来的东西。
- 限流：批量更新（一次 SVN 更新几百个文件）合并成一次通知，避免把 jdt.ls 打满

**验收**：外部改一个文件的类名 → 5 秒内跨模块 definition 指向新位置；SVN 更新 200 个文件后
跳转全部正确；索引目录的 mtime 不出现「全量重建」迹象。

### S4 · 首屏策略（1 天，S0 已定结论）

S0 实测已经把这条分支定死了：**warm ≈ cold ≈ 3~6 分钟**，所以「直接等」不成立。

- **必须双阶段**：先起 single 实例服务当前模块（约 46s 可用），后台起 flat 实例，
  ready 后切换并销毁前者。峰值内存 = 两个 JVM 之和（约 1.7GB），需确认用户机器承受得住
- 🔴 **Phase 1 只能是语义实例，不能用语法实例**（`-Dsyntaxserver=true`）：语法服务器
  `importProjects()` 是空实现、不导入工程，实测 `documentSymbol`/`definition` 全空，
  拿不到任何跨文件跳转 —— 2026-11-21 实测 + 源码确认，见
  `docs/NCForge-GitHub调研-加速方案-2026-11-21.md` §2
- **文案口径**：不能写「首次」。warm 无效 ⇒ **每次启动软件都要等**。
  只能写「全量索引建立中（3~6 分钟），期间可用当前模块的语义功能」
- 双阶段失败必须能自动回落（flat 起不来就留在 single，并提示）
- 🔴 若产品无法接受「每次启动后台烧 3~6 分钟」，则 S1–S3 做完也不该默认开 flat，
  需要先做产品决策（回退 single 优化 / 桥接 Eclipse），**不要先写 S1 再回头推翻**

**验收**：冷启动 46s 内可编辑、可跳转当前模块；flat ready 后跨模块跳转全部命中且 PID 不变；
重启软件后**仍然**要 3~6 分钟（如实记录，不作为回归失败）。

## 6. 风险与对策

| 风险 | 依据 | 对策 |
|---|---|---|
| 陈旧字节码压过源码 | 11-17 实测：single 形态 definition 落 `jdt://`；multi 首版探针没撤 class 目录就落字节码 | **每条 src 带 `output="<模块>/classes"`**（官方 `newar/.classpath` 形态）：该目录是输出、不进 classpath 输入，机制上不会压源码。原「撤 class 目录」是错的做法，已改；S1 验收钉死 output 属性 |
| 跨模块同 FQCN 重复 | 7942 个类型里 1 个（`nc.ui.so.pub.findprice.FindSalePrice` 同时在 `medsoprc` 与 `so`） | flat 会多一个 duplicate type。按「路径字典序最小」稳定选一个，并在 S5 记为已知差异；**不为此改 multi** |
| 无源码模块 | NC 有些模块只有 `classes` | 撤 class 目录时**只撤有源码的模块**，其余保留，否则这些类会消失 |

| 53 个 junction 的清理 | 记忆里 `ensure_link` 的 orphan 逻辑 + 「rmtree 会顺链删目标」的教训 | `sweep_shadow` 只摘链接不递归；清理前后核对目标目录文件数不变 |
| 缓存目录语义变化 | `data_dir_for` key 含 module，flat 后每模块一份会各建一次全量索引（灾难） | key 去掉 module + `DATA_LAYOUT` 加一 |

| **jar 并集撑大 classpath** | `select_jars` 现按模块 import 精选，flat 后是 53 模块并集 | S0 已测：并集 1162 条 / 92KB，可接受；但**必须一次调用**（258s→95s）并缓存 |
| 🔴 **warm 无效：每次启动都 3~6 分钟** | S0 实测：同一 data 目录 354.7→359.1s，峰值 973→296MB（缓存命中但不省时） | ① S4 双进程必须做；② 对外文案「首次 3~6 分钟」不能写「约 2 分钟」；③ 若产品不接受，走桥接 Eclipse（复用其增量 build） |
| 首屏变慢被当成退化 | 46s → 154s 很显眼 | 文案必须写清「首次」与「约 2 分钟」；warm 数字要能立刻回答「为什么第二次快」 |

## 7. 回滚

`lang.shadowMode = "single"` 一处开关回到现状：`generate` 走旧的单模块分支、`data_dir_for` 带上 module、`ensureLang` 恢复切模块逻辑。
**要求**：S1–S3 的改动全部以这个开关为分支，不允许出现「只有 flat 能编译」的代码路径。

## 8. 明确不做

- **不做 multi**（53 个 Eclipse project）：贵 2.2 倍、造影子 9 分钟、收益相同（论证见 §2.5 偏离一）
- **不做 dumb mode**：不是「不值得做」，而是 **jdt.ls 的 import 是同步阻塞的，架构上做不到**。
  S4 的双进程是替代方案，不是对齐
- **不桥接本机 Eclipse**：本机已有一个 `nc.debug.bridge` 型插件（HTTP + 热重载），说明「外部进程 ↔
  Eclipse 插件」这条路技术上可做，且能零成本复用官方 1018MB 索引与 ModuleBuilder。
  但它要求用户装 Eclipse + 用友插件并在 Eclipse 里打开该 workspace，与「一体化工作台」定位冲突。
  **保留为可选加速档**（Eclipse 正开着时代理跳转/编译），不替代主路线
- **不碰跨工作区**：换工程重建是行业同样行为
- **不改编译链路**：编译仍按模块，与索引工程模型解耦
- **不引入新依赖**：jdt.ls 0.57 现有能力足够
- **不用语法服务器做 Phase 1**（2026-11-21 实测 + 源码双重否掉）：
  `-Dsyntaxserver=true` 在 0.57 里存在、6.2s 就能 ready，但 `SyntaxProjectsManager.importProjects()`
  **是空实现** —— 它不导入工程，我们的 223 个源根全被无视，`documentSymbol` 返回 `[]`、
  跨模块 `definition` 永远空。S4 的 Phase 1 只能是 **single 语义实例**。
  详见 `docs/NCForge-GitHub调研-加速方案-2026-11-21.md` §2
- **不为 `sharedIndexLocation` 升级 jdt.ls**：该能力 2023-01（#2341）才有，且只共享**库 jar** 索引；
  我们 warm 实测已证明索引能复用但时间不省，说明瓶颈在 import/build 而非 index
