# NCForge 代码搜索对标与超越方案（2026-11-10）

> 用户原话：「代码页面顶部搜索功能还是不够全面，现在能搜索的东西太少了，你看看别人做了哪些我们要超越对齐。」
> 本文只做对标与方案，**不含实现**。实施前需用户确认批次（见 §6）。
> 调研来源：VS Code 官方文档（Search View / Search Editor）、IntelliJ IDEA 2025.2/2025.3 帮助（Find in Path / SSR）、
> Eclipse 官方文档与 NC 社区实践（Ctrl+H File Search / Java Search）；NCForge 现状逐条有 file:line 证据。

## 1. 结论（TL;DR）

我们不是「什么都没有」——内容搜索的骨架（三档范围、大小写/整词/正则、按文件分组、虚拟滚动、替换、GBK 兼容解码、未保存 overlay）已经超过 Eclipse 的 File Search，与 VS Code 的差距集中在**范围粒度、结果再加工、语义过滤**三处，且**其中一处后端能力已经存在、只是前端没给入口**。

真正能「超越」的不是把 VS Code 抄全，而是三件竞品做不到的 NC 专属能力：**表名→引用结构化检索、中文（GBK）直搜、业务组件/classpath 链范围**。建议顺序：先补 P0 入口级缺口（1~2 天），再做 NC 杀手锏，最后才碰 Search Editor 这类重构建。

三条读表结论：

1. **范围粒度（目录/打开的文件/变更文件）是全场最大面积缺口**，而且 G2 的后端参数已经存在——这是投入产出比最高的一项。
2. **结果再加工（二次过滤/复制/导出/上限可调）**是 VS Code 用户肌肉记忆的一部分，我们没有，属于「不难但天天痒」。
3. **语义过滤与引用搜索**竞品靠语言服务，我们上 Java LSP 不现实（NC 工程编译环境不可控），但 NC 有自己的「轻量语义」可做（§5）。

## 5. 超越对齐项（竞品没有，我们做）

### 5.1 表名 → 引用位置（NC 杀手锏）

输入一张表（`bd_cust`、`pub_workcalendar`）或一个单据模板 key，结果**按载体分面**：

| 分面 | 检索对象 | 实现思路 |
|---|---|---|
| Java 引用 | 字符串字面量里的表名（`"bd_cust"`、`BD_CUST` 常量、`getTable("bd_cust")`） | 文本搜索 + 引号/括号上下文判定，无需 LSP |
| SQL | `.sql` 文件、Java 内嵌 SQL 字符串、sql 片段库 | 按扩展名 + 语言关键字（select/from/join/into/update）邻域判定 |
| 元数据 | `.bmf` / `md_*` 相关 XML/配置 | 已知 NC 元数据文件类型集合 |
| 模板/资源 | 模板文件、查询模板、portal | mask 预设 |

诚实标注：**分面是启发式**（引号/关键字邻域），不是解析器；误判率要实测（抽 20 个表人工核）。但对比「全文一锅粥」，分面本身就是数量级体验差。VS Code/IDEA 都不懂 `bd_cust` 是表名。

### 5.2 中文（GBK）直搜

NC 源码大量 GBK，中文注释、中文 SQL 备注、中文表名（`lengthb(x) > length(x)` 判中文的既有经验）。VS Code 默认对 GBK 会出替换符。我们已有 `decode_lossy` 兼容解码，把它做成**显式卖点**：搜索框输入中文直接命中 GBK 文件，并在 UI 上标注「已按 GBK 兼容解码」。

### 5.3 NC 范围三件套

- **业务组件范围**已有（manifest 登记模块）——保留。
- **hotswap 目标范围**：`src/client` / `src/public`（热替换分目标的既有概念 `hotswap::Target`）可直接作为范围预设——搜「这次要热替换的代码」只搜相关目录。
- **只搜打开的文件**：编辑器标签清单即范围，纯前端可做。

### 5.4 与日志/字典互通（不做重集成）

搜到表名时给一个动作「查数据字典（Ctrl+9）」「查 NC 日志（Ctrl+8）」——复用现有面板，不新建搜索域。这满足「统一入口」的诉求而不动四个入口的存量键位。

## 6. 分批方案（用户确认后实施）

### 批次 A：入口与范围（纯前端 + 已有后端参数，风险最低）

| 项 | 内容 | 涉及 |
|---|---|---|
| A1 | 文件树右键目录「在此目录中查找」；搜索框支持粘贴多目录（`opts.dirs` 已存在） | `TreeHeader.tsx`、`SearchBar.tsx` |
| A2 | mask 单框 → include/exclude 双框（保留 `!` 语法兼容），加 gitignore 联动开关 | `SearchBar.tsx`、`search.rs` 少量 |
| A3 | 「只搜打开的文件」范围档 | 纯前端 |
| A4 | 结果上限可选 500/2000/10000（后端 `maxResults` 已支持，放开 500 封顶） | `search.rs:54`、设置项 |
| A5 | 结果区：二次过滤框（在现有结果内再过滤）+ 复制路径 + 导出命中列表（txt/csv） | `SearchResults.tsx` |
| A6 | 编辑器顶部/标签条放「在工程中搜索」入口（点击展开侧栏搜索并聚焦） | `EditorGroupTools.tsx` |

### 批次 B：NC 语义层（本方案的核心差异）

| 项 | 内容 |
|---|---|
| B1 | 表名 → 引用分面（Java/SQL/元数据/模板），含误判率实测 |
| B2 | 语义过滤预设：「字符串字面量 / 注释 / 全部」——**轻量实现**：按上下文启发式（引号包裹、`//`、`/* */`、`--` 前缀），不上解析器；UI 明示「启发式」 |
| B3 | 类名/方法名 → 引用（利用现有 `search_types` 结果 + 整词搜索组合，Ctrl+Shift+G 键位复用 Eclipse 方案） |
| B4 | overlay 上限提高或按需全量读取（修 G11） |
| B5 | 替换：逐条 diff 预览 + 可取消 + preserve case；全部工程范围评估开放（先做预览，不直接放开） |

### 批次 C：结果页签化（重构建，最后做）

| 项 | 内容 |
|---|---|
| C1 | Search Editor：结果进文档面标签（复用现有 `doctabs` 双标签条架构），支持二次过滤、保存复用 |
| C2 | 搜索配置保存/复用（范围+mask+选项为一组） |
| C3 | Mark Occurrences 现状实测（Monaco 自带是否够用，不够再补） |

### 取舍说明

- **不上 Java LSP / 解析器**：NC 工程依赖 NCHOME，编译环境现场不可控，LSP 误报会摧毁信任。B 批次全部用「文本 + 启发式 + 文件类型」实现，接受并公示误判率。
- **不上倒排索引/多线程**：当前内容包顺序扫描在实测（NC 工程常见体量）够用；先只把上限做成可调，把「慢」的选择权交给用户。若批次 A 后仍有人反馈慢，再立项。
- **批次 C 不抢跑**：Search Editor 是 VS Code 的差异化功能，但我们的双标签条架构要做对成本高；A/B 做完看反馈再定。

## 7. 明确不做（对齐产品边界）

- AI 语义搜索 / NL2SQL / 自然语言描述找代码（14 项禁区，不因竞品有 Copilot 类功能重启）。
- 跨工作区/跨机器全局搜索。
- 全量 SSR（IntelliJ 的语法模板引擎）——B2 的启发式覆盖 80% 场景即可。
- 表数据 diff/ER 图式「关系视图」——禁区，搜索只给引用列表。
- 替换「全部工程」范围直接放开：不可撤销 + 跨工程，维持禁用直至批次 B5 的 diff 预览上线后评估。

## 8. 验收判据（每批次交付前自测）

| 项 | 判据 |
|---|---|
| A1 | 树右键目录 → 范围 chip 正确显示该目录；结果与手工 `dirs` 等价（同参数 CLI 对照） |
| A2 | `!test*` 旧写法行为不变；双框 glob 与 VS Code 语义一致（`{}`、`[!..]`、`.` 前缀各 1 例） |
| A4 | 上限调到 10000 时 20s 预算内返回或明确提示「已到上限」，不得静默截断 |
| A5 | 二次过滤只动视图不动结果集；导出文件可被 Excel/记事本打开 |
