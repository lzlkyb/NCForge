## 2. P0 严重（建议本周内修完）

> ✅ 本节 8 条已全部修复（2026-10-29，前后端门禁全绿）。

### P0-1　新建文件夹后永远显示「加载中…」，必须手动折叠再展开才出内容【M1·100% 复现】

- 位置：`desktop/src/components/workspace/useTreeEdit.ts:135`
- 现象：每次「新建文件夹」回车确认后，新目录展开，但子树位置永久显示「加载中…」；点它只会折叠，再点一次才真正发出读取请求。
- 证据：
  - `useTreeEdit.ts:135` `if (isDir) expand(created);` —— 只 expand 不 load，`dirs[created]` 缓存永远不存在；
  - `FileTree.tsx:155-161` `if (!state || state.status === "loading")` 渲染「加载中…」（`!state` 也走这支）；
  - `useTreeLoad.ts:91` toggle 只在「未展开且未加载」时请求，已展开项点击只会折叠。
- 建议：改为 `if (isDir) { expand(created); void load(created); }`（文件分支已有 `onCreated`，不受影响）。

### P0-2　运行中「清空日志」后，日志面板从此不再显示任何新输出【M5·崩溃排查路径上踩中】

- 位置：`desktop/src-tauri/src/commands/server_cmds.rs:371-384`
- 现象：服务运行中点「清空」，后端把 `middleware.log` rename 成 `.log.1` 再建空文件；但 java 进程持有的是 spawn 时传入的 File 句柄，后续全部输出继续写进 `.log.1`，新 `middleware.log` 永远是 0 字节。前端 offset 归零后读到空，面板定格「暂无输出」——而服务还在刷日志。用户在服务异常后最想做的就是清空重看，必然踩中。
- 证据：`server_cmds.rs:375` `let _ = std::fs::rename(&path, path.with_extension("log.1"));`；`server.rs:212-213` java 继承 stdout/stderr 句柄；`LogPanel.tsx:76-78` 清空后 `reset()`。
- 建议：运行中禁用「清空」（tooltip 说明「运行中清空后新输出会进 .log.1，建议停止后清空」）；或改为只把前端 offset 快进到文件末尾、不动磁盘文件。

### P0-3　「命令行」预览会重写 pathing jar，与启动并发写同一文件，可损坏 jar 导致服务起不来【M5】

- 位置：`launch.rs:280-307`、`commands/server_cmds.rs:387-409`、`components/tabs/ServicesTab.tsx:155-158`
- 现象：`server_command_line` 名为预览，实际调用 `middleware_spec` → `write_pathing_jar`，写的是 `config_dir/tmp/middleware-cp.jar`——与 `server_start` 正在写的是同一个文件、同一个 `.tmp` 中转名。启动准备期（`starting=true`，约 0.6s）点「命令行」，两个 spawn_blocking 任务交错写同一 tmp，rename 出来的是混合垃圾，JVM 报「找不到或无法加载主类」这类无从查起的错。另外「命令行」按钮只按 `previewing` 禁用，不看 busy/starting；服务运行中点它还会换掉运行中 JVM 正在使用的 pathing jar。
- 证据：`launch.rs:284` `let tmp = path.with_extension("jar.tmp");`（两条路径共用）；`ServicesTab.tsx:155` `disabled={previewing}`；`server_cmds.rs:403` 预览同样调 `launch::middleware_spec(...)`。
- 建议：预览改为复用上次启动已写好的 jar（`run.classpath_jar`）只读展示，不重写；若必须重算，启动进行中直接返回「上次启动还没完成」挡住。

### P0-4　已审标记的「本地覆盖层」刷新后不失效：文件被外部改过仍显示「已审」【M6·安全结论失真】

- 位置：`desktop/src/hooks/useSvnStatus.ts:31-47`
- 现象：`mark()` 把结果写进永不清理的 overrides Map，每次新扫描回来 `reviewed = 后端有效标记 + overrides 强制覆盖`。后端 `valid_marks` 会因 mtime/size 变化把标记剔除（`svn_cmds.rs:294-306`），但前端覆盖层又把它加回来。本仓的背景就是 Eclipse 与工作台并行用——标完已审后 Eclipse 改了该文件，回工作台点「刷新」，徽标仍是已审，用户据此跳过审查直接提交。`svn_review.rs:5-9` 的注释原话就是这「比不标更危险」，这条路径完整复现了该场景。
- 建议：overrides 只应在「尚未被下一次扫描确认」的窗口内有效——`status.data` 变化时清空 overrides，让 7.6s 扫描结果成为唯一真相；或 mark 成功后只做局部乐观更新，不引入跨刷新生命周期的覆盖层。

### P0-5　Blame 把 HEAD 版本的行信息与工作副本正文按行号硬配对：有本地改动的文件整篇错位【M6·结论全错】

- 位置：`desktop/src-tauri/svn-bridge/NcSvnBridge.java:245`、`components/svn/RightPane.tsx:128-138`、`components/svn/BlameView.tsx:35-42`
- 现象：`doAnnotate` 固定 annotate HEAD 内容，而右栏传给 BlameView 的正文是磁盘当前内容（`diff.data.workingText`）。对 letter=M/A 的文件（正是会进 SVN 页的文件），两侧行数与行内容都不同，BlameView 仍按 `src[i] ↔ lines[i]` 逐行绑定——第一处本地增删行之后，所有行的作者/版本/日期全部张冠李戴，且没有任何提示。`BlameView.tsx:17-19` 的注释「保证和差异面板看到的是同一份内容」说明作者意图就是工作副本正文，但 SVN 的 blame 先天只能基于仓库版本。
- 建议：仅对无本地改动的文件开放 Blame（其余在按钮 tooltip 说明「基于 HEAD，与本地改动不同行」）；或在 Blame 视图顶部加醒目的「行号对应 HEAD 版本」警示条。

### P0-6　补丁页 M/A 状态徽标全部显示 M【M7·每次进页面都看到】

- 位置：`components/tabs/PatchTab.tsx:58-62`、`components/patch/PatchList.tsx:133`
- 现象：`ChangeItem.path` 是 Java `File.getPath()` 原样透传（Windows 反斜杠、大小写原样，`NcSvnBridge.java:195`），而 `PatchItem.path` 经 Rust `pv::norm` 归一化为正斜杠（`patch_view.rs:19-21`）。letters Map 用原始 path 做键、用归一化 path 查找，Windows 上必败，全部落到 `?? "M"`。新增文件（A）也显示 M，用户无法从清单区分新增/修改。
- 建议：两侧都用 `svn.ts` 里已有的 `keyOf`（反斜杠转正斜杠 + 小写）归一化后再建 Map/查找。

### P0-7　jdt.ls 停止与启动竞态：关开关/切工作区后 700MB 孤儿进程 + 状态说谎【M4·窄窗口高后果】

- 位置：`desktop/src-tauri/src/commands/lang_cmds.rs:280`（注册）、`:324-330`（stop_now）、`:417-422`（关总开关）
- 现象：`stop_now` 只摘取**已注册**的 session；而 `launch` 从生成影子工程到注册 session 有数秒窗口。若 `lang_stop`、`lang_config_set`（关总开关）或切工作区的 `stopLang` 与 in-flight 的 `start_blocking` 并发，stop 拿到 `None` 直接置 stopped，launch 收尾时**不复检停止意图**，照常 `lock_lang(state).session = Some(...)` 并 set_status(indexing)。结果是：用户明确关掉了开关/换了工作区，一个约 700MB 的 jdt.ls 仍在跑（要等下次切模块被 Drop 才杀），状态栏还显示「正在建立索引」。
- 建议：stop 时给 `LangRun` 打「停止中/已作废」代际标记，launch 注册 session 前复检，已作废则直接 `client.kill()` 返回，不注册、不改状态。

### P0-8　运行中更换 NC home：自己的进程永远显示「启动中」，还可能提供「结束该进程」误杀他人 java【M5·破坏性】

- 位置：`components/tabs/ServicesTab.tsx:217-239`、`src-tauri/src/commands/server_cmds.rs:144-154`
- 现象：NC home 的 PathField 保存不检查服务运行态。运行中换成另一个 home 后，每次状态轮询都按新 home 的 prop.xml 取端口：新端口空闲 → 我们的 java 不在该端口监听 → `owned_by_self=false` → 状态永远「启动中」、端口永远「等待监听」，而停止按钮照常工作、用户无法从界面得知服务实际在跑；若新 home 的端口恰被另一个 java 占用，界面会弹出「端口被 java 占用」的冲突警报并提供「结束该进程」——用户很可能以为那是自己没停干净的残留而点下去。工程目录更换同理无「重启后生效」提示。
- 建议：运行中保存 NC home/工程时先弹确认（「服务正在运行，切换后要重启才生效」）；`build_status` 在 `cfg.nc_home` 与本次启动实际使用的 home 不一致时给出 `reason` 提示。

### 新发现：资源包目录名的路径穿越（P0，已修）

第 6 节写过「zip-slip 两遍式校验完备」——那条结论只覆盖了 **zip 条目名**
（`enclosed_name()` 归一化）。漏掉的是**入口侧**：`pack_dir` 用
`format!("{id}@{version}")` 拼目录名，而 `id` / `version` 直接抄自远端
`resources.json`（清单自述不签名），`ResourcesManifest::parse` 只查了非空。

探针实测（`tests/` 临时用例，跑完已删）：`version = "x/../../../evil"` 时
`pack_dir` 得到 `resources/ecj@x/../../../evil`，`create_dir_all` 会先建出中间
目录 `ecj@x` 再逐段回退，**文件最终落在配置目录之外**（实测落到
`%TEMP%\evil\MARK.txt`，`canonicalize` 确认在 cfg 之外）。而 `install_pack`
对这个路径做 `create_dir_all` / `rename` / `remove_dir_all`——即「写/删任意目录」。
利用前提是清单源被投毒（HTTPS 域名失守或 Gitee 镜像被改），与「清单不签名」
这一自述前提吻合，属于该模型下应当堵住的口子。

修法（两道）：
1. `ResourcesManifest::parse` 增加 `safe_component` 校验：只允许字母数字与 `._-`，
   拒绝 `.` / `..` / 空 / 超 64 字节 —— 坏清单在解析期就红。
2. `pack_dir` 内同样过一道 `safe_component`，非法值退化成 `invalid-id` /
   `invalid-version` —— 防本地 `resource-packs.json` 里的 `version` 绕过 parse。
回归测试：`manifest_rejects_path_traversal_in_id_or_version`、`pack_dir_never_escapes_resources`。
