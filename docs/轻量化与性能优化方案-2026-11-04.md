## 2. 优先处理的问题

### P1 / HIGH：SQL 当前语句高亮在主线程反复全量解析

位置：[SqlEditor.tsx:111](D:/AItool/winapp/nc-workbench/desktop/src/components/db/SqlEditor.tsx:111)、[sqlSplit.ts:63](D:/AItool/winapp/nc-workbench/desktop/src/lib/sqlSplit.ts:63)、[sqlSplit.ts:199](D:/AItool/winapp/nc-workbench/desktop/src/lib/sqlSplit.ts:199)。

光标移动、选择变化、内容变化都会安排高亮。高亮先调用 `statementAt`，该函数完整执行一次 `splitStatements`；随后为了判断是否有多条语句又执行一次切分。每条语句的起止行号通过 `lineAt` 从全文开头重新计数，成本随语句数量和文本长度相乘增长。`requestAnimationFrame` 只合并调用时机，不会把解析移出主线程。

**方案：** 切分时在同一遍扫描中累计行号；按 Monaco model 和版本缓存语句区间；光标移动仅在区间中定位，不重新取全文或切分。先用现有解析器实现与缓存验证收益，若内容变化仍产生超过 50 ms 的长任务，再将解析移到 worker。

**验收：** 同一份 144890 字符脚本，移动光标 P95 ≤ 16 ms；内容变化解析目标 ≤ 50 ms。保留 PL/SQL 块、q 引号、注释、独立 `/`、执行当前语句和行号映射的回归测试。

### P1 / HIGH：SVN 勾选集合被反复线性扫描

位置：[svnDraft.ts:25](D:/AItool/winapp/nc-workbench/desktop/src/lib/svnDraft.ts:25)、[svnList.ts:12](D:/AItool/winapp/nc-workbench/desktop/src/lib/svnList.ts:12)、[SvnFileRows.tsx:7](D:/AItool/winapp/nc-workbench/desktop/src/components/svn/SvnFileRows.tsx:7)。

`isSvnPicked` 每次展开整个 Set，并对路径逐项替换分隔符、转换大小写。模块计数、每行复选框、同步草稿和“已选”筛选都会调用这类判断。全选时形成近似 O(行数 × 已选数) 的开销。当前基准还没有计入 JSX 创建、布局与绘制，所以不能将 2.06 秒当作完整页面的上限。

**方案：** 在草稿更新时建立规范化路径集合，判断统一使用 `has(keyOf(path))`；提交时保留原始路径。一次遍历汇总筛选计数，避免每个过滤标签各扫一遍。较大的清单使用可视行渲染。

**验收：** 3000 行全选的成员判断目标 ≤ 10 ms，点击、勾选和筛选 P95 ≤ 100 ms；大小写与分隔符差异、提交范围、刷新不扩大勾选范围、组内半选继续正确。

### P1 / HIGH：Java 切模块会丢弃上一模块的索引缓存

位置：[lang_cmds.rs:337](D:/AItool/winapp/nc-workbench/desktop/src-tauri/src/commands/lang_cmds.rs:337)、[lang_cmds.rs:413](D:/AItool/winapp/nc-workbench/desktop/src-tauri/src/commands/lang_cmds.rs:413)、[lang_cmds.rs:428](D:/AItool/winapp/nc-workbench/desktop/src-tauri/src/commands/lang_cmds.rs:428)。

当前一个语言会话只负责一个模块。切模块时关闭旧 JVM；模块名变化时删除统一的 `jdtls-data`，之后重新生成影子工程、加载全 NC 类名目录并启动语言服务。因此 A → B → A 不能直接复用 A 的工作区索引。缓存隔离是必要的，但用删除旧缓存实现隔离会损失速度。

类名目录即使命中 JSON 缓存，仍会解析清单、逐 jar 取元数据、克隆名字、排序。当前已添加取消检查，这部分不再作为“不能取消”的问题；重复加载本身仍值得优化。

**方案：** 按“工作区、模块、NC 环境指纹、语言服务版本与配置”隔离影子工程和索引目录，复用近期模块的磁盘缓存；全 NC 类名目录按环境共享，环境不变时复用内存对象。保留单个活动 JVM，控制磁盘缓存总量与最近使用淘汰。

**验收：** A → B → A 不删除 A 的有效索引；NC jar、工作区、JDT 版本或相关配置变化时正确失效。与实施前同环境基线相比，返回已索引模块的就绪耗时目标降低至少 50%。固定秒数需先取得真机基线。

### P1 / MEDIUM：语言请求前重复读取已同步文档，改动同步仍传全文

位置：[lang.ts:165](D:/AItool/winapp/nc-workbench/desktop/src/lib/lang.ts:165)、[langProviderContext.ts:21](D:/AItool/winapp/nc-workbench/desktop/src/lib/langProviderContext.ts:21)。

`syncDoc` 先 `getValue()`，进入串行队列后才检查文档是否已同步。补全、悬停、符号等请求前会等待同步，即使版本没变化，也会走一次取全文。真正有变化时，每次通知包含完整文档；大文件显示降级没有减掉这一项成本。

**方案：** 已同步版本直接等待现有 pending promise，同版本在途同步复用 promise；支持增量同步的服务使用 Monaco 变更范围，首次打开及恢复失败时发送完整文本。保持通知完成后才允许语义请求的顺序。

**验收：** 已同步文档连续 100 次 flush 不再取全文；在途 didOpen / didChange 必须被等待；同步失败能够恢复。增加 UTF-16、中文、表情、多处编辑、撤销重做与模块切换场景，保留已通过的同步回归用例。

### P1 / HIGH：类源码正文缓存没有上限，关闭标签不释放缓存文本

位置：[lang.ts:523](D:/AItool/winapp/nc-workbench/desktop/src/lib/lang.ts:523)、[lang.ts:586](D:/AItool/winapp/nc-workbench/desktop/src/lib/lang.ts:586)、[editorStore.ts:33](D:/AItool/winapp/nc-workbench/desktop/src/lib/editorStore.ts:33)。

`jdtText` 保存源码请求的 promise，成功后的 promise 仍引用完整正文。删除仅发生于失败、反编译错误或显式强制刷新，缺少容量限制与会话失效清理。模型仓库已有 32 个 peek model 的上限，但该上限不约束正文缓存，关闭正式标签也不能清除缓存中的正文。

**方案：** 正文缓存增加按字节和条数的 LRU 上限，初始预算可设 32 MiB，并按环境 / 会话正确失效；超大单条不进入缓存。缓存淘汰不影响已打开 model，未保存内容和撤销栈继续由模型仓库持有。

**验收：** 连续浏览并关闭 1000 个不同的类，缓存始终在预算内；环境变化不返回旧正文；重复常用类仍能命中缓存。真机关闭标签后的堆快照与工作集不持续单向增长。

## 5. 实施顺序与取舍

| 批次 | 工作 | 交付与通过条件 |
| --- | --- | --- |
| 第一批：消除可复现卡顿 | SQL 单遍解析与版本缓存；SVN 规范化集合；Java 已同步文档快速路径；正文缓存上限 | 针对本报告规模的基准通过；现有相关行为测试继续通过；实际界面连续输入、勾选和光标移动验证 |
| 第二批：减少重复准备与后台竞争 | JDT 模块缓存隔离与目录共享；搜索取消；监听队列上限与合并期限；目录刷新并发控制 | A → B → A 热回模块复用；事件风暴与快速查询测试通过；不增加常驻 JVM 数量 |
| 第三批：收紧运行与首屏预算 | 发布版测量；Monaco 贡献拆分；大清单可视行；数据库 selector；服务状态探测缓存 | 冷热启动、空闲 CPU、工作集、长任务与交互 P95 达标，并加入回归门禁 |

前两批是改动范围清晰、可以独立验收的工作。第三批按实际瓶颈实施，避免尚未测量就引入新的缓存框架、线程池或依赖。工期需结合第一批修改与真机基线估算，本报告不把未知的 JDT 索引时间计成固定工期。

语言服务有两条可行路线：

| 路线 | 收益 | 成本与取舍 |
| --- | --- | --- |
| **A：单个活动 JVM + 模块独立缓存，建议先做** | 复用返回模块的索引，常驻进程数量可控 | 切模块仍有 JVM 启动与握手成本；实现与既有单模块语义接近 |
| B：单个长期 JVM 按需加载多个模块 | 可进一步减少切模块启动成本 | 需先验证 JDT 0.57 / Java 8 兼容、模块输出与依赖优先级、编码隔离和内存上限，再决定是否实施 |

如运行测量证明语言服务长时间闲置仍占较多内存，再增加安全的空闲回收：无语言请求、无索引、无调试依赖时释放，回来复用磁盘缓存启动。数据库事务与 NC 服务的生命周期由其实际业务操作决定，不用空闲计时器一并释放。

## 6. 建议验收预算

下面是下一阶段的目标，**尚未测出的启动和内存数据不是当前成绩**。以 Windows 16 GiB、SSD、发布版、固定工程为参考环境；主线程交互测至少 30 次，报告 P50 / P95，冷热缓存分开。

| 指标 | 初始目标与口径 |
| --- | --- |
| 冷启动到外壳可操作 | P95 ≤ 2 秒；不包含首次下载、JDT 索引和 NC 中间件启动 |
