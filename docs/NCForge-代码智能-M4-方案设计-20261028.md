## 1. 探针结论

探针脚本：`desktop/scripts/_m4a-lsp.mjs`（最小链路）、`_m4a-nc.mjs`（真实工程）、
`_m4a-def.mjs`（跳转能力边界）；复核探针 `D:\AItool\aiwork\nc-workbench-m0\m4v\probe.py`
（5 组对照，结果在同目录 `run.txt`）。全部跑在 ufjdk 1.8 上。

### 1.2 限制与坑

| 项 | 实测 |
|---|---|
| `classFileContentsSupport` 必须声明 | 不声明时 definition 对一切二进制 class 返回空数组（JDK 的 `List` 也一样）。初稿把这个现象当成了硬限制 |
| `initializationOptions.workspaceFolders` | **必须是 URI 字符串数组**；填 `{uri,name}` 对象时 initialize 整体失败（`LinkedTreeMap cannot be cast to String`）。`initializationOptions` 本身可以嵌套，`settings`、`extendedClientCapabilities` 都是嵌套对象，实测正常 |
| `java.configuration.runtimes` | 必须配（JavaSE-1.8 → ufjdk） |
| JDK 自身的类 | 只能看桩：ufjdk 不带 JDK 源码 |
| 只有 `.classpath` 没有 `.project` | 退化成 **invisible project**（日志：`created a workspace invisible project`），classpath 全部忽略，跳转永远空 |
| 绝对路径 lib 条目 | 可以用，jdt.ls 接受 |
| **诊断前约 20 秒不可信**（M0） | ~750 个 jar 时约 21~24 秒才稳定，期间发布 90+ 次不完整结果（满屏 `cannot be resolved`） |
| **超大文件补全恒为 0**（M0） | gl 的 `VoucherBO.java`（6433 行 / 267KB）返回 0 条；2036 行 / 69KB 正常。补全默认最多 50 条（`java.completion.maxResults`） |

**`.classpath` 路线已补测（M4c 开头，2026-10-28）**：lib 条目写 `sourcepath="..._src.jar"`（注意属性名是
`sourcepath`，不是初稿写的 `source`）后，`BaseDAO` 返回真实源码（41482 字节、带 javadoc），与
`referencedLibraries` 的 `sources` 映射等效。同时发现一个硬要求：**`.classpath` 必须有 JRE 容器条目**
（`org.eclipse.jdt.launching.JRE_CONTAINER/org.eclipse.jdt.internal.debug.ui.launcher.StandardVMType/JavaSE-1.8`），
没有它工程里就没有 JDK 的类，`List` 之类跳转 0 命中。

另外实测了编码登记的作用：影子工程的 `.settings/org.eclipse.core.resources.prefs` 登记了 UTF-8 文件时，
未打开的 UTF-8 文件里的中文类名能被 `workspace/symbol` 搜到；关掉登记就搜不到（对照实验）。

### 1.2.1 影子工程在真实 gl 模块上的实测（M4c，2026-10-28）

按本方案的做法（当前模块源码 + 精选 jar + 99 个公共库 + 类目录）生成影子工程并交给真实 jdt.ls，
`-Xmx1024m`，本机：

| 项 | 实测 |
|---|---|
| 类索引（7156 jar / 50.4 万类） | 9.2s（有磁盘缓存时） |
| 生成影子工程 | **1.85s**：111 个源文件，**502 个 jar**，5 个 UTF-8 文件，`.classpath` 78KB |
| `initialize` 返回 | 2.4s |
| `ServiceReady` | **27.9s** |
| 打开 2 个文件后诊断稳定 | 再 12s，合计约 **40s** |
| 内存（工作集） | **656MB** |
| 跳 NC 标准类 `NCLocator` | 0.24s |
| 补全 | 0.13s，8 项 |

诊断结果与 ecj / Eclipse 逐项一致：`VoucherResources` 0 个错误（M3 里它曾因父类 jar 没选上报
「继承层次不一致」，现在靠提前展开继承链解决了）；`Step4View` 恰好 2 个错误，就是 Eclipse 产物里
带「Unresolved compilation」的那 2 个真错。

注意两点：
- `NCLocator` 所在的 `fwpub.jar` 没有 `_src.jar`，所以跳过去是**桩**（只有签名，没有方法体和 javadoc）。
  7283 个 jar 里只有 2775 个带 `_src.jar`，这是预期内的降级，界面上要标出「无源码，仅签名」。
- 首次切到一个模块的等待约 40s，之后同模块内不用重建；这比初稿估的「几十秒」落在同一量级，
  远好于全量 573s。

### 1.3 性能（原方案被推翻的原因）

| 配置 | 就绪时间 | 峰值内存 |
|---|---|---|
| 7160 源文件 + 0 jar | 371s | 1382MB |
| 961 源文件 + 7283 jar | 221s | 1017MB |
| **7160 源文件 + 7283 jar** | **573s** | **1653MB** |

拆开来算：**源文件解析约 371s，jar 索引约 200s**。（待补：以上测量时 jdt.ls 的 `-Xmx`，它决定 M4e
内存上限的默认值。）

原规划「把 Eclipse 的 classpath 展开后喂进去」得到的是 573s + 1.65G——开一次工作台等
十分钟，且内存逼近 2G 上限（机器 16G，中间件和客户端还要分）。**这条路不成立。**

另外两个必须处理的：

- **`.svn` 必须排除**。不加 `java.import.exclusions: ["**/.svn/**"]` 时，索引在 35% 卡了 60 秒，
  进度消息里的路径全是 `.../src/public/.svn/prop-base`。NC 工作副本每一层都有 `.svn`。
- **`output` 属性必须改掉**。真实 `.classpath` 里每个 src 条目的 output 是 `aert/classes`，
  而 `aert` 是指向真实目录的 junction——原样保留会把编译产物写回用户的工作副本（见第 3 节、第 6 节）。

## 2. 架构：两层分工

jdt.ls 对 jar 内类能补全、能报错、能跳转（配上 `_src.jar` 跳到的是源码），所以语义功能全部交给它：

```
┌─────────────────────────────────────────────────────────────┐
│ 补全 / 诊断 / hover / 签名提示 / 全部跳转（含 jar 内类）  → jdt.ls   │
│   jar 内类：jdt:// URI → java/classFileContents → 只读标签页打开    │
├─────────────────────────────────────────────────────────────┤
│ 查找引用 / 重命名                → 工作台全文搜索兜底           │
│   （按模块加载时 references 只覆盖当前模块；rename 一期不做）     │
└─────────────────────────────────────────────────────────────┘
```

**降级用的源码索引**（只在关掉 jdt.ls 的轻量模式下用）：扫工作区二开源文件的 `package` + 类名，
缓存成 JSON，按 mtime 失效。注意它只覆盖**二开自己的类**（newar 的 7160 个文件不含 NC 标准类）；
NC 标准类只在 jar 里，轻量模式下要跳的话，由 `nc_index.rs` 的「类名 → jar」找到 jar，再从同名
`_src.jar` 读源码。源码索引与 `nc_index.rs` 并列放同一个模块，复用同一套缓存与失效逻辑。

## 3. 影子工程：不碰用户的工作副本

jdt.ls 只认项目根下的 `.classpath` / `.project`，而用户的 `.classpath` 是 SVN 版本控制的
文件，且用的是 UAP Studio 私有 container（`nc.uap.mde.library.container/*`），jdt.ls 没有
那个插件。

做法（探针已验证前 4 步）：

1. 影子目录 `shadow/` 下用 **junction** 把模块目录链过来（`mklink /J`，无需管理员）。
   newar 是 55 个；工作区根实际是 `C:\work\aier`，还有 `pm` 等同级分组。同级分组**不链源码**，
   只把它们的 `classes` 当类目录放进 classpath（见第 4 节）。
2. 生成 `.project`（只保留 `javanature`，去掉 `nc.uap.mde.*` 的 buildCommand/nature）。
3. 生成 `.classpath`：src 条目照抄但**去掉 output 属性**，UAP container 展开成绝对路径 lib；
   **显式写一条 `<classpathentry kind="output" path="shadow-bin"/>`**，指向影子目录内，不能落在
   junction 里。
4. jdt.ls 的 `-data` 指向独立目录。
5. 生成 `.settings/org.eclipse.core.resources.prefs`：工程默认编码 GBK，把探测为 UTF-8 的文件
   （规则同 `workspace.rs::detect_encoding`）逐个登记。newar 有 53 个 UTF-8 文件没在用户的
   Eclipse 偏好里登记，照抄用户的 prefs 会让 jdt.ls 按 GBK 读它们。

**验证过的关键点**：junction 不影响源码跳转（8ms 命中）。所以这条可行。

代价：用户新增/删除模块目录后，影子工程要重建。用一个 `已建` 标记 + 模块目录数比对来触发
重建，成本是一次目录列举。

## 4. classpath 策略：按模块、按需，不全量

| 层 | 内容 | 理由 |
|---|---|---|
| src | **当前模块**的 source folder | 961 个文件约 20s。用户改哪个模块就索引哪个 |
| 类目录 | 工作区各模块的编译产物：`<工程根>/<模块>/classes` → `<工程根>/out/<模块>` → 同级分组 `<工作区>/<分组>/<模块>/classes` → NC home `modules/*/classes` | 其他模块的**二开类**只在这些目录里。多数模块的产物在 `out/<模块>`，只有约 25 个模块有自己的 `classes`。漏掉会报大量假 `cannot be resolved`（M3 编译 baseapp 曾因此报 38 个假错） |
| jar | 按**当前模块全部源文件**的 import 精选 + NC 公共库（`lib`/`framework`/`middleware`），并为有 `_src.jar` 的 jar 配上源码 | 7283 个 jar 要 200s；精选后 gl 模块约 410 个（M3 实测） |
| jar | 其余 jar 不放进 classpath | 补全会缺类，但诊断和同模块跳转不受影响 |

类目录的顺序与来源、jar 的挑选与顺序，都直接复用 M3（`compile.rs` + `nc_index.rs`）已经在真实工作
副本上跑通的实现——同一个输入，换一种输出格式。具体要复用的是四步，缺一不可：

1. `extract_imports` + `add_import`：按 import 反查类索引；
2. `extract_package`：同包的类不需要 import，源文件自己的包也要按包名补 jar；
3. `add_super_chain`：沿父类/接口链读 class 文件头补 jar（否则会出现「The hierarchy of the type X
   is inconsistent」，如 gl 的 `VoucherResources`）；
4. 类目录枚举（上表第二行）。

注意：`discover_jars` 是「根据 ecj 报错补 jar」，依赖编译输出，jdt.ls 这边用不上；如果想拿到同样效果，
可以直接用该模块最近一次编译缓存下来的 jar 集（`compile_cmds.rs` 里按模块缓存的 `resolved_jars`）。

切模块时重新生成 `.classpath` 并触发 `java.project.import`。探针确认这个命令可用
（`Non-Static Commands` 列表里有）。同一模块内切文件**不**重建 classpath。

**能力边界要如实告知用户**：
- 其他模块的二开类能补全、能跳到签名（走类目录），但跳到的是 class 桩，不是源码，直到切到那个模块。
  类目录里的 class 是上次编译的产物，可能比源码旧。
- 超大文件（如 6433 行的 `VoucherBO.java`）没有补全，编辑器要显示提示，不能让用户以为功能坏了。

这是「启动快」换来的，不是缺陷掩盖。

## 6. 三条红线

1. **禁止 jdt.ls 写用户文件**。
   - 保存一律走工作台自己的原子写（已有：无损往返校验 + 按 mtime 防冲突）。
   - 配 `java.autobuild.enabled: false`，影子工程 output 指向影子目录（第 3 节第 3 步），双保险防止
     把 class 写进 junction 链着的工作副本；关掉自动构建也省 CPU。
   - 代码修复等通过 `workspace/applyEdit` 发来的修改，客户端只应用到 Monaco 的 model，由用户自己保存；
     涉及未打开文件、创建/重命名/删除文件的 edit 一律拒绝。
   - jdt.ls 0.57 修过「新建/重命名文件时改写磁盘内容」的 bug，但保存路径不能交给它。
2. **不用它的格式化**。`documentFormattingProvider` 等是服务端声明的能力，客户端的做法是：
   不向 Monaco 注册格式化 provider、不发任何格式化请求，配置里再加 `java.format.enabled: false`。
   NC 代码是 CRLF + 制表符风格，任何自动 format 都是灾难。
3. **索引必须可跳过**。首次切模块仍可能要等几十秒，必须有进度条、有「跳过索引、只补全
   当前文件」的退路，不能卡在启动路径上。

## 8. 验收标准

自动测试能覆盖的：LSP 分帧编解码、initialize 参数（`classFileContentsSupport`、`runtimes`、
`workspaceFolders` 为字符串）、影子工程生成器（给定模块集产出正确的 `.classpath`：含类目录、
output 指向影子目录、`_src.jar` 配对；编码 prefs 登记了 UTF-8 文件）、降级源码索引（含内部类、
同名类多包）、`applyEdit` 只落到 model 不写盘。

要人眼的：
- 真实模块下的完整跳转链路：二开类→源码、NC 标准类→`_src.jar` 源码、没有 `_src.jar` 的类→桩；
- 诊断稳定前不出现满屏假红线；超大文件有提示；
- GBK 文件与未登记的 UTF-8 文件补全、诊断都不乱码；
- 切模块的等待时间、内存占用；
- 用户工作副本里没有多出任何文件（`.classpath`、`.project`、`.settings`、class 文件）；
- **关掉 jdt.ls 之后编辑器还能不能用**。
