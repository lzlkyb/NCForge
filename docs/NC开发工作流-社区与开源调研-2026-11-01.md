# NC 开发工作流：社区与网上调研

> 日期：2026-11-01　方法：GitHub / Gitee 仓库检索 + 招聘 JD + 技术博客 + 官方生态文档，
> 逐条标注来源与可信度；**判断只落在"NC 开发者实际要干的活"上**，不写泛泛的行业分析。
> 结论落点：NC 开发者的活有四类，我们现在覆盖 1.5 类；缺口不在"编辑器"而在
> **元数据侧、部署侧、救火侧**。

---

## 0. 一页结论

1. **开源生态近乎空白**。全网真正在维护的 NC IDE 插件只有一家：
   `airh2o/idea_plugin_ncdevplugin`（31★ / 18 fork / 80 commit，最后一笔 2026-09-30）。
   其余 `TsingJames`、`gogomarine`、`zbsilent`、`yhlx` 全是它的 fork 或同源镜像。
   对比 MyBatis 插件动辄上千星——**NC 开发者长期没有工具生态，靠 UAP Studio + Excel + 口口相传**。
2. **但官方生态已经动起来了**：`YDS Premium Fusion`（`yonbip-devtool`，MIT，OpenVSX 2.5.7）
   是一个 VS Code 侧的 YonBIP/NC 开发插件，功能集几乎就是"NC 开发者一天的活"的官方版清单：
   HOME 配置、服务启停、脚手架建工程/模块、**补丁导出 + 应用到 HOME + 取消补丁**、
   预置脚本导出、**Java 热部署**、OpenAPI 测试、MCP 服务。
   它替我们验证了方向，也划出了三条我们空缺的硬需求（见 §4）。
3. **网上内容严重 AI 污染**。搜"NCC 排障"能搜出拿 Activiti / Canal / Keycloak / Nacos
   解释 NCC 架构的答案——**NCC 里根本没有这些东西**。真正有价值的是 2011–2018 年的老博客、
   用友之家论坛、以及具体到表名字段路径的踩坑记录。这件事本身是个产品机会（见 §6）。
4. **招聘 JD 比技术博客更能说明"活是什么"**：单据/报表二开 + 接口对接 + 补丁部署 +
   权限流程配置 + **日常救火** + 账套备份 + 月末结账保障 + 写文档。
   其中"救火 + 数据修复"占比极高，而这一块工具化程度接近零。
5. 我们的判断要改一次：**编辑器体验已经不是短板**（对标 IDEA 的 P0/P1 都落地了，调试器也通了）。
   短板在**元数据、部署闭环、日志归因**——恰恰是社区里被反复踩、却没人做工具的地方。
6. **元数据已排进三期**（`NCForge-多期规划` §6：「对接 bmf 生成器或可视化编辑，摆脱 UAP Studio」）。
   需要分清的是：三期排的是**生成侧**（建模 → BMF → VO → 建表），
   本文 §2B 里那类高频翻车点是**校验侧**（发布了但表没建、字段名两处不一致、
   访问策略挂错、`islightmodule` 没改）。两者不重复但相邻，
   校验侧成本低、能提前吃掉三期落地前的现场问题，建议作为三期前哨单独评估（见 §7 说明）。

## 2. NC 开发者到底在干什么（四类活）

按"一天里时间的真实分布"归并，而不是按产品模块分：

### A. 写代码（我们覆盖得最好）

- 单据二开：界面类 / 控制类 / 事件处理类、`ICardController`、`getBillType()`、`getBillVoName()`
- 报表二开：取数逻辑、报表模板挂接
- 接口开发：与 WMS / MES / PLM / SRM / OA / 钉钉 对接，WebService / HTTP
- 脚本开发：单据动作脚本、审批流脚本、公式
- 定时任务：`InitSession.init()` 模拟会话（**搞错就是越权**）

→ 我们的编辑器 + jdt.ls + 调试器 + 补丁出包，正好命中这一段。

### B. 配元数据（**我们基本空白，而它最耗时**）

标准步骤链（`zhangzhl5/Document` + 多方博客一致）：

```
元数据建模（或导入 PDM） → 发布元数据 → 生成建库脚本并执行 → 生成 VO 源码
  → 系统类型/功能/单据类型/VO对照/动作/动作组 六处注册 → 导入数据字典
  → 生成单据模板、查询模板、打印模板 → 模板注册
  → 建立界面类/控制类/事件类框架
```

高频翻车点（社区出现频率最高的一类问题）：

| 现象 | 真实根因 | 来源 |
|------|---------|------|
| `ORA-00942: table or view does not exist` | 元数据发布了但表没建，**不是代码问题** | `lpqz.cn` |
| 元数据名称与字段名不一致导致发布报错 | 实体与表两处不一致，得删表重来 | CSDN 142381039 |
| 单据类型管理找不到二开单据 | `bd_billtype.systemcode` 写成模块号大写，与模块编码不一致 | CSDN 117279244 |
| 轻量端看不到重量端新增模块 | `dap_dapsystem.islightmodule` 没改 | 同上 |
| 元数据升级不生效 | 版本号没大于当前版本 | `baiduwuhen` |
| 自定义项配了但用户看不到 | 元数据过滤节点未勾选 / 组织类型挂错 | `rosinanteplusssss` |
| 保存即提交 | `PUB_BILLACTION` 的 `ActionType` 配错 | `zhangzhl5` |
| 审批流建动作脚本编译报错 | jre 里没 `tools.jar` / 没设系统类型 / 内存溢出 | `oyonyou` |

→ 这一整段目前**全靠人肉记忆 + 翻老博客**。这是最大的未开采区。

### C. 出包与部署（我们只做了第一步）

- 补丁导出（`patcherconfig.properties` 类→模块映射）→ **应用到 HOME** → **出问题取消补丁**
- 热部署（改一行 class，不想重启 40 秒）
- 账套管理、数据备份/恢复、版本发布

→ 我们有出包（而且比脚本严谨），但**没有"应用"和"回滚"**，热部署完全空白。
YDS 插件这三件全有，说明这是刚需而不是我猜的。

### D. 现场救火（我们只有半套工具）

- 看 `nclog/run.log`、`err.log`，按报错号定位
- 慢 SQL 定位（哪个模块 → 哪个节点 → 哪个操作 → 耗时 → 捕获 SQL）
- 类冲突 / `ClassNotFound` / jar 版本打架
- PK 锁、ORA-01000（游标超限）、内存溢出
- 数据修复：直接从库里捞数、造数、补数（**我们这块反而很强**）

→ 数据库工具是我们的相对优势，但**日志与报错归因是空白**，
而它恰好是"救火"的入口。

## 4. 对标 YDS Premium Fusion（最扎心的一张表）

它把"NC 开发者要干的活"直接列成了产品功能：

| YDS 功能 | 我们 | 说明 |
|---------|------|------|
| HOME 配置 + 数据源/设计库/基础库 + 测连接 | **有** | `nc_home.rs` 按内容识别，不靠目录名 |
| 打开 SysConfig、看 HOME 日志、配服务参数 | **部分** | 服务启停有，SysConfig 跳转与日志浏览没有 |
| HOME 服务启动/调试启动/停止/状态/日志 | **有** | `server.rs`、`ServicesTab` |
| 脚手架：建工程 / 建模块 / 建业务组件 | **有**（更像"关联已有"） | 我们是接管现场工程，不生成骨架 |
| 补丁导出 | **有**（更严谨） | 逐文件探测产物根、完整方法签名、内存直写 zip |
| **补丁应用到 HOME** | **缺** | 手工解压覆盖，就是我们自己在《借鉴方案》里说的"现场解压覆盖" |
| **从 HOME 取消补丁（回滚）** | **缺** | 只能靠备份手工还原 |
| 预置脚本导出（`item.xml`/`items.xml`） | **缺** | 元数据侧 |
| **Java 热部署**（auto / jdi / ncHotDeploy 三模式） | **缺** | 改一行重启 40 秒 |
| OpenAPI 测试（多环境、GET/POST/PUT/PATCH） | **缺** | 接口联调无工具 |
| MCP 服务 | **缺**（且不必抄） | 它是为了接 AI 编辑器；我们本身就是编辑器 |
| 本地数据资源检索 | **部分** | 我们有全工程搜索 + 符号索引 |

三条硬缺口清晰：**补丁应用/回滚、热部署、接口调试**。
另加一条它没有、但我们有的相对优势：**类路径真源 / 依赖闭包 / 产物过期检查**——
这正是它做不到的（VS Code 侧没有 jdt.ls 那套工程模型）。

## 6. 一个被忽略的机会：AI 污染反而制造了需求

社区里 NCC 排障内容已经烂到"搜出来的答案比问题更危险"的程度。
这反过来说明两件事：

1. **领域知识必须沉淀成可验证的规则，而不是可检索的文本**。
   我们已经做过一次这样的事：`MODULE_CLASS_DIRS` 六段、类路径顺序、12 类库容器——
   这些都是"不照做就是错的"硬知识，写进代码后不再需要人记。
2. 工作台里可以长出一个**报错 → 根因 → 动作**的小库：
   `ORA-00942` → 元数据没发布的表 → 跳到"元数据体检"；
   `ORA-01000` → 游标没还 → 指向代码位置；
   `ClassNotFound` → 类路径缺哪个 jar → 跳到依赖闭包。
   **不接大模型、不搞问答**，就是确定性的映射表 + 跳转。成本低，命中率高。

## 7. 建议的补齐顺序

### P0（都是"每天都用、我们现在完全没有"）

| # | 能力 | 收益 | 底子 |
|---|------|------|------|
| 1 | **补丁应用 / 回滚**：把出好的 zip 解到 HOME，记录清单，一键还原 | 消掉现场最容易出错的手工步骤 | 出包已有产物清单，`svn_backup` 有备份范式 |
| 2 | **日志归因**：读 `nclog/run.log`+`err.log`，抽异常块，映射常见根因 | 救火入口，直接替代"翻日志" | 服务启停已有；`compile_diag` 归因范式可复用 |
| 3 | **数据字典导出**：库 → 表 → 字段 → 中文名，出 Excel/Markdown | 交付文档刚需，几乎每个项目都要 | `db_schema` 缓存 + `sql_refs` 已有一半 |

### P1（收益明确，成本中等）

| # | 能力 | 说明 |
|---|------|------|
| 4 | **热部署**（jdi 优先，失败退化为复制 class） | YDS 已证明三模式可行；先只做 jdi + 复制 |
| 5 | **元数据体检 / 校验侧**（不做建模器） | 检查：实体/表/字段三处一致、必实现接口是否挂上、主子关系访问策略、`islightmodule`、唯一约束冲突。**与三期生成侧不冲突**，见下 |
| 6 | **接口调试**：手填 URL/入参发请求 + 响应查看 | 对接联调常规项；不追求 OpenAPI 全自动 |

### P2

7. 账套/备份台账、月末结账保障清单
8. 报错码 → 根因映射库（可与 #2 合并做）

### 关于 #5 与三期的边界（2026-11-01 用户确认后补）

三期排的是**生成侧**：建模 → BMF → VO → 建库脚本，目标是"摆脱 UAP Studio"。
这是重活，且要跟 UAP Studio / YonBuilder 正面比，成本不可低估。

而 §2B 里那些翻车点全在**校验侧**，与生成侧只共享"读元数据"这一件事：

| 侧 | 做什么 | 依赖 | 成本 |
|----|--------|------|------|
| 三期生成侧 | 产出 BMF / VO / 建库脚本 | 元数据模型、模板引擎 | 高 |
| 校验侧 | 读已发布结果，比三处是否对得上，报出来 | 只需读：`md_class` / `bd_userdefitem` 等表 + 工程里的 VO 源码 | 低 |

**关键判断**：校验侧不需要先有生成侧，因为它比的是"库里发布结果"和"工程里代码"，
两者现在都已存在。而它恰好能在三期落地前就吃掉现场一半的元数据问题。
建议单独评估，不要捆进三期一起排——否则会被生成侧的重活拖住。

## 8. 明确不做

| 不做 | 理由 |
|------|------|
| 可视化元数据建模器 | UAP Studio / YonBuilder 的领地；建模完**必须**经它们发布，做一半等于没做 |
| 低代码/单据模板设计器 | 同上，且是产品核心资产，不对外 |
| 完整 OpenAPI 全自动 | 接口资产在平台上，抓不全；做"发请求看响应"就够 |
| MCP 服务 | 我们是编辑器本体，不是给别的编辑器供能的中间层 |
| 抄 AI 问答式排障 | 社区已被污染，输出不可验证的东西只会更快地把人带沟里 |

## 9. 动手前该先验证的三件事

1. **补丁应用到 HOME 的真实形态**：现场到底是解压覆盖 `modules/<模块>/classes`，
   还是走 `hotwebs` 的 `WEB-INF/extend`？两种都要不要？——先拿一个真实补丁 zip 对照一次。
2. **热部署在这台机器的 NC65 上能不能用 JDI**：需要 `-agentlib` 还是 attach 模式，
   改字段/加方法时退化成什么。这是 P1 里唯一有"能不能成"风险的一项。
3. **`nclog` 的真实格式**：`run.log` 是滚动的还是按模块分文件、异常块怎么界定、
   有没有 traceId 可串。归因做在错误的切分上就是白做。
