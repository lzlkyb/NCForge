## 3. P0：阻塞提交的问题

### 3.1 Rust 体量红线机制已失效（最严重）

`check-source-size.mjs:75` 取「第一个 `#[cfg(test)]` 行之前」算生产段：

```js
const at = lines.findIndex((l) => CFG_TEST.test(l));   // CFG_TEST = /^\s*#\[cfg\(\s*(all\()?test[\s,)]/
```

这条正则会把 **`#[cfg(test)] use ...`、`#[cfg(test)] fn ...`** 也当成测试段起点。实测后果：

| 文件 | 真实生产段 | 门禁认为 | 基线里有没有 |
|---|---|---|---|
| `search.rs` | **2073 行**（`mod tests` 在 2074） | 135 行 | ❌ 没有 → 永远合规 |
| `java_run.rs`（本次新增） | 523 行 | 21 行 | ❌ 没有 |

`search.rs` 是全项目最大的生产文件之一，却因为 135 行处有一个 `#[cfg(test)] fn run` 的测试辅助函数，**从未进入过基线视野**。`patch_build.rs`(1354) / `resource_pack.rs`(2138) / `lsp.rs`(971) / `build_layout.rs`(518) 的 `#[cfg(test)]` 后面确实是 `mod`，判定正确。

修复判据：`#[cfg(test)]` 必须**紧跟 `mod`**（允许中间空行与属性）才算测试段起点，参考 `lsp.rs` 的 `pub(crate) mod tests` 形态。
⚠️ 修完 `search.rs` 会立刻变成新的超标文件（2073 > 600），基线 43 → 44，按「只许减」规则门禁会红。所以这条要单独决策：**先拆 `search.rs`**，还是**修脚本的同时显式上调基线并留痕**。

### 3.5 NC 类引用查询在真实库上必然报错（已提交代码的既有缺陷，影响本次 SQL 辅助）

`commands/db_relations_cmds.rs:8` 的 `NC_REFS` 硬编码 `join md_ormap sm on sm.propertyid=p.id`。
实测这套 NC 库 `MD_ORMAP` 的列是 `ATTRIBUTEID / CLASSID / COLUMNID / DR / TABLEID / TS`，**没有 `propertyid`** → ORA-00904 → 被 catch 成空结果 →
