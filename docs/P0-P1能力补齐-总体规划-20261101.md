## 3. P0-3　数据字典（读 NC 元数据表，不是 Oracle 注释）

### 3.1 为什么值得做

NC 交付里"给甲方一份数据字典"几乎是每个项目都有的动作，现在靠
`65数据字典.chm`（本机 `/d/ncc/65数据字典.chm`，还是 NC65 的）+ 手抄 Excel。
而**开发者真正要的不是全库字典，是"这张表、这个字段到底叫什么"**——
NC 库里大量列名是 `f1`…`f60`、`def1`…`def20`，光看列名没有语义。

### 3.2 关键实测：Oracle 注释是空的，中文名在 `md_*` 表里（A0 已完成）

初稿写的是「从 `all_tab_comments` / `all_col_comments` 取注释」——**这条作废**，
用户实测这些基本都是空的。换方向后查清楚了真正的来源：

- 元数据文件 `modules/**/METADATA/**/*.bmf` 里字段级中文名是全的
  （`<attribute displayName="定义主键" fieldName="guid" fieldType="char">`，
  3711 个 bmf / 247 MB，抽查 20 个 17 个含 `tableName`+`fieldName`）。
- 但**bmf 只是设计态，NC 启动/发布时会把它们按关系写进库表**，而库里那份带二开
  （二开也走发布），比 HOME 里的文件全。所以**权威源是库里的 `md_*` 表，不是文件**。
- 实测印证：`billtype.bmf` 里 `displayName="单据类型"`，而库里 `md_table.displayname='交易类型'`
  ——**库里比文件新**，文件是发布源、库是发布结果。

#### A0 实测结果（2026-11-02，库 `aier260824`，Oracle 19.3 / ZHS16GBK）

| 表 | 行数 | `displayname` 非空 | **含中文** |
|----|------|------|------|
| `md_table` | 5 876 | 99% | **99%** |
| `md_column` | 223 413 | 99% | **99%** |
| `md_property` | 249 470 | 100% | **99%** |
| `md_class` | 9 698 | 100% | **99%** |
| `md_component` | 5 341 | 100% | 78% |

**全列都有中文名的表：5 616 / 5 876 = 95%。** 分域看更高：`so_` / `gl_` / `org_` / `sm_` 100%，
`ic_` 98%、`bd_` 97%、`pu_` 88%。**二开扩展表（`isextendtable='Y'`）1 367 列，100% 有中文。**
`bd_billtype` 41 列逐列核对，**缺失中文 0 列**。

结论：**这个数据源够用，可以做到"交付级"程度**，不只是查询工具。

### 3.2.1 🔴🔴 一个会把人带进沟里的字符集坑（我踩了两次）

本库是 **ZHS16GBK**。判断「这个值有没有中文」时，**绝对不能用**：

```sql
regexp_like(displayname, '[\u4e00-\u9fa5]')   -- ❌ GBK 下严重漏判
```

实测漏判幅度：`md_column` 真实 99% 会被判成 69%（差 67 564 行），
`md_table` 真实 99% 判成 66%。更坑的是**漏判不是均匀的**——看起来像"有些模块填了中文、
有些没填"，会让人得出"覆盖率只有 38%，这功能不值得做"的错误结论（我第一版就是这么误判的）。

正确写法（ZHS16GBK / AL32UTF8 都成立，中文都是多字节）：

```sql
lengthb(displayname) > length(displayname)   -- ✅ 有非 ASCII 字符
```

**同一个坑在 SQL 里做筛选、在 Rust 里做归因都适用**：Rust 侧判断中文别用 `char as u32`
范围猜，直接 `!s.is_ascii()`。

### 3.3 元数据图谱（本机 DDL 实证，不依赖连库）

表结构来自 NC 自带建表脚本，逐字段读过：

```
<HOME>/ncscript/uapServer/uapbs/L_-1/dbcreate/Oracle/00001/tb_nc_pub_md.sql
```

| 表 | 关键字段 | 用途 |
|----|---------|------|
| `md_component` | `id`、`namespace`、`ownmodule`、`name`、`displayname` | 组件，`ownmodule` = 归属模块 |
| `md_class` | `id`、`componentid`、`name`、**`displayname`** | 实体（对应 `XxxVO`） |
| `md_property` | `id`、`classid`、`name`、**`displayname`**、`versiontype`、`industry` | 属性 |
| `md_ormap` | `attributeid`、`classid`、`tableid`、`columnid`、`dr` | 属性 ↔ 列 的桥 |
| `md_table` | `id`、`name`（物理表名）、**`displayname`**、`isextendtable`、`fromsourcebmf`、`isactive`、`industry`、`versiontype`、`resid` | 表 |
| `md_column` | `id`、`tableid`、`name`（列名）、**`displayname`**、`sqldatetype`、`pkey`、`columnsequence`、`nullable`、`precise`、`dr`、`versiontype`、`resid` | 列 |

🔴 **`md_column` 没有 `industry` 列**（实测 `ORA-00904` 撞出来的）。行业过滤只能在
`md_table` / `md_property` 上做，`md_column` 只有 `versiontype`。别照着 `md_table` 的写法套。

一条 JOIN 就能取到「物理表 + 表中文名 + 列名 + 列中文名 + 类型 + 主键」
（`md_column` 实测 223 413 行，`dr` 全是 0，但仍要写条件——别的库不一定干净）：

```sql
select t.name 表名, t.displayname 表中文名,
       c.name 列名, c.displayname 列中文名,
       c.sqldatetype 类型, c.pkey 主键, c.columnsequence 顺序
  from md_table t
  join md_column c on c.tableid = t.id
 where t.name = :tbl
   and nvl(c.dr, 0) = 0
 order by nvl(c.columnsequence, 9999), c.name
```

**`md_table.isextendtable` 是这条路的额外红利**：二开扩展表在库里是有标记的，
所以「我加的那个字段叫什么」也能查到——这正是纯文件方案（本机 `extend` 目录实测 0 个）
做不到的。`fromsourcebmf` 还能区分标准产品与后加的。

### 3.4 🔴 去重口径直接抄 NC 自己（`msql-log` 实证，不要自己发明）

`nclogs/server/msql-log.log` 里记着 NC 自己查元数据的完整 SQL，去重方式是：

```sql
select * from (
  select row_number() over (partition by id order by versiontype desc) rn,
         t1.displayname, t1.isextendtable, t1.fromsourcebmf, t1.isactive, t1.name, ...
    from md_table t1
   where ... and (industry = '0' or industry = '48')
) a where a.rn = 1 order by displayname
```

三条可直接照抄的结论：
- **`partition by id order by versiontype desc` 取 `rn = 1`** = 同一实体取最新版本，这就是多版本去重的正解。
- **`industry in ('0', '48')`** = 基础行业 + 该行业的两套元数据并存，不是只取 `0`。
- **`order by displayname`** = NC 自己就在按中文名排序，说明这列有值（否则排序无意义）。

### 3.5 🔴 四个必须处理的坑（不处理会得到错数据，而且不报错）

1. **`dr` 软删除**：`md_ormap` 明确带 `dr number(10) default 0`。NC 全库通用约定，
   查询一律加 `dr = 0`，否则已删的元数据会混进来。
2. **`versiontype` + `industry` 多版本**：`md_property` 主键是 `(id, versiontype, industry)`，
   **同一属性会有多行**，不筛会一个字段查出好几个中文名且不报错。口径见 §3.4。
   实测分布：`md_table.industry` = `'0'` 5 551 / `'48'` 298 / NULL 26 / `'~'` 1；
   `versiontype` = 0 有 5 710 / 1 有 156 / -1 有 10。**注意 `md_column` 没有 `industry` 列**。
3. **`isactive`**：`md_table` / `md_column` 都有 `是否启用`，停用的不该出现在字典里。
4. **`md_ormap` 的主键只有 `attributeid`**：一个属性只能映射一列。
   主子表/多表继承的实体，属性和物理列不是一对一——字典要按**列**（`md_column`）为主轴，
   属性中文名通过 ormap 补，补不上就留空，**不要因此丢掉列**。

补充：`md_column` 还有 `columnsequence`（字段顺序）、`columntype`、`defaultvalue`、`forlocale`，
都在 NC 自己的 select 列表里，值得一并取——`columnsequence` 能让输出按单据上的字段顺序排，比字母序好读。

   并取交集，但界面上同时开放就无法解释——勾了 20 张、又填了 `bd_`、只出 5 张时，
   用户没有任何线索能想明白为什么。收成和式类型 `Scope`，切换即替换。
   左栏的关键词只用来**找**表，不进生成请求。
2. **左栏不给列数**。`nc_md_tables` 不返回列数：要显示得为每张表做一次分组计数，
   300 多张表多花约 1 秒，而列数并不影响「勾不勾」的决定。列数只在生成后的表卡片抬头给。
3. **导出推给 C 批，B 批不做「复制到剪贴板」**。CSV/Markdown 的渲染在 Rust 里
   （`md_dict.rs`，有单测），前端再拼一份必然漂移成两套格式。C 批由后端出面做落盘 + 定位，
   届时「复制」也可以一并走同一份渲染。
4. **顺手修掉 A 批一处静默截断**。`nc_md_dict` 原来按 `MAX_TABLES` 直接查表，前缀
   `bd_` 这类宽匹配会被 `rownum` 悄悄截断成 500 张却报成功——和缺列一样是「看着完整、
   其实不全」。现在多要一行判超限，超了报 `too-many` 让人把前缀写细。

C 批落地物（已过门禁：`cargo test` 571 条 / 前端 840 条 / 双 feature `clippy -D warnings` /
`vite build`；`MdDictTab` 分块 14.9 kB，仍未把 Monaco 拖进这一页）：

| 文件 | 职责 |
|------|------|
| `md_dict.rs` | 新增 `DocFormat` / `render` / `doc_stem`：格式分发、文件名白名单；6 条单测 |
| `commands/md_dict_cmds.rs` | `nc_md_dict_text`（渲染给复制）/ `nc_md_dict_export`（渲染 + 落盘）；`unique_path` 单测 |
| `desktop/src/lib/mdDict.ts` | `DictDoc` / `ExportOut` / `stampText` / `dictDocOf` 三个 IPC 封装 |
| `MdDictResult.tsx` | 抬头下一条操作条：导出 CSV / Markdown、复制 CSV / Markdown；落盘后就地给「打开所在文件夹」 |

C 批三个取舍：

1. **导出的对象是「屏幕上这一份」，不重新查库**。`DictDoc` 由前端把当前结果整体回传。
   重查要多等 2~3 秒，中间元数据一变，导出的文件与用户刚看过的那份就不是一回事。
   代价是要给 `TableDict` 系结构加 `Deserialize`（原先只有 `Serialize`）。
2. **复制与导出共用同一条渲染**（`md_dict::render`）。前端拼一份 CSV 会立刻漂移：
   BOM、`\r\n`、引号翻倍、Markdown 的 `|` 转义都在 Rust 里有单测，前端重写就是第二套格式。
3. **落盘位置固定 `{config_dir}/exports`，不弹保存框**，与 SQL 导出同一个目录，
   定位复用 `db_export_reveal`（它只允许打开该目录内的路径，不额外开一个新入口）。
   文件名 `NC数据字典-<范围>-<YYYYMMDDHHmm>`：`selection` 与 `generated` 都当外部输入，
   过白名单（ASCII 字母数字 / `_` / 汉字），否则 `关键词 a/b` 这种要到写文件时才炸。

### 3.8.1 A 批实测：五个"不报错但会给错数据"的点

都是在真库上撞出来的，实现里已经兜住，改代码前先看：

1. 🔴 **`md_ormap` 的 1:N 会把列数放大 2.2 倍**。`bd_` 前缀 328 张表，
   join 后是 **18 657 行**，真实列只有 **8 431 列**；`bd_billtype` 41 列 join 出 96 行。
   不折叠就这样吐出去，字典会凭空多一半行，而且**没有任何报错**。
2. 🔴 **`industry` 必须放行 NULL**。NC 自己的 SQL 写 `industry in ('0','48')`，
   照抄会丢 26 张表，其中 **25 张是二开扩展表**（全库 87 张，一下少 29%）。
   NC 那样写是为了渲染某个行业的产品界面，我们要的是"这张表叫什么"。
3. 🔴 **`dr` 是 NULL 而不是 0**（`md_table` 5 866 行 NULL / 10 行 0），只能 `nvl(dr,0)=0`。
   `isactive` 同样全为 NULL（= 启用），写 `isactive='Y'` 会把整库过滤成空。
4. 🔴 **`sqldatetype` 会被填成参照档案名**：42 列是 `'供应商档案'`、
   `'借款单位项目(自定义档案)'` 这种值，另有 29 列自带括号（`varchar2(100)`）。
   当 SQL 类型直接输出会误导人，所以非 ASCII 一律标 `参照:xxx`。
5. 🔴 **桥返回的 `columns` 是对象数组**（`{"name","type",…}`），不是字符串数组。
   按字符串解析会让**每列都读成空串**、字典变成一堆空表却不报错。现在
   `Grid::parse` 两种都收，收不出来直接报错；命令层再校验一次必需的列名。

另外两条口径：表名过滤**不用 `LIKE`**（`_`/`%` 是通配符，搜 `ic_` 会命中 `icXxx`），
改用 `substr`/`instr`；`md_table`/`md_column` 的 `id` 实测完全唯一（5 876/223 413），
多版本的 `rn=1` 去重只对 `md_property`（891 行重复）是必需，其余留着当防御。

`md_ormap` 覆盖 217 638 / 223 413 列（97%），漏的是没走实体映射的技术列——字典以
`md_column` 为主轴、属性补不上就留空，不影响可用性（实测 `bd_` 段缺中文名 15/8 431 列）。

## 4. P1-4　热部署

### 4.1 先纠正一个容易误判的点

本机 `prop.xml` 第 3 行有 `<enableHotDeploy>false</enableHotDeploy>`，
看起来像"NC 的热部署开关"。**它不是**：该文件的根元素是
`ClassType="nc.uap.plugin.studio.ui.preference.prop.PropInfo"`，
即 **UAP Studio 的项目偏好**（IDE 侧"保存时同步到服务器"那个开关），不是运行时开关。
把它改 true 不会让运行中的 JVM 换类。

所以真实可用的只有两条路：

| 路径 | 机制 | 能改什么 | 代价 |
|------|------|---------|------|
| **JDI redefineClasses** | 走已打通的调试通道（`debug.rs` / java-debug 0.32.0） | **只能改方法体**；增删字段/方法、改签名都不行 | 秒级 |
| **复制 + 重启** | 落盘到 `modules/<m>/classes`，重启中间件 | 任意 | 约 40 s |

我们的定位是**第一条自动、第二条兜底**，且**不假装成功**：
JDI 推不动时明确报"结构性变更，需要重启"，并给一键重启。

### 4.2 必须先 spike（0.5 d，go / no-go）

唯一的不确定点：**`redefineClasses` 对 NC 的类加载器成不成立**。
NC 用的不是标准 AppClassLoader，而是 `BootstrapClassLoader` 那一套多段加载，
而 `redefineClasses` 只对"**已被某个 loader 加载过的类**"生效，且要求前后结构兼容。

spike 做法：改一个方法体里的字符串常量 → 触发保存 → 断言
① 能定位到加载该类的 loader；② redefine 返回成功；③ 页面/接口行为真变了。
**失败就只做"复制 + 重启"**，把 JDI 那条降级为"能成再加"。

### 4.3 批次

| 批 | 内容 | 估 |
|----|------|-----|
| 0 | spike（go / no-go） | 0.5 d |
| A | 保存 → 编译当前文件 → 落盘到 HOME（复用补丁应用的落位逻辑） | 1.5 d |
| B | JDI redefine（若 spike 通过）+ 失败降级提示 + 一键重启 | 1.5 d |

🔴 与补丁应用共用落位代码，不要写第二套 —— 两处对不上的后果是"补丁生效了但热部署没生效"。

## 5. P1-5　元数据体检（只查，不建模）

### 5.1 边界（与三期）

三期做**生成侧**（建模 → BMF → VO → 建库脚本）。本项做**校验侧**：
拿"已经发布的结果"和"工程里的代码"对撞。两者只共享"读元数据"，不共享工期。

### 5.2 分两层，文件侧先上（不依赖库）

**文件侧（可以立刻做，零风险）**

| 检查 | 依据 |
|------|------|
| `.upm` 组件重复注册 | **本机日志实测** `DuplicateException: Detail Message: deviceregister`，路径直指 `modules/mmbcm-scm/META-INF/accessright.upm` |
| `METADATA/*.bmf` 与 `META-INF/*.upm` 声明的组件名不一致 | 两处都读，比组件名集合 |
| VO 里 `getAttributeValue(XxxVO.FIELD)` 的常量是否为 `null` | 社区高频坑（"getsStatus 一直是 null，要改 super."）；纯静态分析，扫 `.java` 即可 |

**库侧（连库才做）**

表名已在 §3.3 用 NC 自带 DDL 实证过，不再靠猜。所有检查都是**差集**：
`md_*` 是"声明"，`user_tables` / `user_tab_columns` 是"实际"，两者不一致就是问题。

| 检查 | 依据 | 为什么这条要命 |
|------|------|----------------|
| 元数据声明了表但库里没有 | `md_table` ∖ `user_tables` | **正是 `ORA-00942` 的根因**（元数据发布了但表没建），日志里实测 33 条 |
| 元数据声明了列但库里没有 | `md_column` ∖ `user_tab_columns` | 单据打开时字段取值报错 |
| 库里有列但元数据没有 | `user_tab_columns` ∖ `md_column` | 现场手工 `ALTER TABLE` 留下的，升级会被覆盖或冲突 |
| 组件归属与工程模块对不上 | `md_component.ownmodule` vs 工程目录名 | 补丁打错模块 |
| 必实现接口是否挂上（`IBillInterface` / `pfbizitf` / `general_interface`） | `md_class` + `md_property` | 开发步骤链的硬要求 |

`md_table.isextendtable` / `fromsourcebmf` 让报告能直接标出"这条是二开带的"，
比笼统报"表不存在"有用得多。

### 5.3 输出

问题列表，每条三列：**问题 / 依据（文件:行 或 表.字段）/ 为什么这条要命**。
不输出"评分"，不做"体检通过"的假绿灯——查不出来的就说"未覆盖"。

### 5.4 批次

| 批 | 内容 | 估 |

## 6. P1-6　接口调试

### 6.1 为什么现在做成本最低

`reqwest 0.13` **已经在 `Cargo.toml` 里**（`resource_pack.rs` 的资源包下载在用），不新增依赖。
而"跟 WMS/MES/OA 对接联调"在招聘 JD 里是常规项，现在只能开 Postman 再手抄 NC 的登录态。

### 6.2 形态（刻意做小）

```
[POST ▾]  http://10.200.22.144/nccloud/api/xxx        [发送]
环境: [测试 ▾]   头: Cookie / Content-Type …
Body: { … }
──────────────────────────────────────────
200  127 ms
{ "code": "0", … }
```

- 多环境变量（`{{host}}` 这种占位替换），因为 NC 现场永远是开发/测试/生产三套
- 历史记录（最近 20 条，落本地）
- 响应原文 + 耗时 + 状态码 + 大小

**不做**：OpenAPI 文档同步（接口资产在平台上，抓不全）、鉴权流程编排、压测、断言脚本。
目标是"不用切窗口"，不是"替代 Postman"。

| 批 | 内容 | 估 |
|----|------|-----|
| A | 请求发送（方法/URL/头/体）+ 响应展示 | 1.5 d |
| B | 环境变量 + 历史 | 1 d |
