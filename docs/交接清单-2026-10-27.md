## 5. 关键技术结论（都是实测得来的）

### 5.1 编码与换行
- 合法 UTF-8 且含非 ASCII（或带 BOM）→ UTF-8；非法 UTF-8 → GBK；纯 ASCII → GBK。7219 个真实 .java 验证过 0 个无法无损往返。
- MIXED 换行或孤立 CR 的文件默认只读，需用户选择统一为 CRLF/LF 才能编辑。
- 编辑器只看到 `\n`，换行由 Rust 在写盘时还原。
- **Eclipse 的一个 bug**：newar 里有 53 个 UTF-8 文件没在 `.settings/org.eclipse.core.resources.prefs` 登记，被 Eclipse 按 GBK 编，字符串常量变乱码（「接口」→「鎺ュ彛」）。ecj 逐文件探测编码才是对的。线上补丁是否受影响**未核实**。

### 5.2 编译（ecj）
- 参数：`-1.8 -g -nowarn -proc:none -preserveAllLocals`，缺 `-preserveAllLocals` 会和 Eclipse 产物差几十字节；每个源文件写成 `"path[GBK]"` 或 `"path[UTF-8]"`。
- 必须用 NC 的 ufjdk 1.8（`<NC home>\ufjdk\bin\java.exe`）跑，PATH 里的 java 是 1.7 会报假错。
- 7000 多个 jar 全放 `-cp` 会超 300 秒，不可用。要按需挑 jar：
  1. 按源文件的 import 反查类索引；
  2. **同包隐式 import**：每个文件自己的 `package` 也要按包名补 jar；
  3. 编译报错后分轮补：`The import X cannot be resolved`、`The type X cannot be resolved. It is indirectly referenced`；
  4. **继承链**：`The hierarchy of the type X is inconsistent` 不点名缺哪个类，要读 class 文件常量池沿 extends/implements 逐级补 jar。`zip` 依赖必须开 `deflate`，否则读不出条目内容、静默返回空。
- jar 顺序按 Eclipse 的 classpath 顺序：全路径**大写**后排序（小写会把 `uibc_` 与 `uibcbd_` 排反），分组为 `lib`、`framework`、`external/lib`、`middleware`（各自递归），再 `modules/<名>`（子目录依次 `client/hyext/lib, client/lib, hyext/lib, lib, META-INF/hyext/lib, META-INF/lib`）。该规则对 Eclipse 的 `classpath.args` 复现 100%（7154 个 jar）。
- 类目录（排在 jar 之前）顺序：本工程 `<模块>/classes` → `<工程根>/out/<模块>` → 工作区同级分组（如 `C:\work\aier\pm\phm\classes`）→ NC home 的 `modules/*/classes`。
  - 多数模块的产物在 `newar/out/<模块>`，只有约 25 个模块有自己的 `classes`。
  - 工作区根是 `C:\work\aier`，newar 只是其中一组。
- 验证方法：对照 Eclipse 产物的 `.class`，里面有 "Unresolved compilation problem" 就说明那是代码本身的错，不是我们漏了类路径。
- 当前验证结果：`gl` 编出 192 个类，190 个与 Eclipse 逐字节一致，另 2 个（`VoucherBO`、`GLVoucherService4Fip`）是 Eclipse 编成乱码的；剩 `Step4View` 的 2 个错误是代码本身的。`baseapp` 0 错误。

### 5.3 jdt.ls（M4 要用）
- 版本 0.57.0（最后一个支持 Java 8 的），实测能在 ufjdk 1.8 上跑。安装包在 `D:\AItool\winapp\jdt-language-server-0.57.0-202006172108.tar.gz`，解压示例在 `D:\AItool\aiwork\nc-workbench-m0\jdtls\ls`。
- 四个坑：
  1. initialize 必须声明 `extendedClientCapabilities.classFileContentsSupport=true`，否则跳转到 jar 内的类一律 0 命中（命中是 `jdt://contents/...`，要再发 `java/classFileContents` 取内容）；
  2. 必须配 `java.configuration.runtimes`（JavaSE-1.8 → ufjdk）；
  3. 诊断要等约 21~24 秒才稳定，期间发布 90+ 次不完整结果（满屏「cannot be resolved」），不能当最终结果；
  4. 超大文件补全恒为 0（6433 行/267KB 的 `VoucherBO.java` 返回 0，2036 行正常）。M2 已用「>2000 行降级 + 提示条」兜底，M4 接 jdt.ls 时要在大文件上干脆不派发请求，别让用户等一个注定为空的补全。
- classpath 按 import 反查类索引挑 jar，gl 只需约 108 个 + 基础目录；内存约 550~740MB（-Xmx1024m）。
- 探针脚本：`D:\AItool\aiwork\nc-workbench-m0\m0_jdtls_probe2.py`、`mkjars2.py`。

#### 堆上限：默认 4G，可在服务页改（2026-10-28）

三个数都摆出来，取舍就清楚了：

| 来源 | 值 | 能不能用 |
| --- | --- | --- |
| Eclipse 启动配置 | `-Xmx1024m` | 不够。开发态要装 245 个模块、7230 条 classpath，1G 跑单据转换频繁 Full GC，极端情况直接 OOM，表现是「服务起来了但一点就转圈」 |
| `ierp/bin/prop.xml` 的 `<jvmArgs>` | `-Xmx81920m`（80G） | 不能抄。那是生产服内存的值，16G 笔记本上 JVM 起不来（拒绝启动或换页换死） |
| 本工具默认 | `-Xmx4096m`（4G） | 「够开发、又不吃光同事机器」的折中，各机可改 |

- 常量在 `launch.rs`：`DEFAULT_HEAP_MB = 4096`、`HEAP_MIN_MB = 512`、`HEAP_MAX_MB = 65536`
- 配置字段 `AppConfig.server_heap_mb: Option<u32>`（MB 整数，**不存 `"4G"` 字符串**：存字符串就要在
  某处解析，`"4g"/"4096"/"4G"` 三种写法认错就静默回落成默认，用户还以为改成功了）
- `launch::effective_heap_mb(配置值)` 统一收口：`None` → 4096，越界 → 夹到边界。
  **只在拼启动参数时收口，不改配置本身**，并把生效值回给界面显示
- 命令 `server_heap_set(mb | null)`：越界直接报错（不静默夹边），只写配置不动正在跑的 JVM——
  堆是启动参数，改了要重启服务才生效，界面提示里写明了
- 启动与「命令行预览」共用同一个 `heap_mb` 入参（`middleware_spec` 的第 5 个参数），
  否则会出现「预览里是 4G、真起的是 1G」这种查不出来的错位

#### classpath 已解决（2026-10-28 实测）

**结论：不需要反编译 `nc.uap.mde` 的 `MiddlewareClasspathProvider`。** 按目录约定拼出来即可，
已用真实 JVM 验证能加载主类。

**规则**（`launch.rs`）：
1. 工程各模块的 `classes` 目录（源码输出）——**必须排最前**，改完源码不用出补丁
2. `<NC home>/middleware`、`lib`、`framework`、`external/lib` 下的一层 jar
3. 每个 `modules/<模块>/` 下六个目录的 jar：`client/hyext/lib`、`client/lib`、`hyext/lib`、`lib`、`META-INF/hyext/lib`、`META-INF/lib`（顺序同 `nc_index.rs`）

**规模**：7119 个条目，拼一遍 0.6 秒，pathing jar 479KB。
**为什么用 pathing jar**：7119 条拼成字符串约 500KB，超 Windows 命令行 32767 字符上限。
写一个只有 `META-INF/MANIFEST.MF` 的空 jar，`Class-Path` 列出全部条目，命令行只传 `-cp <jar>`。

**三个必须记住的坑**（都实际踩过，报错都指不到原因）：
1. `std::fs::canonicalize` 在 Windows 返回 `\\?\D:\...`，拼进 `file:` URL 变成 `file:///%3F/...`，
   7000 个 jar 全部失效，报「找不到主类」。要剥前缀（`nc_home::strip_verbatim`）。
2. **目录条目必须以 `/` 结尾**。JAR 规范靠这个斜杠区分「目录」和「jar」，漏了整条 classpath 里的目录全部失效，
   同样报「找不到或无法加载主类」。
3. manifest 每行 ≤ 72 字节、续行以一个空格开头。中文路径一个字 3 字节，必须按字节切。

**实测耗时**：起 JVM + 扫 7119 个 jar，冷 9.6 秒 / 热 0.6 秒；停止 228ms
（`taskkill /T /F`；不带 `/F` 对控制台进程等同无效，会白等 3 秒）。

#### 服务页的实现口径（2026-10-28）

- 「运行中」＝进程活着 **且** 端口是本应用那个 PID 在 listen。只看进程会在
  「java 起着、模块加载失败」时骗人；点启动到端口监听之间十几秒显示「启动中」。
- `ServerRun.starting` 防连点：写 pathing jar 要 ~1 秒，期间两次点击都会通过
  「当前没在跑」检查，最后起两个 java 抢 80。
- 日志按 offset 拉增量（前端 0.5 秒一轮），不用事件推送：漏一拍只是晚一秒，
  事件丢一条就永久缺行，而排查时少的偏偏是那条。
- 日志只留 4000 行、只渲染最后 500 行：中间件跑一天几十万行，全渲染会掉帧。
- 启动时把旧日志轮转成 `middleware.log.1`（不 truncate：进程还持有 append 句柄）。
- 日志与 pathing jar 都放 `%APPDATA%\com.aier.ncforge\`（`logs/`、`tmp/`），
  **不往 NC home 里写文件**——那是同事共用的安装目录。

#### 端口从哪来（2026-10-28 改）

端口**不写死 80**，读 NC 自己的 `ierp/bin/prop.xml`
（`nc.bs.mw.fm.ServiceManager` 在没有 `-Dnc.server.prop` 时默认读
`./ierp/bin/prop.xml`；`bin/sysConfig.bat` 那个 GUI 改的就是这份）：

```xml
<domain><server>
  <servicePort>8005</servicePort>            <!-- Tomcat shutdown 端口，不是监听端口 -->
  <http><address>127.0.0.1</address><port>80</port></http>
</server></domain>
```

- 实现：`nc_home::read_endpoints` 只认 `<http>` 块里的 `<port>`（全文找会串到
  `<servicePort>`）；`<https>` 前缀相同，用「下一个字符必须是 `>` 或空白」区分。
- 文件声明 `gb2312`，但标签与数字都是 ASCII；GB2312 第二字节落在 0x40~0xFE，
  不可能等于 `<`(0x3C)/`>`(0x3E)，所以按文本找标签不会被中文注释带偏。
- 读不到/解析失败回落 80，并置 `from_config=false`：界面悬停「端口」会说明
  「按默认 80 显示」，不假装这是配置里的值。
- 连带跟随的点：状态判定、端口占用者查询、「结束占用进程」的目标端口、
  启动前的冲突检查，全部用同一个端口。

**要改端口，点状态卡上的端口号即可**（本应用代劳写 NC home——每个人的 NC 安装目录都是
本机独立、自己装的，不存在改到同事环境的可能）。弹窗会先列出「哪个文件、从几改成几」，
确认后同时改下面两处，并各自留 `*.ncforge-bak` 备份：

| 文件 | 项 | 不改会怎样 |
|---|---|---|
| `ierp/bin/prop.xml` | `<http><port>` | 服务还是起在旧端口 |
| `hotwebs/web/WEB-INF/classes/system.properties` | `system.ejb.port` | 服务起在新端口，但网页端/门户连的还是旧端口，「服务起来了、浏览器打不开」 |

服务运行中会被拦下（JVM 已读过的配置不会重读）。读完的规则写在 `nc_port.rs` 头注释里：
字节级替换（不重新编码，否则 gb2312 的中文注释会乱码）、只认 `<http>` 块、值非纯数字就拒绝、
应用前重新生成一次方案（防止预览期间被 `sysConfig.bat` 改过）、写完复核读回的端口。

仍要手工同步的地方（工具改不到，弹窗里会列出来）：

1. 客户端连接端口：Eclipse 里 JStarter 启动配置的 `-Dnc.jstart.port`；
2. 生成客户端安装包时填的端口（`bin/buildmisc.xml` 的 `ci.port`，默认 80）。

**不想让工具写文件时，可以走 NC 自己的工具**：

- `bin/sysConfig.bat`（官方 GUI），或直接改 `ierp/bin/prop.xml` 的 `<http><port>`；
- `<address>` 保持 `127.0.0.1` 只有本机能访问；要让同事/手机访问才改 `0.0.0.0`
  （本工具目前只改端口，不改监听地址）。

无论用哪种方式改，本应用都不需要改代码或配置：状态卡会显示新端口，悬停能看到读数来源。

## 9. 这台机器 / 环境的坑

- 用 cc-bridge 操作 Windows：`run_command` 默认壳是 Git Bash，**不是 cmd**；Windows 的 python 不认 `/d/...` 路径要写 `D:\...`；Git Bash 里 `taskkill` 要加 `MSYS_NO_PATHCONV=1`，参数写 `/PID`。
- `run_command` 超时**不会杀进程**，只是断开输出；长任务用后台 + 轮询，超时后先 `tasklist` 再动文件。
- Windows 上没有 `iconv`（管道会把目标文件截成 0 字节），转 GBK 用 python 并回读校验。
- 改文件时在 Python 里写含反斜杠或中文的 Rust/TS 代码要小心转义：`\a`、`\n` 会被转成控制字符。绕法是用 `char::from(92)` 或统一用 `/`；改完 grep 一遍控制字符。
- 不要按命令行模式批量杀进程；只按 PID 杀自己启动的。机器上 2026-10-26 起有两个别的 python 进程不是本项目的，别动。
- 截屏会拍到用户其他窗口，非必要不要截。
- 本机 Eclipse 工作区：`C:\work\aier`（newar、pm、EyePortal 等分组），NC home：`D:\ncc\1909home`。
