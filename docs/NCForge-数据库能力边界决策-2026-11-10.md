## 1. 决策内容

| 能力 | 决策 | 明确不做的事 |
| --- | --- | --- |
| ER 图（表关系可视化） | **不做** | 全库 ER 图；以单表为中心的局部关系图；关系画布 / 连线 / 自动布局 / 缩放导航；把 `TableRelations` 清单改造成图 |

### 1.1 第二次拍板新增的不做项（11 项）

编号对应 `docs/NCForge-数据库行业差距终版台账-2026-11-10.md` 第 3 节，逐项现状、行业对标与理由见该台账。

| 12 | Oracle 用户 / 角色 / 权限图形管理 | 实施账号无授权能力，误操作面大；`db_user_cmds.rs` 只是 NC 操作员只读列举 |
| 13 | 对象依赖树 / 影响分析 | 与 ER 图同源，字典依赖树会漏掉 `md_*` 元数据里的引用 |

### 1.2 第三次拍板：执行历史脱敏不做（台账 X2）

| 项 | 决策 | 明确不做的事 | 明确保留的事 |
| --- | --- | --- | --- |
| 执行历史脱敏（X2） | **不做** | `dbHistory.ts` 不做 SQL 文本脱敏（`identified by`、`password=`、身份证、手机号等）；不做写入前改写、不做存量明文历史的一次性清理迁移；台账 19 列级脱敏展示随之不做 | `ncforge-db-history` 的存储、搜索、高亮、加载回编辑器、按连接 `clearHistory` 全部保留；执行、输出区、结果导出行为一概不变 |

**为什么不做**（记录当时判断，供以后回溯，不作为重新论证的入口）：

- 判定为风险可接受。脱敏防的不是入侵——能读 WebView2 用户数据目录的程序，同样能读 SVN 凭据、能截屏、能注入进程；它实际只降低「截图外发 / 机器交接 / 取证」这三条出口的面。
- 现有出口有限：历史抽屉只有搜索、高亮、加载到编辑器，**没有复制、没有导出**。出口面本身窄。
- 代价虽小，但产品负责人判断当前不值得为它改动历史层。

**已知限制（不在本次决策内解决，必须留档）**：

- `desktop/src-tauri/src/nc_password.rs:95` 的注释写「密码明文不进脚本（只进哈希），所以脚本可以安全地存盘 / 发给同事执行」。该结论对弱口令**不成立**：`encoded_password` 是 `MD5(cuserid + 明文)` 单次哈希，`cuserid` 在 `sm_user` 里公开可读、无随机盐，NC 默认口令（`nc@123`、`1`、`123456`）可被离线还原。
- 因此「重置操作员口令」生成的 `update sm_user set password='…'` 语句**应按凭据对待**，而它会随执行进入历史并以磁盘明文留存。这是 X2 不做之后仍然存在的既定事实，不是待修缺陷；后续若有人重开此议题，从此处起算。

**重开条件（任一成立即重开，不需重新对比行业）**：

1. 历史新增**导出 / 复制 / 分享**能力——出口一旦增加，X2 必须重开，不得单独上线。
2. 客户现场提出等保、审计取证或机器交接的书面要求，且要求落到工具层。
3. 交付形态变化（例如交给非本公司人员长期使用），使「工具内留存生产数据条件」成为责任项。

## 2. 判定理由

### 2.1 ER 图

- **规模不成立**：NC 库两千多张表，全库图不可读。`docs/NCForge-数据库缺口补全-方案设计-20261031.md:247` 已按此判死，同文档第 962 行把 ER 图列入「C（判死）」清单。
- **数据源错配，画出来会误导**：通用 ER 图基于 `user_constraints` 的声明外键；NC 的关联大量存在于 `md_*` 元数据配置（`md_property` / `md_ormap` / `md_class`），不建外键。按 FK 画出来是一批互不相连的节点，比没有图更糟。
- **「看懂结构」这条需求已有更贴现场的替代**：
  - 数据库层：`db_relations_cmds.rs` 的 `FOREIGN_KEYS` + `NC_REFS` 已读出「源表 → 目标表 + 字段对」，`TableRelations.tsx` 用清单 + 「打开关联记录」直接沿关系查到数据。现场要的是那条记录，不是一张图。
  - 业务模型层：`docs/元数据编辑工作台升级方案-2026-11-05.md` 的 BMF 实体画布（主子关系、字段端点、中文名、拖把手建关系）已实施并验收。
- **局部图一并搁置**：技术上可行、原料现成，但属于「做得出来、用不上」。本决策明确不区分全库与局部，均不新增。

### 2.2 多数据库

- **ROI 不成立**：`docs/NCForge-数据库缺口补全-方案设计-20261031.md:1130` 的权重表里「多库 / 迁移」占 5%、现状 5 分，做满也只加不到 5 分（百分制）；而「排障」10% 权重从 20 → 65 同等收益，成本低一个量级。
- **成本是重写而非适配**：每加一个库要一套元数据 SQL、分页 / 引号 / 类型方言、类型映射、LOB 与事务语义、错误码映射；现有纯 Rust thin 驱动与 JDBC 常驻 JVM **两套引擎各适配一遍**，还会把已收敛的 Oracle 正确性面重新摊开。
- **用户不匹配**：NC 实施与二开连的是账套库，NC 只跑 Oracle；面向的是「在熟悉的账套里安全改数」，不是通用 DBA 的多库取数。定位见 11-08 评价报告第 01 节。

### 2.3 其余 11 项

共同判据：要么需要 DBA 级权限或服务端工具（05/06/12/14/17 这类在台账里同样被建议不做），要么服务的是「第一次连上陌生库 / 通用取数 / 团队协作」而不是「在熟悉的 NC 账套里安全改数」。完整逐项论证见台账第 3 节「理由」列与第 7 节证据索引。

## 3. 边界澄清：不做 ≠ 删除

以下能力继续保留、继续维护，不受本决策约束：

| 能力 | 为什么不属于被否的项 |
| --- | --- |
| `db_relations` 与 `TableRelations.tsx` 关联记录跳转 | 清单 + 跳转，不是关系图 |
| BMF 元数据编辑工作台实体画布 | 业务模型层，不是数据库层 ER 图 |
| `db_struct_diff` 结构对比、`db_transfer_rows_*` 跨连接搬运 | **跨连接 ≠ 跨数据库类型**，两端都限定 Oracle |
| `sqlFormatPrefs.ts` 的达梦 / 金仓 / PostgreSQL 方言选项 | 仅 SQL 排版偏好，不代表支持该库连接 |
| NC 中文名 / 数据字典、按值反查、结果与计划 A/B 对比 | 既非关系可视化，也非多库 |
| SQL 片段库、执行历史全文检索、工作台文件编辑器与版本控制页 | 已有「找回来」的通道，不因「脚本工程」不做而删除 |
| `db_user_cmds.rs` 的 NC 操作员只读列举 + 生成改密脚本 | 仍只读、仍不执行，不属于 Oracle 权限管理 |

## 4. 重开条件

只有前提发生实质变化才重新评估，且必须有新的产品决策；**不因「竞品有」而重启**。此条对本表全部 14 项（含第 1.2 节的 X2）与台账 16 项待评估项一律适用。

- **多库**：NC 官方适配达梦 / openGauss / 金仓等，形成换库迁移的硬需求。此时起点是 DDL 生成与方言翻译（UAP MDP 已有 8 种方言，见 `docs/NCForge-对标UAP-Studio-生成能力-方案-2026-11-05.md`），而不是把现有 Oracle 链路抽象成通用客户端。
- **ER 图**：出现「同屏理解多表拓扑」的明确现场场景，并给出比清单 + 跳转更高的效率证据；且必须先解决 NC 类引用与外键的统一建模，否则仍会画出误导图。
- **PL/SQL 调试（台账 04）**：先拿出 NC 现场确实写存储过程的频次证据，再决定是否属于真需求。
- **其余项**：出现明确现场场景 + 可量化效率证据，且不与「不静默错数据」冲突。

3. S2 / S3 / S4 残留与 a11y 收尾。
