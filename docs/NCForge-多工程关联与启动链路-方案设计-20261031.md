## 0. 一页结论

2026-10-31 在本机三个真实工程上做了实测（`C:\work\aier\{newar,pm,EyePortal}`）。
**依赖链与用户描述一致**：`EyePortal → pm → newar`，声明在各自 `.classpath` 里（§2）。
实测同时**推翻了本方案初稿的一处设计取向**——不需要用户手工排序，`.classpath` 里已经写清楚了（§2.2）。

| # | 缺陷 | 证据（我们） | 证据（参考插件） | 性质 |
|---|------|-------------|-----------------|------|
| **D0** | `project_class_dirs` 漏掉 Eclipse 的**默认输出目录 `bin/`**；无条件收全部兄弟工程；顺序是字典序 | `launch.rs:170-216`。实测 `pm/bin` 有 339 个 class，**一个都进不了类路径**（§2.3） | 交给 IDE | **P0**：改动小、当场可验、直接对应"改了不生效" |

## 1. 参考插件到底怎么让 NC 在"编辑器"里跑起来

它本身不实现编译器和类加载器，五件事全部委托给 IDEA：

```
① 工程结构    每个 NC 模块 = 一个 IDEA Module，源码根 src/public|client|private
② 类路径      Module 的 OrderEntry（库 + 其他模块），由 IDEA 的依赖图解析
③ 编译        BuildBeforeRunTask：先 build 再 run
④ 运行        ApplicationConfiguration + mainClass + VM 参数 + workingDir=NCHOME
⑤ 命令行压缩  ShortenCommandLine.MANIFEST（长 classpath 写进 manifest）
```

关键在 `generateRunMenu`（`IdeaProjectGenerateUtil.java:239-403`）：

```java
conf.setMainClassName("ufmiddle.start.tomcat.StartDirectServer")
conf.setWorkingDirectory(ncHome.getPath())
conf.setModule(getProjectModules(project)[0])       // ← 类路径来自这个 module 的依赖图
conf.setShortenCommandLine(ShortenCommandLine.MANIFEST)
conf.getBeforeRunTasks().add(new CompileStepBeforeRun.MakeBeforeRunTask())
```

逐条对照我们的实现：

| 它的做法 | 我们 | 判定 |
|---------|------|------|
| `mainClass = ufmiddle...StartDirectServer` | `launch.rs:25` 同 | ✅ 已对 |
| `workingDirectory = NCHOME` | `ServerSpec.work_dir = nc_home`（`launch.rs:281`） | ✅ 已对 |
| `setModule(...)` 决定类路径 | 隐式目录扫描（`launch.rs:170-216`） | ❌ **这就是 D1** |
| `ShortenCommandLine.MANIFEST` | pathing jar（`launch.rs:307-337`） | ✅ 同思路，我们做得更细（72 字节续行、百分号编码） |
| `BuildBeforeRunTask` | **没有** | ❌ 点"启动服务"不先编译。改完代码忘了编译就启动，跑的是旧 class，且没有任何提示（D4 的另一面） |

### 1.1 它真正独有的一段：运行前把配置搬进 NCHOME

`copyProjectMetaInfFiles2NCHomeModules`（`:579-628`）在**每次运行前**做三件事：

| 动作 | 源 | 目标 | 方法 |
|------|----|------|------|
| ① META-INF 落地 | `<模块>/META-INF/**` | `<NCHOME>/modules/<模块>/META-INF/` | `:630-666`，带 `isNoChange` 跳过未变文件 |
| ② NCC yyconfig | `<模块>/src/client/yyconfig/**` | `<NCHOME>/hotwebs/nccloud/WEB-INF/extend/yyconfig/` | `:673-726` |
| ③ NCC client action | 编译产物里的 client 包 | `<NCHOME>/hotwebs/nccloud/WEB-INF/classes/` | `:733+` |

① 里最有价值的一行是 `modeluUmpDir.mkdirs()`（`:648-650`）——**NCHOME 下没有这个模块目录时会主动建**。

这解释了两类现场问题，而我们的实现对此**一无所知**：

- **改了 upm 不生效**：我们只把 `<模块>/classes` 塞进 classpath，`META-INF/*.upm` 不在 classes 里（ecj 不搬资源文件），NC 也不会去 classpath 找 upm——它是按 `<NCHOME>/modules/<m>/META-INF/` 的**文件路径**读组件元数据的。所以工程里改了组件注册，运行时读到的还是 NCHOME 里那份旧的。
- **新增模块起不来**：NCHOME 下没有这个模块目录，模块扫描就发现不了它，classpath 里有类也没用。

**upm 是什么（本机实测，`D:/ncc/1909home/modules/gl/META-INF/gl_main.upm`）**：

```xml
<module name="gl1">
  <public>
    <component priority="0" singleton="true" remote="true" tx="CMT">
      <interface>nc.itf.gl.pub.ICommAccBookPub</interface>
      <implementation>nc.impl.gl.glcom.ImpCommAccBook</implementation>
    </component>
```

**它是接口→实现的注册表**。也就是说：二开里新增一个组件（`nc.itf.xxx.IXxx` + `nc.impl.xxx.ImplXxx`），这个组件要在 upm 里登记，`NCLocator.lookup(IXxx.class)` 才找得到。工程里改了 upm 而 NCHOME 里是旧的 ⇒ **lookup 抛组件找不到** ⇒ 表现就是"启动 dev 报错"或某个功能一点就报错。

本机 `D:/ncc/1909home` 实测：245 个模块，**244 个带 `META-INF/`**，目录里全是 `.upm`。这不是边角情况，是主路径。

### 1.2 本机实测：38 个 upm 在 NCHOME 里根本不存在

不是理论推演。拿本机现有的工程与安装目录直接对了一遍（`workspace_root = C:\work\aier\newar`，`nc_home` 取默认 `D:\ncc\1909home`）：

| 模块 | 工程 `META-INF` 文件数 | NCHOME 里没有的 | 内容不同 |
|------|---------------------|----------------|---------|
| `uapbd` | 39 | **36** | 1（`P_PharmSupplierMap60.upm`） |
| `ic` | 15 | **2**（`50vim.upm`、`CabinetStockService.upm`） | 0 |
| `pu` | 12 | 0（逐个比对相同） | 0 |
| `ct` | 4 | 0 | 0 |

工程共 63 个模块目录、36 个带 `META-INF`。没在 NCHOME 里的那批全是二开单据与组件：

```
P_Eyeadjustbill60.upm      P_Eyehisgatherbill60.upm   P_Eyehisrecbill60.upm
P_Eyerecbill60.upm         P_Eyebgwork60.upm          P_Drugprocurement60.upm
eyevim.upm                 drugdict.upm               rfid.upm
hisdoc.upm                 logforInterface.upm        saleoutmhsend.upm
…（共 36 个，另有 eyevim.rest / wmshr.rest 等 REST 声明）
```

**再看一眼反例**：`uapbd/lib/*.jar` 里逐个查过，**没有任何一个 jar 含 `.upm`**。
所以不存在"从 classpath 的 jar 里也能读到 upm"这条路——它就是按 `<NCHOME>/modules/<m>/META-INF/` 的文件路径读的。

**结论**：在这台机器上，用现在的实现直接启动服务，这 38 个组件注册**全部不生效**。
`NCLocator.lookup(IXxx.class)` 找不到实现，或者是"单据模板不存在""功能点没注册"这类报错。
如果现场的"启动 dev 报错"发生在二开功能上（而不是启动过程本身），这就是答案。

> 仍保留一次启动验证（§2 探针 A）：改一个能在界面上看出变化的名字，确认改动是否生效。
> 这一步的价值是**证明修好之后确实变了**，而不只是证明"两份文件不一样"。

## 2. 实测：依赖链与类路径组成（2026-10-31 已跑完）

### 2.1 依赖链确认：`EyePortal → pm → newar`

依赖**不在** `.project` 的 `<projects>` 里（三者都是空），而是写在 `.classpath` 里，形如
`<classpathentry kind="src" path="/<工程名>" combineaccessrules="false" exported="true"/>`：

| 声明位置 | 内容 |
|---|---|
| `pm/.classpath:37` | `kind="src" path="/newar" exported="true"` |
| `EyePortal/.classpath:38` | `kind="src" path="/pm" exported="true"` |
| `newar/.classpath` | 无任何工程引用（它是基座） |

同一工作区里还有三个工程也引用 `/newar`：`aierhh/.classpath:18`、`epuip/.classpath:33`、`TestBill/.classpath:18`。
`aiertest` 什么都不依赖。⇒ **引用关系是显式的、可解析的，不需要我们猜。**

### 2.2 三条推翻初稿的实测结论

**(1) `exported="true"` 让依赖变成传递的，这一条是承重的，不是装饰。**

逐 import 解析（只用工程源码，不含 NCHOME jar）：

| 边 | 引用了对方独有类的数量 | 典型包 |
|---|---|---|
| `pm → newar` | **151** | `nc.ui.pubapp` 22、`nc.ui.pub` 17、`nc.itf.util` 12 |
| `EyePortal → pm` | **76** | `nc.vo.pim` 47、`nc.vo.phm` 8、`nc.vo.uapbd` 7 |
| `EyePortal → newar`（**经 pm 传递**） | **95** | `nc.vo.uapbd` 12、`nc.itf.util` 11、`nc.itf.uapbd` 9 |

第三行是关键：EyePortal 直接用到了 95 个**只存在于 newar** 的类，它之所以能编译，是因为 pm 那条
`/newar` 带着 `exported="true"`。**如果按"只连直接依赖"建图，EyePortal 编译立刻挂。**
（已排除"NCHOME 里也有"这条退路：`nc.bs.pu.aier` 在 `D:/ncc/1909home/modules/pu/classes` 下不存在。）

**(2) 工程名 ≠ 目录名，`newar` 这个地方就有坑。**

`newar/.project:3` 自称 `<name>ar</name>`，但工作区里注册的工程名是 `newar`
（`C:/work/aier/.metadata/.plugins/org.eclipse.core.resources/.projects/` 下只有 `newar`，没有 `ar`）。
Eclipse 实际按**目录名**解析 `/newar`。⇒ 我们的解析器**不能只信 `.project` 的 `<name>`**，
必须先按目录名匹配，再退到 `.project` 名。这条如果写反，A 工程直接解析失败。

**(3) 同名类重名是真的，而且内容不同。**

| 对 | 同名 FQCN | 内容不同 |
|---|---|---|
| newar ↔ pm | 37 | **18** |
| newar ↔ EyePortal | 1 | 0 |
| pm ↔ EyePortal | 1 | 1 |
| 三方同时重名 | 0 | — |

18 个不同的里包括 `nc.bs.uapbd.pjentlic.ace.bp.AcePjentlicUpdateBP`（源 2092 vs 2747 字节）、
`nc.bs.uapbd.plugin.LabeldeptLoadingPlugin`（9880 vs 16626 字节）。**顺序不是美观问题，是行为问题。**

### 2.3 D0 的实证：`pm/bin` 完全不可见

`pm/.classpath` 里 `uapbd/src/{client,private,public}` 与 `pubapp/src/client` **没有 `output=` 属性**，
按 Eclipse 规则落到工程默认输出 `bin`。于是：

```
pm/bin                        339 个 class   ← 我们的 project_class_dirs 从不扫这个目录
  nc/bs/uapbd  108    nc/ui/uapbd 69    nc/bs/pub 42    nc/vo/uapbd 36 ...
```

而 `newar` 的同一批类在 `newar/out/uapbd`（2699 个 class，`out/*` 被扫到了）。
两个位置都有 `AcePjentlicUpdateBP.class`，md5 不同（`6a3e68dc…` vs `cca61f41…`）。

⇒ 从 pm 或 EyePortal 启动时，实际加载的是 **newar 的版本**；在 pm 里改 `AcePjentlicUpdateBP`
并编译到 `pm/bin`，**运行时根本不会加载它**。这是"改了代码不生效"的一条现成解释，
而且它不依赖任何新功能，属于纯缺陷。

同时，兄弟扫描是**无条件**的：`C:/work/aier` 下 `TestBill`、`aierhh`、`epuip` 也各有 classes 目录，
里面同样有 `nc/bs`、`nc/ui`、`nc/vo` 的类，会按字母序插到 `newar`/`pm` 前面或后面——
谁生效取决于目录名字母序。四处来源、零处声明。

### 2.4 D3 的实证：编码写死得不对味

参考实现在 `IdeaProjectGenerateUtil.java:328-333` 按版本分支：**NCC/BIP 用 `-Dfile.encoding=UTF-8`，
NC5/NC6 用 GBK**。本机 `D:/ncc/1909home` 有 `hotwebs/`、三个工程里有 36 个 `nccloud` 源目录
⇒ 明确是 NCC 形态。而我们 `launch.rs:117` 无条件写 `-Dfile.encoding=GBK`。

另外 Eclipse 侧还有**逐文件编码覆盖**（`EyePortal/.settings/org.eclipse.core.resources.prefs` 里
`...OrderConstants.java=GBK` 与 `...EyeStoreRestResource.java=UTF-8` 并存）。我们的编译器是启发式
`detect_encoding`（`compile.rs:609`），与 Eclipse 的显式声明可能不一致——这类差异表现为"我这边编译过了，
Eclipse 报乱码"或者反过来的中文乱码常量。

### 2.5 D6 的实证：hyext 层与"六段散类目录"

NC 的类路径是**「段 × 层」**的二维结构：段 = `public` / `client` / `private`，层 = `hyext` / 标准。
参考插件的六个库容器就是这六格，每一格 = **散类目录在前 + jar 目录在后**
（`IoUtil.java:223-239 / 247-260 / 315-331`，容器的构造方式就是 `classes.addAll(jars)`）：

| 段 | hyext 层 | 标准层 | 容器方法 |
|---|---|---|---|
| public | `modules/<m>/hyext/classes` | `modules/<m>/classes` | `:223` / `:235` |
| client | `modules/<m>/client/hyext/classes` | `modules/<m>/client/classes` | `:247` / `:265` |
| private | `modules/<m>/META-INF/hyext/classes` | `modules/<m>/META-INF/classes` | `:315` / `:327` |

（散类目录的扫描实现分别在 `IoUtil.java:453 / 463 / 473 / 484 / 494 / 505`。
另有一处 U8Cloud 专属的 `client/hyext/extension/classes`（`:251-259`，数据交换用），本机不存在，先不接。）

本机实测（`D:/ncc/1909home/modules`，245 个模块）：

| 目录 | 存在个数 | `.class` 个数 |
|---|---|---|
| `modules/*/classes` | 49 | 258 |
| `modules/*/client/classes` | 60 | **67** |
| `modules/*/META-INF/classes` | 50 | **80** |
| `modules/*/hyext/classes` | **0** | **0** |
| `modules/*/META-INF/hyext/classes` | 1 | 1（`platform` 的 `TranslatorRowService`，NCC 自带） |
| `modules/*/client/hyext/classes` | 0 | 0 |

> **更正（同一轮里我算错过一次）**：初次统计用 `-path "*/hyext/classes"` 匹配，
> 把 `platform/META-INF/hyext/classes` 同时计进了 public 段和 private 段，得出"public hyext 有 1 个 class"。
> 按 `modules/<m>/hyext/classes` 精确逐模块判断，public 段是 **0 个**。
> 教训：`-path "*/X/Y"` 会跨层级命中，段位判断必须用固定层数（`*/hyext/classes` vs `*/META-INF/hyext/classes`）分别验。
>
> **第二次更正（2026-10-31 复核）**：上表第一行原本写「161 个目录 / 458 个 class」，那是把
> 各层级的 `classes` 目录（含 `client/classes`、`META-INF/classes`）一起 `find` 出来的数，混算了。
> 按段分别 `find -name '*.class'` 重数：**49 目录 / 258 class**，六段合计 160 目录 / 406 class。
> `tests/nc_class_dirs_live.rs` 打印的就是这组数，两边应当一致。

**⚠️ 上面这张表只代表「干净安装」，不能代表现场。** 本机 `D:/ncc/1909home` 从未装过补丁
（`modules/*/replacement` 不存在、hyext 段基本空），所以 hyext 三行看着"几乎没东西"。

现场已确认（2026-10-31 用户答复）：**补丁装完后 hyext 里是散文件**
`modules/<m>/hyext/classes/<pkg>/X.class`，与我们 `patch_view.rs:176-192` 的出包形态**一致**。
推论链条：

```
补丁落 modules/<m>/hyext/classes/   （现场形态，散文件）
  ↓
开发机的 NCHOME 只要装过一次补丁，这个目录就有类了
  ↓
我们的类路径完全不扫 modules/<m>/hyext/classes
  ↓
⇒ 补丁类在本地启动时根本不在 classpath 上
```

而且 hyext 的**语义**就是"覆盖标准产品类"——补丁把类放在 hyext，就是要求它优先于
`lib/*.jar` 里的标准实现。我们既没扫它、更没排在标准层之前，语义双失。

所以 **D6 里 N1/N3/N5 三个 hyext 散类段是现场必需的，不是"顺手补的边角"**。
本机测出来"hyext 段是空的"，恰恰是因为这台机器没装过补丁——这个数据不能用来说这条不重要。

而 `nc_index.rs` 的 `module_class_dirs` **只收第一行**。漏掉的是 148 个 class，
内容全是二开覆盖类，例如：

```
nc/bs/ct/purdaily/insert/PurdailyInsertBP.class     ← ct
nc/bs/ct/purdaily/update/PurdailyUpdateBP.class
nc/ui/arap/gatheringbill/action/RedInvoiceAction.class
nc/eyes/cmp/paybill/PaybilltoCbsImpl.class
nccloud/iuap/sync/listener/IuapSyncEventlistener.class
```

**这条比"顺序不对"严重**：漏扫是"看不见"，顺序错是"看错了"。看不见的后果是编译报
`cannot be resolved`，而运行时确实有这个类——编译期与运行期两份真源。

hyext 侧的 jar 数量（实测）：public `hyext/lib` 61 个、client `client/hyext/lib` 66 个、
private `META-INF/hyext/lib` 62 个，合计 **189 个 jar、2998 个不同的 class 条目**。这些**已经在**我们的
`MODULE_JAR_DIRS` 里了，所以 jar 侧不缺；缺的是散类目录。

**顺序**：参考插件把库容器按「段优先、段内 hyext 在前」挂进工程（`IdeaProjectGenerateUtil.java:473-510`）：

```
public_extra → public_hyext → public_std
→ client_extra → client_hyext → client_std
→ private_extra → private_hyext → private_std
```

注意 `:449` 的 `boolean hyVersion = true;` —— 真正的版本判断被注释掉了，**hyext 容器永远挂载**。

我们的 `MODULE_JAR_DIRS`（`launch.rs:39-47`，`nc_index.rs:28-35` 是同一份）是
`client/hyext → client → hyext → lib → META-INF/hyext → META-INF`，且外层循环是**模块优先**
（`launch.rs:148-155`）。两处都与 Eclipse 不一致：

1. **段的先后反了**：public 应在 client 之前，我们把 client 排最前；
2. **分组粒度错了**：Eclipse 是"先跨模块汇总某一层，再下一层"（层优先），我们是"一个模块全扫完
   再下一个模块"（模块优先）。

**实测影响面（诚实报告，但要把适用条件写清楚）**：把 245 个模块、6280 个标准 jar 全扫一遍，
按我们现有顺序会被标准层抢先的类**只有 1 个**（`riart` 的 `nc/ui/bd/ref/RefTableColumnModel.class`，
被 `riart/client/lib` 抢先）。

这个"1 个"**只在干净安装上成立**：该机器的 `hyext/classes` 是空的，所以比的只是 189 个 hyext **jar**
与标准 jar 的先后。装了补丁的现场机器上，`hyext/classes` 里有类，而这些目录我们**压根不扫**
（见上），此时的问题不是"顺序错"而是"缺位"——数量级完全不同，也无法用本机数据估。

结论：**顺序偏差按"几行就能修对"处理，不单列排期**；但**散类目录缺位是 P0**，两者一起改。

**一个反例值得记**：本项目的 `.classpath` 里**没有任何 hyext 容器**（9 个容器全是标准层）。
也就是说团队现在在 Eclipse 里构建时，`hyext/lib` 的 189 个 jar 根本没上构建路径。
我们是超集——这一处我们比 Eclipse 全，别为了"和 Eclipse 一致"把它删掉。

## 3. D1：类路径按 Eclipse 语义重建（一期主交付）

### 3.1 现状为什么不够

`launch.rs:170-216` 的 `project_class_dirs` 是**编译、启动、语言服务三处共用**的唯一入口
（`compile.rs:621` 编译、`launch.rs:263` 启动服务、`shadow.rs:279` jdt.ls 影子工程全部引它）。
这个结构是对的，改一处三处生效，必须保留。

但它现在有**四处**隐式扫描，每一处都在猜：

```
1. <工程根>/<模块>/classes            ← 自己的模块（扫到了）
2. <工程根>/out/<模块>                ← Eclipse 的另一种输出（扫到了）
3. <工程根>/bin                      ← ❌ 根本不扫（pm 的 uapbd/pubapp 全在这里）
4. 同父目录下所有兄弟分组的 <分组>/<模块>/classes   ← 无条件、字典序、且不扫兄弟的 out/ 和 bin/
5. <NCHOME>/modules/*/classes
```

对照 `.classpath` 这份**已有的权威声明**，我们等于把所有信息重新猜了一遍，而且猜漏了：

| 信息 | `.classpath` 里怎么写的 | 我们现在怎么取 | 结果 |
|---|---|---|---|
| 哪些工程是依赖 | `path="/newar"`，5 处 | 父目录下所有兄弟目录 | 多收 `TestBill`/`aierhh`/`epuip`，漏掉跨盘工程的依赖 |
| 依赖的先后 | 条目出现顺序 | `dirs.sort()` 字典序 | 18 个同名类里 newar 压过 pm（应为 pm 优先） |
| 产物目录 | 每条 src 的 `output=` + 工程默认 output | 只认 `<mod>/classes` 与 `out/<mod>` | **`pm/bin` 339 个 class 全丢** |


### 3.2 新方案：读 `.classpath`，不再猜目录

初稿设计是"用户手工排序一串关联工程"。实测后改掉：**这个信息已经存在 `.classpath` 里，而且是权威的。**
让用户再排一遍，等于把已经写对的东西用人工方式重抄一次，还会抄错。

新建 `src-tauri/src/eclipse_cp.rs`（纯逻辑 + 单测，不依赖 tauri）：

```rust
pub struct ProjectCp {
    pub name: String,              // 以目录名为准，.project 名只作参考（§2.2(2)）
    pub default_output: String,    // <classpathentry kind="output" path="…">
    pub outputs: Vec<PathBuf>,     // 各 src 条目的 output，去重；缺省回落到 default_output
    pub refs: Vec<CpRef>,          // kind="src" 且 path 以 '/' 开头
}

pub struct CpRef { pub name: String, pub exported: bool }
```

四条解析规则，每条都要有单测：

1. `output=` **缺省**时用工程默认输出。本机三种形态都存在：`pm` → `bin`、`newar` → `out/bin`、
   多数模块另外显式写了 `<mod>/classes` 或 `out/<mod>`。**光靠 `<mod>/classes` 猜必漏**（§2.3）。
   注意 `<classpathentry kind="output" …/>` 是**文件里最后一行**，必须两遍扫描（先取默认值，再处理 src），
   否则前面的 src 条目会拿到 `None`——本轮写解析脚本时就踩了一次。
2. 同一个 output 目录被多条 src 条目共享（`public`/`client`/`private`/`resources`/`test` 五条常指同一个），**去重**。
   实测去重后：`newar` 35 个、`pm` 8 个、`EyePortal` 9 个（35 条来自 223 个 src 条目）。
3. `path="/X"` 是 Eclipse **工程名**，不是路径。解析成目录的顺序：**先按兄弟目录名匹配 → 再按 `.project`
   的 `<name>` 匹配 → 再按工作区 `.projects/` 注册表匹配**。本机 `newar` 的 `.project` 叫 `ar`，
   顺序写反就直接解析失败。
4. `exported="true"` 才继续往下传递。**这一条不能省**：EyePortal 有 95 个类只能经 `pm → newar` 拿到（§2.2(1)）。
   本机三个工程里的引用全部带 `exported="true"`，也就是说这条路径天天在用。

### 3.3 解析顺序（唯一真源，三处共用）

```
位 0     主工程 outputs（按其 .classpath 顺序）
位 1..n  依赖工程 outputs（.classpath 出现顺序 + exported 传递，深度优先、已访问跳过）
── 以下是 NCHOME，按「六个容器」排，每个容器 = 散类目录 + 该容器的 jar ──
C1  public  hyext     modules/*/hyext/classes                  → modules/*/hyext/lib/*.jar
C2  public  标准      modules/*/classes                        → modules/*/lib/*.jar
C3  client  hyext     modules/*/client/hyext/classes           → modules/*/client/hyext/lib/*.jar
C4  client  标准      modules/*/client/classes                 → modules/*/client/lib/*.jar
C5  private hyext     modules/*/META-INF/hyext/classes         → modules/*/META-INF/hyext/lib/*.jar
C6  private 标准      modules/*/META-INF/classes               → modules/*/META-INF/lib/*.jar
最前     middleware / lib / framework / external/lib 的 jar（保持现状，它们不属于任何模块）
```

**为什么不写成"所有 classes 在前、所有 jar 在后"**：参考插件的每个容器都是
`serachAllNcXxxClass() → addAll(serachAllNcXxxJars())`（`IoUtil.java:223-239`），
即 `public_hyext` 的 jar **也**排在 `public_std` 的 classes 之前。若按"classes 全在前"排，
`modules/pu/classes` 里一个旧类就会压过 `modules/pu/hyext/lib` 里的覆盖版本——正是 hyext 要解决的场景。

**这会影响函数签名**：`middleware_classpath(home, project_classes: &[PathBuf])`（`launch.rs:125`）
现在收一个扁平的目录列表、后面统一追加 jar，装不下"容器内 classes 与 jar 交替"。改成收六段：

```rust
pub struct HomeClasspath {
    pub containers: [Vec<PathBuf>; 6],   // C1..C6 的散类目录
    pub home_jars: Vec<PathBuf>,          // middleware/lib/framework/external
}
pub fn middleware_classpath(home: &Path, project_classes: &[PathBuf], hc: &HomeClasspath) -> Vec<PathBuf>
```

四条硬规则：

1. **工程永远在最前**。改自己的代码必须立刻生效，不能被任何依赖工程或 NCHOME 覆盖。
2. **依赖顺序 = `.classpath` 里写的顺序**，不是路径字典序、也不是字母序。用户想调整时，改的是
   应用内的覆盖表（写进本机配置），不动 `.classpath`——那是团队共享的文件，我们无权改。
3. **NCHOME 永远在最后**，内部按 `C1..C6` 容器序，每个容器内散类在前、jar 在后。hyext 必须排在
   同段标准之前，这是"二开覆盖标准"的实现机制；顺序写反不会报错，只会静默用旧类。
4. **`launch.rs` 与 `nc_index.rs` 的同名常量必须逐字一致**。现在两处各有一份 `MODULE_JAR_DIRS`，
   注释互相指向；改一份漏一份，表现是"编译找不到类但启动能跑"。收敛成一份 `pub const` 更好。

签名：

```rust
pub struct ClassRoots<'a> { pub primary: &'a Path, pub overrides: &'a [LinkedOverride] }
pub fn project_class_dirs(roots: &ClassRoots, nc_home: &Path) -> Vec<PathBuf>
```

`LinkedOverride` 只做三件事：停用某个关联工程、强制某工程排到最前/最后、手工补一个 `.classpath`
没声明的目录（给 EJB 生成目录、老工程这种特例用）。**默认全部留空**——绝大多数用户不需要碰它。

> 旧的 `project_class_dirs(project_root, nc_home)` 保留为薄包装（内部 `overrides: &[]`），
> 让 `shadow.rs` 与测试逐步迁移。**不要长期留两个入口**，迁移完就删，
> 否则迟早有人在单工程版本上调用，表现为"语言服务能跳转、编译说找不到类"。
>
> **实际落地（2026-10-31）没有引入 `ClassRoots`**：`overrides` 暂时没有调用方，
> 提前加一层包装只会多一个「有人传了覆盖却不生效」的入口。实际签名仍是
> `eclipse_cp::class_roots(primary: &Path, nc_home: &Path)`，由
> `launch::project_class_dirs(project_root, nc_home)` 薄转。等批次 4 做前端「停用/补目录」
> 时再加 `ClassRoots`，届时覆盖项是**唯一**入口参数，不再留两套签名。

### 3.3.1 数据结构的降级

初稿的 `LinkedProject { root, order, enabled }` 降级为 `LinkedOverride { root, mode }`：
**不再要求用户填写关联工程列表**，界面上的主视图变成"自动识别到的依赖链（只读 + 可停用）"，
`EyePortal → pm → newar` 会直接显示成一条链。迁移逻辑（§3.4）也随之简化成"清掉旧启发式的隐式发现"。

### 3.4 老用户迁移：隐式发现不再写进配置

直接删掉兄弟目录扫描会让现有用户（`newar` + `pm/phm` 那套）立刻退化。

**做法**：读到"有 `workspace_root` 但 `eclipse_links_init` 字段不存在"的配置时，**不写任何条目**，
只跑一次自动发现（读 `.classpath` + 兄弟目录兜底），把结果作为「本次读到 N 个依赖工程」提示出来。
本机实测：从 `EyePortal` 打开会解析出 `pm → newar` 两级，从 `newar` 打开解析出 0 个。

用 `eclipse_links_init: bool` 标记只做一次（同 `db_conns_init` 的既有做法，`config.rs:74`）。
之所以不像初稿那样把发现结果**固化成配置**：路径是本机事实，固化进配置后同事换了目录结构就会得到一份
陈旧且静默生效的列表——而这正是 D0 想根除的那类问题（信息有两处真源）。配置里只留**覆盖项**，默认空。

### 3.5 D4：编译期"关联工程未编译"诊断

现在 `compile.rs` 的报错闭环是"缺 jar → 补 jar"，补不出来就停（`:650-656`），把 ecj 原文扔给用户：

```
IVoucherQuery cannot be resolved to a type
```

用户无法判断这是代码写错，还是关联工程没编译。**加一层归因**：

1. 报错里的名字（`compile.rs:213-235` 已经在解析它了）加上该文件的 `import` / 同包声明，推成 `nc.bs.foo.Xxx`；
2. 转成相对路径 `nc/bs/foo/Xxx.java`；
3. 在该模块对应的各 root（主工程 + 各关联工程）的 `<模块>/src/{public,client,private}` 下找；
4. 命中 → 追加一条可读诊断，而不是替换 ecj 原文：

```
关联工程「B」里有这个类的源码，但它没有编译产物：
  E:\projB\newar\gl\src\private\nc\bs\foo\Xxx.java
先编译 B（或点「按依赖顺序全部编译」）。
```

**还要加"陈旧检测"**（比"不存在"更危险，因为它静默通过）：产物的最新 mtime 早于该模块源码最新 mtime ⇒ 警告「B 的产物比源码旧，本次编译可能用到旧类」。这一条只在编译前提示，不阻断（阻断会挡住"我只想先编 A"的正常用法）。

陈旧检测要同时看**两种产物布局**——这是本机真实存在的状况（`config.rs:47-50` 的注释已经记过）：

| 布局 | 谁产出 | 检查对象 |
|------|--------|---------|
| `<模块>/classes` | 本工作台的编译 | `classes` 目录下最新 class 的 mtime |
| `<根>/out/<模块>` | Eclipse（显式 `output="out/x"`） | `out/<模块>` 下最新 class 的 mtime |
| `<根>/bin` | Eclipse（**未写 `output=` 时的默认输出**） | `bin` 下最新 class 的 mtime；本机 `pm/bin` 就属于这一类 |

第三种是本轮实测补的：`pm` 的 `uapbd`/`pubapp` 源码没有 `output=`，产物全在 `pm/bin`（339 个 class）。
只看前两种会得出"pm 的 uapbd 根本没编过"这种错误结论。三种都按 `.classpath` 里那条 src 条目的
实际 `output` 判定，不要写死目录名。

### 3.6 D5：同名类冲突可见化

不新增扫描开销，做成**按需触发**（工程页一个「检查类冲突」按钮）：

- 遍历各 root 的**全部** output 目录（含 `bin`），收集相对路径 → 出现次数 > 1 的
- 输出：冲突的类全名、出现在哪几个 root、**当前实际生效的那个**（按 §3.3 顺序算）
- 不做自动裁决。同名类在 NC 二开里经常是**故意**的（覆盖标准产品类），工具只负责让人看见。

本机按此规则跑，第一批就会报出 37 个 newar↔pm 同名类（其中 18 个内容不同），这正是应该被看见的。

### 3.7 编译顺序

有了 `.classpath` 这份声明，"按依赖顺序全部编译"从"靠用户排序"变成**可以直接拓扑排序**：

- 有向图：`工程 → 它 .classpath 里声明的工程`，边方向就是编译顺序的逆序
- 「全部编译」= 先编叶子（`newar`）→ 再编 `pm` → 最后编主工程
- 环（A 引用 B、B 也引用 A）只警告不阻断，退化成"按发现顺序编两遍"
- 单个编译仍然只编一个模块（不做连带编译，`compile.rs:9` 的既有结论：`-sourcepath` 连带会滚雪球）

> 初稿判断"不做 import 级拓扑推导、用人工顺序表达依赖"，在拿到 `.classpath` 之后**部分作废**：
> 工程级依赖不用推，文件里写着；但**类级**依赖（谁覆盖了谁）仍然不做推导——那才是真正费力不讨好的部分。

### 3.8 前端

工程页（现有空态入口 `src/components/workspace/NoWorkspace.tsx`，已打开工程时挂在工程设置里）
新增「依赖工程」区块。**主视图是只读的依赖链，不是让用户填的表**：

```
主工程  EyePortal        C:\work\aier\EyePortal        9 个输出目录
  └─ pm                  C:\work\aier\pm               8 个输出目录（含 bin，339 个 class）
       └─ newar          C:\work\aier\newar            35 个输出目录（含 out/bin）
                            ↑ 来自 EyePortal/.classpath:38、pm/.classpath:37
```

- 每行显示：名称 / 路径 / 来源（`.classpath:行号` 或「工作区兜底」）/ 产物目录数 / 是否比源码旧
- 「停用」开关（写进覆盖项，不改 `.classpath`）
- 「补一个目录」用于 `.classpath` 没声明的特例（EJB 生成目录等）
- 「检查类冲突」「按依赖顺序全部编译」两个动作按钮
- 解析失败时（引用的工程找不到目录）**红字标出来**，而不是静默跳过——本机 `newar` 的 `.project` 名是 `ar`，
  这类不一致必须有可见的兜底提示

### 3.9 范围取舍：关联工程的模块**不进**文件树

一期只做三件事——类路径、后台编译、启动落地。**不把关联工程的模块并进左侧文件树 / 模块树**。

理由：

1. 文件树现在受 `security::path` 的"只允许落在 `workspace_root` 之下"约束（`config.rs:23`）。多根化要动这个安全边界，是本方案里唯一真正危险的一处，值得单独立项评估，不要和类路径改造捆在一起。
2. 文件树多根还要处理：`module_of()` 的模块归属（`compile.rs:101-121` 按第一级目录判模块）、SVN 状态、搜索范围、记账。工作量至少翻一倍，而它对"能编过、能起动"没有帮助。
3. 用户当前的需求是"启动 A 要能用到 B 的类"，不是"在 A 的窗口里编辑 B 的代码"。B 的源码照样可以用 SVN 客户端 / 另一个窗口改，改完点「全部编译」即可。

如果后面确实要在同一窗口编辑两个工程，那是一个独立的功能（多根工作区），届时再谈 `security::path` 的改法。

## 4. D2：启动前的配置落地（已实证，批次 2）

### 4.1 目标

启动服务前，把参与工程的 `modules/<模块>/META-INF/**` 同步到 `<NCHOME>/modules/<模块>/META-INF/`，让 NC 的模块扫描能看到工程里改过的组件元数据。

NCC 的 yyconfig / hotwebs classes 分支按用户答复**不做**（团队无 NCC 前端二开，同 `NCForge-借鉴-…-20261031.md` 的 B7 决定）。

### 4.2 安全设计（这是往同事共用的安装目录写文件，必须收得很紧）

| 约束 | 做法 |
|------|------|
| 只写自己放过的东西 | 维护 `<config_dir>/nchome-deploy/<ncHome 标记>/manifest.json`：记录"哪个文件、什么 mtime/size、来自哪个工程" |
| 绝不删非我方文件 | 清理时只删 manifest 里登记过的路径；NCHOME 原有文件即使同名也不在我们的清理范围内 |
| 同名覆盖前先备份 | 首次要覆盖一个"NCHOME 原有"文件时，先复制到 `<config_dir>/nchome-deploy/backup/`，manifest 记 `overwritten_original: true` |
| 不碰目录结构 | 只做文件级的写（和 `mkdirs` 建缺失的 `<模块>/META-INF`），不移动、不重命名 NCHOME 里的任何东西 |
| 路径必须落在 NCHOME 内 | 目标路径 `canonicalize` 后必须仍在 NCHOME 下（复用 `security::path` 的既有守卫），防符号链接逃逸 |
| 默认开、可关 | 配置项 `deploy_on_start`（默认 true）+ 一次性的"本次不落地"选项 |
| 出错不阻断启动 | 落地失败只记日志与 warnings，服务照常起——先让人能干活 |

### 4.3 增量与幂等

沿用参考插件的思路（`:658` `isNoChange` 跳过），但判断条件要更严：

- 相等（size + mtime）→ 跳过
- 我方登记过且内容变了 → 覆盖 + 更新 manifest
- NCHOME 有、我方没登记过、内容相同 → 登记为我方管理（不覆盖，只接管记录）
- NCHOME 有、我方没登记过、内容不同 → 备份后覆盖（这是"工程里改过 upm"的正常路径）

### 4.4 落点

新建 `src-tauri/src/nchome_deploy.rs`（纯逻辑 + 单测，不含 tauri 类型），命令层 `commands/deploy_cmds.rs` 只做转发。启动流程在 `server_cmds.rs:215` 的 `server_start` 里、`middleware_spec` 之前插一步。

**不能塞进 `patch_build.rs`**：那是"出包"，这是"就地部署"，失败语义与安全边界完全不同（出包失败重来即可，落地失败可能污染同事的安装目录）。

### 4.5 三个必须想清楚的问题

**① 停止服务后还原吗？—— 不还原（跟参考插件一致），但给清理按钮**

| 方案 | 好处 | 坏处 |
|------|------|------|
| 停服即还原 | NCHOME 保持原样 | 服务异常退出就还原不了，状态不一致；下次启动又要写一遍；**服务停着时 NCHOME 缺 upm，用别的工具（如 Eclipse 直启）会起不来** |
| 不还原 + 可清理 | 简单、幂等、和参考插件行为一致；开发机上的 NCHOME 本就是沙箱 | NCHOME 里留有二开文件，同事在这个安装目录上跑标准产品会看到二开组件 |

选**不还原**。配套：manifest 驱动的一个「清理本工具放过的文件」按钮（只在工程页出现，明确写"会删掉 N 个文件，其中 M 个已备份"），以及首次启用时的确认弹框。

**② 多个工程共用一个 NCHOME 会互相覆盖**

这是 D1 场景的必然结果：A 与 B 都往 `NCHOME/modules/uapbd/META-INF/` 写，同名 upm 内容不同就互相踩。

约定：

- 落地集合 = **当前编译/运行组合的并集**（主工程 + 各 enabled 关联工程），不是"当前打开的那个工程"。这样和 §3.3 的 classpath 口径一致——类路径与配置来自同一个组合，不会出现"类来自 B、upm 来自 A"的错配。
- 同一路径在多工程里内容不同 → **按 classpath 顺序取第一个**，并在服务页显示冲突（哪个文件、被谁覆盖）。规则和同名 class 完全一样（§3.6），用户学一次就够。
- manifest 记录每个文件来自哪个工程 + 组合指纹；启动时发现"上次是另一个组合部署的"，在日志里明确写一行 `[nc-forge] 已切换部署组合：A+B → A`，不弹框（这是正常操作，不是错误）。

**③ 开发机上的 NCHOME 装过补丁后，就不再是"干净基座"**

这条是"现场 hyext 是散文件"直接带来的。装过补丁的 `D:/ncc/1909home` 里同时存在三份来源：

| 位置 | 来自 |
|---|---|
| `modules/<m>/hyext/classes` | 补丁（现场散文件） |
| `modules/<m>/META-INF/*.upm` | 补丁 + D2 刚落地的工程 upm |
| `modules/<m>/lib/*.jar` | 标准产品 |

于是本地启动跑出来的东西是**三者混合**，而用户以为自己在测"我改的代码"。典型误判：

- 补丁里有、工程里没编译的类 → 修好 D6 后会被加载（**这其实是好事**，等价于现场环境）；
- 补丁改过、工程里也改过同一个类 → 工程 `classes` 在 classpath 前段，工程赢（符合预期）；
- 补丁改过、工程**没改**这个类，但工程里存在同名源码（旧版）→ 编译过的话工程赢，**行为比现场旧**，
  而用户看不出来。

第三行是真正会误导人的一条。**不做自动裁决**（没法判断哪个"应该"赢），但要在服务页显示一行环境提示：

```
NCHOME 已装过补丁：hyext/classes <N> 个类、META-INF <M> 个 upm
本次启动：工程类路径优先，补丁仅补充工程没编译的类
```

（`<N>` / `<M>` 是运行时数出来的真实数量，不写死。本机现在是干净安装，`N=0`，所以这条提示
在没装过补丁的机器上不出现——出现即说明"你正在一台装过补丁的环境上开发"。）

数据来源是 D6 修好后本来就要枚举的目录，无额外扫描成本。这条不做"阻断"，只做"让人知道自己测的是什么"。
