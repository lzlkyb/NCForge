## 0. 一页结论

**问题**：看代码时跨模块跳转，每切一个模块就要等「智能代码准备」，单次 10~40s，
日常跨 10 个以上模块。

**根因（已定位，不是猜）**：不是索引慢，是**切模块 = 杀进程重启**。

1. `data_dir_for(.., module, ..)` 的 hash key 里含 `module` ⇒ 每个模块一个独立 jdt.ls 数据目录
2. 前端 `useLangWiring` 打开 `.java` 就按该文件所在模块调 `lang_start`
3. 影子工程只链当前模块（single），classpath 变了必须重新导入

**解法**：**一次 flat 导入 + 常驻不重启**。把「每个模块等一次」变成「一天等一次」。
这是唯一有效手段；升级 jdt.ls、换语言服务器都解决不了（见 §3）。

**总工期**：约 11.5 个工作日，分 6 个阶段，每个阶段独立可回滚。

**由此确定的四条硬约束**：

- **必须全量**：依赖闭包只有 1 个工程，覆盖不到模块 ⇒ flat 就是全工作区
- **冷启动每次都要付**：warm 无效 ⇒ 只能靠常驻摊薄，不能靠缓存
- **单实例边导边用不可能**：import 期间零响应 ⇒ 必须有快通道（双阶段）
- 🔴 **运行时 JDK 锁死 NC 自带**（2026-11-21 用户确认）：`<nc_home>/ufjdk/bin/java.exe`
  （1909home = 1.8.0_202），见 `lang_cmds.rs` 的 `launch()`。产品**永不要求用户另装 JDK**。
  任何「换引擎 / 升级 LS / 加大版本 JVM」的方案，只要把 JDK 版本要求转嫁到用户机器，
  一律不做 —— 与 §3「升级 jdt.ls」被否是同一个理由，别再绕回来。

## 2. 目标态

```
打开工作区
   │
   ├─ 立刻：后台生成 flat 影子工程（1 project + 53 源根 + 1162 jar）
   │        └─ prewarm，不阻塞 UI
   │
   ├─ 0~60s：Phase 1 快通道服务（声明索引 或 single 语义实例）
   │         → 跳转/引用/补全 可用（覆盖全部模块）
   │
   └─ flat ready 后：切 Phase 2（flat 语义实例）
             → 诊断/重构/重命名/调试 逐步接管
             → 之后切任何模块：**零等待、零重启**
```

关键指标：

| 指标 | 现状 | 目标 |
|---|---|---|
| 切模块等待 | **10~40s，每模块一次** | **0**（同一工作区整个会话一次都不重启） |
| 首次可跳转 | 10~40s | **< 60s** |
| 全天总等待 | 跨 10 模块 ≈ 100~400s，且反复 | **一次 3~6 分钟（后台）** |

## 3. 已否决的方案（别重复调研）

| 方案 | 判定 | 决定性证据 |
|---|---|---|
| **升级 jdt.ls 到 1.63** | ❌ | ① v1.31+ 要 JDK 21、main 要 **JDK 25**，我们只有 1.8；② 语法服务器在 main 分支仍是 `// do nothing at syntax server mode.`；③ 索引单线程（维护者原话 + 实测只用 5% CPU）；④ CHANGELOG 18 条 perf 全是 10% 级且过半是 Maven/Gradle 专属 |
| **jdt.ls 语法服务器**（0.57 就有） | ❌ | 源码级 `importProjects()` 空实现；实测 definition 300s 恒空 |
| **sharedIndexLocation 共享索引** | ❌ 不对症 | 只共享**库 jar** 索引；warm 实测已证明瓶颈不在库索引 |
| **整体换语言服务器** | ❌ 无候选 | 没有第二个 Java LS 同时给 跳转+补全+诊断+重构+DAP+扩展 bundle |
| **预建索引分发（S6）** | ❌ 失效 | warm 无效 ⇒ 分发索引不省时 |
| **「要更快就得让用户装新 JDK」** | ❌ 不成立 | 2026-11-21 实测：随包 ECJ 3.22 在 **1.8.0_202** 上做声明索引，7524 文件 **9.06s** + 589 jar **5.02s**。新 JDK 从来不是架构要求，只是 java-ls/Metals 自己运行时的要求（§4.1） |
| AppCDS / G1GC / 关 importer | ⚠️ 早已做到 | 我们走自制 classpath，不经 maven/gradle |

**保留的唯一外部参考**：`tsmaeder/java-ls` 的「context-free 声明索引」架构（trino 11044 文件
+ 979 jar = **25s**，indexer 可选 ecj）。**但仓库无 LICENSE ⇒ 只能借鉴架构，不能集成代码。**
`Metals v2` 原打算当对照验证工具，**已不需要**：自己用随包 ECJ 量出的数字更贴我们的工程（§4.1）。

## 4. 阶段计划（这就是最佳顺序）

依赖关系：

```
阶段1 URI多前缀 ──→ 阶段2 常驻 ──→ 阶段3 增量同步
                        │
                        └──→ 阶段4 首次体验（快通道 + 双阶段）
                                    │
                                    └──→ 阶段5 回归与发版

阶段0 基线固化（可与阶段1 并行）
```

**为什么这个顺序**：

- 阶段 1 必须在常驻前 —— flat 之后一个实例覆盖 N 个模块，URI 映射还是单前缀就会跳错文件
- 阶段 2 收益最大且不引任何新依赖 ⇒ 优先做
- 阶段 3 在常驻后才有意义（实例活着，增量推送才有人收）
- 阶段 4 依赖阶段 2（必须先有 Phase 2 的 flat 实例）
- 阶段 5 收口

### 阶段 1：URI 多前缀映射（1 天）· ✅ 通道已落地

> **2026-11-21 完成**：`lang.rs` 新增 `PathPair` / `swap_prefix_multi` / `find_root`
> / `swap_path_fields_multi`；`LangSession` 由「单对前缀」改为 `roots: Vec<(真实, 影子)>`
> + `with_roots()`；`Handler` 的诊断映射同步改为多前缀。`cargo clippy --all-targets` 干净，
> `cargo test --lib lang::` 15 过（含 4 条新单测：多模块往返、最长前缀、`gl`/`gl2` 不串台、
> `find_root` 拒绝外部路径）。
>
> **2026-11-21 补**：构造点已随阶段 2 翻 flat 换成全模块清单（`lang_cmds.rs` 按
> `project.modules` 逐模块建 `PathPair`，flat 时覆盖全部源根）。「真实跨模块跳转」
> 验收已由阶段 2 的 `s2_生产flat_单实例跨模块跳转` 覆盖（aim → uapbd）。

**改造前的问题**：`Handler` 与 `LangSession` 都只有一对 `real_prefix` / `shadow_prefix`
（按单模块构造）。flat 后服务器返回的 URI 可能来自 53 个 junction 中的任意一个，
单前缀匹配会让其他模块的路径原样漏过去 —— 前端拿影子路径找 model 全部落空。

**做什么**：

1. `LangSession` 的路径映射从「单前缀对」改为 `Vec<(real: PathBuf, shadow: PathBuf)>`
2. 查表规则：**最长前缀优先**（模块名可能是前缀关系，如 `gl` / `gl2`）
3. 反向映射（客户端 → 服务器）同样走这张表
4. `from_server_paths` 现有语义不变：只替换 `path` 字段，含 `..` 的不替换

**验收**：

- 单测：53 条前缀 + 嵌套前缀（`gl` / `gl2`）+ 同名前缀目录（`gl` vs `gl-extra`）全部命中正确
- 现有 single 模式零回归（`cargo test --lib` 全绿）
- 真实跳转：从 `ic` 里的文件跳到 `gl` 里的定义，URI 往返一致

**回滚**：纯内部重构，`git revert` 即可。

### 阶段 2：常驻（3 天）· ✅ 已落地

**问题**：两个开关都指向「按模块重启」：

- `data_dir_for(.., module, ..)`：key 含 `module` ⇒ 每模块一个数据目录
- 前端 `useLangWiring`：打开 `.java` 才 `ensureLang(activePath)`

**落地情况**（2026-11-21）：

| 计划项 | 落点 |
|---|---|
| `data_dir` 去模块化 | `DATA_LAYOUT` 1→2；`data_dir_for(base, root, nc_home, ls_dir, shadow)` —— 模块**不在签名里**（编译期保证）；目录名用工作区末段（`newar-<指纹>`） |
| 生产启用 flat | `lang_cmds::launch` 传 `extra_modules: (Flat).then_some(workspace_modules(root))`；清单每次现扫（模块会增删） |
| 打开工作区即 prewarm | 新命令 `lang_prepare`（`Result<(), AppError>`）；`useLangWiring` 订阅 `useWorkspaceRoot()`，root 变了就 fire-and-forget 一次 |
| 切模块复用 | `LangRun.workspace` + `start_blocking` 判「同工作区 + 状态健康 ⇒ 只改 `status.module` 标签」；拉起**开始时**就登记 workspace，否则冷导期间点别的模块会反复杀掉重启 |
| 开关 | `AppConfig.lang_shadow_mode: ShadowMode`（`"flat"`/`"single"`），走 `lang_config_set`；**参与 `data_dir` 指纹**（形态变了 jdt.ls 会按旧 `.classpath` 缓存工程结构） |

**连带改动（不改就会静默失效）**：

- `Handler::on_notification` 的 `language/status` 过滤从「模块名相同」改成「**代数相同**」。flat 下切模块只换标签、进程不重启，按模块名比会把首次导入剩下的通知全丢掉 ⇒ 状态栏永远停在「正在建立索引」。
- `ts-mirror` 新增**枚举支持**（生成字面量联合），否则 `ShadowMode` 过不了桥；`bindings.check.ts` 的 `keyof` 断言要求手写类型同步。

   - `single` 时行为与今天完全一致（`extra_modules: None` + 按模块 data_dir）

**必须同时做的两件事**（否则第一次体验倒退）：

- **进度可见**：冷启动 3~6 分钟内，状态栏必须有「准备中 3/4：导入 53 个模块…」，
  且**不再是阻塞式**——用户可以继续看文件（只是没有智能提示）
- **不阻塞打开文件**：prewarm 期间打开 `.java`，不得卡住 UI，不得弹 modal

**验收**：

- 同一工作区打开 10 个不同模块的 `.java`：`jdtls-stderr.log` 只有一份，
  进程启动次数 = **1**；`lang_start` 只被调用 **1 次**
- 第二次切回已打开过的模块：**0 等待**
- 关闭再打开 NCForge（同工作区）：首次仍要等（warm 无效，已知），但只等一次
- 开关切回 `single`：行为与今天完全一致

**验收结果**（2026-11-21，`tests/shadow_scale_live.rs::s2_生产flat_单实例跨模块跳转`，**通过**）：

| 项 | 实测 |
|---|---|
| 链入模块 / 源文件 / jar | 6 / 2990 / 797 |
| 建场（含 `select_jars`） | 63.1s |
| `initialize` 返回 | 15.6s |
| `ServiceReady` | **99.3s** |
| 跨模块 `definition` | **3.06s → `SendMessage.java:8`**（`aim` → `uapbd`，正确） |

> 6 个模块 99.3s 就绪 —— 比 single 单模块的 46s 只多一倍，覆盖面从 1 个模块变成 6 个。
> 全量 63 模块的 154~355s 是 S0 实测值，两者不矛盾（文件数与 jar 数都差一个量级）。
> 这个测试同时钉住两条红线：清单里每个模块的 junction 都在，且 `.classpath` 里
> **每条源根的 `output` 都以 `shadow-bin/` 开头**（照抄官方的 `<模块>/classes`
> 会经 junction 把 class 写进用户工作区）。
>
> 调试这条测试踩了两个坑，都是**测试自己**的错、不是产品缺陷，记下来免得重犯：
> 1. URI 拼错：`strip_prefix(&src_mod)`（相对路径）永远失败，回退成绝对路径后
>    `Path::join` 直接整个替换 ⇒ URI 指向**真实文件**，`definition` 恒空。
> 2. 期望值取错：拿了**引用方**的文件名当跳转目标。目标应该是 `import` 里那个类
>    所在的文件 —— 首轮就是这么「失败」的，实际配置完全正确。


**风险与对策**：

| 风险 | 对策 |
|---|---|
| 首次 3~6 分钟，用户以为卡死 | 进度条 + 文案「首次打开需要 3~6 分钟，之后切模块零等待」 |
| flat 实例内存更高 | 实测 cold 峰值 973MB / warm 296MB，`-Xmx2048m` 够用；监控 OOM 自动降级 single |
| 某个模块源码有语法错误导致整工程 build 报错 | 已验证：ECJ 报错不影响其他文件的跳转，只需确认状态栏不把「有编译错误」当失败 |

**回滚**：`lang.shadowMode = single`，立即回到今天的行为，无需回滚代码。

### 阶段 3：增量同步（1.5 天）· ✅ 已落地

**问题（已实测）**：junction 源根**不穿透**文件变化 —— 普通目录能自动感知，
junction 不能。S0 探针证明：显式推 `workspace/didChangeWatchedFiles`（**junction 侧 URI**）有效。

**落地情况**（2026-11-21）：

| 通道 | 落点 | 触发 |
|---|---|---|
| 本应用保存 | `lib/lang.ts::notifyLangSaved` ← `fileSave::saveOne` | 写盘成功后 fire-and-forget，**不 await**（保存已经成功，通知慢一拍不该让它失败） |
| 外部改动 | `lang_cmds::notify_external_changes` ← `workspace_cmds::restart_watcher` 的 `fs-changed` 回调 | 复用**已有**的 `watcher`（`notify` crate，350ms 合并）；只在 `batch.java` 非空时推 |
| 节流 | watcher 的 `DEBOUNCE`（350ms）+ 批次去重 | 不需要第二层去抖 |

**为什么不用另起文件监听**：`watcher.rs` 已经在逐条看工作区每个变化（文件树 / 审查 /
SVN 脏集都靠它），`WatchBatch.java` 就是「外部改动的 `.java` 绝对路径」清单。
再开一条 notify 监听纯属浪费。

**URI 从哪来**：`session.shadow_uri_of(real)` —— 服务器只认影子路径，
且 flat 下它会按最长前缀落到正确的模块。变更类型统一用 `2`（Changed）：
这里只知道「变了」，新建 / 删除在 jdt.ls 侧都会以「读不到」收场，不会误判成成功。

**验收**（待实机）：

- 用编辑器外部改一个 `.java` 的方法名 → **3s 内**在另一个模块里跳转能到新位置
- SVN update 改动 10 个文件 → 只发 1 批通知，跳转全部更新
- 不改文件时**零额外通知**（避免触发无谓重建）

**回滚**：关掉通知即可（服务器仍能用，只是外部改动后要重开文件）。

7419 个源码文件只命中 **3 个** jar，且因为没有断言，只表现为「精选没生效」。
现在日志会打 `精选 N/M`，`N == M` 就是要查这件事。

**索引成功后才写**（顺序反过来会让「建索引失败」被判成「已是最新」）。

**该结论已推翻**：实测一遍走盘 3.5s / 7419 文件，远比重建（30s+）便宜，

#### 4.2.2 成员级跳转（2026-11-21 落地）

**为什么单独立一节**：类型级跳转只回答「这个类在哪」，而 NC 二开时用户点下去的多数是
**成员** —— `vo.getCode()`、`this.billType`、局部变量 `vo`。这也是与本机 Eclipse 差距
最直观的一条（Eclipse 的窗口期是全套语义）。

**索引格式 v3**：每个成员多写 `i32` 声明行（源码侧）。jar 侧成员行号恒 0 ——
字节码里的 `LineNumberTable` 指向原始 `.java`，而反编译视图（CFR）的行号跟它没关系。

| 手段 | 代价 | 换来 |
|---|---|---|
| 源码侧成员 + 声明行（约 20 万条） | 索引 20.5 → **24.26 MB** | 窗口期能跳方法/字段 |
| `--no-jar-members`（jar 侧 145 万条不写） | jar 类跳不到成员（本来也不行） | 省 ~100 MB 与 jar 阶段主要 CPU |

**分层与「只有非空才认领」这条铁律**（`src/fast_member.rs`）：

```
fast_member::resolve  ──Some(非空)──▶  用它（成员级）
        │ None（没答上）
        ▼
fast_definition::resolve ──▶ 类型级（import / 同包 / 通配 / 全库兜底）
```

🔴 第一版不是这样：限定访问（`x.`）一律认领，答不上也返回 `Some(空)`，结果
**`import com.x.y.Itf;` 里的 `Itf` 被当成「`y.Itf` 成员访问」而彻底不回退** ——
类型级本来一猜就中的全限定名引用反而跳不了。已用回归测试钉住
（`import里的全限定名交回类型级`）。代价是成员没命中时多跑一次类型级（微秒级），
换的是「漏跳」变成「多查一次」。

**三层判据**（从确定到猜测）：

1. `接收者.成员`，接收者是**类型名** → import/同包/通配/兜底消歧出全限定名，查其成员
2. `变量.成员` → 在当前方法里找 `Type 变量` 的声明（`=` / `;` / `,` / `)` / `:` 收尾，
   前面是类型词），得到类型后再查。支持泛型 `List<Foo>`、数组 `Foo[]`、限定名 `java.util.List`、
   参数、`for (X v : …)`、`catch`；且**不跨方法**（遇到缩进 ≤ 4 的 `}` 就停）
3. 裸词 → 先找当前方法的局部变量/参数声明（跳本文件行），再找当前类型的成员
   （`this.x` 走这条；嵌套类按 `Outer$Inner` 拼）

**刻意不做**（写在这里免得下次有人当成 bug 修）：

- **父类/接口的成员**：索引没存 `extends`，查不到就交回类型级。猜一个父类去跳，
  落到错地方的代价比跳不到大得多。要做得先给 `types.idx` 加父类字段 + 沿链查询。
- **泛型实参推断**：`List<Foo> xs; xs.get(0)` 里 `xs` 的类型是 `List`，`get` 不在 `List` 里。
- **jar 侧成员**：行号恒 0，`Decl::method_line` 直接 `filter(|l| *l > 0)` 挡掉。

**行号校正**：成员行号与会话内的源码改动同理会漂，`decl_drift::fixed_member_line` 按
「声明形态」重新定位（方法 = `[修饰符] 返回类型 name(`，排除 `vo.name(` / `return name(`；
字段 = `Type name` 后跟 `=` / `;`）。找不到就原样返回，不丢目标。

**实测（真实工作区 `C:\work\aier\newar`）**：构建 31.8~42.9s（热/冷盘）/ **24.26 MB** /
298357 类型（源码 7790 + jar 290567）；复用 5.5~6.4s（含一遍 7419 文件走盘）。
端到端用例 `真实索引能跳到源码里的成员`：`QueryJcOutAndYsInDataBO.java` 的
`queryJCDatasForHH` → 同文件第 1118 行。单测 16 条。

**第 2 步（`INameEnvironment` 适配）的替代结论**：原计划让 ECJ 查类型时从内存索引读，
用来提升**同名类消歧精度**。成员级跳转落地后发现，更划算的顺序是先用启发式拿到「80% 正确」，
`INameEnvironment` 留给「父类成员 + 精确接收者类型」一起做（只做一半会有一半跳错候选）。

**「binding 精度对齐 Eclipse」分三层看（2026-11-21 用户追问后补，别再当一件事）**：

| 层 | 能否对齐 | 手段 | 状态 |
|---|---|---|---|
| ready 后的光标级精度（definition/hover/继承成员/精确接收者） | **已对齐** | jdt.ls 就是 JDT 编译内核（`jdtls/plugins` 里的 `jdt.core_3.22.0`），与 Eclipse 4.11 同源代码线；classpath 由我们生成（flat + jar 展开）， fidelity 取决于 classpath 正确性 | ✅ 现有链路 |
| 窗口期（3~6 分钟）的光标级精度 | **能，未做** | 持久 ECJ + `ASTParser.setResolveBindings(true)` + `INameEnvironment`：源码类型问索引（java-ls 巧思）、jar 类型问盘。按查询懒 resolve（这正是 jdt.ls 慢的原因——它全量建 JavaModel，我们不必），热查询百毫秒级 | 即本第 2 步，1.5 天 |
| 工作区级引用索引（Ctrl+Shift+G 的全量结果） | **对齐不了（除非学 Eclipse 存 1GB 倒排）** | 真 binding + 全工作区 reconcile 的产物；jdt.ls ready 后有，窗口期没有 | ❌ 已判定不做（§4.4 第 2 件） |

⇒ 结论：**binding 精度没有「把索引改聪明」这条路**（索引是名字→位置的表，近似不了类型系统），
唯一正道是跑编译内核——问题只是「常驻一个按需 resolve 的 ECJ」还是「等 jdt.ls 那个」。
现状选后者；重开条件：实机清单跑完后，窗口期内「Ctrl+点击跳到类型/没反应」的抱怨集中出现
（尤其继承成员场景），或有人愿意用常驻 JVM（+300~500MB）换窗口期精度。

落地件：
- `src-tauri/ecj-bridge/NcIndexer.java` —— 独立 main，**并入 `ncecj.jar`**（复用 Java 8 编译约束 + 契约测试，不新造打包链路）
- `src-tauri/src/decl_index.rs` —— 读取器 + 5 条单测（手写字节钉格式、魔数/版本/截断、前缀枚举不串名）
- `src-tauri/tests/decl_index_live.rs` —— 端到端（`#[ignore]`，需要真实生成的 idx）
- `scripts/ecj-bridge-contract.test.mjs` 第 ⑦ 条 —— 最小工作区跑一遍，防「改了 Java 忘打包」

**第 1 步踩到的四个坑（都已固化在代码注释里）**：

1. **`getProblems()` 占 parse 的 1/3**：JDT 在 recovery 时生成 7.8 万条假错，遍历它们纯浪费。
   索引不要 problems ⇒ 15.1s 降到 8.6s（默认关，`--stats` 才开）。
2. **`File.listFiles` 比 `Files.walkFileTree` 慢一倍**（5.6s → 12.6s，Windows）：
   反直觉，但实测如此，别「优化」它。
3. **路径表必须按下标顺序写**：`paths` 是 `HashMap`，`entrySet()` 顺序 ≠ 分配的下标顺序，
   直接遍历写会让所有记录指向错的路径。且路径表要放在**记录之前**，读取端才能一遍读完。
4. **standalone `ecj-3.17.jar` 没有 `org.eclipse.core.runtime`**：`ASTParser.createAST(IProgressMonitor)`
   的签名依赖它，索引器的编译与运行 classpath 都得带 `jdtls/plugins/*`。

#### 4.3 编排：**不需要第二进程**（2026-11-21 更正）

原规划是「Phase 1 起一个独立 JVM 服务 + Phase 2 起 flat jdt.ls，两进程并存约 1.7GB」。
**实际不需要第二进程** —— 声明索引是 **Rust 进程内的数据**（29.8 万类型，`load_meta` 1.1s，
常驻约 90MB），查询是本地二分（微秒级）。真正起进程的只有「一次性构建」那 21 秒，构建完就退出。

于是编排退化成三件事，**没有双实例、没有切换、没有 `lang.dualPhase` 开关**：

- **打开工作区就预热**：`lang_prepare` 里先 kick 索引（~21s），再起 jdt.ls（冷导 99~355s）。
  索引先能用 —— 用户不必等到第一次 Ctrl+点击才触发构建
- 构建期间查询返回空 → 前端退回内容搜索，**用户无感**；jdt.ls ready 后请求走原路径，
  **但空结果会回退到索引**（NC 工程里「类不在 classpath」很常见，纯 jdt.ls 会给「什么都没发生」）
- 索引持久在 `{config_dir}/decl-index/<root 哈希>/types.idx`，跨重启复用

**三条保证「绝不跳到错位置」**（比「跳得快」更重要）：

1. **过期判据**：头部 `builtAtMs`（格式 v3）+ jar 清单 + `fast_decl::scan_sources`
   （源码 mtime 与文件数）。早先只比 jar 清单 ⇒ 昨天的索引今天照用 ⇒ **跳到昨天的行号**
2. **原子替换**：写 `types.idx.tmp` 再 rename，`jars.done` 最后写。重建失败不会毁掉还能用的旧索引
3. **行号自愈**：`fast_decl::fixed_line` 跳转前用目标文件核对/重找 `class X` 那一行。
   会话内不做重扫（一次走盘 3.7s），所以以磁盘为准

**实测（真实工作区 `C:\work\aier\newar`，2026-11-21）**：

| 项 | 数值 |
|---|---|
| 建索引 | **31.8s（热盘）~42.9s（冷盘）** → **24.26 MB** / 298357 类型（jar 290567 / 源码 7790，**含源码侧成员**；纯类型口径 21.4s / 20.5MB） |
| 复用 | **5.5~6.4s**（含一遍 7419 文件走盘；纯类型口径 3.85s） |
| 加载 | `load_meta` **2.1~3.1s**（只跳 jar 侧成员；纯类型口径 1.1s） |
| 失败退避 | 30s 起翻倍，封顶 10 分钟 |

**已知边界（设计内，不是 bug）**：

- ~~只到类型，不含成员位置（`--no-members`）~~ **已补齐（2026-11-21 三次收口，见 §4.2.2）**：
  源码侧成员带声明行，窗口期 `vo.getCode()` / `this.x` / 局部变量都能跳到声明行。
  **剩下的成员边界**：父类/接口成员（索引没存 `extends`）、泛型实参推断、jar 侧成员（行号恒 0）
- jar 精选按 import 收集包（1329/4367）⇒ 纯全限定名引用（代码里直接写 `a.b.C`、没有 import）的
  jar 可能不进索引 ⇒ 该目标退回内容搜索
- `src/test` 不进索引（与 `compile.rs::SRC_DIRS` 同源）⇒ 从测试类跳出去没问题，跳进测试类要走内容搜索
- 会话内改动不触发重扫 ⇒ 靠行号自愈兜住；`builtAt` 判据在下次启动时才生效
- 索引格式 **v3**（v2 只有类型级；v3 每条成员多写 `i32` 声明行，头部末 8B 仍是 `builtAtMs`）。
  v1/v2 旧文件在读头部时报版本不一致 ⇒
  `fresh` 判不可用 ⇒ **自动重建一次**，不需要用户手工删文件

**验收（已被端到端测试覆盖）**：

- ✅ 跨包 + 跨源根跳转正确（`tests/decl_index_live.rs`「真实索引能答一次跳转」）
- ✅ 跳 jar 内类并产出 `jdt://`（同上「真实索引能跳到_jar_里的类」）
- ✅ 索引不存在时不阻塞、不报错（回空数组）
- ✅ 改/增/删源文件都会重建、未改则复用（同上「源码变更后索引重建_未变更则复用」）
- ⏳ 真实界面里 `!langReady()` 期间 Ctrl+点击的手感 —— 需实机确认（阶段 5 清单）

**回滚**：删掉 `lightDefinition` 里那段 `invoke("lang_fast_definition")` 即可，
其余行为与改动前完全一致（它本来就是内容搜索兜底）。

#### 4.4 与本地 Eclipse 4.11 的对照（2026-11-21 实测）

同一台机器、同一个工作区（`C:\work\aier`，Eclipse 索引在
`.metadata\.plugins\org.eclipse.jdt.core`）：

| 维度 | Eclipse 4.11（实测） | 我们（Phase 1） | 判定 |
|---|---|---|---|
| 索引对象 | 全部 classpath：223 源根 + **4858 个外部 jar** | 7419 源码 + **精选 1329 / 4367 jar** | 差一档 |

`首次可跳转` 补到 **类型 + 源码侧成员**，而 Eclipse 在窗口期是全套语义
（jar 内成员、继承来的方法、精确 binding）。

**仍然差的三件事（按性价比排）**：

1. **父类/接口成员 + 精确接收者类型**（P1）：`vo.getCode()` 里 `getCode` 定义在父类时
   现在跳不到（索引没存 `extends`）。要做就一起做：给 `types.idx` 加父类字段 + 沿链查询 +
   必要时上 4.2.1 第 2 步的 `INameEnvironment`。只做一半会有一半跳到错候选。
2. **引用搜索 / Open Type 走索引**（P2）：Eclipse 的 `Ctrl+Shift+G`、`Ctrl+Shift+T` 都吃这张表；
   我们现在只有跳转，引用要等 jdt.ls。索引里没有「引用位置」，得另存一份倒排，成本明显高于收益。
3. **`src/test` 进索引**（P2，几分钟）：与 `compile.rs::SRC_DIRS` 同源，改了会动所有既有数字，
   收益只是「跳进测试类」这一种场景。
