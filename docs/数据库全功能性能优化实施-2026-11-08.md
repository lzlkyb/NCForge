# 数据库全功能性能优化实施

> **⚠️ 事后修正（同日）**：本轮把 Rust 查询的 `prefetch_rows` / `fetch_array_size`
> 提到 128（目录查询 512）的改动**已全部回退**，下表「普通查询取数」与
> 「表清单 / 中文名」两行不再是当前实现。原因见文末[「事后修正：TTC 流错位」](#事后修正ttc-流错位)。
> 其余改动（并行预热、零统计探测、**连接探测改只读查询**、元数据合并、Worker 复用等）保持不变。

本轮检查整个数据库模块，目标是降低客户端可控制的建连、排队、往返、重复计算与资源开销。所有真实业务 SQL、事务和账号权限判断保持原有约束。不将“优化到极致”描述为未经实测的绝对时延保证。

## 本轮实际修改

| 路径 | 原开销 | 修改 |
|---|---|---|
| 首次 SQL / 断开后再连接 | 主会话登录完成后，再登录 SQL 独立会话 | 仅有活动 SQL 标签且尚无槽时，请求后端并行准备；两条会话仍独立。结果携带预热槽，首查不重新申请 |
| 预热异常路径 | 标签变化或主连接失败可能遗留额外会话 | 无法接收的预热槽释放；主连接失败时后端回收已建立的预热槽；不创建无界连接池 |
| 连接身份与版本 | 要等待额外版本查询，Schema 可能等元数据返回才校准 | Rust 优先使用握手里的服务端版本；连接响应直接带回实际 Schema 与警告，首查使用真实上下文 |
| 普通查询取数 | Rust 默认首包 2 行、后续 100 行；JDBC 依赖驱动默认值 | ~~正常查询按请求行数设置首包／批量，上限 128 行，并保留一行前瞻~~ → **Rust 侧已回退，见「事后修正」**；JDBC 侧有界取数保留 |
| 表清单 / 中文名 | 窄列目录查询仍以小批次取数 | ~~两个引擎对表目录及中文名设定 512 行批量~~ → **Rust 侧已回退，见「事后修正」**；只影响读取批次，不截断目录内容 |
| 执行统计 | 每条语句执行前后查询统计视图，增加两次往返；无权限时仍重复探测 | 普通执行默认零统计探测；需要时从“工具 → 执行当前语句并采集统计”单次开启。不可用结果按会话记忆，失败后跳过后快照，重连后恢复尝试；绑定协议的参数布局保持不变 |
| 连接探测 | Rust thin 驱动的 ping 在部分服务端可能遇到无法解析的 TTC 消息，导致 SQL 未发送 | 采用轻量只读查询检查连接，保留原有会话安全判断与结果游标 |
| 元数据加载 | 并发重复请求，四项全部结束才显示表清单 | 同一上下文合并请求，各项返回独立发布；断开与新一轮加载使旧响应失效 |
| 其他对象 | 未展开时也加载包、过程、序列等清单 | 展开才请求，关闭再打开复用，切换 Schema 重新读取 |
| 本地缓存 | 异步命令线程同步读盘、解析并组装大 JSON | 缓存状态、缓存表名和补全缓存转到阻塞工作线程执行 |
| 连续筛选 / 排序 | 每次重建 Worker、重新分批复制全部结果，固定等待 120ms | 复用已完成计算的同一数据 Worker，再次操作不复制数据、不额外防抖；正在计算的旧请求仍直接终止，闲置 5 秒自动释放 |
| 宽表滚动 | 每个可见单元格线性查找列位置 | 每帧建立列索引，单元格查找改为常数时间，冻结与虚拟列逻辑保留 |
| 耗时反馈 | 只报告后端 SQL 用时，可能掩盖申请会话及 IPC 等待 | 单条语句客户端调用用时明显高于 SQL 用时时，在现有输出日志补充用时；连接确认前的耗时由连接任务单独记录 |

对于普通查询，128 行上限控制驱动缓冲增长；512 行仅用于列数很少的目录查询。不会通过一次读取全部业务数据来换取速度。主会话与 SQL 会话并行是缩短两次初始化的串行路径，并不是只使用一条物理连接。

## 事后修正：TTC 流错位

当天晚些时候用户报告：「第一次查询正常，第二次执行**一模一样**的 SQL 就报
`internal error: unknown TTC message type 32 at packet 1, offset 11`，SQL 是
`select * from bd_material`」。真库（`10.200.22.144:1521/aier260824`，19.3.0.0.0）
只读探针复现如下（每轮独立连接）：

| 场景 | 修正前 | 回退后 |
|---|---|---|
| 小表（5 行）→ probe → 同样 SQL | ✅ | ✅ |
| 大表取 500 行（游标未取完）→ probe → 同样 SQL | ❌ `type 0 @ offset 2482` | ✅ |
| 大表 → **不同** SQL | ✅ | ✅ |
| 大表 → `more` 再取 10000 行（仍有更多）→ 同样 SQL | ❌ `type 0 @ offset 2482` | ✅ |
| 连接错位后继续任意语句 | ❌ `type 50` / `type 1` / `type 32` | — |

`32 / 0 / 50 / 1` 是同一个现象：**流错位后把残留字节当 TTC 消息头读**，所以数字随机；
`vendor/oracledb/src/constants.rs` 里根本没有 32 号消息。一旦发生，连接永久不可用。

### 根因

`fe83580` 把 `run_with` 从驱动默认的 `conn.query(sql, params)`
（`prefetch_rows=2` / `fetch_array_size=100`）改成按请求行数设置、上限 128 的
`prefetch_rows` + `fetch_array_size`。驱动把执行过的 SQL 放进语句缓存，第二次执行
**同一条** SQL 时走 `TTC_RPC_REEXECUTE_AND_FETCH`（`messages/execute.rs::write_reexecute`
里 `num_iters = prefetch_rows()`）。此时上一条的分页游标还有大量行未取，服务端预取的
行包与重执行响应交错，驱动解析失败。换一条 SQL 不命中缓存重执行路径，所以反而正常——
这也是它很像「偶发网络问题」的原因。小结果集一次就发完，同样测不出来；
上述验收记录里那条「开启分页游标后连续三次探测」用的是 5 行小表，恰好绕开了触发条件。

驱动侧 `Statement::drop → return_statement` 只把语句放回缓存，不会排空服务端剩余行包，
所以产品代码不能靠「丢掉 Cursor」来收尾。

### 修正

- `db_rust.rs` 三处自定义取数批量（`run_with`、`tables`、`nc_names`）回退到
  `conn.query(...)`，并在 `run_with` 留下醒目的「别再调大 prefetch」注释。
  少几次往返换来正确性，不值得赌 vendor 的重执行路径。
- `db_engine.rs::connection_lost` 把 `unknown ttc message type` 识别为连接丢失：
  这种错误是永久性的，界面不能再复用坏连接，要按既有会话安全判断走重连/提示。
- 新增真库回归 `tests/db_rust_live.rs::same_sql_rerun_with_unfinished_cursor_keeps_stream_clean`
  （`#[ignore]`，需真库）：大表取 500 行留游标，同一 SQL 连跑三次 + 换一条 SQL。
- 新增单测 `db_engine.rs::unknown_ttc_message_type_is_connection_lost`。

**没有改动** `probe` 的只读查询实现、`db_version` 用握手版本、零统计探测等本轮其它优化：
探针证明 probe 在游标开着时连续两次都正常，不是触发条件。
