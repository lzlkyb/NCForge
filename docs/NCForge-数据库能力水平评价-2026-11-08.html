NCForge 数据库模块水平评价

评价对象：v0.2.0 数据库工作台（Oracle 单体）。参照：PL/SQL Developer 17、DataGrip 2026、DBeaver 25、Navicat 18 for Oracle、dbForge Studio for Oracle、Oracle SQL Developer。
评价日期 2026-11-08 代码基线 约 3 万行（前端 14.3k / Rust 13.7k / Java 桥 2.3k） 测试 前端 68 文件 / Rust 105 单测 方法 源码核对 + 既有审查记录 + 公开文档比对
8.3作为 NC 专用工作台（10 分制）
6.0作为通用 Oracle 客户端
5 / 10对标行业头部的能力覆盖项
7 项对手普遍不具备的独占能力

01一句话结论

它不是一个通用数据库客户端，而是一台「NC 现场作业机」。 在 Oracle 单库的日常读写、结果阅读、事务安全和 NC 语义理解上，已经达到或超过 PL/SQL Developer 的日常使用面； 但在通用客户端的三大标配（多数据库、PL/SQL 调试、结构与数据同步）上仍是空白。 判断它好不好，取决于你拿它跟谁比——拿它替 PL/SQL Developer 做 NC 开发，它是升级；拿它替 DBeaver 做通用取数，它是降级。

这个定位不是缺陷，是取舍。真正需要警惕的不是「少功能」，而是「功能多但数据正确性还没沉淀到行业老工具的确定性水平」——v0.2.0 一轮审查就暴露出 8 个 P0 级数据正确性问题（导出截断、RAW 变 null、事务漏计等），全部集中在「预览通道被当成全量通道」这一条结构性设计上。

03逐维评分与理由

维度得分判断依据（源码核对）
执行与事务9.0
事务条按「会话 × 标签」建模，`TxBar` 常驻显示未提交语句数；只读连接是连接级而非标签级；`fallback-tx` 在兜底会话有写入时强制回滚而不是静默提交；生产库写操作有环境标记 + 二次确认 + 按连接记忆的免打扰窗口。这套东西比 DBeaver/Navicat 的「事务模式下拉框」细一档，是行业里少见的「不让你手滑」设计。
结果集阅读8.5
虚拟滚动 + 双层表头（技术字段名 / NC 中文名 ?? 数据类型）+ canvas 精确列宽（扣 52px 表头 chrome）+ CLOB 8K 预览与「加载完整值」+ 二次编码自动解码（hex/base64→UTF-8/GBK）+ 16MB 结果内存预算 + 隐式结果集多 tab。单看「读数据」这一件事，体验在 PL/SQL Developer 之上，接近 TablePlus 的手感。
连接与环境管理8.5
从 NC `prop.xml` 直接导入连接并解出加密口令（对手全无）；口令走 DPAPI / macOS 钥匙串；只读连接、默认 schema、环境标签（测试/生产）、连接排序、运行时切换 schema 会同步到所有槽与兜底会话。缺的是连接分组、颜色、跨环境配置同步。
诊断与对比8.5
执行计划树 + 成本条 +「保存为对照 / 与上次对比」直接给「加索引前后」的结论；结果 A/B 比对按复合键对齐、区分 NULL 键与重复键；按值反查全库（找这个单据号落在哪张表）；会话与锁面板。对比能力密度超过 Navicat，接近 DataGrip。
对象与元数据7.5
表/视图/过程/序列按需展开，结构/索引/DDL 子页，对象搜索 + 收藏 + 中文名 + NC 类引用（非外键的元数据引用）。缺 ER 图、权限管理、依赖树、对象 DDL 差异。
导入导出7.5
导出 10 种格式（TSV/CSV/XLSX/JSON/JSONL/HTML/Markdown/INSERT/WHERE/UPDATE + NC INSERT），原生流式写 XLSX、后台任务 + 进度 + 停止 + 原子替换 + 部分结果改名。扣分在导入只有 CSV/TSV（无 XLSX/JSON/SQL 文件导入），以及 CLOB 全量导出仍未打通（8K 截断，只做到「明确告警」）。
SQL 编辑7.0
补全带中文名与主键标记、Ctrl+点击表名开 DDL 页（对标 PL/SQL Developer 的跳转）、格式化、按光标/选区精确执行并显示行范围与语句数、PL/SQL 块与 `q'[…]'` 的语句分割正确。缺函数签名帮助、JOIN 条件推导、代码检查/重构、SQL 方言级 lint。
工程质量7.5
前端 68 个测试文件 / Rust 105 个单测 / 231 条命令契约检查 / 五路并行静态审查 + 主审逐条回源码核对行号。这套自审强度超过大多数商业小工具。但 P0 缺陷密度说明「正确性沉淀」还在一轮轮补课（见第 6 节）。
生态与扩展3.5
只有 Oracle，无 SSH 隧道（已论证否决）、无插件体系、无 AI、无云同步、无跨库。这三项是被对手拉开代差的地方。

加权口径：通用 Oracle 客户端（生态 25% / 编辑 15% / 诊断 15% / 导入导出 15% / 数据编辑 15% / 其他 15%）≈ 6.0；NC 开发工作台（事务 20% / 结果 20% / 连接 15% / 诊断 15% / 元数据 15% / 导入导出 15%）≈ 8.3。

04真实优势：别人做不到的

这几条不是「做得更好」，是「别人没有」。护城河在 NC 语义，不在通用数据库能力。

优势为什么对手做不到证据
prop.xml 一键接账套要读 NC 私有的加密格式并解口令，还得跟本地 JVM 配合；通用客户端只能让用户手填 IP/端口/账号/口令。ConnImportPanes / PropFileImportPane / prop_password_ready
NC 中文字段语义表头第二行就是中文名、补全项带中文描述、数据字典三入口。这要求把 md_* 元数据表当一等公民，通用工具不会为一个 ERP 做这种适配。dbColumnZh.ts / db_zh.rs / md_dict
NC 类引用关系NC 的关联大量存在于元数据配置而非数据库外键，通用工具的 FK 图看不到，这里点一下就能沿引用链查记录。dbRelations.ts（外键 + NC 类引用）
NC 迁移导出格式NC INSERT / WHERE / UPDATE 三种脚本 + 绑定参数复核 + 转义规则，是给「跨账套搬数据」准备的，不是通用 CSV 能替代。db_transfer.rs（10 种 TransferFormat）
生产库防误写环境标记 + 按「标签×连接」记忆的免确认窗口 + 连接级只读 + 兜底会话强制回滚。商业工具多是「一个 Safe Mode 开关」，粒度粗得多。dbConfirm.ts / dbReadOnly.ts / fallback-tx
双引擎可切换JDBC 常驻 JVM（能力全）与纯 Rust thin 驱动（省内存、启动快）并存，还能在能力不足时自动路由到 JVM 兜底。业界没有第二个这样做的 Oracle 客户端。db_engine.rs Caps / exec_via_java
二次编码自动解码NC 的 CLOB 里常塞 hex 编码的 JSON 报文。这里在显示层识别并解码（含 GBK 兜底），还能一键生成解码 SQL。极冷门，但现场天天遇到。cellCodec.ts（80% 命中 + JSON 校验）

05差距：分三类，别混着排期

S 战略不追　追了会输，因为不是我们的战场

多数据库支持DataGrip/DBeaver/Navicat 的护城河。NC 只跑 Oracle，做多库是给别人的场景付费。真要通用，成本是「每个库一套元数据 SQL + 方言 + 类型映射」，等于重写三遍。
SSH 隧道已论证否决（系统 ssh.exe 不可用、自研成本高于收益）。NC 现场多是内网直连或 VPN，隧道不是高频路径。
插件体系 / AI插件是生态生意，v0.2.0 做等于给空生态建市场。AI 可以后置——先把「结构化上下文」（表、中文名、计划）做干净，比接个大模型有用。

A 必须补　对手标配，且是 NC 现场高频

缺口现状难度
行级 INSERT / DELETE表页只能改单元格（UPDATE + 原值校验 + 冲突停止）。新增/删除记录得手写 SQL。这是与 DBeaver/Navicat/DataGrip 差距最大、感知最强的一项。中
跨连接数据传输有导出/导入两段，中间靠文件。缺「A 库表 → B 库表」直连搬运与「结构+数据一起搬」。NC 建账套/搬基础数据时正好要这个。中高
表结构对比（DDL diff）完全没有。跨环境核对表结构现在只能人工看 DDL。对手（dbForge/Navicat/DataGrip）都是标配。中
CLOB 全量导出8K 预览通道被复用为导出通道，>8K 的 CLOB 写不全（当前只做到「告警 + 文件名标部分结果」）。正解是给引擎加全量取数命令族。中
XLSX / JSON 导入只有 CSV/TSV/TXT + .sql 逐条回放。实施顾问手里最常见的输入是 Excel。低中

B 打磨　有，但离「老工具的确定性」还差一层

问题现状
事务状态判据仍靠「首关键字 + 乐观计数」猜 for update / PL/SQL 块 / 手写 COMMIT；正解是查 v$transaction 做真源，关键字只当降级。
执行身份状态机running / executionId / slot 三处各自复位，历史上一处漏写就出现「永久 loading」「结果落错连接」。该收敛成单一 runToken。
超时覆盖只有 exec 有 call_timeout；more / lobValue / 元数据命令遇对端黑洞会无限期持锁。
可访问性网格焦点环、错误播报、确认框默认焦点（当前落在「10 分钟不再询问」上）等一批硬伤；键盘流不完整（Home/End 无行为、Ctrl+A 选整页）。
凭证与隐私执行历史明文存完整 SQL（含 identified by、证件号），每连接 500 条无脱敏。

06最该警惕的：成熟度差在「确定性」，不在功能数

v0.2.0 的一轮静态审查（五路并行 + 主审回源码核行号）挖出 8 个 P0：导出把 CLOB 预览文案当正文写进文件且零告警、RAW 超 64 字节静默变 null、临时会话不继承运行期 schema 导致导出读错账套、BLOB 全量读内存致 OOM、编辑连接绕过未提交事务确认、静态 SimpleDateFormat 跨线程共享导致日期错位、事务漏计、导入无生产确认。

这些缺陷的共同点不是「粗心」，而是同一个结构性错误：把「给人看的预览」和「要落盘的全量」压在一条取数通道上，把「事务状态」建立在关键字猜测上。 老工具（PL/SQL Developer 二十多年）的确定感，来自这些边界被无数现场事故磨过一遍。功能可以补，这类「静默错数据」的免疫只能靠架构收敛 + 回归测试沉淀。

好消息是：这一轮已修 7 个 P0 + 9 个 P1，并补了 3 个守卫测试（预览文案契约、事务计数判据、RAW 不静默 null）。坏消息是：3 个结构性设计缺陷（全量取数通道、事务真源、runToken）明确「未修，需单独排期」。

07该往哪走

批次内容理由
第一批
把「确定性」补齐		 全量取数命令族（导出/传输只走它）· 事务真源改 v$transaction · 统一 runToken · 全覆盖 call_timeout 这三件是 P0 的生产者。不修，功能越多、错数据的面越大。用户不会因为「少个 ER 图」弃用，但会因为「导出少一半字」再也不信它。
第二批
补对手标配		 行级 INSERT/DELETE · XLSX/JSON 导入 · 表结构对比（DDL diff） 这三项是「换掉 PL/SQL Developer / Navicat」的最后门槛，也是 NC 建账套、跨环境核对的高频动作。
第三批
做别人做不到		 跨连接数据传输（结构 + 数据 + NC 类引用一起搬）· NC 专用数据体检（脏数据/孤儿引用/编码异常扫描） 这才是真正的差异化：通用工具即使愿意做，也缺 NC 元数据语义。把护城河从「读得舒服」推到「搬得对、查得出问题」。

不建议排期：多数据库、SSH 隧道、插件市场、AI 助手。至少在 NC 场景的数据库链路做到「零静默错」之前，这些只会摊薄注意力。

08结论

已经超越的地方

事务可视化与写保护、结果阅读手感、计划对比、NC 语义（中文名/类引用/迁移格式）、双引擎架构、生产环境防误操作。这些是「用过就回不去」的部分。

还被压着的地方

数据编辑只到 UPDATE、无结构对比、无跨库传输、无 PL/SQL 调试、无 ER 图、导入格式单一。前四项是日常高频，不是锦上添花。

真实水平

在「NC 开发者用的 Oracle 客户端」这个细分里，已经是国内能拿到的最完整的一个（没有第二个做 NC 语义适配的竞品）。放到通用 Oracle 工具货架上，属于「有特色但覆盖不全的中量级选手」。

一句话建议

把「不静默错数据」当第一优先级，把「行增删 + 结构对比 + 跨库搬运」当第二优先级。其余功能在 v0.2.0 阶段都是噪声。
