# NCForge 元数据三期：调研与方案

> 日期：2026-11-04
> 范围：三期「元数据（BMF）：对接 bmf 生成器或可视化编辑，摆脱 UAP Studio」
> 结论先行：**读、校验、生成预览可以完整自研；发布（写 md_* + 建表）不碰，留给 UAP Studio 或另立 POC。**
> 本文只做方案，不改代码。

---

## 0. 结论先行

1. **本地有一整套可参考的实现，但不适合直接复用。** UAP Studio 的
   `NCMDP_6.5.0.201405291435.jar` 负责 GEF 编辑与发布动作，
   `com.yonyou.mdp.middleware.jar` 负责真正的发布/建表脚本/代码生成。前者绑死
   Eclipse `IFile/IResource` 与 SWT，后者绑死 NC 运行时（`NCLocator`、`BaseDAO`、
   `DataSourceCenter`、`JdbcSession`），都不是可嵌入的库（证据见 §1.5）。
2. **BMF 本身足够规整，适合自研解析器。** 本机 3711 个 `.bmf` 全部能被标准 XML
   解析器解析，根节点统一是 `component`，99.8% 是 CRLF、3691 个声明 UTF-8。
   未知节点按原始字节保留，就能做到「只改该改的那几个属性」。
3. **先做「看」和「校验」，再做「生成」，最后才碰「写回」。** 三期真正的痛点是
   UAP Studio 重、慢、要开 Eclipse；不是「必须由 NCForge 执行发布」。把设计态
   （BMF）、发布态（md_*）、物理库（user_tables）三者的漂移看清楚，价值已经成立。
4. **推荐分四批：M0 视图（3 d）→ M1 校验 + 生成预览 + 新建向导（5 d）→ M2 受控写回
   （6 d）→ M3 发布 POC（1 d 试探，条件满足才做 3 d）。** M0+M1 八天就能交付可用版本，
   全程零数据库写入、不覆盖任何已有源文件。
5. **与 P1-5 元数据体检共用读层，不重复做。** P1-5 是「文件/库对撞」，本方案 M0/M1
   是「设计态/发布态/物理库三方对照 + 生成侧」，边界见 §1.6。
6. **「UAP助手」的一键生成可以学，但它只是个脚手架。** 五种单据形态 = 五份内置模板 +
   三项输入 + 全量换 ID（§2.6）。我们把它做成 M1 的新建向导：模板目录 + 命名推导 +
   全量预览，只写新文件；模板资产、字符串替换实现和联网心跳都不引入。

### 1.5 为什么不能直接复用

不是「不想复用」，是三条路都被绑住了：

**A. `JGraph` / `JGraphSerializeTool` 绑 Eclipse**

- `BaseOperationFacade.publishMetaData(JGraph, boolean)` 的字节码只有一句实质逻辑：
  `JGraph.getIRes()` 强转 `IFile`，再调 `publishMetaData(IFile, boolean)`。
  没有 `IFile` 就没有发布入口。
- `JGraphSerializeTool` 的常量池里直接引用
  `org.eclipse.jface.dialogs.MessageDialog.openError` 与
  `org.eclipse.swt.widgets.Display`。也就是说，即使只想「读一个 BMF」，错误路径也要
  拖进 SWT/JFace；无头进程一旦走到错误分支就可能弹窗或直接崩。
- `JGraph` 继承 GEF 模型，类加载就会拉 `org.eclipse.draw2d` 等一整条 RCP 依赖。

**B. `PublishServiceImpl` 绑 NC 运行时**

`publishMetaDataForBMF(String)` 虽然只收一个路径，但字节码里用了：

- `nc.bs.framework.common.NCLocator.getInstance/lookup`
- `nc.bs.dao.BaseDAO`（`executeQuery` / `executeUpdate` / `insertVOArray` …）
- `nc.jdbc.framework.DataSourceCenter.getInstance/setTLDataSourceProvider`
- `nc.jdbc.framework.JdbcSession.getConnection`
- `nc.bs.ml.NCLangResOnserver`（读语言资源）

它必须在 NC 运行时里、且数据源已初始化时才能跑。`publishMetaDataForBMF` 内部还会
`getRelatedMetaFromDB(...)`，没有库连不上就发布不了。

另外，在 `D:\ncc\1909home` 的 `lib/`、`framework/`、`external/` 顶层 jar 中**没有**
找到 `nc/md/persist/designer/PublishServiceImpl.class`（扫描范围为这三个目录两层内的
jar，未做全盘扫描）。本机确认存在的实现只在 UAP Studio 的
`com.yonyou.mdp.middleware.jar` 里。

**C. 许可与分发**

UAP Studio / NCMDP 是用友商业插件。NCForge 不能把它们打进安装包再分发；即使运行时
调用用户本机已安装的 jar，也需要先确认许可边界。M3 若做，必须以「用户本机已有环境、
不随包分发、不复制类文件」为前提。

### 1.6 与 P1-5 的边界

`docs/P0-P1能力补齐-总体规划-20261101.md` §5 已经把 P1-5 定义为**只查不建模**：

- 文件侧：`.upm` 重复注册、BMF 组件名与 `.upm` 不一致、VO 里
  `getAttributeValue(XxxVO.FIELD)` 常量为 null。
- 库侧：`md_table ∖ user_tables`、`md_column ∖ user_tab_columns` 等差集。

本方案的关系：

| | P1-5 元数据体检 | 本方案 M0/M1 | 本方案 M2 |
|---|---|---|---|
| 读 BMF | 只读组件名 | 完整实体/属性/枚举模型 | 完整模型 + 可编辑 |
| 读 md_* | 要 | 要（复用 P0-3 取数层） | 要（只读对比） |
| 写 | 无 | 无 | 写 BMF / VO / SQL 文件 |
| 发布 | 无 | 无 | 无（M3 另议） |

**不重复做两件事**：不重新写一套 md_* 查询；不把 P1-5 的检查项再实现一遍。M1 的规则
引擎直接吃 P1-5 的检查清单，并补上「生成前」才需要的规则（主键、长度、枚举、版本）。

## 2. 对标

### 2.1 BIP 网页端的元数据视图

从用友官方与培训材料能确认的交互（按操作顺序）：

1. 进入**应用工厂** → **元数据设计**（培训材料原话：「相当于设计数据库」）。
2. **新增**元数据，填写名称、创建人、名称空间等属性。
3. 修改**访问器类型**、**主实体类名称**。
4. 点击**发布元数据**。
5. 发布后进入**代码定制**，选择刚发布的元数据组件，配置页面/参数，**下载源码**。
6. 实体必须先发布，页面建模才能引用它。

数据建模页面的结构：

- 三个页签：**实体 / 查询 / 枚举**。
- 实体支持**新增、复制已有、Excel 导入**。
- 属性类型为单选/多选时引用枚举；单选引用/多选引用时引用已发布实体。
- 操作流：新建应用 → 新增枚举 → 新增实体/属性/引用接口 → 保存 → 发布。

BIP 的元数据分层（官方文章）：

- 按层次：UI 元数据、领域元数据（实体/服务/规则）、BI 元数据、AI 元数据。
- 按生态：标准元数据、扩展元数据、租户元数据。

**可借鉴的是交互骨架**：列表 → 详情 → 保存 → 发布 → 生成物；**不可照搬的是分层
模型**：NC 1909 没有租户/扩展元数据这套运行时，硬套只会造出假的「BIP 对齐」。

### 2.2 UAP Studio MDP 的元数据工作流

社区资料与本机插件一致：

```text
元数据建模（或从 PDM 导入）
  → 发布元数据
  → 生成建库脚本并执行
  → 生成 VO 源码
  → 系统类型/功能/单据类型/VO对照/动作/动作组 六处注册
  → 导入数据字典
  → 生成单据/查询/打印模板并注册
  → 建立界面类/控制类/事件类框架
```

常见坑（与本方案规则引擎直接相关）：

- 元数据发布了但表没建 → `ORA-00942`（本机日志实测 33 条）。
- 实体/表字段不一致。
- `bd_billtype.systemcode` 大小写/模块不匹配。
- `dap_dapsystem.islightmodule` 配错。
- 版本号没有大于已发布版本。
- 元数据过滤/组织类型不匹配。
- `PUB_BILLACTION.ActionType` 配错。
- `tools.jar` 等类路径问题。

### 2.3 能力映射：BIP ↔ NC 1909 ↔ NCForge

| 能力 | BIP 网页端 | NC 1909 / UAP Studio | NCForge 方案 |
|---|---|---|---|
| 元数据列表 | 应用工厂 → 元数据设计 | MDP Explorer 树 | 左侧「模块 → 组件」树 |
| 新建/复制 | 新增、复制已有、Excel 导入 | 新建组件、从 PDM 导入属性 | M2 新建/复制；导入 PDM 不做 |
| 实体 | 实体页签 | `celllist/entity` | 中间实体/属性表 |
| 属性 | 属性编辑 | `attributelist/attribute` | 右侧检查器 |
| 枚举 | 枚举页签 | `Enumerate/enumitem` | M1 只读，M2 编辑 |
| 查询 | 查询页签 | 无直接对应 | 不做 |
| 发布 | 保存 → 发布 | 发布元数据（写 md_*） | M1 预览生成；M3 POC |
| 建库脚本 | 平台自动 | 生成建库 SQL 并执行 | M1 生成脚本预览；M2 导出/执行（可选） |
| 代码生成 | 代码定制、下载源码 | 生成 Java 源码 | M1 VO 预览；M2 写文件（GBK） |
| 关系视图 | 实体关系画布 | GEF 画布 | M0 只读自动布局；不做自由拖拽 |

| 扩展/租户 | 标准/扩展/租户三层 | 无 | 不做 |

### 2.4 对标结论

- **BIP 的「元数据设计」本质是表结构设计器 + 发布 + 代码生成**，与 NC 1909 的
  「组件/实体/属性 + md_* + DDL + VO」是同一类问题，只是运行时分层不同。
- NCForge 应该学它的**信息架构和发布前校验**，不应该学它的**租户扩展模型**。
- UAP Studio 的强项是**语义完整**（GEF 模型、PDM 导入、映射、特性），弱项是
  **启动重、离开 Eclipse 不可用、错误提示偏底层**。NCForge 的机会是「轻、快、能看
  懂为什么错」，不是「功能更多」。

### 2.5 学习边界：学做法，不学代码

可以，而且这正是推荐路线。UAP Studio 的价值不在它的 Java 实现，而在它把「设计态 →
发布态 → 物理库 → 生成物」这条流水线固化了十几年。我们要学的是这条流水线的**契约**，
不是它的类。

**学的（行为/契约）**

| 可学的做法 | 具体内容 | 在本方案落到哪 |
|---|---|---|
| 三层分离 | BMF 设计态、md_* 发布态、user_tables 物理态，各有各的所有者 | M0 三方对照；M2 只写 BMF/文件 |
| 组件为中心 | 组件拥有实体、枚举、参照、访问器、特性；表只是投影 | 左侧按组件建树，不按表 |
| 保存 ≠ 发布 | 保存只改 BMF；发布是独立动作，带版本门禁 | M2 保存不触发发布；M3 才谈发布 |
| 生成物是派生物 | DDL/VO 可重复生成；手改会被覆盖 | M1 预览；M2 覆盖前确认 |
| 依赖先行 | 发布前先加载依赖（`MDFileDependSearcher`） | 规则引擎建依赖图，按序校验 |
| 版本/行业语义 | version 必须递增；industry 过滤；存在「忽略版本发布」逃生口 | 校验提示，不自动改版本 |
| 特性/模式复用 | `Features.xml` 的 TreeMode/orgAuditInfo/orgDef 一次套用 | M2「套用特性」，不手填 def1–def20 |
| 表驱动类型映射 | `baseType.xml` 把逻辑类型、DB 类型、Java 类型、长度分开 | 运行时读取用户 NC home 的 `baseType.xml` |
| 代码风格分档 | NC传统/标准/自定义三档影响包名、类名、代码形状 | VO 生成先支持 NC传统，检测并提示其它风格 |
| 访问器语义 | `AggVOStyle` / `POJOStyle` 决定主子表与 AggVO 生成 | 模型暴露 accessor；主表生成 AggVO |
| 向导式高风险操作 | 生成 SQL/代码都是「选项 → 预览 → 执行」 | M2 导出/执行分离，执行二次确认 |
| 校验先行 | `JGraph.validate()` 在发布前 | 所有写操作前先跑规则 |
| 错误分类 | ORA-00942、版本不够、模块不匹配等 | 规则引擎里的「为什么这条要命」 |

**不学的（实现/资产）**

- `JGraph` / GEF 对象模型、`JGraphSerializeTool`、`XMLSerialize` 的实现。
- Eclipse `IFile` / `IResource`、SWT/JFace 对话框、Eclipse 工作区假设。
- `PublishServiceImpl`、`PublishServiceHelper`、`SQLGenerator`、
  `MetaDataVOCodeGenerator` 的代码。
- 用友 jar、类名、内部常量、语言资源字符串、UI 图标/布局/文案。
- md_* 写入协议与缓存清理细节。

**四条执行规则**

1. **黑盒取证**：只记录「输入 BMF → 输出 VO/DDL/md_* 差异」这种可观察行为；
   字节码只用来确认公开入口和依赖边界，不逐行翻译实现。
2. **独立实现**：Rust 侧从零写解析/生成；不复制类名、方法名、常量名、注释和错误
   文案。代码相似度不是目标，行为一致性才是。
3. **运行时读取**：`baseType.xml`、`Features.xml`、`Patterns.xml` 从用户本机 NC home
   读，不 vendor 进仓库；既避免分发问题，也自动跟随用户版本。
4. **可复核记录**：每个学来的契约都在 `docs/` 留一条「观察到的行为 + 样本 + 我们的
   实现位置」，验收时用行为 diff 证明，而不是「我觉得 UAP 是这么做的」。

> 这不是法律意见。严格意义上的 clean room 需要隔离团队；我们做不到也没必要。务实的
> 边界是：**不复制代码与资产，只复现可观察契约，并把证据留在仓库里。**

### 2.6 「UAP助手」：一键生成的真身是「模板 + 再修改」

用户提到的「UAP 小助手」不在 MDP 插件里，而是第三方挂在资源树右键上的一个独立
插件：`D:/NC65/yonyou_studio_nc65_wending/Common/Core/plugins/bmfplugin_16.6.21.eye.jar`
（插件 id `uap63makebmf`，菜单名「UAP助手」）。它不属于用友 MDP，作者是
`uapdev.com`（`AboutAction` 直接打开该网址）。

**它做的事情只有四步：**

1. 在工程里右键 `src/public`（或 `private` / `client`）目录，选一种单据形态；
2. 弹一个 Swing 小窗，填三项：单据编码、单据名称、模块编码；三项都非空才继续；
3. 把 jar 内置的同名模板 BMF 复制到 `<工程>/METADATA/<编码>.bmf`，替换 ID 与占位符；
4. 弹一句「已生成，请刷新 JAVA 工程，再切换到 MDP 透视图刷新文件夹」。

之后全部靠用户在 MDP 里手工改。所以它不是「元数据生成器」，是**脚手架生成器**。

|---|---|---|---|---|---|
| NC单主表单据 | `singleHdemo.bmf` | `HVO` | 48 | `${mkbm}_${djbmlower}_h` | `AggVOStyle` |
| NC主子表单据 | `demo.bmf` | `HVO` + `BVO` | 76 + 59 | `..._h` / `..._b` | `AggVOStyle` / `NCBeanStyle` |
| NC单子表单据 | `singleBdemo.bmf` | `BVO` | 33 | `..._b` | `NCBeanStyle` |

- 表头 22 个管理字段：`pk_head`、`pk_body`、`pk_group`、`pk_org_v`、`pk_org`、
  `vbillcode`、`busitype`、`pk_billtypecode`、`pk_billtypeid`、`vtrantypecode`、
  `ctrantypeid`、`dbilldate`、`fstatusflag`、`creator`、`creationtime`、`modifier`、
  `modifiedtime`、`approver`、`taudittime`、`vapprovenote`、`enablestate`、`vnote`；

**生成机制（读源码确认）**

1. **全量换 ID**：root、entity、attribute、`Reference`、`Enumerate` 及其 `enumitem`、
   `busiIterface` 及其 `busiItfAttr`、`notecell`，以及 `connectlist` 下的
   `busiitfconnection` / `AggregationRelation` / `noteConnection`，逐个换新 UUID。
   做法是 `str.replace(旧ID, 新UUID)` 的**全局字符串替换**——因为 BMF 里实体/属性关系
   全是裸 ID 引用（如 `mainEntity`、`keyAttributeId`、`pk_body` 的 `dataType`），
   只能靠「全文件同值同换」保持引用一致。
2. **替换 6 个占位符**：`${djbm}` 原样、`${djbmlower}` 小写、`${djbmupper}` 大写、
   `${djbmvo}` 首字母大写、`${djmc}` 中文名、`${mkbm}` 模块小写。
3. **dom4j 重排整棵树**后按 UTF-8 落盘；树卡额外写一份 `BD_REFINFO` 的 INSERT SQL
   和一个 `XxxClassRefModel` 模板类。
4. 不更新 `createTime` / `modifyTime` / `version`（模板里还是 2012/2014 的时间戳，
   `version` 仍是 1，LFW 模板是 41），也不写 `md_*`、不建表、不发布。

**一线项目确实就是这么用的。** 用户自有工程里的
`C:/work/aier/newar/uapbd/METADATA/sz02.bmf`（任务接口配置，105,698 字节）与 `demo.bmf`
的表头有 **42 个同名属性**（22 个管理字段 + `def1..def20`，相对顺序与模板一致），
但在管理字段之后插入了 `taskid` / `taskname` 等 5 个业务字段，`def21..def50` 和
`code/name/dr/ts` 被删掉。即：模板铺底 → 删掉用不上的自定义项 → 加业务字段。这验证了
「模板 + 再修改」在真实交付里的工作方式。

**它的毛病（我们不照抄的部分）**

- **只新建，不编辑**：已有组件想改字段，还是回 MDP。
- **覆盖写**：同名 `.bmf` 直接删了重建，无备份、无冲突提示。
- **全局换 ID**：依赖模板内 ID 全局唯一；按字符串替换一旦同值复用就会串。我们按
  XML 节点身份换 ID，并按引用表校验。
- **整树重排**：注释、原有缩进/换行、属性顺序、BOM 全被 dom4j 规整，和仓库里
  99.8% CRLF 的现状不一致。我们写回必须字节保留（§3.6）。
- **零校验**：不查表名/字段名重复、不查 `baseType.xml`、不查模块是否存在、不查
  目标文件是否已被别人改过。
- **无预览**：三项输入直接落盘，类名/表名/字段清单事先看不到。
- **不可依赖**：`Activator` 每 5 分钟访问 `http://www.uapdev.com` 做联网心跳；
  `BillInputUI` 是 Swing 叠在 SWT 上、用 `Thread.sleep(300)` 轮询模态。引入它等于
  引入一个会外联的未知组件。

**学什么、落到哪**

| 学到的做法 | 我们的实现 | 落在 |
|---|---|---|
| 按单据形态给骨架，而不是空组件 | 模板目录：树卡 / 单主表 / 单子表 / 主子表 / 自由 | M1 新建向导 |
| 三个参数起手 | 编码 + 名称 + 模块，其余全部推导 | M1 |
| 命名推导集中 | 编码 → 组件名 / 类名 / 包名 / 表名的规则表，可改、可校验 | M1 |
| 生成后立刻可改 | 生成即打开我们自己的属性表，不要求切透视图刷新 | M1 |
| 只生成草稿 | 不自动写 DDL/VO，不发布；仍走预览与确认 | M1 / M2 |
| 标准字段清单 | 用「字段清单 + 类型规则」表达，类型运行时取自 `baseType.xml` | M1 |

**不学的**：内置模板 BMF、`BmfUtil` 的字符串替换实现、`treeCardRefModel.r`、
生成的 SQL 文案、Swing 弹窗。骨架内容按本仓规则重建，模板资产不入库。

> 这一节把「一键生成」从神秘功能降级成一个可替换的向导：输入三项、套一份字段清单、
> 换一批新 ID、写一个新文件。真正难的不是生成，而是**生成后还能安全地改**——那才是
> M2 的事。

## 3. 技术路线

### 3.1 三条路线

| 路线 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 复用 JGraph | 拉起 Eclipse/Equinox + NCMDP，无头调用序列化/校验 | 语义最完整 | 依赖 SWT/JFace/GEF；启动几百 MB；许可风险；错误路径会弹窗 | 不选 |
| B. 复用 PublishServiceImpl | 用 NC home 类路径起 JVM，初始化数据源后调用发布/生成 | 发布结果与官方一致 | 依赖 NC 运行时与数据源；本机顶层类路径未找到该类；许可与版本风险 | 仅 M3 POC |
| C. 自研解析 + 自研生成 | Rust 解析 BMF，生成 DDL/VO；写回按字节保留 | 轻、快、可控、可测 | 需要覆盖 BMF 语义；发布必须另找官方途径 | **主路线** |

### 3.3 模型与解析

最小模型（Rust）：

```rust
struct BmfDoc {
    path: PathBuf,
    root: Component,          // name/namespace/ownModule/gencodestyle/version/mainEntity
    entities: Vec<Entity>,    // id/name/fullClassName/tableName/accessor/isPrimary
    enums: Vec<EnumDef>,      // name/display/items
    raw_spans: Vec<Span>,     // 未识别节点的原始字节区间
}

struct Entity {
    id: String,
    name: String,
    display_name: String,
    full_class: String,
    table: String,
    accessor: String,
    is_primary: bool,
    attrs: Vec<Attr>,
}

struct Attr {
    name: String,             // 逻辑名
    field: String,            // 数据库字段
    display_name: String,
    type_name: String,        // UFID / String / CUSTOM / user …
    data_type: String,        // 基础类型 ID 或枚举/实体 ID
    style: DataTypeStyle,     // SINGLE / REF / ARRAY
    length: Option<u32>,
    precision: Option<u32>,
    db_type: String,          // char / varchar / decimal / image …
    field_type: String,
    ref_model: String,
    is_key: bool,
    nullable: bool,
    raw: Span,
}
```

解析要求：

- 用 `quick-xml`（新增一个小依赖）或现有 XML 能力做**只读解析**；不要求 serde 全量
  往返。
- 每个节点记录原始字节区间。没有改动的节点写回时原样拷贝，保证「未编辑文件字节
  不变」。
- 未知标签、未知属性、命名空间前缀一律保留，不猜测、不排序、不重排属性。
- 解析失败不吞：进入「问题列表」，标明文件、字节偏移、错误原因。
- 139 个零实体组件正常入树，标为「无实体组件」。

### 3.4 类型映射

以 `D:\ncc\1909home\ierp\metadata\baseType.xml` 为准，`typeName` 只作辅助：

| NC 类型 | 数据库 | Java（VO） |
|---|---|---|
| `String` / `CUSTOM` / `MEMO` / `Multilangtext` | varchar(50/101/200) | `String` |
| `UFID` | char(20) | `String` |
| `Integer` / 枚举 | int | `Integer` |
| `UFDouble` / `UFMoney` / `BigDecimal` | decimal(28,8) | `UFDouble` |
| `UFBoolean` | char(1) | `UFBoolean` |
| `UFDate` | char(19) | `UFDate` |
| `UFDateTime` | char(19) | `UFDateTime` |
| `UFLiteralDate` | char(10) | `UFLiteralDate` |
| `UFTime` | char(8) | `UFTime` |
| `IMAGE` / `BLOB` | image | `byte[]` |
| `dataTypeStyle=REF` | char(20) | `String`（存主键） |
| `dataTypeStyle=ARRAY` | 无列 | 子实体 VO 数组 |

规则：

- **先看 `dataTypeStyle`**：`REF` 一律按主键字符串处理，避免生成参照 VO 类型。
- **再看 `typeName`**；`CUSTOM` 回退到 `dataType` + `fieldType` + `length`。
- 映射表不硬编码在 UI，放在 Rust 常量表里，加类型只加一行；未知类型进问题列表，
  不静默当 `String`。

### 3.5 生成物

**建库脚本（M1 预览）**

- 从 BMF 直接生成，Oracle 优先；输入是实体/属性，不依赖 md_*。
- 必须覆盖：主键、非空、默认值、精度/标度、注释（若有）、子表外键、索引（若 BMF
  有声明）。
- 明确标注「预演脚本」：与 UAP Studio 的「生成建库 SQL 并执行」不是同一条链路，
  在 M1 验收前不得默认执行。
- 差异对比：同一组件的 UAP Studio 输出作为基准，逐行解释差异；解释不了的不许上线。

**VO（M1 预览，M2 写文件）**

- 包名：`fullClassName` 去掉类名；类名：`fullClassName` 最后一段。
- 字段：`public <Type> <field>;`，按 BMF 顺序。
- Getter/Setter：每个属性一对，命名 `getXxx/setXxx`（首字母大写，保留原字段下划线
  风格，与 `Sz02HVO.java` 一致）。
- 固定尾部：`getMetaData()` 返回
  `VOMetaFactory.getInstance().getVOMeta("<namespace>.<ClassName>")`。
- 头部：`package`、`import nc.vo.pub.*`、`import nc.vo.pub.lang.*`、
  `import nc.vo.pubapp.pattern.model.meta.entity.vo.VOMetaFactory`；只导入用到的类型。
- 编码：**GBK**（现有 `Sz02HVO.java` 实测为 GBK），换行 CRLF？生成文件按目标工程
  现有文件的换行与编码检测决定，默认 GBK + CRLF。
- 注释：与现有生成器保持同样的 Javadoc 形状，中文按目标编码写出；不做「美化重排」。

**新建组件（M1，只写新文件）**

- 骨架不是模板 BMF 拷贝，而是「字段清单 + 类型规则」在内存里建模后序列化：
  主表 22 个管理字段 + `def1..def20`（默认 20 条，可增减；助手模板铺 50 条，
  `sz02` 实测删到 20）+ `code/name/dr/ts`，
  表体 6 个管理字段 + `bdef1..bdef20` + 来源单据三件套。
- 命名推导一处集中：`${djbm}` / `${djbmlower}` / `${djbmupper}` / `${djbmvo}` /
  `${mkbm}` 的等价规则用函数实现并单测（不做全文件字符串替换）。
- 引用关系按 ID 建图：`mainEntity`、`keyAttributeId`、`pk_body.dataType`、
  `Reference`、`AggregationRelation` 一次性生成，避免悬空引用。
- 生成前必须展示：组件名、实体名、类名、包名、表名、字段清单、DDL/VO 预览。
- 目标文件已存在 → 拒绝；同目录原子写；生成后返回新文件路径供 UI 打开。

**注册清单（M1 只生成清单，不自动改）**

- 需要新增/修改的 `.upm` 组件声明。
- 需要注册的系统类型/功能/单据类型/VO 对照/动作/动作组（六处）。
- 每项给出文件路径、现有条目、建议条目；M2 再决定是否自动改 `.upm`，`.java` 注册
  默认只给清单。

### 3.6 写回策略（M2）

**BMF**

- 只改用户明确编辑的属性；其它字节原样保留。
- 换行保持 CRLF；编码保持原文件（3691 UTF-8 / 20 无声明，实测无 GBK BMF）。
- 写前备份到 `{config_dir}/bmf_backup/<时间戳>/`，写后生成 unified diff。
- 版本号：编辑保存时提示「当前 version=N，是否 +1」；不自动发布、不自动改
  `modifyTime`（由用户确认）。
- 原子写：同目录临时文件 + rename（复用 `atomic_file.rs`）。

**VO**

- 目标路径由 `fullClassName` 推导，默认写到当前工程的 `src/public/...`。
- 已存在文件：先 diff，再让用户选择「覆盖 / 另存 / 取消」；不静默覆盖。
- 编码/换行检测：读目标文件 BOM 与换行；无目标文件时用工程默认（GBK + CRLF）。
- 写后跑一次语法检查（现有编译链路可复用），失败则回滚并保留备份。

**SQL**

- 默认只导出 `.sql` 文件，不执行。
- 执行是显式二次确认：显示目标连接、库、将执行的语句、影响对象；执行前备份 DDL
  （`user_tables`/`user_tab_columns` 快照）。M2 可先不做执行，只做导出。

### 3.7 发布（M3，条件触发）

只做 POC，不做产品化承诺。候选路线：

1. **NC 运行时无头调用**：用用户本机 NC home 的类路径起 JVM，初始化
   `DataSourceCenter`，调用 `PublishServiceImpl.publishMetaDataForBMF(path)`。
   需要先验证：类是否在用户环境的类路径里、数据源如何初始化、缓存如何清理、
   失败是否可回滚。
2. **Eclipse 无头**：Equinox + NCMDP dropins，调用 `BaseOperationFacade`。
   依赖重、许可风险高，默认不做。

**Kill criteria（任一满足即停）：**

- 一天内无法在测试库上完成一次可回滚的发布。
- 必须把用友 jar 打进 NCForge 安装包。
- 发布结果与 UAP Studio 不一致且无法解释。
- 需要修改 NC 服务端配置或重启才能生效。

### 3.8 UI 信息架构：独立页签

**结论：开一个独立的一级页签「元数据」，不并进数据库页，也不塞进代码页的文档标签。**

理由：

- **对象不同**：数据字典是「已发布的库表」，元数据是「设计态组件/实体」。混在一起
  会让人误以为改 BMF 等于改库。
- **动作不同**：数据字典只读查询；元数据有校验、生成、写回，风险等级不同，需要独立
  的编辑模式与确认链。
- **布局不同**：数据字典是「选表 → 看结果」；元数据是「树 + 表 + 检查器 + 底部问题/
  预览」的常驻三栏，塞进 DB 页的文档区会被挤扁。
- **归属不同**：数据字典跟连接走；元数据跟工作区/工程走。

**入口与快捷键**

- `WORKSPACE_NAV` 末尾追加：`{ key: "meta", label: "元数据", icon: "layers" }`。
- 按本仓「新项只能追加在末尾」的规则，快捷键变成 **Ctrl+5**，设置顺延到 Ctrl+6
  （日志仍是 Ctrl+4）。这是一次可见的键位变更，必须在快捷键表与更新日志里写明。
- 命令面板加「转到：元数据」；数据字典与元数据之间提供交叉跳转。
- 作为 hosted 工具页保活，切走再切回保留选中组件与栏宽。

**页面骨架（桌面三栏，不做网页式单列）**

```text

├──────────────┬──────────────────────────────────────┬──────────────────┤
│ 左：组件树    │ 中：组件工作区                        │ 右：检查器        │
│ 工作区        │  分段：实体 / 枚举 / 关系              │ 类型/长度/参照    │
│  └ 模块       │  实体列表（主表/子表）                 │ 主键/可空/默认值  │
│     └ 组件    │  选中实体的属性表                      │ 原始 XML          │
├──────────────┴──────────────────────────────────────┴──────────────────┤
│ 底部（可折叠）：问题 | 生成预览                                          │
└─────────────────────────────────────────────────────────────────────────┘
```

- 左栏：工作区 → 模块 → 组件；组件节点带实体数和漂移徽标；139 个零实体组件标
  「无实体」，不隐藏。
- 中栏：分段「实体 / 枚举 / 关系」；关系页 M0 只读、自动布局，不做自由拖拽。
- 右栏：M0/M1 只读；M2 才出现可编辑控件，并在顶部显示明确的「只读 / 编辑」开关与
  横幅，避免误以为浏览态能改。
- 底部：问题行可点回对应字段；生成预览支持复制/导出，不自动落盘。
- 空状态：无工作区、无 NC home、无 BMF 分别给可操作提示，不显示空白表格。
- 记忆：上次选中的组件、栏宽、过滤条件，按工作区分键持久化。

**与数据字典的交叉链接**

- 数据字典表详情 → 「在元数据中查看」→ 打开元数据页并选中对应组件/实体。
- 元数据属性 → 「查看发布列」→ 打开数据库页的数据字典标签并定位到该表/列。
- 两边共用 `md_*` 取数层，不复制查询。

**不做的 UI**

- 不做网页式单列居中；保留桌面三栏骨架。
- 不做 GEF 式自由拖拽画布；M0 只读关系图。
- M3 之前不在顶栏放「发布」按钮，避免把高风险动作做成主路径。

**M0 界面验收**

- 从侧栏一键进入，3 秒内看到当前工作区组件树。
- 任意组件三次点击内看到属性表。
- 从数据字典跳到元数据、再跳回，选中项不丢。
- 1440×900 与 1280×800 下三栏不互相挤压，右栏可折叠。

## 4. 分期

### M0　元数据视图（读）

**工期：3 d**

范围：

- 扫描工作区 `modules/**/METADATA/**/*.bmf`，建索引；支持多工程（现有工作区模型）。
- 左侧「模块 → 组件」树；中间实体/属性表；右侧检查器（类型、长度、参照、主键、
  可空、默认值、原始 XML）。
- 顶部搜索：组件名、实体名、表名、字段名、显示名。
- 状态徽标：未发布 / 已发布一致 / 有未发布修改 / 表缺失 / 仅库中存在。
- 复用 `md_dict` 取数层，按 `md_table` / `md_column` / `md_ormap` 对比。
- 只读，不写任何文件、不写库。

验收：

- 3711 / 3711 解析成功；139 个零实体组件可见且有解释。
- 冷启动索引 < 2 s（本机 247 MB），热启动 < 500 ms（缓存）。
- 任选 10 个组件，BMF 与 md_* 的差异列表可复现；抽查 3 个与手工 SQL 一致。
- 全程零写入（用文件 mtime 与库会话只读账号双重验证）。

### M1　校验 + 生成预览 + 新建向导（不落库、不改已有源）

**工期：5 d**

范围：

- 新建组件向导（学 §2.6 的「模板 + 再修改」）：
  - 五种骨架：树卡 / 单主表 / 单子表 / 主子表 / 自由组件（LFW 不做，见 §2.6）；
  - 输入编码、名称、模块；类名 / 包名 / 表名 / 字段清单全部由规则推导并**先预览**；
  - 只允许写新文件：目标 `.bmf` 已存在则拒绝，不覆盖、不备份式删除；
  - 生成后直接进入属性表，不要求切透视图刷新。
- 规则引擎（文件侧 + 模型侧 + 发布态）：
  - 主键缺失/多主键；主键类型不是 `UFID`。
  - 表名/字段名重复；字段名与实体属性不一致。
  - 长度与类型不匹配（如 `UFID` 不是 20、`UFDate` 不是 19）。
  - 必填字段无默认值；参照字段长度不是 20。
  - 枚举值为空/重复；枚举类型与字段类型不匹配。
  - `def1..def20` 重复或与业务字段重名。
  - 组件 version 不大于已发布版本（仅提示，不阻断）。
  - 组件名与 `.upm` 声明不一致（复用 P1-5）。
  - 表在 `md_table` 有、`user_tables` 无（复用 P1-5）。
- DDL 预览（Oracle）。
- VO 预览（GBK/CRLF，按 §3.5）。
- 注册清单（只列，不改）。
- 每条问题必须带：问题、依据（文件行/表/字段）、为什么这条要命、建议动作。
- 不做评分、不做「全部通过」的假绿灯。

验收：

- 3 个样本（`baseapp/area`、二开 `uapbd/sz02`、一个单实体小组件）的 DDL/VO 与
  UAP Studio 输出逐行对比；差异必须有解释，解释不了的不许交付。
- 规则种子：把 P1-5 与本机日志里的已知坑做成 20 条反例，命中 20 / 20。
- 3711 个 BMF 全量跑规则，误报清单逐条列出；误报率 > 5% 的规则必须降级为「提示」。
- 新建向导五种骨架各生成 1 个：全部能被 UAP Studio 打开、无重复 ID、无悬空引用；
  `demo.bmf` 同构的主子表骨架与本章字段清单逐项一致。
- 向导全程只创建新文件；已有文件路径冲突时拒绝并给出原因（用文件哈希验证未被改动）。
- 预览全程零写入。

### M2　受控写回（编辑 BMF + 写 VO / SQL）

**工期：6 d**

范围：

- BMF 编辑：实体/属性/枚举的基础增删改；只改已知节点，未知节点原样保留。
- 写回：备份 + diff 预览 + 显式确认 + 原子写；CRLF/编码断言。
- VO 写出：路径推导、覆盖确认、编码/换行检测、写后语法检查、失败回滚。
- SQL 导出：默认只导出文件；执行作为可选开关，二次确认 + DDL 备份。
- 不自动改 `.upm`、不自动做六处注册；只给清单。

验收：

- 未编辑的 100 个 BMF 走「解析 → 序列化」字节完全一致（或仅允许可解释的差异，
  且默认为 0）。
- 编辑 20 个 BMF（加字段、改长度、加枚举项），用 UAP Studio 实际打开无报错；
  SVN diff 只出现预期行。
- 生成的 VO 在目标工程编译通过（复用现有编译链路），GBK 打开无乱码。
- 备份/回滚演练：写坏一个文件后能一键恢复；回滚后字节一致。
- 所有写操作都有「谁、什么时候、改了哪个文件、备份在哪」的记录。

### M3　发布 POC（条件）

**工期：1 d 试探 + 3 d（仅在试探通过后）**

范围：

- 只在测试库、只对 1 个组件、只走官方接口。
- 记录：类路径、数据源初始化、发布前后 md_* 差异、缓存行为、失败回滚。
- 产出是「可行性结论 + 操作手册」，不是产品功能。

验收/停止条件见 §3.7。

**总工期：M0–M2 14 d；M3 另计。建议先交付 M0+M1（8 d），用真实工程验一轮再决定
M2 的编辑范围。**

## 5. 不做项与触发条件

| 不做 | 原因 | 什么时候再做 |
|---|---|---|
| 直写 `md_*` / 自研发布协议 | 版本规则、行业、缓存、权限都在 NC 运行时里，复现风险极高 | 永不；只走官方接口 |
| 复用 NCMDP/JGraph 做编辑器 | Eclipse/SWT/GEF 依赖 + 许可风险 | 除非官方提供无头 SDK |
| `.mbe` / `.mbp` / `.bpf` 编辑 | 三期的真实需求集中在 `.bmf`；另外三类占比低 | 有用户明确要，且 `.bmf` 稳定后 |
| GEF 式自由画布 | 桌面端做自由图编辑成本高，收益低；表格式更适合字段级工作 | 只读关系图不够用时 |
| PDM / XSD 导入导出 | 低频，且格式解析成本高 | 有真实 PDM 样本和明确诉求 |
| 多语、映射、特性编辑 | UAP Studio 已有，NCForge 复刻性价比低 | M2 稳定后按需 |
| 自动改 `.upm` / 六处注册 | 注册面广、格式杂，写错会直接导致启动失败 | M2 写回稳定，且用户要求 |
| BIP 租户/扩展元数据分层 | NC 1909 没有对应运行时，做了也是假对齐 | 不做 |
| 内置/分发用友 jar | 许可与分发风险 | 不做 |
| 「UAP助手」模板资产与 LFW 骨架 | 模板 BMF 是第三方资产；LFW 与 NC 标准单据不同源 | 永不引入资产；LFW 有真实诉求再单独立项 |

## 6. 验收与度量

### 6.1 语料

- 全量：3711 个 `.bmf` / 247.1 MB。
- 解析成功率：100%。
- 未知标签覆盖率：统计每个文件的未知标签数；任何未知标签必须出现在「原样保留」
  清单里，不能丢。
- 零实体组件：139 个，单独统计。

### 6.2 往返（M2）

- 未编辑文件：字节一致率 100%（以 SHA-256 计）。
- 编辑文件：diff 只含预期行；换行 CRLF 保持；编码保持。
- UAP Studio 打开：20 个编辑样本全部通过（人工门禁，必须真开一次）。

### 6.3 生成物

- DDL：3 个样本与 UAP Studio 输出逐行 diff；差异 0 或全部有解释。
- VO：字段名/类型/顺序/getter/setter/`getMetaData` 与现有生成器一致；编译通过；
  GBK 无乱码。
- 注册清单：六处注册一项不漏；每项有路径和现有条目。

### 6.4 规则

- 20 条历史坑反例：命中 20 / 20。
- 全量误报：逐条列出；单条规则误报率 > 5% 降级为提示。
- 不允许「静默跳过」：跳过必须计数并可见。

### 6.5 性能与内存

- 冷启动索引 < 2 s；热启动 < 500 ms。
- 打开单个组件 < 100 ms（已索引）。
- 全量规则扫描 < 10 s。
- 解析 3711 文件常驻内存目标 < 200 MB；超限要能降级为按需解析。
- 遵守本机重负载约束：批量解析分批、限制并发，不把内存顶满。

### 6.6 写安全

- M0/M1：已有文件 mtime / SHA-256 不变、库只读账号无写记录；新建向导只创建目标
  不存在的路径，冲突时拒绝。
- M2：每次写前备份、写后 diff、失败回滚；回滚后 SHA-256 一致。
- 任何执行 SQL 的动作都要二次确认，且默认关闭。

## 7. 风险

| 风险 | 等级 | 应对 |
|---|---|---|
| BMF 语义未文档化，未知节点被改坏 | 高 | 字节区间保留；未编辑文件字节一致；UAP Studio 人工门禁 |
| GBK/CRLF 写回改坏文件 | 高 | 编码/换行检测 + 断言 + 备份 + 回滚；复用 `atomic_file.rs` |
| 生成 DDL/VO 与官方不一致 | 高 | 3 样本逐行 diff；差异必须解释；解释不了不上线 |
| 139 个零实体组件被当成异常 | 中 | 正常展示并单独统计；不假设「组件必有实体」 |
| `CUSTOM` 类型映射错 | 中 | 以 `dataType`/`fieldType` 为准；未知类型进问题列表 |
| 发布链路依赖 NC 运行时 | 高 | M3 只做 POC；不把发布放进主路径 |
| 用友 jar 许可/分发 | 高 | 不打包、不复制；M3 仅调用用户本机环境，且需书面确认 |
| 多工程/多版本 BMF 冲突 | 中 | 按工作区+模块索引；同组件多份时标明来源，不自动合并 |
| 性能/内存（247 MB、3711 文件） | 中 | Rust 索引 + 惰性解析 + 缓存；分批；限并发 |
| 与 P1-5 重复开发 | 中 | 共用 md_* 取数层与检查清单；边界写进任务卡 |
