## 3. C4：删掉一行死 import

`src/lib/monacoContributions.ts` 原来 import 了 Monaco 的 `linkedEditing` contribution。它是编辑器侧的实现，需要有 provider 才会生效；全仓 grep 只有这一行、没有 `registerLinkedEditingRangeProvider`，jdt.ls 那边又直接 `-32601`。

保留的唯一效果是多打一个 chunk 进包。已删除，并在原位留注释说明「要恢复先注册 provider」。

> 顺带纠正方案里的说法：这里从来不是「引了贡献但没验」，而是**验了，没有 provider，所以不可能生效**。

## 5. B1：循环依赖实测是「静默忽略」

在 `eclipse_cp.rs` 造 A→B→A（两边都 `exported="true"`）：

- **不死循环**：DFS 只有 `seen`，回到已访问工程直接 continue；
- **不报错**：`notes` 里一个字都没有；
- **静默错序**：两个工程的输出目录各出现一次没错，但 `compile_order` 给出 `["b", "a"]`——它只做「类路径出现顺序取反」，**从不读依赖关系**。

处置：在 `walk` 里加了一条只用于提示的路径栈（`WalkState.stack`），回边时往 `notes` 里写一条「模块循环依赖：a → b → b」，告诉用户「只改一个模块就单模块编译、同时改两个就整体编译一遍」。

**为什么不按 SCC 缩环编译**：编译单位是整 IProject，`newar` 只有 1 个 `.project`，缩环要改 `CompileEnv` 的单位定义；先让用户看见，比改错单位的风险小。

**为什么不剪枝**：剪掉一条回边就是少一个类目录，编译期表现成「类找不到」，比多一句提示严重得多。

测试钉住两条：`循环依赖报出来但照旧收集目录`、`菱形依赖不算循环`（a→b→c 且 a→c 是重复访问不是环，误报会让正常工程每次打开都弹提示）。

### 6.1 一条命令出全表：`npm run test:perf`

打点有了，但「现在到底多快」仍要人肉翻三份 JSON 加一份日志。新增 `scripts/perf-baseline.mjs`（CLI）+ `scripts/lib/perf-baseline.mjs`（纯函数，16 项单测）把四路输入汇成一张表：

| 通道 | 取数来源 |
|---|---|
| compile | Rust `#[ignore]` 测试 `单文件编译_p50` 的 `PERF ` 输出行 |
| incremental | Rust `#[ignore]` 测试 `增量编译_p50` 的 `PERF incremental-compile` 行（2026-11-16 接入） |

**契约只有一条：没数就是没数。** 任何一路缺席 / 跳过 / 编译失败，对应行一律 `未测` 并带原因，绝不填 0、不填上轮旧值。`incremental`（1–5 文件增量编译）2026-11-16 已接独立探针，**仍不拿单文件的数字顶替**（两条通道各有 PERF 行，单测钉住互不串台）。

不进 CI：这些数字依赖真机 java / jdt.ls / NC home，机器间差一倍很正常，卡 CI 只会让人去调阈值。默认超标也不改退出码，`--strict` 才当失败。

单路探针有 8 分钟上限（`--timeout-ms` 可调）。原因见 §8.2 的清理坑：测量早已落盘，进程却可能卡在收尾。到点 kill 后照常读已落盘的 JSON，并打印「测量结果若已落盘仍会采用」。

#### 🔴 读与写必须分两个目录：`target/perf/` 才是结论的家

第一版把汇总和快照都写进 `target/test-tmp/`，结果 **`--reuse` 出表全是「未测」**——因为 `scripts/rust-gate.mjs::wipeTmp()` 会清空 `target/test-tmp` 的**全部条目**（不区分文件还是目录）。也就是说：**跑一次 rust 门禁，就把自己上一轮的性能结论删了**。

现在的分工：

| 目录 | 谁写 | 谁清 | perf-baseline 怎么用 |
|---|---|---|---|
| `src-tauri/target/test-tmp/` | 各探针 | `rust-gate.mjs::wipeTmp()` | **只读**，找不到就回落 |
| `src-tauri/target/perf/` | perf-baseline 自己 | 只有 `cargo clean` | 汇总 + 快照写这里 |

`readJson(name)` 先读 `perf/`，没有再读 `test-tmp/`；**从 `test-tmp/` 读到的顺手抄一份进 `perf/`**。这样探针照旧写自己的目录（不用改探针），而结论不会被门禁清掉。`--reuse` 因此可以跨门禁复用。

## 7. A4：大文件降级的缺口只有一处

`heavy` 降级机制**本来就有**（阈值 `LARGE_FILE_LINES = 2000`、提示条、小地图/折叠/括号着色/内联提示全关），缺的是最贵的那一项：**自动弹出的补全没关**。

实测 6003 行：补全热 p50 **1165 ms**（普通文件 10~58 ms），意味着每敲一个字都要卡一秒——比没有补全更难受。

处置按「最小伤害」：

| 动作 | 做不做 | 理由 |
|---|---|---|
| 关 `quickSuggestions`（输入即弹） | **做** | 这是「每敲一个字卡一秒」的唯一来源 |
| 关 `suggestOnTriggerCharacters`（`.` 触发） | **不做** | `.` 是 Java 最常用的补全入口，关掉等于毁掉补全 |
| 关 `Ctrl+Space` 手动触发 | **不做** | 手动是用户明确要，1 秒可以等 |
| 关语义高亮 | **不做** | 一次性请求、可缓存，且关了颜色会掉 |

`largeFile.ts` 原来那句「不能仅凭行数关闭补全」保持不变——我们没关补全，只关了「不问自取」。提示条文案同步改，否则用户会以为补全坏了。

测试：`editorPrefs.test.ts` 的「大文件只关『输入即弹』的补全」钉住三条（heavy 关 quickSuggestions、不动 triggerCharacter、其余降级项不变）。

### 7.1 补上字节阈值（2 MB）与真实接线

只看行数会漏掉 NC 现场最常见的一类输入：**行数不多但单行极长**——报文 XML、一整年堆在一起的 SQL、导出的日志切片。它们可能只有几百行，却能把 tokenize 拖住。

- `largeFile.ts` 加 `LARGE_FILE_BYTES = 2 * 1024 * 1024`，判据 `isHeavyFile({lines, bytes})` 两条线取**或**，且都是**严格大于**（正好 2000 行 / 正好 2 MB 不算大文件）。
- `TabMeta.bytes` 设为**必填**（不是可选）：可选字段会让「忘了填」静默退化成「按行数判」，而那正是我们要修的漏洞。必填后 tsc 直接把 13 个测试 fixture 顶出来，逐个补齐。
- 取值口径：磁盘文件用 `FileContent.size`（**不是** `text.length`——GBK 下一个汉字 2 字节，用字符数会偏小）；`jdt://` 虚拟文件没有磁盘字节数，用 `text.length` 近似；后台恢复的空标签 `bytes: 0`。
- 真实调用点三处：`FilesTab.tsx:216`（提示条）、`:235`（传给 `FilePaneSlots`）、`EditorGroupsPane.tsx:97`（分屏 `heavy`）。链路终点是 `editorPrefs.ts::monacoOptionsOf`。

测试：`largeFile.test.ts` 5 项（字节超阈 / 行数超阈 / 都不超 / 两条边界 / 空标签）+ `tabSession.test.ts` 3 项（`bytes === c.size`、GBK 下 size ≠ text.length、虚拟文件用字符数）。

| fresh（新排除，空 data） | 9 193 ms | **12 792 ms** | 3 599 ms |

| old（只排 `.svn`，空 data） | 11 324 ms | **16 485 ms** | 5 161 ms |

两句必须诚实说的话：

1. **缓存复用对索引段没有帮助**（3 546 vs 3 599）。`Refreshing '/bench'` 那一阶段无论如何都要重扫一遍文件时间戳，缓存省的是「解析」不是「扫描」。以后要再提速，只能从「少扫点」或「JVM 更强」入手，不要再指望缓存。
2. 这份数据是 2000 文件，真实 `newar` 是几万文件 / 152 s。**-22% 是按比例外推，不是实测**。~~真数字仍要一份真实工作副本。~~ **2026-11-16 补**：真实副本找到了（`nc65newwork`，1245 java），`--root` 实测首次导入 43.3 s，见 §1.0.1；但那是 1245 文件不是几万，`newar` 规模仍待现场。
3. （复跑补）上面第 1 条的方向是对的，但理由说浅了：不只是「缓存对索引段没帮助」，而是**两轮的总耗时差根本不在索引段**。详见 §8.1。
4. （2026-11-16 补）真实工程上索引段 fresh 19.5 s vs warm 11.9 s **确有差异**——比合成 fixture 大时缓存对索引本身也有收益，但引导段差 12.4 s 仍是总差大头。第 1 条「缓存对索引段没帮助」只在 2000 文件 fixture 上成立，别外推到所有规模。

### 8.1 复跑推翻了一半结论：差异在 OSGi 引导段，不在索引段

2026-11-15 傍晚同一 fixture 复跑（`--files=2000`），数字与上表不同，而且**差异的归属完全不同**：

| 轮次 | 到就绪 | OSGi 引导段 | 状态推进段 |
|---|---|---|---|
| fresh | 17 792 ms | **13 437 ms** | 4 355 ms |
| warm | 12 963 ms | **8 679 ms** | 4 284 ms |
| old | 17 445 ms | **12 804 ms** | 4 641 ms |

按 `language/status` 时间戳拆开看：总耗时 fresh−warm = **4 829 ms**，但状态推进段只差 **71 ms**。**差异几乎全在引导段**——那是 OSGi 解析 bundle、建 config area 的开销，第一次要解压校验，后两次沾的是文件系统缓存与 OSGi 产物已存在的光。

🔴 **所以「缓存复用省了 4.8 s」是错的读法**，它把 JVM/OSGi 启动的抖动记到了索引账上。同理本轮 `old` 与 `fresh` 只差 347 ms（上轮是 3 693 ms），**不足以支撑「产物目录排除 -22%」这个稳定结论**——排除本身仍然该做（`.svn` 不排除会卡在 35% 一分钟以上是确凿的），但收益数字必须标注为「随冷热波动，单次测量不可靠」。

判据已写进代码：`scripts/lib/perf-baseline.mjs::splitIndexRound` 把一轮拆成引导 + 推进两段，表格备注只报这两段，**不再输出「缓存复用节省 X ms」**，并有单测钉住这个措辞不许回来。

方法论教训（与长期记忆里「先查指标自己的历史基线」同源）：**拿总耗时的差当某一段的收益之前，先把那段单独拆出来**。总耗时里混着 JVM 启动、OSGi 引导、文件缓存三层噪声，任何一层的抖动都够伪造出一个「优化有效」。

### 8.2 探针收尾会被沙箱拖成 20 分钟

`lang-index-bench` 三轮测量只花 48 s，但**清理 fixture 花了 20 分钟以上**：`NODE_OPTIONS` 注入的 `node-safe-delete-shim` 逐条拦 `unlinkSync`，2400 个文件删起来约每秒 0.2 个（实测 5 秒删 25 个）。

这不是代码 bug，是环境特性。处置：`perf-baseline.mjs` 给单路探针设超时，到点 kill 后照常读已落盘的 JSON——**「测量完成」与「进程退出」是两件事**。残留目录都在 `src-tauri/target/test-tmp` 下，跟着 `cargo clean` 或下一轮 `rust-gate` 的 `wipeTmp` 走，不污染系统盘。

实测这条机制生效：索引通道设 `--timeout-ms=180000`，180.0 s 到点被 SIGTERM 中止，但三轮测量早已落盘，**数据照常采纳**（9 490 ms = 引导 6 873 + 索引 2 617）。

⚠️ 但残留**结论文件**不能跟着一起被清——那是 §6.1 那个坑，汇总与快照已改落 `target/perf/`。

## 9. A3 启动分段与索引进度

`language/status` 的 `message` 原文**本来就带百分比**（实测）：

```
Starting:     0% Starting Java Language Server
Starting:    30% Starting Java Language Server
Starting:    35% Starting Java Language Server - Refreshing '/jdt.ls-java-project'.
Starting:    66% Starting Java Language Server - Refreshing '/bench'.
Starting:   100% Starting Java Language Server - Refreshing '/bench'.
Started:      Ready
ServiceReady: ServiceReady
```

所以不用估算，直接解析：

- `lang.rs::parse_progress` 认 `NN%` 与 `A/B`，取不到返回 `None`——**不编百分比**；
- `lang.rs::stage_of` 把英文原文归纳成中文阶段。顺序有讲究：`refreshing` 必须排在 `starting` 之前，否则「66% Starting … Refreshing」会被说成「启动服务」；
- `LangStatus` 加 `progress` / `stage`，状态栏显示「代码智能：建立索引 66%」。

启动分段（命令 `boot_stage` + `lib/bootTrace.ts`）四段各报一次：

| 段 | 触发点 |
|---|---|
| `editable` | 首帧 rAF（`boot_report`，上一轮已有） |
| `tree` | 第一次 `fs_list_dir` 成功 |
| `index` | `lang-status` 变 ready |
| `diag` | 诊断 settle 完成（此前那批「找不到类」是索引没算完的假象） |

Rust 日志形如 `启动分段：进程启动 → index 152340 ms`。四段合起来才回答得了「启动慢在哪一段」。

## 10. B2 多项目多版本：基础早就有，缺的是「看得见、清得掉」

`data_dir_for` 的哈希键是 `(版式号, 工作区根, 模块, NC home, jdtls 目录)`——**工程和 NC 版本档位本来就是隔离的**；切工程也在同进程内完成（`applyWorkspace` → `stopLang` → 打开 java 文件时按新工程重启 jdt.ls）。

缺的两件：

1. **保留份数 4 → 8**。原来按「同时两个工程」估；现场是三个工程乘两三个模块，4 份会在切回第一个工程时把它挤掉，等于每次切回去都从头索引。
2. **给用户一个入口**：`lang_cache_stats` / `lang_cache_clear`（新文件 `commands/lang_cache.rs`）。状态栏代码智能菜单里显示「索引缓存 6 份 · 占 480 MB」并给「清理」项；语言服务在跑时后端拒绝清理（它正握着其中一份目录），UI 据此灰掉按钮。

要讲清的边界：切工程**仍然要重启 jdt.ls**（它一个 workspace 只能一个 root），所以「切换快」指的是**索引不用重建**，不是进程不重启；而 §8 的实测说明缓存省的是解析不是扫描，所以切回旧工程仍有 `Refreshing` 那一段。

## 11. B3 VO ↔ 表 ↔ 字段反向

正向（表 → VO）在数据字典里，反向没有。而现场更常见的问法恰恰是「我正在看这个 VO，它是哪张表、哪个字段」。

只查库、**不做类名推断**：`CalbdocVO → bd_calbdoc` 这种约定在 NC 里成立九成，剩下那一成会让用户对着错误的表改代码。

- SQL `md_dict_sql::vo_tables_sql`：`md_ormap → md_column → md_class / md_table`，类名认三种写法（简单名 / 全限定名 / 以 `.` 结尾匹配）；
- 命令 `nc_vo_tables(class_name)`（`commands/vo_map_cmds.rs`）：命中表后**复用字典那套** `tables_sql` + `columns_sqls` + `md_dict::build`，字段口径与数据字典完全相同；
- 入口：命令面板「查看这个 VO 对应的表与字段」（`db.voTables`），类名取**光标所在最内层类**——文件名对不上时查错表比查不到更糟；
- 展示：`VoTableDialog`，表名可点「在工程中搜索」（复用 `setSearchForm` + 切页事件，不另造导航）。

查不到时给三种原因（纯前端 VO / 元数据没发布 / 类名写法），而不是一句「没有结果」。

## 12. B4 报错 → 根因

只做确定性映射，认不出返回 `null` 并保留原文——猜错的根因比没有根因更贵，用户会照着它改错地方。

`lib/rootCause.ts` 的判定顺序：`ORA` 码 → 连接类 → 编译错误 → NC 异常。顺序是刻意的：一条 NPE 的 message 里带 `ORA-01722` 时，后者才是根因。

- 数据库错误码与连接类**不重写**，直接调 `oraHint` / `dbConnectionHint`，同一份文案只有一个出处；
- 新增两块空白：10 条 ecj 句式（`cannot be resolved to a type`、`must implement the inherited abstract method`、`Duplicate method` 等）与 8 条 NC 异常（`NCLogicException`、`NoSuchMethodError`、`StackOverflowError` 等），每条带「下一步」，写的是 NC 现场的原因（模块没关联、补丁没重新部署、`UFBoolean` 当 `boolean` 用）；
- 展示：问题面板每条错误下面一行（`ProblemCause`），**不用悬停**——扫一遍列表就知道这十几条是同一类问题；认不出的不占行。

6 条单测钉住：ORA 认码、连接类带动作、编译句式、`NCLogicException` 明说「不是缺陷」、ORA 优先于 NPE、认不出返回 `null`。

**已知遗留**：ORA 文案现在还有第三个出处——`nc_log_rules.rs` 的 7 条（NC 服务日志页的「为什么 / 下一步」）。它服务的是日志归因，不是问题面板，本轮没有合并；如果以后要改 ORA 文案，三处都要看（`oraErrorHint.ts` / `dbConnectionHint.ts` / `nc_log_rules.rs`）。合并的前提是把 Rust 侧那张表做成前端可读的唯一数据源，那是独立一件事。

## 12.1 A1 复测：单文件编译 p50 = 31~33 ms，方案里的 1.1 s 是池化前的旧数

新增 Rust `#[ignore]` 测试 `ecj_worker.rs::单文件编译_p50`：同一常驻 worker 连编同一文件，前 3 次预热丢弃、后 20 次取中位数（第一次会拉起 JVM，算进去等于量冷启动）。

**实测 p50：首测 33 ms（n=20，26~43 ms）、复测 31 ms（n=20，25~48 ms）**，目标 `< 400 ms`。两次差 2 ms，属稳定达标——与索引那项的 8.3 s 波动形成对照。

结论要说清楚：这**不是本轮优化出来的**。`ecj_worker.rs` 的池化 + `MIN_IDLE` 5 分钟 + OOM 回退，以及 `compile.rs:815` 的 `TieredStopAtLevel=1` / `UseSerialGC` 早就在了。方案 §4.2 写的「当前 1.1 s」是**池化之前的数字**，一直挂在表里没复核，导致 A1 被误列为待做项。

防呆上限设 5 s 而不是 400 ms：**0.4 s 是目标不是门槛**，机器差异让测试红等于把目标变成阻塞。编译失败时打印 `PERF … failed` 并跳过，绝不拿失败耗时当基线。
