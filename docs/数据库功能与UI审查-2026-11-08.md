审查范围：前端 `desktop/src`（lib + components/db + 相关 CSS）、Rust `desktop/src-tauri/src`（引擎、命令层、传输导出导入、搜索、连接）、Java 桥 `db-bridge/NcDbBridge.java`。合计约 2.1 万行。

## 一、P0：数据错误 / 数据丢失 / 进程崩溃

### P0-1 导出与传输把 CLOB 的「预览文案」当成真实值写入文件，且不再告警（**本次回归，已核**）

链路：

1. `commands/db_export_cmds.rs:242` 取数统一走 `exec` / `more`，和网格用的是同一条路径。
2. 该路径对 CLOB 只回 8K 预览并**在文本尾部拼一句中文**：`db_rust.rs:1673-1682` `preview_text()` → `" …（共 N 个字符，只显示前 8192，点「加载完整值」查看）"`；Java 桥 `NcDbBridge.java:1902` 同型。
3. 截断统计 `db_export_cmds.rs:327` 判 `v.len() >= CLOB_LIMIT`，而 `CLOB_LIMIT = 1024*1024`（`:38`）。预览最长 8K，**永远够不到 1MB**，因此 `long_values` 恒为 0。
4. `:164-169` 的告警因此永不触发；`sql_export::render` 把「8K 正文 + 中文说明」按原样写进 INSERT 脚本 / CSV / XLSX。

传输路径同款：`commands/db_transfer_cmds.rs:591-596` `count_long()` 阈值也是 1MB。

后果：任何超过 8192 字符的 CLOB（NC 的 `outtranslatejson`、备注、报文原文）导出后正文残缺，且数据里混入一句中文提示。用户拿去做基础数据迁移，重放即脏数据，界面上显示「导出成功」。

严重度说明：本次改造前是「1MB 截断 + 有告警」；改成 8K 预览后变成「8K 截断 + 零告警」。**净效果变差**，因为告警阈值没跟着 `LOB_PREVIEW` 一起改。

修法（二选一）：
- 正解：导出/传输不复用网格取数。给引擎加 `execFull`（LOB 走 `CLOB_MAX` 或流式），导出路径专用。
- 兜底：阈值改 `>= LOB_PREVIEW`，把该项计入 `truncated`，输出文件名带「部分结果」，并在对话框用红色列出受影响行数。

### P0-2 RAW 列超过 64 字节在 INSERT 脚本里变成 `null`（已核）

`sql_export.rs:314-319`：值必须 `len%2==0 && 全 hex` 才输出 `hextoraw('…')`，否则 `"null"`。而桥对 RAW 只给前 64 字节并把 `…` 拼在末尾（`NcDbBridge.java:1907` `hex(b,64)`），**必然**不是合法 hex。
后果：GUID/摘要类主键或业务列在脚本里被写成 `null`，重放时要么 ORA-01400，要么静默写入 NULL。

修法：非法 hex 时返回 `Err`（宁可整条导出失败），或统一告警 + 不静默写 null。

### P0-3 一次性临时会话不继承「运行期切换过的 schema」，导出会读错库（已核）

`commands/db_cmds.rs:533` `open_temp_session` 用的是调用方传进来的 `conn`（配置里的 `default_schema`），**没有**走 `conn_with_runtime_schema()`。对比 `commands/db_import_cmds.rs:164` 做对了，`db_transfer_cmds.rs:217-227` 还额外显式钉住 `source_schema`。

受影响入口：导出 INSERT / 导出文件（`db_export_cmds.rs:212`）、按值反查（`db_search_cmds.rs:120`）、账号列表（`db_user_cmds.rs:68`）、关系图（`db_relations_cmds.rs:46`）。

后果：用户切到 schema B，表页显示 B 的数据，导出文件里却是 A 的同名表数据；`table_meta` 的列、主键、多语判定也全按 A 取。跨账套迁移时是静默错数据。

修法：`open_temp_session` 内改 `conn_with_runtime_schema(state, conn)`；导出另加可选 `source_schema` 显式钉死（同 transfer）。

### P0-4 BLOB 为了显示「多少字节」把整列读进内存（已核）

`db_rust.rs:1585-1592`：`row.get::<Option<Vec<u8>>>(i)` 先全量分配，再用 `b.len()` 输出 `<BLOB N B>`。LONG RAW 分支（`:1594-1600`）只取前 64 字节做 hex，却同样先读了整个值。

后果：NC 附件表（`ic_*` 附件、图片）一次 `select *`，500 行 × 数十 MB，主进程直接 OOM 被杀——用户看到的是应用自己退出，不是报错。

修法：BLOB 用 `Lob::get_size()` 拿长度（不读内容）；RAW 用 `Lob::take(64)`。

### P0-5 编辑已连接连接的地址/账号/引擎后保存，绕过未提交事务确认（已核）

`components/db/ConnManualForm.tsx:105`：`if (target && conn && rtOf(conn.id).status === "connected") await disconnect(conn.id);`
直接调 store 的 `disconnect`，**跳过** `lib/dbActions.ts:121-128` 的 `guardAllSessions`（primary + 每个槽逐个问「提交/回滚/取消」）。后端 `db_cmds.rs:1131-1157` 的注释明确写着「未提交的改动由桥回滚——界面已经先问过用户」。

后果：用户改了个端口保存，界面弹绿色「配置已保存」，未提交的 UPDATE 已经全部回滚。

修法：改走 `disconnectConn(conn.id)`；保存前若 `tx.statements > 0` 先弹确认。

### P0-6 导入对话框不显示目标连接与环境，无生产库确认，逐批独立提交（待核）

`components/db/ImportDialog.tsx:166-171` 头部只有 `→ {table}`；`:104` 每批 `importRows` 独立提交；`TablePage.tsx:92-99` 的入口不传连接信息。`confirmProdWrite` 在该路径上完全没被调用。

后果：生产库导入错列/错表，第一批 200 行已落库，「取消」只能停在批边界，无法整体回滚。

### P0-7 Java 桥用静态 `SimpleDateFormat` 跨会话共享（已核）

`NcDbBridge.java:1869` `private static final SimpleDateFormat DATE_FMT = ...`，`:1878` `DATE_FMT.format(ts)`。每个 Session 有独立 worker 线程（`:349`），`value()` 是 static。

后果：两个槽同时取含 DATE 的结果集时，格式化内部 `Calendar` 被并发改写 → 日期串错位（对账按错日期）或抛 `ArrayIndexOutOfBoundsException` 整页失败。

修法：`ThreadLocal<SimpleDateFormat>`（桥要兼容 NC 的 Java 7，别用 `java.time`）。

### P0-8 事务可见性靠「首关键字猜」，`for update` / PL/SQL / 手写 COMMIT 全部漏计（已核）

Rust：`db_rust.rs:721` 对 `select … for update` 调 `track_tx("lock", 0)`，而 `is_write`（`:1983-1985`）只认 `insert/update/delete/merge/replace` → `"lock"` 恒假，计数不动。
Java：`NcDbBridge.java:955-971` 用 `^\s*(insert|update|…)` 锚定首词，同样漏 `begin/declare/call` 块内 DML 与 `with … update`。

后果链：
1. 事务条显示「0 条未提交」，`for update` 拿到的行锁在界面上不存在；
2. 随后切只读 / reconnect / 关标签触发 `rollback()`，**静默释放行锁、结束事务**（`db_rust.rs:579-582` 的守卫 `tx_statements > 0` 失效）；
3. `exec_via_java` 的 `fallback-tx` 守卫读 `ping.tx.statements`（`db_cmds.rs:1325`）判 0 → 不回滚、不报错，把「写入停在临时会话里、进程退出即丢」当成功返回。

另：手写 `COMMIT;` / `ROLLBACK;` 也不清计数（`is_ddl`/`is_write` 都不认），此后 `set_readonly` 永远拒绝，而库里其实早已提交。`db_engine::settle_transaction_flag` 已经专门处理了这几种情形并有单测，说明两个引擎口径本应一致，只有 Rust 引擎这一侧漏了。

修法：`track_tx` 增加 `lock`（乐观计一次）与 `commit|rollback`（`reset_tx`）分支；`begin/declare/call` 一律按写计。更稳的做法是查 `v$transaction` 反查真实事务状态，取不到再退回关键字法。

## 三、P2：边界与体验（按主题归并）

**取值与显示**
- `DBMS_OUTPUT` 只在成功路径取，失败语句的输出会串到下一条（`db_rust.rs:657` vs `:666`）。
- `explain` 的 `delete from plan_table` 走裸 `conn.execute`，auto-commit 下每次看计划都留一个未提交事务且不计入 `tx`（`db_rust.rs:1252-1255`）。
- `stats_unavailable` 一次抖动就永久关掉 Autotrace，只能重连恢复（`db_rust.rs:639-646`）。
- `schema_batch` 静默截断到 1000 行，响应里没有 `hasMore`/`total`（`db_rust.rs:1393-1405`）。
- `lob_value` 的 `truncated` 用 `>=`，长度恰好等于上限时误报「还能再加载」（`db_rust.rs:1751-1756`）。
- `cellText` 按 UTF-16 码元截断，可能切出半个代理对（`db.ts:255-260`）。
- 网格对大文本只给 4px 圆点且 `aria-hidden`，单元格无 `aria-label`（`ResultGrid.tsx:265-288`）。

**导出与传输**
- `db_export_insert` 把 10 万行全量读进 `Vec<Vec<String>>` 再拼整串，与 `db_export_file` 的流式设计相反（`db_export_cmds.rs:275-294`）。
- XLSX 遇一个含控制字符的单元格就整次失败，已写几十万行全部作废（`db_transfer_xlsx.rs:327-331`）。
- UPDATE 格式导出遇到一行无改动就整体 `Err`，正常页面必然存在这种行（`db_transfer.rs:962-964`）。
- 转置导出的 `rows` 报的是输出行数（= 源列数），不是数据行数（`db_transfer_cmds.rs:706-732`）。
- INSERT 脚本固定 UTF-8 且无 BOM，在 `NLS_LANG=…ZHS16GBK` 的 SQL*Plus 里重放中文乱码（`db_transfer_cmds.rs:540-549`）。
- `sql_export::render` 的列清单不加引号，而 `quote_ident` 又把 `select`、`_X` 判为 plain（`sql_export.rs:421-422`、`:184-194`）；同功能的 `db_file_export.rs:161-167` 用的是引号版。
- 关系图每类静默截断 1000 行，无提示（`db_relations_cmds.rs:19,61-64`）。
- `db_relations` 出错时返回 `{"rows":[]}`，缺 `kind/columns/ms/tx`，与 TS 声明的 `ExecResult` 不符（`db_api.ts:507`）→ 外键读取失败被显示成「没有关联」。
- `db_conn_test` 与 `db_conn_list` 的 `PROBE` 共用同一个会话键并主动销毁（`db_conn_cmds.rs:414,450`）→ 一边点测试一边初始化列表，会把对方会话强杀成 `session-lost`。

**前端状态**
- 切换连接时不清操作员列表（`dbUsers.ts:98-119`）→ A 库账号显示在 B 库面板上，据此生成错误库的改密脚本。
- 生产库「10 分钟免确认」按 `tabId` 记，不含连接 id（`dbConfirm.ts:272-290`）→ 同标签切到另一个生产库不再确认。
- 结果重排回调不校验连接归属，旧库的行会落进已切到新库的标签（`dbResultActions.ts:49-52`）。
- 内存预算裁剪把 `hasMore` 置 true，行数与总数对不上；预算耗尽时最后追加的新结果分到 0 字节，网格空白（`dbResultBudget.ts:41-57`）。
- 纯 DML 脚本跑完清空 `results`，把上一次查询结果一起抹掉（`dbActions.ts:300-327`）。
- 每次击键把整份标签写 localStorage，失败 `catch {}` 静默，此后草稿全丢（`dbStore.ts:669-673`）。
- 执行历史明文存完整 SQL（含 `identified by`、证件号字面量），每连接 500 条无脱敏（`dbHistory.ts:16-17,50-58`）。

**UI**
- 结果区最小高度 90px 装不下「结果条 40 + 工具条 36 + 底栏 30」，拖到顶时 `.dbx-rbody` 被压成 0，一行数据都看不到（`useSqlConsoleSplit.ts:4`）。

- `ComparisonGrid` 每个滚动像素写一次全局 store，整页重渲染（`ComparisonGrid.tsx:56-61`）。
- 查询设置浮层非模态却 `aria-modal="true"`，反过来让 Ctrl+K / Ctrl+1..N 全部失效（`QuerySettings.tsx:91-93` → `App.tsx:313`）。
- IDEA 键位方案下 Ctrl+Shift+F 被工作区搜索抢走，格式化永远不触发（`SqlEditor.tsx:161-168` vs `App.tsx:321-333`）。

## 四、设计缺陷（不是单个 bug，是产生上述 bug 的结构性原因）

1. **事务状态靠「首关键字猜测」，而不是问数据库。**
   整套事务条、切只读守卫、`fallback-tx` 守卫、空闲槽回收都建立在 `is_write(head)` 这个启发式上，P0-8 是它的必然产物，不是偶发。`db_engine::settle_transaction_flag` 与 `db_rust::track_tx` 两套口径已经分叉。
   建议：以 `v$transaction`（按 `sid` 过滤）为真源，关键字法只作降级；两个引擎共用同一张判定表并加对照测试。

2. **网格的「预览」与导出的「全量」共用一条取数通道。**
   网格要的是「能塞进 16MB 预算的代表性样本」，导出要的是「一个字节都不能少」。把两者都压在 `exec/more` 上，P0-1、P0-2 是结构性的，不是参数没调好。
   建议：给引擎加显式的「全量取数」命令族，导出/传输只走它；`exec/more` 明确标注为「预览通道」。

3. **一次性任务从「配置文件」复制连接参数，而不是跟随当前会话。**
   `open_temp_session` 复制 `conn`，运行期状态（schema）留在 `AppState.db_schemas` 里没人合并，P0-3 必然复发——每加一个新的「一次性任务」入口都会再犯一次。
   建议：把「连接参数 = 配置 + 运行期覆盖」收敛成一个构造函数，禁止直接拿 `DbConnConfig` 去 connect（可用 clippy 自定义 lint 或 code review 约定 + 单测）。

4. **连接收尾有两套逻辑，且 key 命名不统一。**
   `db_disconnect` 逐个 `drop_bridge` 槽 + `java_key`，`db_conn_delete` 只 `drop_bridge(id)`（P1-7）。槽键 `id#N` 与主会话键 `id` 没有统一的「按连接清除」入口。
   建议：抽出 `drop_all_sessions(state, id)`，两个命令共用，并加单测断言「删除后 `state.db` 里没有以 `id#` 开头的键」。

5. **前端没有「执行身份」抽象，靠 `executionId + slot` 组合判活。**
   P1-2、P1-3、以及「旧结果落进新连接」都源于此：任何一处状态清理漏掉一个字段，就出现永久 loading 或结果错配。
   建议：引入单一 `runToken`（含 connId、slot、代次），所有回写前只校验它；`running` 改为从当前 token 派生而不是独立字段。

## 七、列宽自适应与表头可读性（2026-11-08 18:40 批次）

### 根因
不是「估算略有偏差」，是**表头没给按钮留位置**。列名可用宽度 = 列宽 − 52px：

| 来源 | 扣掉 |
|---|---|
| `.dbx-gh { padding: 0 10px }` | 20 |
| `.dbx-gh[data-has-menu] .dbx-header-action { width: calc(100% - 18px) }` | 18（列菜单按钮） |
| `.dbx-gh .nm { max-width: calc(100% - 14px) }` | 14（排序箭头，没排序也占位） |

旧公式 `字符数 × 7.4 + 28` 只留 28px ⇒ 每个列名都少 24px 以上，`PK_HEAD` 也显示成 `pk_…`。
实测（Edge，真实渲染）：旧公式 7 个样本列名（`pk_head` / `outtranslatejson` / `creationtime` /
`billcode` / `name` / `code` / `pk_org`）**全部截断**；新公式 7/7 完整，误差 0px。

### 修法

| 项 | 内容 | 位置 |
|---|---|---|
| A 测算 | `textWidth()` 走 canvas `measureText` + 按字符串缓存；表头/单元格分开算预算（`HEADER_CHROME=52` / `CELL_CHROME=20`）；列宽 = `max(列名宽, 样本值宽)`，夹 72–420，**向上取整**；采样 50 → 200 行；超长值按 120 字符探测后封顶 | `resultView.ts` |
| A 缓存 | `initialWidths` 用 `WeakMap<rows>` 缓存（拖列宽会重算全部列宽，一次是「列数 × 200 行」次测量） | `resultView.ts` |
| B 表头 | 第二行从「有中文名才渲染」改成 `中文名 ?? 数据类型`，两行共 38px（头部 40px）；`.nm` 显式 `line-height:17px`，删掉单行居中分支 | `ResultGridHeader.tsx`、`db-console.css` |
| C 手势 | 双击列分隔线 = 本列 fit；表头右键「本列 / 全部列自适应宽度」；工具条加一行内自适应按钮；`GridColumns` 的旧按钮就此真正生效 | `ResultGrid.tsx`、`ResultGridHeader.tsx`、`ResultTable.tsx` |
| C 防呆 | 拖拽 `finish` 只在宽度真的变了才写布局——否则双击的第一下会把自动宽度固化成手调值 | `ResultGrid.tsx` |
| D1 提示 | 被列宽挤掉的值给 `title`（完整值前 500 字）；`fitsCell` 用长度下界先挡掉长文本，不进测量缓存 | `cellCodec.ts`、`resultView.ts` |

### 🔴 遗留结论
- **字体族顺序必须与 CSS 一致**（`system-ui, "Segoe UI", sans-serif`）。写成 `"Segoe UI"` 在前，
  Windows 上 `system-ui` 解析到另一个字体，同一串文本**窄 11%**（`pk_head` 49.2px vs 54.3px），
  真机上列名照样截断而本地看不出来。
- 无 canvas（jsdom）走字符类别估算（小写 7.2 / 大写 9.4 / 数字 7.6 / 中文 13.5，宁宽勿窄），
  用例断言用 `textWidth` 自身表达，不写死像素。
- 对比网格（`ComparisonGrid`）用独立的 `c.width`，不在本批次范围。
