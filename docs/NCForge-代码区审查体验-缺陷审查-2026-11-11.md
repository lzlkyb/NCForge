# NCForge 代码区审查体验 A/B/D —— 缺陷审查（2026-11-11）

> 审查对象：2026-11-10 落地的 A（改动色条/peek/单块还原）、B（时间线/多文件 diff/已审角标）、D（改动区诊断/表名核对/审查清单）。
> 方法：读回全部实现源码 + 后端 `svn_review.rs` / `svn_cmds.rs` + 现有事件源，按**真实用户操作序列**逐段走查，不跑演示用例。
> 状态：**只审查，未改任何代码**。所有条目都标了证据类型：`[源码]` 可直接引 file:line；`[复现]` 给出操作序列；`[判断]` 是交互/产品取舍。

## 0. 一句话结论

功能都"在"，但**审查闭环在真实流程里是断的**：最关键的三个动作（点「核对」、看这一轮改了哪些、标记已审）在默认使用路径下分别表现为「点了没反应」「面板是空的」「角标过几秒自己消失」。更根本的是口径错配——**代码面色条画的是「相对 SVN BASE 的全部未提交改动」，不是「AI 这一轮改了什么」**，而用户的主诉是后者。

上一轮门禁 416 文件 / 2791 测试全绿，下面这些一个都没被抓到：单测覆盖的是纯函数，缺陷全部落在「组件挂载时序」「跨模块状态口径」「真实操作序列」这三层。这不是测试写少了，是测试层根本没覆盖审查流程本身。

## 1. P0 —— 功能不可用或明确误导（建议先修这 6 条）

### P0-1 「核对」按钮首次点击完全无效 `[源码]`
- `ChangedLinesBar.tsx:27-28` 派发 `window.dispatchEvent(new CustomEvent("ncforge-review-checklist"))`。
- 全库唯一监听者在 `ChangeTimelinePanel.tsx:43-51` 的 `useEffect` 里；而该组件在 `BottomPanel.tsx:25-27, 165-169` 是 `React.lazy` 且**只在 `tab === "changes"` 时挂载**。
- `setSession({ panelOpen: true, panelTab: "changes" })` 和 `setView("checklist")` **都写在那个监听回调里**。默认 `panelTab` 不是 `changes`，所以第一次点「核对」时监听者还不存在 → 事件无人接收 → 什么都不发生。
- 附加：即使面板已挂载，若用户当前在 db / meta / patch 页，只 `setSession` 不 `navigate("files")`，底部面板在文件页，用户依然看不到清单。
- 修法：把「打开审查清单」提成模块级函数（不依赖组件挂载），派发方直接 `setSession({ panelOpen:true, panelTab:"changes" }) + navigate("files")`；`view` 提到 store 或 session，由面板订阅，别用 window 事件传 UI 状态。

### P0-2 改动时间线在用户第一次打开面板之前不采集任何事件 `[源码][复现]`
- `changeTimeline.ts:66-72` 的 `initChangeTimeline()` 全库唯一调用点是 `ChangeTimelinePanel.tsx:35` 的 `useEffect`——也就是**用户切到「改动」页签那一刻才开始订阅**事件源。
- `events` 只存内存、不落盘（`changeTimeline.ts:33`），重启即空。
- 复现（正是主诉场景）：AI 改 5 个 .java → 用户在代码面审代码 → 想看「这轮一共动了哪些」→ 切到底部「改动」页签 → 显示 `还没有改动记录`（`ChangeTimelinePanel.tsx:106`）。**之前发生的一切都已丢失**。
- 修法：`initChangeTimeline()` 移到 App 启动路径（或模块顶层），面板只负责展示；内存事件至少要能从最近一次本地历史归档点回填一轮。

### P0-3 SVN 提交 / 更新 / 还原之后基线永不刷新，色条持续误报 `[源码]`
- `changedLinesStore.ts:104-108` 的 `refreshBaseline` 全库唯一调用点是 `ChangeTimelinePanel.tsx:71`，而那次是「还原本轮」——只改工作副本内容、**BASE 根本没变**，等于唯一一次调用还用错了地方。
- 真正让 BASE 变的是 `useSvnChanges.ts:56 / 86 / 102` 的 `svnCommit` / `svnUpdate` / `svnRevert`，三者收尾都走 `rescan()`，**没有任何一处接 `refreshBaseline`**。
- 后果：提交完 r14232，代码面还画着 `+9 −4 · 相对 SVN 基线`，摘要条、清单、色条一起说谎，直到重启应用。
- 修法：在 `rescan` 成功后对受影响路径批量刷新（或订阅 `useSvnStatus` 的 revision 变化），不要依赖用户手动重开文件。

### P0-4 「标记已审」写入 revision=0，后端下一次扫描即判失效 `[源码]`
- `reviewMarks.ts:44`：`const revision = revisions.get(keyOf(path)) ?? 0`，`revisions` 只在版本控制面扫描时由 `syncReviewMarks` 填充。代码面右键标记（`TabStrip.tsx:174-175`）时通常没有这份数据 → 传 0。
- 后端 `svn_review.rs:47-48` `is_valid` 要求 `mark.revision == revision`；`valid_marks:73,80` 对**在改动列表里的文件**取扫描到的真 revision（如 14231）。`0 != 14231` → 失效。
- 讽刺的是 `valid_marks` 对「不在改动列表」的干净文件 `unwrap_or(mark.revision)` 退回 0，反而能保住——**恰好只对用户真正想标记的「有改动文件」失效**。
- 表现：右键「标记为已审」→ 角标立刻出现 → 下次 status 扫描后自动消失。设计文档里「revision 取 0 仍可用」的判断不成立，revison 维度在后端已经落地了。
- 修法：后端 `svn_review_mark` 自己从工作副本读 BASE revision，不让前端传；或代码面标记前先取一次该文件的 revision。

### P0-5 Alt+↑/↓ 全局吞键，破坏 Monaco 默认「移动行」 `[源码][复现]`
- `changedLinesGutter.ts:217-222`：每个编辑器无条件 `preventDefault() + stopPropagation()`。
- 项目自身没有占用 Alt+↑/↓（`editorActions.ts:284-294` 只有 Alt+Enter / Insert / J），但 **Monaco 自带 `moveLinesUpAction` / `moveLinesDownAction` 默认绑定 Alt+↑/↓**。
- 更糟的是 `jumpChanged`（`changedLinesGutter.ts:31-35`）在没有改动块时直接 `return`——事件已被吞掉 → 复现：打开一个干净文件，按 Alt+↑ 想上移一行，**静默无反应**。
- 修法：仅在 `snap.blocks.length > 0` 时拦截；或换成不冲突的键并给设置项。别在「AI 时代不怎么写代码」的前提下默认牺牲一个标准编辑键。

### P0-6 单块还原会用过期行号改错行 `[源码][复现]`
- `changedLinesRestore.ts:31-35` 注释说「快照之后用户可能又编辑过，所以列号必须按现在的模型算」——但**只重算了列号，`startLine/endLine` 仍是快照时刻的行号**。
- 浮层挂在 body、非模态（`changedLinesGutter.ts:64-120`），用户开浮层后仍可打字；装饰重算还有 800ms 防抖（`:29`），窗口不小。
- 复现：点色条开浮层 → 在块**前面**插入一行 → 点「还原此块」→ `applyRevert`（`:122-129`）用旧行号 `executeEdits`，改的是无辜的那一行。这是四批里唯一会写用户代码的操作，错了没有二次确认。
- 修法：还原前重算当前 snapshot，拿 `block.currentLines` 在邻域做内容校验并重定位；匹配不上就提示「文件已变化，请重新点击色条」，绝不盲写。

## 4. 流程是否最优：不是

当前真实主线：

```
AI 改文件 → 打开文件 → 代码面看满屏「相对 BASE」色条
  → 点色条看基线原内容
  → 想确认全貌：切到底部「改动」页签（大概率是空的，见 P0-2）
  → 点「比较」进底部第二层 diff 视图，换文件要点左侧列表
  → 右键标签「标记为已审」（文件级，且过几秒会消失）
  → 点「核对」看清单（首次点击没反应，见 P0-1）
```

三个断点，都不是实现细节，是结构问题：

1. **审的对象错位**。色条回答「这个文件相对 SVN 服务端差多少」，用户要的是「AI 刚才动了哪几处」。NC 现场工作副本本来就脏，这个口径下色条越准越吵。
2. **审的动作要离开代码面**。行业把「看 → 判断 → 接受/拒绝/标记 → 下一处」压在同一屏；我们把「看」放代码面、「全貌」放底部时间线、「逐块比较」放底部第二视图，来回横跳，而用户明确说了编辑区是最高频界面。
3. **没有「审到哪了」**。只有无差别的「下一处改动」，审过的不会跳过；20 处改动按 20 次，没有进度感，也没有块级状态。

### 建议的目标流程（不推翻 A/B/D，补一层「轮」作为主轴）

```
时间线选中一轮（或自动识别最近一轮外部写入）
  → 代码面色条收敛到「这一轮」的改动（基线 = 该轮前的本地历史归档点，可切回 SVN BASE）
  → Alt+↓ 跳「下一处未审改动」（不是下一处改动）
  → peek 浮层内直接完成：标记此块已审 / 复制给 Claude / 还原此块 / 下一处
  → 摘要条显示「2/3 块已审」，该轮全审完才提示去看清单
  → 清单按「该轮文件范围 + 该轮改动区诊断」生成，不再混全会话
  → 时间线 ↔ 代码面双向联动：点轮滚到首处改动，点色条反查属于哪一轮
```

三个增量都不需要新后端：① 基线可切换（SVN BASE ↔ 归档点，本地历史已存原字节、GBK 安全）；② 块级 `reviewed` + 跳转过滤；③ 时间线选中态与代码面共享一份 store。这才是把「审 AI 代码」的体感做出来的部分，A/B/D 只是铺了地基。

## 5. 建议修复顺序

1. **先修 P0 六条**（多为小改动，且互相独立）：事件接线提前、按钮改直接调函数、commit/update/revert 后刷基线、revision 由后端取、快捷键加条件、还原前行号校验。这批不修，功能在默认路径下就是坏的，谈体感没意义。
2. **再修清单口径**（P1-5 / P1-6 / P1-7）：按当前轮取范围、空态不假绿、去掉常态误报、编译错误放开到「本轮文件」而不只是当前文件。否则清单会被当噪音。
3. **最后上「轮 ↔ 代码面联动」**：基线切换 + 块级已审 + 双向定位。这是差异化，也是唯一直接对准主诉的一层。
4. P1-2（非 .java）、P1-3（两点比较）、P1-4（还原确认）按现场反馈排，不阻塞主线。

## 6. 门禁为什么没抓到

2791 个测试全绿是有原因的：本轮新增单测集中在 `computeChanged` / `revertEdit` / `changedProblems` / `changedTables` / `changeTimeline` / `reviewNotes` 这些**纯函数**，而 P0 六条里有五条是「组件是否挂载」「事件监听是否早于事件派发」「两个模块的状态口径是否一致」「后端 revision 语义」。建议补三类回归：① 挂载时序测试（未打开「改动」页签时派发事件，断言 session 与视图）；② 一次完整操作序列的集成测试（改文件 → 提交 → 断言色条归零）；③ 后端 `valid_marks` 与前端 `markReviewed` 的契约测试（revision 0 必须被拒绝或由后端补齐）。
