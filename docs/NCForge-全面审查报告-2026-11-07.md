| 级别 | 数量 | 构成 | 判定口径 |
|---|---|---|---|
| **P0** | 5 | 退出链路 4 + 事务放行 1 | 可造成未保存内容或未提交事务不可逆丢失 |

| 合计 | 49 | — | — |

三条主线：

1. **点 X 是当前最主要的数据丢失入口，且是一组竞态叠加而不是单点疏漏。** `quit_cmds.rs` 的 `quit_checking` / `quit_acked` / 5 秒计时器由三个互不协作的异步写者操作；`quitGuard.ts` 把「检查不可用」与「没有问题」混为一谈；`db_pending_tx` 总 deadline 把已成功的探测结果一起丢掉。四条路径单独看都"有兜底"，组合起来能绕过整个守卫。
2. **未提交的数据库重构接线完整（无残留 import、新组件均已渲染、slot/primary 分流一致），但把状态校验放在了循环外。** 后端 `may_have_transaction` 只在「执行成功且恰好是小写 commit/rollback」时清除；前端 `previousResults` / `executionId` / `txNotice` 新增了多条跨连接写回路径，却只有切连接与循环前的一次校验，缺 epoch。
3. **界面问题不是"不好看"，而是若干条 CSS 声明实际未生效、若干控件在最小窗口下不可操作。** Error Lens 三级诊断色因 token 类型用错被浏览器整条丢弃；玻璃材质只覆盖 9 个样式文件；控件高度有十档、断点有十余档、系统缩放与触屏命中区零适配；600px 高窗口下编辑器被 chrome 挤到约 100px。

## 2. P0 — 立即修

### P0-1　退出确认框未决时再点一次 X，5 秒后强退，未保存文件与未提交事务全部丢失

- **位置**【复核】：`desktop/src-tauri/src/commands/quit_cmds.rs:56-78`（`:56 swap(true)` 连点闸、`:60 quit_acked.store(false)`、`:71-77` 计时器）；`quit_cmds.rs:87-95`（`quit_check_acked` 只置 ack、`quit_cancel` 只复位 checking）；`desktop/src/lib/quitGuard.ts:117-120`（`inFlight` 早退）、`:196-198`（`finally` 才复位）。
- **具体表现**：第一次点 X → 前端 `:133` 发 `quit_check_acked`（`quit_acked=true`）→ 弹确认框，前端 `inFlight=true` 一直保持到流程结束。5 秒后计时器 T1 因 ack 不强退，但 `:77` 在 `if` 块**之外**无条件把 `quit_checking` 置回 `false`。此时确认框仍开着，用户以为没响应再点一次 X → `swap(true)` 通过 → `:60` 把 `quit_acked` 重置为 `false` → 第二次 emit → 前端 `inFlight` 仍为 `true` 直接 `return`，**不重发 ack** → T2 五秒后看到 `quit_acked=false` → `app.exit(0)`。
- **影响范围**：全局。Monaco 未保存 model、全部连接（含独立会话槽）的未提交事务；Oracle 会话随进程结束隐式回滚；无任何提示。
- **触发条件**：确认框打开超过 5 秒后再点一次 X。「点 X 没关掉就再点」是常见行为，不是极端路径。
- **建议方案**：把退出改成一轮一 id 的状态机——`begin_quit_check` 生成递增 `round_id`；计时器只在 `round_id` 仍匹配且 `!quit_acked` 时强退；`quit_acked` 本轮置位后不再重置；`quit_checking` 只在 `quit_cancel` / `app_quit` / 强退三处复位；强退前发一个可观测事件或落日志。前端 `quitGuard` 收到重复 `app:quit-request` 时应重发 `quit_check_acked` 而不是静默 return。
- **优先级**：P0，第一批。

### P0-2　「未保存文件检查不可用」被当成「没有未保存文件」，三条路径直接放行

- **位置**：`desktop/src/lib/quitGuard.ts:137-144`（空 catch 后 `files=[]`）；`desktop/src/lib/saveAllDirty.ts:84-87`（`if (!tab || !isUnsaved(tab)) { saved.push(f.path); continue; }`）；`desktop/src/lib/terminatePreflight.ts:49-59`（`required=false` 时 `return true`）；`desktop/src/hooks/useProjectSwitch.ts:53`（切工程调用点）；对照 `terminatePreflight.ts:49` 已有不依赖 Monaco 的静态 `isUnsaved`。
- **具体表现**：① 退出时动态 `import("./saveAllDirty")` 的 chunk 加载失败 → 整个未保存分支被跳过 → `app_quit`；注释「编辑器模块没起来时不可能有编辑中的文件」不成立，tab/model 是模块级 `workspaceSession`/`editorStore` 状态，与该 chunk 可独立存在。② 批量保存期间标签被关闭或会话被 `applyWorkspace()` 清空 → `!tab` 被计入 `saved`，弹框显示「已保存 N 个文件」，内容随 model dispose 丢失。③ 切工程时 `required` 默认 `false`，检查失败直接 `return true`，`switchWorkspace.ts:37-49` 随即清空 `tabs`。
- **影响范围**：代码页编辑内容；退出、切工作区、安装更新三条路径。
- **触发条件**：打包异常 / Vite HMR 中断 / 磁盘或权限问题 + 存在脏标签；批量保存与切工作区并发。
- **建议方案**：先用静态 `isUnsaved` 扫 `getSession().tabs` 做兜底；只要静态判定有脏标签而 `collectUnsaved` 失败，一律 `quit_cancel()` + 明确报错，不区分 `required`；`saveAllDirty` 把 `!tab` 计入 `failed`（原因「标签已关闭，内容未保存」）；批量保存期间对会话加只读快照或操作锁。
- **优先级**：P0，第一批。

### P0-3　`emit("app:quit-request")` 失败即直接放行退出

- **位置**【复核】：`quit_cmds.rs:61-66`。
- **具体表现**：`window.emit` 返回 `Err` → `quit_approved=true` + `return false`（`false` = 不拦关窗）→ 窗口关闭 → `RunEvent::Exit` → 进程退出。前端收不到事件，未保存检查与 `db_pending_tx` 事务确认整条链路被跳过。
- **影响范围**：全局，用户零提示。
- **触发条件**：webview 事件通道异常、窗口正在销毁、emit 序列化/发送失败。
- **建议方案**：emit 失败时保持窗口（返回 `true`）并给出降级可视提示；不要用 `quit_approved=true` 一键跳过守卫。注释里「别把用户关在应用里」的权衡没有把「静默丢数据」计入代价，建议改写成三态（可确认 / 确认不可用 / 已批准），只有第三态放行。
- **优先级**：P0，第一批。

### P0-4　退出时 `unknown` 事务被完全跳过，用户选「提交」却一条都没提交

- **位置**：`desktop/src/lib/quitGuard.ts:180-187`（`for (const r of rows.filter((x) => x.kind === "pending"))`）；`quit_cmds.rs:147-164`（`timeout(...).await.unwrap_or_default()` 整体超时返回空 Vec，所有连接补成 unknown）；对照 `terminatePreflight.ts:109-115`（重启路径对同样的 rows 会逐会话处理并中止）。
- **具体表现**：任一连接把 `db_pending_tx` 拖过 3 秒总 deadline → 已成功返回的 `pending` 结果随 `unwrap_or_default()` 一起丢弃，全部标 `unknown` → 用户在确认框选「提交」→ `filter` 后循环体一次不执行 → 直接 `app_quit` → 全部隐式回滚。界面呈现「已选择提交并退出」。
- **影响范围**：生产库 / 多连接；同一份 rows 在「重启」路径会被拦住，退出路径却放行，口径相反。
- **触发条件**：连接探测超时、bridge 卡住、连接已断。
- **建议方案**：对每个 future 单独 timeout 并保留逐项结果（或用 `FuturesUnordered`）；`unknown` 行必须明确告知「这些连接无法提交，退出后将被回滚」并二次确认；把退出与重启的事务处理收敛成同一函数。
- **优先级**：P0，第一批。

### P0-5　事务状态探测失败一律放行，关标签/切连接静默回滚

- **位置**【复核】：`desktop/src/lib/dbConfirm.ts:180-195`——
  `try { tx = (await dbApi.tx(connId, "status", slot)).tx; } catch { return true; }`。
- **具体表现**：注释 `:178` 写的是「槽已经没了（空闲回收 / 连接断开）时直接放行」，但 `catch` 吞掉的是**全部**错误：IPC 超时、bridge 忙、SQL 异常、权限不足都被当成「没有事务」。同仓 `terminatePreflight.ts:102-105` 探测失败一律 `return false`，`quit_cmds.rs:224-228` 探测失败标 `unknown`，只有这一处放行。
- **影响范围**：数据库写入，关 SQL 标签 / 切连接 / 断开三条路径。
- **触发条件**：网络闪断、后端忙、桥进程异常，且槽里存在未提交的 `update`。
- **建议方案**：按结构化错误码白名单放行（仅 `slot-not-found` / `session-closed` / `already-disconnected`）；其余保守 `return false` + toast，或弹「事务状态未知，是否仍要关闭」三选一框（复用 `QuitRow.kind="unknown"` 展示）。
- **优先级**：P0，第一批。

## 7. 布局优化方案

### 7.1 当前布局问题（基于截图与源码实测）

`light-classic-normal.png`（约 1080×608）显示的是一条**七层横向带状结构**：顶栏 → rail → 资源管理器 → 主区顶部工具条 → 文件标签条 → 编辑器 → 底部 SVN 行 / 面板标签 / 状态栏。

- **垂直空间被 chrome 吃掉约 198px**：顶栏 40 + 分组工具条 36 + 文件标签 36 + 底部状态行 28 + 面板标签 32 + 状态栏 26。600px 高窗口正文只剩约 400px；把底部面板拉到 65%（`workbench-layout.css:44` 允许 390px）时编辑器只剩约 104px，`light-classic-low.png` 里文件树只显示到 File11。
- **水平空间 274px 给导航**：60px rail + 210px 资源管理器 + 4px 手柄，占 1080 宽的 25%；≤650px 时侧栏改 overlay 抽屉（`light-classic-narrow.png` 盖住主区约 60%），`.wb-resize-x{visibility:hidden}` 让宽度完全不可调。
- **顶栏塞了 10+ 个元素**：品牌、更多菜单、工程选择、`clamp(230px,32vw,440px)` 全局搜索（1080 宽占约 32%）、4~5 个图标、3 个窗口控件；窄窗口只能把搜索框压成一个放大镜。
- **状态栏一行 8 项**：路径、轻量模式、工程关联、NC 服务、隐藏面板、文件状态、编码、行列，全用 `●` 分隔，主次不分。
- **两个"面"的建模不干净**：`.wb-file-tabs`（`workbench-layout.css:70`）注释自称「文件标签条是代码面的第一行」，实际装的是 `EditorGroupTools`（`FilePaneSlots.tsx:171-173` 的执行/分组工具条），真正的文件标签在 `TabStrip.tsx:173` 并 portal 到 `wb-code-body`。按注释去改样式会改错层；`index.css:858-866` 的 `.app-shell` 定义又被 `workbench-layout.css:205` 覆盖，是死代码。
- **浅色下分隔线几乎不可见**：`--border` 与白卡约 1.33:1，截图里资源管理器与主区之间、工具条与编辑区之间缺少边界，只能靠背景色差分辨。

### 7.2 信息层级

现状是「每层都有可点控件、没有主任务区的视觉锚点」。建议收敛成三层：

| 层 | 应该放什么 | 现状问题 | 调整 |

## 8. 复核后排除或降级的结论（避免把推断写成漏洞）

1. **`security/path.rs:41-68` 新建路径 remainder 的符号链接逃逸 —— 排除，不列为漏洞。** 仓库已有实测回归 `junction_cannot_escape_allowed_root`（`security/path.rs:263-350`），注释明确写「三条断言都来自实测，不是推断」：目标存在的 junction 被 `parent.exists() → canonicalize` 解掉、真实路径落在根外即拒绝；悬空 junction 解析层虽放行，但 `create_dir_all` 在链接目标处失败，字节落不下去；目标一旦被建出来，解析立刻转为拒绝。本次未重跑该测试，但不把「能绕过」写成结论。**保留一条加固建议**：对 remainder 中已存在的部分用 `symlink_metadata` 显式拒绝 reparse point，让解析层本身也拒绝，不必依赖下游写失败。
2. **`canonicalize_roots` 的 fallback（`security/path.rs:12-17`）—— 从「安全 P0」降级为「跨平台可用性 P1」。** 后果是所有合法路径被误判为不在白名单（`Access denied`），不是逃逸。已列入 P1-7。
3. **「数据库页同时出现两套标签条」—— 排除。** `workbench-layout.css:3` 的 `.app-shell [hidden]{display:none!important}` 兜住了 `.wb-code-surface{display:flex}` 的覆盖风险；db 页 `ToolTab` 因 `custom:true` 返回 `null`（`ToolTab.tsx:18`），`DbDocTabs` portal 落在文档面内。未找到能同屏的路径。但 `.wb-file-tabs` 命名与注释不符属实，保留为 P2 维护陷阱（见 7.2）。
4. **自动编译重试计数不复位导致永久停摆 —— 排除。** `autoCompileQueue.ts:88` 的 `queueAutoCompile` 确实会 `retries = 0`。
