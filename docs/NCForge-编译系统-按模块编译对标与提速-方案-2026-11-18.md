## 0. 结论先看

**基础设施已经齐了，缺的不是「再换一个构建引擎」，而是三件事：**

1. **make 语义**。手动「编译本模块」目前**始终整模块全量**（`compile_cmds.rs:336-337` 注释原话：「用户点它就是不相信产物是最新的」），且**不处理依赖模块**。IDEA 的 Build Module 是增量 make + 递归 make 依赖；Eclipse 保存即增量。我们改一个方法体也要重编几百到 2000+ 个文件，这是「按模块编译慢」的第一来源。
2. **模块依赖图没有成为一等公民**。真实 NC 工作区是**单根 `.classpath`**（223 个 src 条目），模块没有自己的 `.classpath`，`module_deps` 推出来是**空的**（`build_engine.rs:1000-1002` 注释已承认）：拓扑分层实际是一整层，「按依赖顺序」实际是 classpath 声明顺序。跨模块引用边（import/同包/通配）已经存在，但只用于「补编引用方」，没有用于 make 编排与下游失效。IDEA/Eclipse 之所以能按模块又快又准，前提是它们有**显式模块依赖图**（`.iml` / `.classpath` 工程引用）；我们没有，必须自己从源码派生——原料（`workspace_types` 类型索引 + `SourceDeps`）都已存在。
3. **两个精度洞**。
   - **字符串常量内联**：`abi_fingerprint` 先 `strip_comments_and_literals`（`build_state.rs:428-429, 483-531`），`public static final String X = "a"` 改成 `"b"` 指纹不变 → 引用方不重编 → ecj/javac 内联的旧常量留在引用方字节码里，运行期才炸。Eclipse 比对新旧 class、JPS 的 `FieldRepr` 记录 ConstantValue、Gradle 明文规定常量变更后下一轮不走增量——三家都把常量当危险类，我们漏了。
   - **增删文件一律整模块全量**（`build_state.rs:813-821`）。Eclipse 把新增类型入队增量编译，只有引用方受影响；我们新建一个类就全模块重编，日常开发频繁新建类，这是第二速度税。

**修复路线（已定案）**：不给源码 ABI 解析器打补丁——传播触发器改为**新旧 class 结构 diff**（Eclipse/JPS 路线）。已核实：本地 `desktop/src-tauri/resources/ecj/ecj-3.17.jar` 自带 `org/eclipse/jdt/internal/compiler/classfmt/ClassFileReader`（含 FieldInfo/MethodInfo），常驻桥加一个命令即可，零新依赖；常量、private 常量、注解等整类近似 bug 一起消失。详见 §3.4。

**对标一句话**：IDEA = 脏文件范围 + **产物字节码级**反向依赖 + 多轮 differentiate + 模块 make（递归依赖、独立模块并行、依赖变更可令下游整模块重建）；Eclipse = 常驻构建器 + 资源 delta + 队列 + **新旧 class 结构比对** + 编译器记录的 build state；Gradle = **ABI 快照** compile avoidance + 字节码类依赖增量。共同点：**增量单位是「受影响的编译单元」，模块只是编排单位；依赖数据来自编译器/字节码，不是源码文本猜测**。我们的源码文本近似是过渡形态，P0 起按定案退役，触发器换成 class 结构 diff（§3.4）。

**分三期**：P0 把语义做对（make 化 + 下游失效 + class 结构 diff 触发器 + fixture 级差分门禁），P1 把精度做够（派生模块图持久化 + 增删增量 + 内容哈希 + 差分门禁扩到真实模块），P2 只做测量与触发项。ecj 3.17 批编译 + 常驻 worker 的构建真源地位**不变**（2026-11-06 定案，重估触发条件未满足）。

## 2. 对标：他们怎么做到「又快、又能按模块/项目编译」

### 2.1 IntelliJ IDEA（JPS，源码就在 GitHub：`JetBrains/intellij-community`，master，2026-11-18 抓取核对）

**用户可见契约**（[官方帮助：编译与构建](https://www.jetbrains.com/help/idea/compiling-applications.html)、[Compiler 设置](https://www.jetbrains.com/help/idea/compiler.html)，2026.3 帮助）：

- Build = make：「只编译变化的类，并**递归编译这些类的依赖**」；Build Module 会**把依赖模块一并构建，从依赖最少的模块开始递归**。
- Rebuild = 清输出 + 全量（「Clear output directory on rebuild」）。
- 「Build project automatically」：保存/自动保存/**VCS 更新**后自动编译。
- 「Compile independent modules in parallel」：无相互依赖的模块并行，Enable/Automatic 两档。
- 「**Rebuild module on dependency change**」：依赖变了的模块**整模块重建**——这是 IDEA 给跨模块失效的粗粒度保底档。

**内部机制**（以下符号均对抓取源码核对）：

- 脏范围：`DirtyFilesHolder` + `FSOperations`（时间戳/FS 事件）；删除/移动的类在首轮先把依赖方标脏（`JavaBuilderUtil.markDirtyDependenciesForInitialRound`）。
- 每轮编译后做 **differentiate**：`Mappings.differentiateOnIncrementalMake(delta, removedPaths, filesToCompile, compiledWithErrors, allCompiledFiles, allAffectedFiles, filter)` 算出新增受影响文件 → `FSOperations.markDirty` → **再编一轮**，直到稳定（`JavaBuilderUtil.updateMappings`，`additionalPassRequired`）；diff 判定不可增量 → **整 chunk 标脏全量**。
- 依赖数据来源是**产物字节码**：`dependencyView/ClassfileAnalyzer` 用 ASM `ClassReader/ClassVisitor` 读编译出的 class，生成 `ClassFileRepr`；字段表示 `FieldRepr` **携带 ConstantValue**（`new FieldRepr(..., value)`，源码 :464-466）——常量值变更能被结构 diff（`Difference`）抓到。javac 的 AST 引用（`JavacFileData`/`JavacRef`）也同时登记。
- 更精的「编译器反向引用索引」（`JavaBackwardReferenceIndexWriter`，`jps.backward.ref.index.builder`）**默认关**、且仅 javac 可用；新一代统一 `DependencyGraph`（`GlobalOptions.DEPENDENCY_GRAPH_ENABLED`）也**默认关**。即 IDEA 的默认档 = 字节码结构 diff + 多轮传播，不是 AST 级精确图。
- 循环依赖模块合成 `ModuleChunk` 一起编；执行用进程内 javac（`JavacMain.compile`）或 fork 的 `ExternalJavacManager`（**空闲进程保留 2 分钟**复用）；ecj 是可选编译器（非 javac 时 `setProcessConstantsIncrementally(false)`，反向引用索引禁用）。

**对我们的启示**：① make 语义（增量 + 递归依赖）是「按模块编译」的正解，全量只留给 Rebuild；② 依赖/结构数据最终要落到**产物 class**上，源码文本是近似；③ 跨模块失效要有保底档（我们对应「传播解析不出 → 下游全量」）；④ 常驻 + 有界并行我们已有，不重复建设。

### 2.2 Eclipse JDT（[AOSA《Eclipse》章](https://aosabook.org/en/v1/eclipse.html) §6.1.2；[官方 Java Builder 文档](https://help.eclipse.org/latest/topic/org.eclipse.jdt.doc.user/concepts/concept-java-builder.htm)）

- 构建器**常驻 IDE 进程**；保存触发资源 delta（新增/修改/删除）。
- **队列模型**：变更/新增类型入队 → 逐个编译 → **新 class 与旧 class 比对结构变化**（改签名、增删方法等）→ 有结构变化就把**所有引用它的类型**入队（引用关系来自 build state，由编译器在历次编译时记录）→ 循环到队空；删除的源文件删对应 class。
- build state 持久化，重开工作台后恢复（[IBM JDT FAQ](https://m.ibm.com/docs/zh/rational-soft-arch/9.6.1?topic=reference-frequently-asked-questions-jdt)：关闭时保存内部状态到文件）。
- 工程依赖：required projects 先构建（autobuild 沿 `.classpath` 工程引用传播）。

**对我们的启示**：① 增量单位 = 受影响编译单元，**新增类型也走队列**，不是全工程重编（直接打脸 G5 的保守策略）；② 结构比对发生在**真实字节码**上，常量天然覆盖（G4 的正解方向）；③ 引用关系由**编译器解析**记录，同包/通配/隐式引用不会漏——我们的文本边是它的近似，必须保留「宁可多编 + 解析不出就全量」的退路。

### 2.3 Gradle（[Java Plugin 官方文档](https://docs.gradle.org/current/userguide/java_plugin.html)，v9.9.1，2026-11-18 抓取）

- **Compile avoidance**：依赖工程 ABI 兼容变更（方法体、注释、private 成员、资源、参数改名、jar 改名）→ 下游编译任务 **UP-TO-DATE**，不重编。
- **Incremental compilation**：affected = 变化的类 + 传递依赖它的类；类依赖来自**字节码类型引用或编译器插件符号分析**；分析结果缓存在工程目录并进 build cache。
- 明文保守规则：source-retention 注解变更 → 全量；**编译出错后或 Java 常量变更后，下一轮不走增量**。

**对我们的启示**：① 「下游要不要重编」由 **ABI 快照**决定，不是 mtime——我们的 `classpath_fp` 应逐步纳入上游产物的 ABI 摘要（P1 模块图的边数据）；② 常量变更被单列为危险类，与 G4 互证；③ 内容快照（哈希）避免 touch 白编（G7）。

### 2.4 GitHub 上的「轻量化」路线

- **vscode-java / Theia / Che**：构建与诊断都走 jdt.ls（Eclipse JDT 构建器装进 LSP 服务器，[redhat.java](https://marketplace.visualstudio.com/items?itemName=redhat.java)、[VS Code Java FAQ](https://code.visualstudio.com/docs/java/java-faq)）。**我们已实测否决**：真实 NC 工作区导入 152s、全量 autobuild 12 分 22 秒，且不认 `nc.uap.mde.library.container/*`（2026-11-06 定案）。轻量壳 + 重内核，在 7000 jar 规模下不轻。
- **BlueJ / DrJava / jGRASP** 等教学轻量 IDE（[综述](https://zhuanlan.zhihu.com/p/635158069)）：面向小规模工程，编译 internals 公开资料少，**没有可对标 NC 规模的证据**，不作为参照。
- 真正可研读的开源「轻量 IDEA」构建系统就是 **JPS 本身**（§2.1 全部源码可查）——本方案的机制对标以它和 JDT 为准。

### 2.5 四条共同结论

1. **增量单位是受影响的编译单元；模块是编排单位，不是编译单位。**
2. **依赖与结构数据来自编译器解析或产物字节码**；源码文本近似只能作过渡，且必须配「宁可多编 + 不确定就全量」。
3. **模块 make = 显式依赖图 + 递归 make 依赖 + 下游失效**；NC 没有显式图，就要自己派生并持久化。
4. **常驻暖编译器 + 有界并行 + 持久化构建状态**是标配——我们已具备，差距不在基础设施。

## 3. 目标设计

### 3.1 命令语义（对齐 IDEA，保留现有入口）

| 命令 | 现语义 | 目标语义 |
|---|---|---|
| `compile_module`（编译本模块） | 始终全量、不管依赖 | **make**：先递归 make 本模块引用的工作区模块（Auto，能跳就跳，失败 blocked），再 Auto 编本模块；无清单/配置变化仍全量 |
| `rebuild_module`（重新编译本模块） | 清理 + 全量 | 不变（= IDEA Rebuild，用户的「我不信产物」出口） |
| `compile_all_modules` | Auto、无跨模块传播 | make all：真实模块图分层 + **层间 ABI 传播**（§3.3） |
| `compile_file` / 保存自动 / 空闲增量 | 快速 + 传播 | 不变 |

UI 文案与日志沿用「为什么全量/跳过」的 reason 机制（已有），make 化后主按钮旁保留「重新编译本模块」下拉（已有）。**不加新开关**：make 是默认行为变更，靠日志可解释 + rebuild 出口兜底。

### 3.2 派生模块依赖图（补 G6，原料全部已有）

- 边定义：模块 X 的源文件引用的**外部类型**（显式 import、同包点名、通配 import 按包）→ 经 `workspace_types`（FQCN → 模块）落到声明模块 Y → `X → Y`。提取逻辑复用 `compile.rs` 的 `extract_imports`/`extract_dotted_chains` 与 `build_state::SourceDeps`，不另写一套正则。
- 持久化：每模块清单（`Manifest`，schema +1）记录「外部引用类型集合」与「依赖模块集合」；读不出/版本不对 → 当没有图，编排退化为现状（单层 + classpath 顺序），**图是优化不是正确性前提**（沿用账本三纪律）。
- 刷新：watcher 已对源码改动 `mark_dirty`（`workspace_types.rs`），类型索引增量刷新后图随之更新；不为建图全树重扫（7000 文件机械盘十几秒的教训已写在 `workspace_types.rs:32-34`）。
- 环：沿用 `topo_levels` 的「环内剩余放最后一层」，同层共编（借 JPS `ModuleChunk` 思路，现有代码已覆盖）。
- 用途：① `compile_module` 的递归 make 闭包；② `build_all` 真实分层（并行终于有真实边）；③ 下游失效（§3.3）。

### 3.3 跨模块失效（补 G3，两档组合）

- **精确档（默认）**：`build_all` 每层编完，收集本层有结构变化（class diff 判定，§3.4）模块的 changed 文件，对**下游模块**复用现有 `propagate_abi`/`cross_module_groups`（`build_engine.rs:972-1034`，已在空闲路径验证过）。
- **保底档**：上游 ABI 变了、但下游模块「解析不出类型名」（`cross_module_groups` 现在直接跳过，注释原话「空闲增量宁可漏编」）→ 在 build_all 语境**不允许漏**：该下游模块强制 Full。这等价 IDEA「Rebuild module on dependency change」的保守精神，但只在解析不出时触发，不做粗粒度默认（否则 2000 文件模块 routinely 全量）。
- 传播仍守 30% 阈值（超了整模块，现有口径）。

### 3.4 传播触发器：class 结构 diff（补 G4，取代源码 ABI 指纹）

**定案（2026-11-18）**：不给 `abi_fingerprint` 打补丁——手写 Java 声明解析器的近似 bug 补不完（常量之后还有 private 成员、注解、泛型细节）。改为 Eclipse/JPS 路线：**「签名变没变」在真实字节码上判定**。

**资产（已核实）**：本地 `resources/ecj/ecj-3.17.jar` 清单含 `org/eclipse/jdt/internal/compiler/classfmt/ClassFileReader.class`（30,829 字节）与 `FieldInfo`/`MethodInfo`——ecj 自己的字节码结构读取器，与编译器同一 jar，语义天然对齐；常驻桥（`NcEcjBridge`）已存在。

**机制**：

1. 桥新增 `struct` 命令：输入 class 文件路径，输出结构摘要 JSON（层次、成员签名 + 访问修饰、字段 ConstantValue、注解）。契约测试进现有 `scripts/ecj-bridge-contract.test.mjs`。
2. decide() 改**两轮模型**（Eclipse 队列 / JPS 多轮 differentiate 的等价物）：
   - 第一轮编译**前**，对变更文件**预读旧 class 结构摘要**（ecj 会覆盖输出目录里的旧 class，必须在编译前读；只读变更文件，量小）；
   - 第一轮只编变更文件 → 读新 class 结构 → 与旧摘要 diff；
   - **无结构变化**（只改方法体）→ 结束，不传播；
   - **有结构变化** → 现有 `referrers` 文本边找引用方（模块内 + 跨模块 `propagate_abi`）→ 第二轮编译；引用方自己结构再变 → 继续传播，**多轮直到稳定**；30% 阈值、解析不出 → 全量，不变。
3. 结构变化定义（保守，宁可多编）：层次变化；public/protected 成员增删/签名变化；**字段 ConstantValue 变化不论访问修饰**（private 常量会被 nest 内联）；注解任何变化。
4. **找引用方仍用文本边**——Eclipse 用编译器记录的精确引用，我们没有；class diff 替换的只是触发器，不是反向索引。字节码级反向边仍是 §5 触发项。
5. **退役与迁移**：`SourceStamp.abi`/`abi_stale` 由 class 结构摘要哈希取代（schema +1，与 §3.2/§3.6 同批）；`compile_files` 的 `preserve_abi` 双阶段逻辑相应改为「单文件编译标待 diff、空闲增量补 diff」；`abi_fingerprint` 及其调用点（`decide`、`changed_against_manifest`、`source_stamp`）一并退役。
6. **回退**：桥不可用 / `struct` 失败 → **按有结构变化处理**（宁可多编），绝不静默跳过传播；第一轮有错误 → 不传播、不更新清单（现有纪律）。
7. **反例门禁（先红后绿）**：String 常量、private 常量 + 内部类引用、数字常量三组必须传播；方法体改动必须**不**传播；签名改动必须传播。

> **实现修订（2026-11-18）**：第 2 条的「编译前预读旧 class」改为**清单存基线**——
> `SourceStamp.struct_fp` 保存上次成功编译的结构指纹；保存快速编译（`preserve_struct=true`）
> 沿用旧指纹并标 `struct_pending`，空闲增量编完 pending 文件后与清单基线 diff。
> 预读方案要在 ecj 覆盖产物前抢读磁盘旧 class，时序脆弱且每次保存多一轮 IO；
> 清单基线在 schema 2 里天然持久，语义等价（基线 = 上次成功编译的结构）。
> 任一侧指纹未知（桥失败 / 新增文件 / 旧清单无指纹）一律按结构变化处理（宁可多编）。

> **审查修订（2026-11-19）**：实现后代码审查发现并修复三处漏编 / 漏记：
> ① 跨模块传播把「做过结构传播的模块」整体 skip，同轮一起改、互相内联常量的
> 两个源模块之间的边被吞掉（先编的一方带着对方旧常量）。改为种子分 intra / fresh
> 两类、按种子归属模块过滤：intra 只排除归属模块的模块内引用方，跨模块边照常成立。
> ② `build_one` 只报「源码变的」文件当跨模块种子，漏掉模块内传播里「源码没变但
> 内联常量被连带更新」的引用方（S→R→T 链里 T 漏编）。种子改为源码变的 ∪ 结构变的。
> ③ 保存后空闲增量不写构建历史，统计口径缺这一块。补 `append_history`。
> 三处均有先红后绿反例：双源互引 / 三跳链进 `结构传播反例门禁_live`（旧语义断言
> 确实漏边 + 新语义产物与全量逐字节一致），归属过滤进 `cross_module_groups` 单测。

**代价**：多一轮暖态 JVM 往返（24~54ms/轮，变更文件通常 1~5 个，可忽略）；全量路径只对「相对旧清单变更的文件」做 diff（先 stat + 哈希过滤），不是全部产物。

### 3.5 增删文件增量（补 G5，借 Eclipse 队列）

- 新增：编新文件 + 其**同包/通配 import 引用方**（现有 `referrers` 边已按包过度连边）；解析不出 → 仍全量。
- 删除/改名：清对应产物（现有 `stale_classes` 机制）+ 编引用方；解析不出 → 全量。
- 30% 阈值与「ABI 不确定就全量」退路不变。

### 3.6 内容哈希（补 G7）

- `SourceStamp` 加内容哈希（schema +1，与 §3.2 同批迁移）；mtime/size 变但哈希同 → 不算 modified。哈希只在 stat 命中后读文件时顺带算（decide 的 ABI 分支本来就要读文件），不新增全树读。

### 3.7 差分门禁（正确性验收，前序方案 §9 已点名；**fixture 级前移到 P0**，作为 make 化的退出条件）

- P0：fixture 级「增量产物 == 全量产物」；P1 扩到抽样真实模块。class 字节比对；ecj 参数已钉死 `-1.8 -g -nowarn -proc:none -preserveAllLocals`，M0 已验证与 Eclipse 产物字节级对齐，具备比对前提。
- 常量/增删/SVN touch 三组反例进回归矩阵（P2-12 横切矩阵的编译切片）。

### P0：把「按模块编译」做对（正确性优先）

退出标准（真机）：
- 改一个方法体 → 编译本模块只编 1 个文件，**不传播**（diff 判无结构变化），依赖模块 Skip（日志可见 reason）。

- fixture 差分门禁绿；`struct` 失败注入 → 宁可多编，不静默跳过。

退出标准（真机，perf-baseline 现有 `PERF ` 前缀机制扩条目）：
- 模块 make p50、build_all（无变更）≈ 扫描 + 指纹成本、build_all（单模块签名变更）下游传播文件数正确，三组数进基线。
- 新建一个类 → 不再整模块全量（fixture 与真实模块各验一次）。

> **实测（2026-11-19，真实工作区 `C:\work\aier\newar`，探针 `模块make速度_live` / `传播扇出探针_live`）**：
> - **make 热路径 p50**（保存→单文件编译→struct 判定，常驻 worker）：可单独编过的候选全是 1 文件模块，medsoprc 569 / platform 395 / ufoc 621 ms。比纯单文件编译（~400ms）多 ~150ms = struct 判定成本。**大模块端到端 make 未实测**（缺兄弟依赖编不过），需完整工作区探针。
> - **无变更扫描**（decide→Skip，只读，cp/cc 桩掉类路径指纹）：bc 1 文件 13ms / riamm 21 文件 53ms / ic 994 文件 978ms，**约 1ms/文件线性涨**。这是大模块 make 与 build_all 无变更的前置成本，真实命令还要加类路径指纹。
> - **传播扇出**（文本边 `referrers_of_names` 跨全部源，9 个抽样类型）：**中位 1、最大 9（logmanagervo，跨 4 模块）、零个触 30% 整模块**。
> - **结论**：精度（文本边→精确反向图）**不是速度瓶颈**——扇出本就极小，精度省的绝对量可忽略；且干净对齐不可行（字节码反向图漏常量内联，需已否决的进程内编译图）。**大模块 make 慢的主因是 decide 全模块扫描（~1ms/文件），不是精度**。速度真要优化，治扫描（增量 stat / 缓存 stamp）比治精度划算。第三组「签名变更下游传播文件数」与「大模块端到端 make」仍待完整工作区探针。

> **扫描提速 P1+P2 已实现（2026-11-19，治「decide 全模块扫描」这条瓶颈，非上文精度 P1）**：
> - **P1 增量 stat（`compile_dirty.rs` 纪元脏集注册表）**：监听脏集 + 前端 `compile_incremental` 路径注入喂 `mark`；每模块全扫成功后 `baseline` 记当前纪元，下次 `decide_with_hint` 在「基线纪元 == 当前纪元」可信时只 stat 脏路径（`decide_incremental`，含增/删/改），否则回落全扫。溢出/重扫/监听出错/`invalidate` → 纪元 +1 → 全模块基线作废，杜绝「A 基线了让全局可信、B 没扫」的漏编。设置页可见开关「编译判定只查改动文件」（`incremental_stat`，默认开，本机持久化、不进导出）。
> - **P2 有界并行扫描（`scan_with`）**：`std::thread::scope` 按 `div_ceil` 分块，≥128 文件用 4 线程否则串行，结果按 `collect_sources` 排序保序，与串行字节一致（回归 `并行scan与串行结果一致`）。
> - **实测（同工作区，`模块make速度_live` 无变更回路同时测全扫与注册表路径）**：ic 994 文件 decide 全扫 **1159ms → 注册表增量 1ms（约 1000×）**；bc 11→0ms；riamm 54→0ms。`PERF module-nochange-incr` 进 perf-baseline 基线通道（target:null，只记数不判过）。
> - **正确性反例**：`脏集增量全流程_基线后只查脏文件_溢出回落`、`不可信回落全扫抓全部`、`信任边界`、增/删/改各一例；监听 `Err` 回调由「只 log」修成置 `lost`（触发回落），`compile_incremental` 主动注入路径不依赖监听事件时序（idle 窗可能滞后 2.5s）。
> - **验证链**：Rust 1374/0、clippy/fmt/源码体量 44/44 绿、live 5/5、前端全量 vitest 590 文件 4417 例全过、BuildSettings 6/6、bindings 重生成干净。**未提交**（待用户「提交」）。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| 文本边漏编（反射、`Class.forName`、隐式同包） | 静态手段三家 IDE 也覆盖不了反射；保留「宁可多编 + 解析不出全量 + 30% 阈值」，差分门禁兜底；运行期问题靠现有热替换/重启链路 |
| make 化改变用户预期（「点编译=全量」） | 日志 reason 可解释 + rebuild 出口保留 + 无清单仍全量；发版说明写明语义变化 |
| 建图/刷新成本（7000 文件、机械盘 + 杀毒） | 复用 `workspace_types` 缓存与 watcher 标脏，禁止每次构建全树重扫；图读不出退化为现状 |
| schema 迁移 | 旧清单自动作废走全量（现有纪律），一次性成本 |
| class diff 扩大传播面 | 注解变化保守算结构变化（宁可多编）；反例门禁 + 30% 阈值防失控 |
| `ClassFileReader` 是 ecj 内部 API | 版本已钉死 3.17（与编译器同一 jar）；升级 ecj 需重验，现有 `compiler_fp` 失效机制覆盖 |
| 旧 class 预读时机（ecj 会覆盖输出） | 第一轮编译前读旧结构；读失败 → 按有结构变化处理，宁可多编 |
| 桥协议变更 | `struct` 命令契约测试 + 不可用回退；`compile` 命令行为不变 |
| 并行/内存压力 | 上限 1~4、默认 2 不变；worker 池上限 4 不变（BSOD 史） |
| 共享树并行会话 | 实施按 AGENTS.md 门禁链（rust-gate + 前端 scope），提交前实时复核归属 |

## 7. 验收矩阵（关键项）

| # | 场景 | 预期 |
|---|---|---|
| 1 | 改方法体后点「编译本模块」 | 只编该文件；依赖模块 Skip；日志 reason 齐全 |
