# NCForge 代码区审查体验对标与方案（2026-11-10）

> 用户原话：「现在都是 AI 时代，写代码可能很少了，最重要的是审查 AI 的代码，编辑区域看代码是最常用的了，要把这一个体感做的最好，看看行业是怎么做的，还有开源社区怎么做的，给我方案。」
> 本文为对标与方案；**2026-11-10 用户已拍板批次与顺序，实施状态见 §7 / §11**。
> 调研来源：Cursor / VS Code Copilot / Zed / JetBrains 官方文档与帮助（2026-11-10 检索），aider / Cline / Continue / difftastic 开源项目文档与评测；NCForge 现状逐条有 file:line 证据。

## 1. 结论（TL;DR）

**我们的审查闭环是断的，而且断在最常走的那一步**：AI（远程 Claude Code 经 cc-bridge）改完文件，人想「看看它改了什么」，必须离开代码面、切到「版本控制」面、在左栏逐个文件点开 diff。代码区本身没有任何「这一行被改过」的提示——M2 规划过「改动行左侧色条，点击可看原内容或单块还原」，至今没有落地（`grep glyphMarginClassName` 全书签与断点，无改动装饰）。

行业在 2026 年已经收敛到一套明确范式：**diff 先行、逐 hunk 接受/拒绝、每轮一次 checkpoint、审查状态可见、批注能回流给 AI**（Copilot working set、Zed Review Changes、Cursor checkpoint、JetBrains per-iteration review）。开源社区给出两条可借鉴的机制：**Cline 的 shadow-git 快照**（每次工具调用一个可 Compare/Restore 的点）和 **aider 的「一次改动一次提交 + 作者标注」**（用版本历史当归因）。

但**不能照抄**：NC 代码在 SVN 不在 git（aider 的 git 归因不迁移）；我们的本地历史已经比 shadow-git 更强（存原字节、GBK/混合换行安全、20 版/文件）。真正该抄的是**交互范式**，该用自己家底的是**机制**。

方案分四批，全部本地、无 AI 服务、不碰数据库读写语义：

| 批 | 内容 | 性质 | 依赖 |
|---|---|---|---|
| A | 代码区改动可见性：基线色条 + 下一处导航 + peek 原内容 + 单块还原 | 纯前端，已有后端能力 | 无（M2 欠账） |
| B | 改动时间线（我/外部二分类归因）+ 多文件 diff + 已审进代码面 | 前端为主 | 无（复用 `onExternalJavaChanged`） |
| C | AI 会话归因增强 + 「复制给 Claude」暂存区 | 只读跟读 audit.log | cc-bridge（可降级） |
| D | 改完即验：改动区编译错误 + 表名/字段核对 + 补丁审查清单 | NC 杀手锏 | 后端小改 |

**建议先做 A**（2–3 天，把最断的一环补上），B 是 A 的自然延伸，D 是竞品抄不走的差异化。

## 2. 先把「审 AI 代码」拆开：审查闭环的六个问题

用户的工作流是既定事实（`docs/NCForge-多期规划-方案设计-20261027.md` §1：AI 走远程 Claude Code + cc-bridge，工作台本身不跑 AI）。人打开工作台审 AI 改的代码，实际在问六个问题：

| # | 问题 | 现在的答案 | 成本 |
|---|---|---|---|
| Q1 | AI 改了哪些行？ | 切到版本控制面，逐文件看 diff | 一次审查切面 N 次 |
| Q2 | 这一处原来长什么样？ | diff 面里有；代码面没有 | 切面 |
| Q3 | 这块不要，只退这一处 | 只能整文件 SVN revert，或本地历史整版恢复 | 丢好代码 |
| Q4 | 哪些改动是 AI 的、哪些是我自己的？ | 无答案（本地历史只有时间+大小） | 只能靠记忆 |
| Q5 | 改得对不对（编译得过吗、表名字段对吗）？ | 编译默认自动开、问题面板可跳；表名核对是 M7 欠账 | 部分可用 |
| Q6 | 这里不对，怎么让 AI 知道？ | 无（「复制给 Claude」是 5.2 未做项） | 手工复制粘贴 |

Q1–Q3 是**纯阅读体验**，竞品做得最成熟也最该先补；Q4 是归因；Q5 是我们的护城河；Q6 是回流。

## 4. 对标：行业与开源社区怎么做

### 4.1 交互范式（五家收敛度最高，2026-11 文档实证）

| 范式 | Cursor | VS Code Copilot | Zed | JetBrains（Junie/Air） |
|---|---|---|---|---|
| **diff 先行** | Cmd+K 左右对比，Esc 拒/Enter 受；生成中实时 diff，方向不对点 Stop | Chat 里点文件开 diff；pill 显示文件数+统计 | 面板显示改了哪些文件、几个、多少行 | 每轮回复带文件清单（文件数/+−），Review 从第一个文件开始逐个过 |

| **会话/归因** | 对话时间轴 | 按 harness 分会话跟踪 pending edits；cloud session 走 PR | 线程标题、follow the agent | session 列表带改动统计 |

### 4.2 开源社区的机制（可迁移的思想）

| 项目 | 机制 | 对我们的意义 |
|---|---|---|
| **Cline**（61.8k★） | shadow git：每次工具调用后把工作区快照进**独立影子仓库**；对话里每个 checkpoint 带 Compare（开 diff）/ Restore（文件/任务/两者） | 「一轮改动一个可 Compare/Restore 的点」——我们已有本地历史（原字节、更安全），缺的是**把归档点组织成「轮」并给 Compare 入口** |
| **aider**（40k★） | 每次改动一个 commit，author 标注 `(aider)`；`/diff` 看自上次消息以来的全部改动；`/undo` 精确撤最后一次 | 「一次改动一次记录」让 diff 和 undo 都精确。**但依赖 git——NC 代码在 SVN，不迁移**；可迁移的是「归因写进记录本身」 |
| **Continue** | Edit 模式：选中代码 → 指令 → **行内 diff 流式出现**，逐条或全部 accept/reject（Ctrl+Alt+Y/N） | 单文件小改的审查就在原地发生，不开第二视图 |
| **difftastic** | tree-sitter 语法感知 diff：忽略格式噪声、识别移动的代码块；语法错误/超大文件自动回退行级 | Java 重构噪声的解法。**但引入解析器引擎成本高**，见 §6 的轻量替代 |

### 4.3 明确不采纳的部分（对齐产品边界）

- Cursor Agent Review / Bugbot、Copilot code review、JetBrains Group with AI / Recap / Insights：都是 **AI 审人**。命中 14 项不做里的「AI 助手」，**不做**。用「编译 + 规则核对」承担同一职能（见批次 D）。
- Cursor/Cline 的 shadow-git 快照引擎：我们的本地历史已覆盖且更强（原字节、编码安全），**不引入第二套快照机制**。

## 5. NC 专属超越机会（竞品没有，也抄不走）

1. **编译即审查**。竞品的验证闭环是通用 lint/test；我们的是 ecj 3.17 增量编译（单文件 3–13 秒、与 Eclipse 产物 377/379 字节一致）且**默认开启**。把「改动区内的编译错误」单独呈现，AI 改坏的文件一眼可见——这是把 M3 的家底变成审查体验。
2. **表名/字段核对**。AI 写 NC 代码最高频的错误就是表名、字段名、字段长度（M7 规划未做）。改动行命中 `md_*` 表名/字段 → 悬停展示测试库真实结构；出包前核对存在性与长度。**注意边界**：这是「代码引用的表结构核对」，不是 14 项不做里的「表数据 diff」。
3. **补丁清单即最终审查单**。按 `.class`/`.java` 配对、SQL 是否带上、编码异常集中列出——领域审查，竞品不存在对应物。
4. **归因不靠 AI 协议**。`onExternalJavaChanged`（外部写入，已排除本人保存）+ `isRecentLocalSave`（本人保存）**现在已经能把「AI/外部改的」和「我改的」分开**。零协议依赖即可做二分类归因；cc-bridge audit.log 只是增强（见批次 C）。
5. **编码安全是竞品的盲区**。GBK 81%、混合换行 2.2%、18% 无结尾换行（多期规划 §附 C 实测）——色条、时间线、单块还原全部走**原字节口径**（本地历史存原字节、`svn_diff` 回传 `encoding`/`eol`，`lib/svn.ts:63-72`），竞品在这一步会直接坏掉。
6. **异常栈 → 改动行**。日志异常点击跳源码（已有）+ 「跳到下一处改动」（批次 A）组合：AI 改完重启出事，一键定位到它改的那行。

## 6. 缺口 → 方案映射（含 A/B 取舍）

### 批次 A：代码区改动可见性 + 单块还原（P0，纯前端，约 2–3 天）

**A1 基线改动色条**。打开的文件相对 SVN 基线（pristine）计算行级 diff，在行号槽右侧画窄条（新增/删除两色，直接复用版本控制面现有 diff 配色，不新造色板）。

- 数据链全部现成：`svnDiff(path)` 已回传 `baseText`/`workingText`/`encoding`/`eol`（`lib/svn.ts:63-72`，`:146`）；行级 diff 算法已现成（`lib/textDiff.ts:26-45`，带公共前后缀裁剪，4000 行/侧上限）。
- 挂点：`lib/` 新文件 `changedLines.ts`（纯函数：base+current → 变更行区间，可单测）+ `changedLinesGutter.ts`（快照 → Monaco 装饰，仿 `bookmarkGutter.ts:21-65` 的结构），在 `EditorPane.tsx:117-121` 旁边挂载。
- **口径（写进注释，避免后人改错）**：色条 = diff(SVN 基线, **当前编辑器模型内容**)——即同时覆盖已保存与未保存改动；未纳入版本控制的新文件整篇算新增；超过 `textDiff` 上限（4000 行/侧）不画并给一句提示，与 `heavy` 降级（`lib/largeFile.ts:9`）口径一致。
- 重算触发：打开/切文件、保存后、该文件的外部改动事件（`onExternalJavaChanged`）、模型内容变化防抖 800ms；按路径缓存，输入没变不重算（仿 `compileMarkers.ts:43-61` 的 lastInput 手法）。

**A2 下一处/上一处改动**。代码面内导航，不跳面（建议 Alt+Down / Alt+Up，避开 F3 搜索命中）。

**A3 peek + 单块还原**。点色条 → 该行旁浮层显示原内容与「还原此块」；还原 = 把该 hunk 的新侧行区间替换回基线旧侧内容（写进编辑器 buffer，用户保存后落盘）。必须自绘浮层（要放按钮，不能用 Monaco hover）。

**A4 摘要**。编辑区工具行显示「本文件 +A −B · 相对 SVN 基线」，未提交才显示。

> **A 批两个待定项（建议默认前者）**：
> ① 色条形态：**行号槽窄条**（`linesDecorationsClassName`，VS Code SCM gutter 同款，不挤代码宽度——NC 中文注释密集，行背景会挡看代码）vs 行背景着色。
> ② 交互入口：**点色条出浮层**（轻）vs 右侧常驻「改动」侧栏（重，与批次 B 合并考虑）。

### 批次 B：改动时间线 + 多文件 diff + 已审进代码面（P1，前端为主，约 3–4 天）

**B1 「改动」时间线**。底部面板加一个页签（挂点现成：`PanelTabs.tsx:8-9` 的 `PANEL_NAMES`/`ORDER` + `workbenchLayout.ts` 的 PRIMARY/SECONDARY），内容 = 三类事件的按时间合并：

| 事件 | 来源（已存在） | 徽标 |
|---|---|---|
| 本人保存 | `lib/localSaves.ts` | 「我」 |
| 外部写入（AI/更新/别的编辑器） | `onExternalJavaChanged`（`externalJavaChanges.ts:29-41`） | 「外部」 |
| 本地历史归档点 | `captureLocalHistory`（`localHistory.ts`） | 版本号 |

这就是穷人版 checkpoint + 归因：不需要 cc-bridge、不需要 shadow-git，把已经存在的事件流组织成「轮」。

**B2 任选两个时间点 → 多文件 diff**。把 `SvnDiffEditor` 从单文件比较器扩成多文件容器（**改造而非新写**：复用它的 `createViewModel`/`retireModels` 生命周期，`SvnDiffEditor.tsx:17-24`、`:111-146`，那套 worker 释放顺序是踩过的坑），左侧文件清单、右侧当前文件 diff，与版本控制面同行为。

**B3 「还原本轮」**。对选中时间点之后的本地历史版本批量恢复（本地历史逐文件恢复已支持，批量 = 循环 + 进度；后端恢复前会自动归档当前内容，`localHistory.ts:41-47`，可再退回来）。

**B4 已审进代码面**。标签页角标 + 「标记为已审」，与版本控制面共用同一份数据（`svnReviewMark`/`reviewedSet`，`lib/svn.ts`）；**文件再被改自动失效**（对齐 VS Code 语义，这是 G5 的正当行为，不是 bug）。

> **B 批待定项**：多文件 diff 用 ①改造 `SvnDiffEditor` 成容器（推荐，生命周期坑已踩过）vs ②新写 multi-diff 编辑器（VS Code 式，工作量大一倍）。

### 批次 C：AI 会话归因增强 + 「复制给 Claude」（P2，约 2–3 天，可降级）

计划内 5.2（多期规划 §5.2：cc-bridge 联动）的**只读**子集，且**不做成硬依赖**——B1 的二分类归因已覆盖 80% 场景，C 只是加分。

- **C1 会话级归因**：只读跟读 `%APPDATA%\com.ccbridge.desktop\audit.log`（JSONL，已确认可只读跟读）→ 文件打「AI 改过」徽标，与 B1 时间线按时间窗对齐，把「外部」细化成「AI · 某次会话」。

## 9. 风险与口径（实施前必须知道）

1. **`svn_diff` 全量回传两份全文**。几千行 Java 约 100–200KB，IPC 本身可接受，但**不能每次输入都算**：按路径缓存 + 防抖 + lastInput 比较（仿 `compileMarkers.ts:43-61`）；>4000 行/侧直接不画。验收卡「重算 < 200ms」。
2. **色条与「异地修改」横幅的关系**。二者不互斥：色条永远相对 SVN 基线（含未保存与外部改动），横幅照旧提示磁盘被改。未保存 + 外部改的场景以「基线 vs 编辑器内容」为准，不引入第三种口径。
3. **单块还原会覆盖编辑器里该块的当前内容**。浮层里明示「将把这一块恢复为基线内容，编辑器里这一块的未保存改动会丢失」；hunk 内混有本人未保存改动时二次确认。
4. **本地历史上限可能挤掉关键版本**。每文件 20 版 / 总计 512MB（`HistoryPanel.tsx:158`）是按「人保存」频率设计的；高频外部改动（AI 连改多轮）下，B 批要评估「外部改动版本至少保留 N 版」或提高单文件上限。
5. **多文件 diff 复用 `retireModels` 的 worker 释放顺序**（`SvnDiffEditor.tsx:17-24` 的注释是踩坑记录），改造时不许简化掉 `waitForDiff()` 那一步。
6. **工程约束**：新文件 ≤300 行、useState+useEffect ≤8（`.ts` 同扫）；色条/时间线各自独立文件 + hook，别塞进 `EditorPane.tsx`；组件测试 mock `workspaceSession`/`editorStore`。
7. **EOL 口径**：Monaco 模型是 LF 归一的，`svn_diff` 回传 `eol`；色条按行号映射，不按字节偏移——混合换行文件（2.2%）行号仍对齐，但浮层里展示原内容要用基线原文（含原行尾），避免「看着一样、存进去变了」。

## 10. 验收判据（每批次交付前自测）

**批次 A**
- 打开一个被外部改过的 `.java`：1 秒内出现色条；Alt+Down 逐处跳；点色条浮层显示基线原内容；「还原此块」后保存，该 hunk 与基线一致、其余改动保留。
- GBK 文件色条行号与编辑区显示一致；2000+ 行文件不掉帧（重算 < 200ms）；>4000 行不画且有提示；无基线（新增文件）整篇算新增且不报错；未纳入 SVN 的目录打开不崩。

**批次 B**
- 外部改 3 个文件 → 时间线出现一条「外部」记录（带时间与文件列表）；选两个时间点出多文件 diff；「还原本轮」后 3 个文件回到上一时间点。
- 标签页标记已审 → 版本控制面「只选已审」能看到它；该文件再被外部改 → 已审自动失效。

**批次 C**
- 选 3 行 → 复制的 Markdown 带 `file:line` 与代码块；audit.log 不存在/不可读时全部功能静默降级，无报错弹窗。

**批次 D**
- AI 改出编译错误 → 错误只出现在改动行（不改动的旧错误不重复出现）；改动行引用测试库不存在的表 → 悬停/清单明确提示；补丁清单正确标出缺 `.class` 配对或缺 SQL 的项。
