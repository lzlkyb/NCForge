## 0. 一页结论

**做什么**：一个默认关闭的设置。打开后，在 jdt.ls 冷启动的 3~6 分钟窗口期里，
Ctrl+点击先用**常驻 ECJ 编译内核**做真 binding 解析（继承成员、精确接收者、同名消歧），
答不上再退回现有链路（声明索引 → 内容搜索）。jdt.ls 就绪后 resolver 自动退场。

**为什么现在能做**：基建全部就位——常驻 Java 桥模式（`ecj_worker.rs` + `NcEcjBridge`
行协议 + `java_bridge::Bridge`）、ECJ 在 1.8.0_202 上跑通的实测（9.06s / 7524 文件）、
索引格式 v3（源码侧成员带行号）、jar 反查与 `jdt://` 反编译链路。

**代价**：开关打开期间额外一个常驻 JVM（`-Xmx768m`，懒起 / 空闲 120s 自退 / 就绪即退），
单查询首次秒级、热后百毫秒级（S0 已量：首次 3.9s 热缓存 / 82.9s 冷缓存，热查询目标靠
**自持 LookupEnvironment 跨查询**达成，见 §6.1 归因）。

**总工期**：约 2 天，四步（S1 已砍，见 §6.2），**S0 探针是止损门（已过判定：朴素路线不过关，
按预案走自持环境路线）**。

> **2026-11-21 晚用户拍板改 C 路线**（S0 数据触发，记录在 §6.2）：放弃「索引摘要 NDJSON 当
> `INameEnvironment` 答案源」，改为**自持 ECJ `LookupEnvironment` + 内置 `FileSystem` 直读
> 真实源根**。原 NDJSON 是为绕开「每查询重读源码」；持久化环境后源码只读一次、绑定全缓存，
> NDJSON 收益消失，只剩代价（导出 ~7790 条摘要、合成二进制类型、init 后编辑会答旧位置）。
> 连带影响：**S1（v4 extends）整体砍掉**，设置文案里「首次触发索引重建 30s」一句删除。

## 1. 架构

```
Ctrl+点击（窗口期，jdt.ls 未就绪）
   │
   ▼
provideDefinition ──ctx 为 null──▶ lightDefinition
                                      │
                                      ├─ ① lang_fast_definition（声明索引，微秒级）──有结果──▶ 打开
                                      │        （空）
                                      ▼
                                      ├─ ② lang_binding_resolve（★ 新，开关开才问）
                                      │        常驻 ECJ：自持 LookupEnvironment 跨查询
                                      │        + FileSystem（154 真实源根 + 1204 jar 并集）
                                      │        ──有结果──▶ 打开
                                      │        （空 / 超时 / 进程不在）
                                      ▼
                                      └─ ③ searchDeclarations（内容搜索兜底）──现状不变
```

**为什么插在 ① 之后**：① 是微秒级本地二分，② 首次可能秒级。② 的价值是接住
「索引答不上」的场景（继承成员、接收者推不出、同名歧义）——这些正是真 binding 的强项。
「索引答错」② 接不住（有结果就不会问②），那是启发式固有边界，由行号自愈兜底。

**开关在后端判**（命令入口读 `AppConfig`），前端不判：常驻 JVM 的代价判断放一处，
避免「前端缓存旧配置 / 别的调用点漏判」把 JVM 拉起来。

|---|---|---|

## 3. 协议（照 `NcEcjBridge` 的行协议，id 必须是字符串）

```
→  id \t init \t <argsFile>        argsFile：每行一个 classpath 条目（154 源根 + 1204 jar + 167 类目录）
→  id \t resolve \t <argsFile>     argsFile：{"path":"…","offset":123}（offset = UTF-16 code unit）
→  id \t invalidate \t <argsFile>  文件已保存：作废该文件相关绑定（防陈旧），argsFile 每行一个路径
→  id \t quit
←  {"id":"N","ok":true,"data":{…}}
←  {"id":"N","ok":false,"code":"timeout|oom|other","detail":"…"}
```

`resolve` 的 data：
`{"kind":"method|field|type|local","fqcn":"nc.vo.pay.AggPayBillVO","name":"getCode",
  "line":42,"jar":"pubarap_paybill.jar"?}`

- `fqcn` + `name` + `line` → Rust 查 `decl_index.find(fq)`（源码）或 `method_line`（成员行）；
- `jar` 非空 → `pick_jar` + `jdt://` URI（复用反编译链路，**不预建 model**，与现状一致）；
- 泛型/数组绑定先 `getErasure()` 归一；
- `kind=local` → 目标就是本文件（`#局部名` 命名约定，走 `fixed_member_line` 同款校正）。

⚠️ **跨查询缓存（S0 已实测，结论：必须自持，无备选）**：`ASTParser` 每次 parse 新建
`LookupEnvironment` ⇒ 每查询固定过路费 ~515ms（随环境规模增长，最小环境仅 2ms）；
ASTParser 实例复用第 2 次起**静默失败**（返回无绑定 AST）。⇒ `BindingResolver` 用 ECJ
内部编译器 API 驱动：**一个 `LookupEnvironment` 跨查询存活**。S2a 实测（§6.3）：
冷查询 1024ms（闭包构建 57 类型，只付一次）、跨文件 39ms、CU 缓存命中 0ms，
继承案例 10/10 PASS，peakHeap 138MB。

`invalidate` 的实现语义 = **`le.reset()` + 清 CU 缓存**（reset 清 knownPackages ⇒
全部已注册类型不可达；FileSystem/classpath 配置保留）。不能只摘单文件：残留的
SourceTypeBinding 会让变更后的同文件撞 `The type X is already defined`（§6.3 坑 5）。
代价是下次查询冷走全流程（~1s），窗口期保存少见，可接受。

## 4. 生命周期

| 事件 | 行为 |
|---|---|
| 第一个窗口期查询到达（开关开） | 起进程 + `init`（classpath 用**影子工程同一份 jar 并集**，不重跑 `select_jars` 95s） |
| 空闲 120s | 发 `quit` 自退（省内存） |
| jdt.ls `ServiceReady` | 主动退场——它唯一的使命就是窗口期（后端退，不依赖前端）。**✅ 已接线（2026-11-21）**：`lang_cmds.rs::on_notification` 的 `ServiceReady` 分支调 `bind_resolver::shutdown()`（代数门之内，旧会话的通知不会误杀新会话的 resolver） |
| 查询超时（5s） | 杀进程，该次回退内容搜索；**不**原地重试 |
| 连续失败 | 指数退避 30s→10min（仿 `Holder.failures/retry_at`） |
| 进程崩溃 / 协议错 | 杀，下次查询重起；stats 计数 |
| 文件保存（`notifyLangSaved` 既有路径） | 发 `invalidate <path>`：`le.reset()` + 清 CU 缓存，下次查询冷走全流程（~1s，S2a 实测）。窗口期编辑少，宁可重读也不答旧位置。**✅ 已接线**：`fileSave.ts` 在 `notifyLangSaved` 后并排调 `notifyBindingSaved`（同款 fire-and-forget + 开关门，不 await） |
| 关软件 / 切工作区 | 显式 `shutdown`（挂 `stopLang` / `quitGuard` 既有路径）。**✅ 已接线（2026-11-21）**：`app_lifecycle::shutdown`（Holder 是进程级 static 永不 drop，不显式杀会留孤儿 JVM）+ `workspace_cmds::set_workspace`（spawn_blocking，不依赖 env_key 懒换代）；契约由 `shutdown_无条件调用是无害noop` 单测钉住 |

`-Xmx768m`：懒 resolve 只碰该 CU 的传递闭包，不是全量；爆堆回 `oom` 帧 → 杀 + 退避。

### 6.1 S0 实测结论（2026-11-21 晚，探针已跑完）

环境：本机 1.8.0_202，`-Xmx768m`，**影子工程同一份 classpath**（154 源根 + 1204 jar / 526MB + 167 类目录），
案例 CU `ct/src/private/nc/bs/ct/aier/daily/AierPrintCtDailyBO.java`（GBK）offset 892 = `getBaseDAO()`，
真相 `BaseSignCtDaily.java:77`。

| # | 场景 | wall | 峰值堆 | 判定 |
|---|---|---|---|---|
| 1 | 冷页缓存 + 全新 JVM（首次查询） | **82.9s** | 78MB | ❌ 其中 ~79s 是 526MB jar 的磁盘读 |
| 2 | 热页缓存 + 全新 JVM | **3.9s** | 76MB | ⚠️ 勉强在 5s 超时内 |
| 3 | 热查询，每查询新建 parser | **1.25~1.33s** | 155~263MB | ❌ 目标百毫秒级，差 13x |
| 4 | 场景 3 + 4 线程 I/O 施压（模拟 jdt.ls 冷导入抢盘） | **2.5~2.7s** | 246MB | ❌ 差 25x |
| 5 | 零闭包地板（合成 CU，全环境，新建 parser） | 517ms~1.06s | 78~160MB | 归因用 |
| 6 | 最小环境（1 源根 / 0 jar / 无 boot，合成 CU） | 374ms 冷 / **2ms 热** | 63MB | 归因用 |
| 7 | 复用同一 parser 第 2 次起 | 1~20ms 但**绑定为 null** | — | ❌ 不可用 |
| 8 | 继承成员案例（8 次查询全量断言） | 全部 PASS | — | ✅ |
| 9 | 内存（`-Xmx768m`） | 峰值 263MB | — | ✅ 装得下 |

**三条归因（都指向同一个对策）**：

1. **每查询固定过路费 ~515ms，且随环境规模增长**：全环境新建 parser 的热查询 517ms，
   最小环境只要 2ms。这笔钱花在 ECJ `FileSystem` 每次建环境时对 1371 条 classpath 的处置上，
   **持久化 `LookupEnvironment` 只付一次**。
2. **ASTParser 复用第 2 次起静默失败**（返回无绑定的 AST，1~20ms 假快）⇒ 「每查询新建 parser」
   不可省，只能连环境一起自持（即风险表预案「自持 NameEnvironment 包装」）。
3. **冷启动是延迟/CPU 主导，不是吞吐主导**：4 线程施压读 jar 并集可达 ~197MB/s 聚合，
   而冷查询只从 3.9s 劣化到 4.1s。⇒ 风险表第 2 行「与 jdt.ls 抢盘」对**首查询**影响小，
   对**热查询**约 2x（1.3s→2.6s），而持久化后热查询是毫秒级，此风险基本消失。

**止损门判定**：朴素「每查询新建 parser」路线**不过关**（热 1.3s vs 目标百毫秒）；
正确性与内存过关。按 §7 风险表既定预案继续 ⇒ **S2 必须自持 NameEnvironment/LookupEnvironment
跨查询**，S0 数据支持这条路（预期热查询落到百毫秒内）。

**S0 同时推翻了一个设计前提，已由用户拍板（2026-11-21 晚）**：§3 的「索引摘要 NDJSON 当
`INameEnvironment` 答案源」原是为绕开「每查询重读源码」。持久化环境后源码只读一次、
绑定全缓存，NDJSON 的收益基本消失，只剩代价：导出 ~7790 条摘要、合成二进制类型、
以及**快照陈旧**（init 后编辑窗口期文件 ⇒ 答案可能过期）。

### 6.3 S2a 实测结论（2026-11-21 深夜，探针 persist 模式）

判据（§6 S2 行 / §9 item 11）：**自持环境热查询 ≤200ms 且继承案例持续 PASS**。实跑
`RESOLVE_PROBE_PERSIST=1 REPEATS=5`（同一份影子工程 classpath：154 源根 + 1204 jar/526MB + 167 类目录，`-Xmx768m`）：

| 查询 | wall | 结果 |
|---|---|---|
| r1 AierPrintCtDailyBO（冷，环境预热 + 闭包构建） | **1024ms** | PASS：`kind=method name=getBaseDAO declaring=nc.bs.ct.aier.daily.BaseSignCtDaily binary=false params=0 decl=BaseSignCtDaily.java:77`——与 S0 ASTParser 路线逐字一致 |
| r1 SyntheticProbe（第二个文件，闭包已热） | **39ms** | PASS：`kind=var name=a` |
| r2–r5 两文件（CU 缓存命中） | **0ms**（<1ms） | 持续 PASS，10/10 轮 |
| 闭包规模 | **57 个类型**（源 + 二进）即稳定，不再增长 | 与文件数无关，只跟被解析类型的可达闭包有关 |
| peakHeap | **138MB** | 低于 S0 的 263MB（S0 每查询新建环境，闭包反复重建） |

**判定：过。** 热查询比 200ms 门低一个量级；冷查询 1024ms 与 S0 的 ASTParser 冷查询
同级（同一件事：构建类型闭包），只付一次。

**实现级踩坑记录（产品代码必须照抄，全部 javap 反汇编 + 实测坐实）**：

1. **源根要混进 `FileSystem` 的第一个参数**（classpathNames）。`sourcepathNames` 构造参数
   **不参与类型查找**——`findType` 只遍历 `classpaths` 数组（ASTParser 的 `getClasspath`
   也是把 sourcepaths 经 `Main.processPathEntries` 塞进同一个列表）。顺序照 ASTParser：
   boot(rt.jar) → 源根 → jar/类目录（源优先）。漏了这条 ⇒ `BaseSignCtDaily cannot be
   resolved`，继承链全断、ECJ 只能 recovery 出假绑定（declaring 指向本类）。
2. **`completeTypeBindings()` 必须无参版**。单参 `completeTypeBindings(CUD)` 只做
   `checkAndSetImports` + `connectTypeHierarchy`，**从不解析类型**。无参版才驱动
   units 三循环（imports → 类型层级 → 字段/方法签名）+ 闭包注册。
3. **`LookupEnvironment` 构造器的 `ITypeRequestor` 不能传 null**。`askForType` 找到
   源/二进制类型后回调 `accept`，null 直接 NPE。闭包生长全靠它：源类型
   `dietParse` + `buildTypeBindings`（注册进 `le.units`），二进制类型
   `createBinaryTypeFrom`——照抄 `Compiler.accept` 的流程。
4. **`cud.resolve()` 才是语句级绑定**。完整每单元流程：
   `parse` → `buildTypeBindings` → `completeTypeBindings()` → `unitBeingCompleted=cud`
   → `getMethodBodies`（全解析过的单元直接返回）→ `scope.faultInTypes()`
   → `scope.verifyMethods(methodVerifier)` → **`cud.resolve()`**。缺最后一步
   `MessageSend.binding` 全 null（类型签名有了、语句绑定没有）。
5. **同一文件重复 `buildTypeBindings` 撞 `The type X is already defined`**——新 CUD 的
   绑定全变 problem binding。⇒ **CU 缓存是硬需求**（不是可选项）：同文件未变更直接
   复用首次解析的 CUD（绑定已在），文件变更才重走全流程。这也正面解释了 S0 观察到的
   「ASTParser 复用第 2 次起静默失败」同源病。
6. DOM 与内部 compiler API 的 `ASTVisitor`/`ASTNode` 单类型 import 撞名 ⇒ 内部侧一律
   全限定名；内部 `ASTVisitor` 没有 `visit(TypeReference, BlockScope)`（抽象类），只有
   `SingleTypeReference`/`QualifiedTypeReference` 等具体子类重载。
7. **`OffsetFinder` 必须同时重载 `BlockScope` 与 `ClassScope` 两套 `visit`**（2026-11-21
   S2 落地坐实）。`ASTVisitor` 按 scope 静态类型重载解析：extends/implements 子句走
   `ClassScope`，语句级与方法签名全走 `BlockScope`（`MethodScope` 是其子类；
   `AbstractMethodDeclaration.traverse` 是空方法，实现在 `MethodDeclaration.traverse`）。
   只重载一套 ⇒ 漏一半节点，「点继承来的成员」这种核心场景正好落在漏掉的那半。
8. **`QualifiedNameReference` 要逐 token 归属**，不能按整链返回 binding（2026-11-21
   合成冒烟抓到）：只取整链 binding 会把点 `label` 判成接收变量 `p`。正确做法 =
   `sourcePositions` + `indexOfFirstFieldBinding` + `otherBindings` 定位 offset 落在
   哪个 token，取其 binding。推论：`Parent.TAG` 点 `TAG` 回 field；点 `Parent`（类型名）
   没有 per-token 绑定 ⇒ 回 null 交回内容搜索（Rust 侧 `resolver_live` 单测钉住）。
9. **offset 口径**（前端 Monaco → Java resolver，2026-11-21 落地坐实，`lang_binding_cmds.rs`
   单测钉死；2026-11-22 审查补第 4 条）：
   - **解码规则按 Java 侧**：UTF-8 严格试（`CodingErrorAction.REPORT`，malformed 与
     unmappable 都报）→ 失败整份回 GBK。**不能**用前端 `workspace::decode` 那套
     （UTF-16 BOM → UTF-8 BOM → `utf8_multibyte_shape_says_utf8` 启发式 → GBK）——
     两套规则在边界案例上结论不同，offset 必须按 Java 实际读到的字符数。
   - **CRLF**：Java `char[]` 里 `\r\n` 是两个字符；前端 `read_text_file` 把 `\r\n`
     归一成 `\n` 再建 Monaco 模型 ⇒ 每个前置行要按磁盘真实行尾计（`split('\n')`
     留下的 `\r` 正好算进去，无需特判）。
   - **UTF-8 BOM**：char[0] 是 `\uFEFF`、模型里没有 ⇒ 落在第 1 行长度里，公式
     自动 +1，无需特判。
   - **`character` 是 UTF-16 code unit 口径**（LSP 规定，Monaco 列同此）⇒ 行内必须
     按字符逐个累加 `len_utf16()` 够数即停。**不能 `take(character)` 个字符**：
     光标前有 emoji（1 字符 = 2 unit）时会少数一个 unit 整体向后串位——点收尾引号
     会落到分号上（2026-11-22 审查抓到原实现，回归测试 `行内emoji按utf16单位累加不串位`
     钉住；落代理对中间钳到该字符前）。

## 7. 风险表

| 风险 | 影响 | 对策 |
|---|---|---|
| S0 探针：单 CU resolve 慢（秒级以上）或热查询不缓存 | 体感卡 | 5s 超时回退；缓存不达标则自持 NameEnvironment 包装（+0.5d）。**实测（§6.1）：热 1.3s 不达标、每查询固定过路费 ~515ms 随环境规模增长、ASTParser 复用第 2 次起静默失败 ⇒ 预案坐实为必走，无备选** |
| **窗口期与 jdt.ls 冷导抢盘**（S0 实测导入是 I/O 主导） | 两者都变慢 | classpath 复用影子工程同一份（页缓存热）；S0 实测冷启动是延迟/CPU 主导（施压 197MB/s 时冷查询仅 3.9→4.1s）⇒ 首查询影响小；持久化后热查询毫秒级，此风险基本消失 |
| 内存 | 8GB 机器紧张 | `-Xmx768m` 硬顶 + 空闲自退 + 就绪即退；文案写明代价。S0 实测峰值 263MB |
| 编码（87% 文件 GBK） | resolve 失败/位置错 | 源根统一按 GBK 读（与影子工程 `.settings` 的 `<project>` 默认值一致）；CU 自身仍按字节严格试 UTF-8 再回退；抽 `NcIndexer` 同款回退成公共静态，单测钉住 |
| offset 语义 | 跳错字符 | LSP/Monaco 是 UTF-16 code unit，Java `char` 同语义，**直接传不转换**；单测钉一个含中文的行 |
| 协议错误/进程死 | 点击无反应 | 杀 + 重起 + 退避；`ok:false` 帧分类（timeout/oom/other） |
| 内部 API 驱动 ECJ（C 路线新增） | 版本耦合、静默错 | **S2a 已实测通过（§6.3）**：5 个实现级坑全部 javap 反汇编坐实并有对策（源根混进 classpathNames / 无参 completeTypeBindings / typeRequestor 非 null / cud.resolve() 语句级绑定 / CU 缓存防重复定义）；照抄 `Compiler` 与 `Compiler.accept` 参照流程，契约测试 smoke 钉住 |
| 与编译 worker 池混淆 | 生命周期互相杀掉 | **独立进程**，不并进 `NcEcjBridge`（worker 池 env_key 按模块，resolve 要全工作区 classpath） |

## 8. 明确不做（防范围蔓延）

- ❌ resolver 版引用搜索（工作区级，见实施方案 §4.4 第 2 条——那要 1GB 级倒排）
- ❌ 让 resolver 接管补全 / 诊断 / 重构（jdt.ls ready 后这些本来就比它全）
- ❌ 并行查询（串行队列够；ECJ 非线程安全）
- ❌ 跨查询 CU 解析缓存（除非 S0 实测证明必要）——**S0 已证明必要，且升级为「自持 LookupEnvironment」必走项，不再是可选项**。S2a 进一步坐实它是**硬需求**：不缓存则同一文件第二次查询撞 `The type X is already defined`、绑定全变 problem binding（§6.3 坑 5）。缓存 key = 文件路径 + 内容字节；`invalidate` 即删该条目
- ❌ 启发式沿父类链查成员（错跳风险，见 §4.2.2「只做一半会有一半跳错候选」——
  extends 在这里的唯一用途是喂给编译器当真相；C 路线连这口也省了——编译器直接读真源码）
