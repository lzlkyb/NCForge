# NCForge 窗口期精确解析（binding resolver）—— 设计方案

> 2026-11-21。本文是「用户可选开启的窗口期真 binding 跳转」的执行真源。
> 上位依据：`NCForge-智能代码-实施方案-2026-11-21.md` §4.2.1 第 2 步（原「降级为按需」，
> 经用户 2026-11-21 拍板改为「做成开关，愿意要精度的人自己开」）。
> 前置事实（别再重测）：§4.2.2 的 binding 三层表、§4.3 编排三件事、§1 的四条硬约束。

## 0. 一页结论

**做什么**：一个默认关闭的设置。打开后，在 jdt.ls 冷启动的 3~6 分钟窗口期里，
Ctrl+点击先用**常驻 ECJ 编译内核**做真 binding 解析（继承成员、精确接收者、同名消歧），
答不上再退回现有链路（声明索引 → 内容搜索）。jdt.ls 就绪后 resolver 自动退场。

**为什么现在能做**：基建全部就位——常驻 Java 桥模式（`ecj_worker.rs` + `NcEcjBridge`
行协议 + `java_bridge::Bridge`）、ECJ 在 1.8.0_202 上跑通的实测（9.06s / 7524 文件）、
索引格式 v3（源码侧成员带行号）、jar 反查与 `jdt://` 反编译链路。

**代价**：开关打开期间额外一个常驻 JVM（`-Xmx768m`，懒起 / 空闲 120s 自退 / 就绪即退），
单查询首次秒级、热后百毫秒级（S0 探针量出来才算数）。

**总工期**：约 2.5 天，五步，**S0 探针不过就整体止损**。

## 1. 架构

```
Ctrl+点击（窗口期，jdt.ls 未就绪）
   │
   ▼
provideDefinition ──ctx 为 null──▶ lightDefinition
                                      │
                                      ├─ ① lang_fast_definition（声明索引，微秒级）──有结果──▶ 打开
                                      │        （空）
                                      ▼
                                      ├─ ② lang_binding_resolve（★ 新，开关开才问）
                                      │        常驻 ECJ：ASTParser.setResolveBindings(true)
                                      │        + INameEnvironment（源码问索引摘要 / jar 问盘）
                                      │        ──有结果──▶ 打开
                                      │        （空 / 超时 / 进程不在）
                                      ▼
                                      └─ ③ searchDeclarations（内容搜索兜底）──现状不变
```

**为什么插在 ① 之后**：① 是微秒级本地二分，② 首次可能秒级。② 的价值是接住
「索引答不上」的场景（继承成员、接收者推不出、同名歧义）——这些正是真 binding 的强项。
「索引答错」② 接不住（有结果就不会问②），那是启发式固有边界，由行号自愈兜底。

**开关在后端判**（命令入口读 `AppConfig`），前端不判：常驻 JVM 的代价判断放一处，
避免「前端缓存旧配置 / 别的调用点漏判」把 JVM 拉起来。

## 2. 组件与复用点

| 组件 | 新建/复用 | 说明 |
|---|---|---|
| `ecj-bridge/BindingResolver.java` | **新建**（并入 `ncecj.jar`，第三入口） | 常驻行协议 main：`init` / `resolve` / `quit`。语法 Java 7（与 `NcEcjBridge` 一致） |
| `src/bind_resolver.rs` | **新建**（仿 `ecj_worker.rs` 的单 worker 形态） | 懒起 / 空闲 TTL / 超时杀 / 指数退避 / Stats。≤600 行红线 |
| `src/commands/lang_binding_cmds.rs` | **新建** | `lang_binding_resolve` + `lang_binding_status` 两条命令 |
| `java_bridge::Bridge` | 复用 | 行协议 + pending 映射 + `quit` 全套 |
| `decl_index.rs` / `types.idx` | 改（v4 加 extends） | 只加**源码侧**父类/接口名；jar 侧问盘不需要 |
| `decompile::pick_jar` / `parse_jdt_uri` | 复用 | jar 目标 → `jdt://contents/…` |
| `fast_decl::Holder.failures/retry_at` | 仿制 | 退避模式照抄，不新造 |
| `ecj-bridge-contract.test.mjs` | 扩展 | 第 ⑧ 条：`BindingResolver` 在 jar 里 + 协议 smoke |

**不新造**：打包链路（`build-bridge-jar.mjs` 的 `extraSrc`）、编码回退（抽 `NcIndexer`
的「UTF-8 严格试 → GBK 回退」成公共静态）、进程管理（`java_bridge`）。

## 3. 协议（照 `NcEcjBridge` 的行协议，id 必须是字符串）

```
→  id \t init \t <argsFile>        argsFile：每行一个 classpath 条目 + 一行索引摘要路径
→  id \t resolve \t <argsFile>     argsFile：{"path":"…","offset":123}（offset = UTF-16 code unit）
→  id \t quit
←  {"id":"N","ok":true,"data":{…}}
←  {"id":"N","ok":false,"code":"timeout|oom|other","detail":"…"}
```

`resolve` 的 data：
`{"kind":"method|field|type|local","fqcn":"nc.vo.pay.AggPayBillVO","name":"getCode",
  "line":42,"jar":"pubarap_paybill.jar"?}`

- `fqcn` + `name` + `line` → Rust 查 `decl_index.find(fq)`（源码）或 `method_line`（成员行）；
- `jar` 非空 → `pick_jar` + `jdt://` URI（复用反编译链路，**不预建 model**，与现状一致）；
- 泛型/数组绑定先 `getErasure()` 归一；
- `kind=local` → 目标就是本文件（`#局部名` 命名约定，走 `fixed_member_line` 同款校正）。

**索引摘要**（Rust 在 `init` 时从 `decl_index` 导出 NDJSON，只源码侧 ~7790 条，毫秒级）：
`fqcn \t superFqcn \t ifc1,ifc2 \t memberSig…`。Java 启动时装进 `HashMap`（几 MB）。
这是 `INameEnvironment` 源码侧的答案源——**「索引项在编译器眼里就是 class file」**
（java-ls 巧思）：编译器问「`nc.vo.pay.AggPayBillVO` 是什么」，摘要答「类，父类 X，
成员这些」；编译器问 jar 里的类型，委托 `FileSystem` 读真字节码（ECJ 自己缓存）。

⚠️ **跨查询缓存是实测项**：`ASTParser` 每次 parse 新建 `LookupEnvironment`，二进制类型
缓存可能不跨查询保留。S0 探针必须量「热查询耗时」；不达标则按 java-ls 做法自持
`NameEnvironment` 包装 + 缓存（工作量 +0.5 天，写进风险表）。

## 4. 生命周期

| 事件 | 行为 |
|---|---|
| 第一个窗口期查询到达（开关开） | 起进程 + `init`（classpath 用**影子工程同一份 jar 并集**，不重跑 `select_jars` 95s） |
| 空闲 120s | 发 `quit` 自退（省内存） |
| jdt.ls `ServiceReady` | 主动退场——它唯一的使命就是窗口期（后端退，不依赖前端） |
| 查询超时（5s） | 杀进程，该次回退内容搜索；**不**原地重试 |
| 连续失败 | 指数退避 30s→10min（仿 `Holder.failures/retry_at`） |
| 进程崩溃 / 协议错 | 杀，下次查询重起；stats 计数 |
| 关软件 / 切工作区 | 显式 `shutdown`（挂 `stopLang` / `quitGuard` 既有路径） |

`-Xmx768m`：懒 resolve 只碰该 CU 的传递闭包，不是全量；爆堆回 `oom` 帧 → 杀 + 退避。

## 5. 设置项

- `AppConfig.lang_binding_resolver: bool`，**默认 false**（`config.rs` + `config_io` 局部更新 +
  ts-mirror 自动过桥 + `bindings.check.ts` 的 `keyof` 断言同步加字段）。
- 设置页「代码智能」卡：`ToggleRow` + 一行状态（`lang_binding_status`：`idle/starting/ready/
  backoff`、查询数、失败数、退避剩余）。
- **文案（说清代价，不许含糊）**：
  > 未就绪期间的精确跳转（实验）：代码智能冷启动的几分钟里，用常驻编译内核做真 binding
  > 解析，能跳继承来的成员。开启后额外占用约 300~500MB 内存，只在索引答不上时触发，
  > 就绪后自动退出。**首次开启若触发索引重建（格式升级），要多等一次约 30 秒。**

## 6. 阶段拆分（每步独立验收，可中途停）

| 步 | 内容 | 工期 | 验收 |
|---|---|---|---|

| S2 常驻 resolver | `BindingResolver.java` + `bind_resolver.rs` + 命令三处注册（`#[tauri::command]` → `commands/mod.rs` → `nc_forge_commands!` 宏表，路径 `$crate::commands::`） | 1d | 单元：协议编解码 / 退避 / TTL；`error:check` 无新增 |
| S3 接入 | `lightDefinition` 插 ②；开关 + 状态行 + 文案；`lang-status` ready → 后端退场 | 0.5d | 开关关 = 行为与今天逐字节一致；e2e：窗口期继承成员落到父类声明行 |
| S4 回归 | 探针数据进文档；杀进程/超时/切工作区降级；全量门禁 | 0.5d | `cargo test --lib` 只许既有 2 红；`decl_index_live` 全过；契约过 |

## 7. 风险表

| 风险 | 影响 | 对策 |
|---|---|---|
| S0 探针：单 CU resolve 慢（秒级以上）或热查询不缓存 | 体感卡 | 5s 超时回退；缓存不达标则自持 NameEnvironment 包装（+0.5d） |
| **窗口期与 jdt.ls 冷导抢盘**（S0 实测导入是 I/O 主导） | 两者都变慢 | classpath 复用影子工程同一份（页缓存热）；查询低频天然错峰；S0 量「jdt.ls 导入期间 resolve」的耗时 |
| 内存 | 8GB 机器紧张 | `-Xmx768m` 硬顶 + 空闲自退 + 就绪即退；文案写明代价 |
| 编码（87% 文件 GBK） | resolve 失败/位置错 | 抽 `NcIndexer` 同款回退成公共静态，单测钉住 |
| offset 语义 | 跳错字符 | LSP/Monaco 是 UTF-16 code unit，Java `char` 同语义，**直接传不转换**；单测钉一个含中文的行 |
| 协议错误/进程死 | 点击无反应 | 杀 + 重起 + 退避；`ok:false` 帧分类（timeout/oom/other） |
| v4 格式升级 | 用户机器索引重建 30s | 已有「读头部报版本不一致自动重建」机制；文案提前说明 |
| 与编译 worker 池混淆 | 生命周期互相杀掉 | **独立进程**，不并进 `NcEcjBridge`（worker 池 env_key 按模块，resolve 要全工作区 classpath） |

## 8. 明确不做（防范围蔓延）

- ❌ resolver 版引用搜索（工作区级，见实施方案 §4.4 第 2 条——那要 1GB 级倒排）
- ❌ 让 resolver 接管补全 / 诊断 / 重构（jdt.ls ready 后这些本来就比它全）
- ❌ 并行查询（串行队列够；ECJ 非线程安全）
- ❌ 跨查询 CU 解析缓存（除非 S0 实测证明必要）
- ❌ 启发式沿父类链查成员（错跳风险，见 §4.2.2「只做一半会有一半跳错候选」——
  extends 在这里的唯一用途是喂给编译器当真相）

## 9. 验收清单（发版前逐条打）

1. S0 探针数据（冷/热/内存）写进本文 + 实施方案 §4.1 表
2. 窗口期 Ctrl+点击一个继承来的方法 → 落到父类声明行（真实工程）
3. resolver 进程被任务管理器杀掉 → 下一次点击自动恢复，用户只感觉慢一次
4. 查询超时 → 该次走内容搜索，**不弹错、不转圈超过 5s**
5. 开关关闭 → 无常驻 JVM、行为与今天逐字节一致（`lightDefinition` 链路 diff 为空）
6. jdt.ls ready 后 10s 内 resolver 进程退出（任务管理器核查）
7. 切工作区 → 旧 resolver 退出、新工作区首次查询重新 init
8. 含中文/GBK 文件上的成员点击位置正确
9. `cargo test --lib` 仅既有 2 红；`decl_index_live` 8 条全过；`ecj-bridge-contract` 过
10. 门禁：`fmt` / `clippy --lib --bins` / `error:check` / `source-size` / `tokens` / `tsc`
