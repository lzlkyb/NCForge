# NC 开发者痛点：一手材料调研

> 日期：2026-11-07
> 方法：4 轮网络检索（中文社区 / 官方文档 / 竞品自述 / 媒体报道），只采**能指到具体操作细节**的陈述。
> 与 [`NC开发工作流-社区与开源调研-2026-11-01.md`](./NC开发工作流-社区与开源调研-2026-11-01.md) 的关系：
> 那份回答"NC 开发者在干什么活"，这份回答"**他们干这些活时哪里最疼，以及原话怎么说的**"。
> 本文不重复它的四类活划分，只补一手引述与新发现。

---

## 0. 一页结论

1. **最硬的一手材料来自竞品作者自己**。一个 IDEA 插件作者在推广文里把 UAP Studio 的四条结构性缺陷讲透了（多模块、循环引用、版本切换、文件多了卡死），
   每一条都直接对应"客开"这个工种的真实形态。这份材料比任何技术博客都可信——他没有理由美化 UAP Studio。
2. **痛点的形状不是"缺功能"，是"搬运"**。打一个补丁 8 个手工步骤、提一次日志要改级别+清空+复现+复制粘贴、
   出一次包要人肉判断"我这次到底改了哪些文件"。**每一次搬运都是一个丢失上下文的断点。**
3. **"改完不生效"是最高频的一类事故，且大多不报错**。前端不重编、元数据没发布但有缓存、`share_flag` 配错导致数据静默消失、
   子表外键没回填保存后全是空——**不报错的坑比报错的坑更贵。**
4. **元数据是行业公认的空白**。两个独立竞品都明确写了"元数据编辑暂不完成 / 只开发了一部分"。
   没人做成，不是因为没人要，是因为门槛高。**这既是我们最大的机会，也是最大的坑。**
5. **一个必须正视的约束：开发者常常在客户现场，没有 IDE**。
   原话："在客户现场没有IDE调试条件的时候，日志就是唯一的眼睛。" 这直接质疑"独立桌面应用"的形态假设，见 §5。
6. **付费意愿存在但市场极小**：订阅制插件作者自述"订阅的开发者已有 100 多人"，且"有私单才能继续维护插件"。
   100 人量级的市场，**赢的方式是口碑和严谨度，不是规模**。

## 1. 可信度分级与"AI 污染"现状

| 级别 | 判定 | 本次命中的来源 |
|------|------|---------------|
| **A 可直接采信** | 第一人称亲历、给出具体路径/表名/命令、有可验证的操作细节 | 竞品作者推广文、博客园补丁流程、CSDN 踩坑记录、官方日志提取帮助、插件 README |
| **B 可参考** | 技术细节正确但叙述经过整理，或站点性质为运营号 | 用友内幕报道、插件注册博客 |
| **C 不可采信** | 行文模板化、出现未替换占位符、术语可疑 | 见下 |

### C 级样本的特征（比上一轮判断更严重）

本轮命中 `hqwc.cn`、`kwkr.cn`、`sheratonhq.com`、`mynw.cn` 四个站点，呈**同一套模板矩阵**：

- 标题统一格式：「XXX：从 A 到 B 的完整指南 / 五层加固与避坑指南」
- 开头统一是"我干了十年用友系开发 / 我带过几个模拟项目"式资历声明
- **出现未替换的占位符**：`我带过的几个模拟项目X中` —— 直接暴露是模板生成
- 技术细节（`md_class_field`、`share_flag`、`is_visible`、`PK_MD_BIZITFMAP`）却是对的

判断：**这类内容是从真实资料拼装出来的，术语可信、结论不可信**。
它们可以当"线索"（提示去哪儿查），不能当"证据"（不能据此下结论）。
真正可采信的仍是 2011–2018 年的老博客、官方 helpcenter、以及竞品作者自己的话。

> 这条本身就是产品机会的佐证：**搜"NC 排障"，前两页已经一半是机器写的**。
> 领域知识必须沉淀为可验证的规则（工具行为），而不是可检索的文本。

## 2. 痛点按"时间是怎麼没的"归并（六类）

### 2.1 等：编译 / 启动 / 部署

| 引述 | 来源 | 可信度 |
|------|------|--------|
| "如果当前项目中 java 文件数量多的情况下 UAP Studio 就非常卡顿，严重影响开发效率" | 竞品作者推广文 | A |
| "这个过程（更新类路径）在 UAP Studio 中非常耗时" | 同上 | A |
| "传统方式每天要花半小时等待项目编译部署" | mynw / CSDN 环境搭建文 | **C（数字不可采信，仅作旁证）** |
| "改一行 class，不想重启 40 秒" | YDS 功能说明反推 + 多方一致 | B |

**判读**：具体秒数不可信，但"等"这件事被两条独立材料印证。
关键不在单次多久，而在**一天要等多少次**——每改一次就要走一遍"编译→部署→重启"。

### 2.2 找：找类、找表、找配置、找"改了哪些文件"

| 引述 | 来源 | 可信度 |
|------|------|--------|
| "对于用友二开最痛苦也是最快乐的事即是找代码位置了，仅有的少的可怜的文档着实让人头大……最牛拜的一次寻找代码位置是一个 JAR 包挨着一个 JAR 包翻的" | CSDN 105813944（报销 portal 二开亲历） | A |
| "通常开发人员可能会有个疑问，这个 VO 对应的是哪个表。来，他来了，在这搜。这个主键字段是哪个表的字段，来这里搜。" | 竞品作者推广文（他把这做成了核心功能） | A |
| "特别在共享项目开发中修改 js 文件后运行成功，文件多了的话都不知道是改了哪些文件" | 同上（所以他做了 hotwebs/modules 自动同步） | A |
| "检查 NC 代码规范因为需要全局扫描会比较慢，没反应就多点几次检查就好了" | 插件 README「常见问题」 | A |

**判读**：三类"找"是三件不同的事，别混：
- **找代码**：标准产品源码不在工程里，在 jar 里（我们已有 CFR 反编译 + `jdt://` 打开，命中）
- **找表**：VO ↔ 表 ↔ 字段的映射（我们数据字典有了，但**没有从 VO 反查表**）
- **找改动**：补丁范围识别（我们靠 `patcherconfig` + 产物探测，比人手强，但没有"多人协作时谁改了啥"）

### 2.3 搬：手工流程的断点

**补丁部署的完整手工链路（博客园，A 级，逐条有路径）：**

```
1. Windows+R → mstsc 远程连到客户机器
2. 停服务
3. 后端补丁：resources/ 覆盖到 nchome/resources，modules/ 覆盖到 nchome/modules
4. 前端补丁：dist/ 覆盖到 nchome/hotwebs/nccloud/resources
5. yyconfig 放到 nchome/hotwebs/nccloud/WEB-INF/extend
6. nccloud 放到 nchome/hotwebs/nccloud/WEB-INF/classes
7. 进 bin 目录跑 SysConfig.bat 重新部署
   （client 目录下的不用重部署；public / private 下的必须重部署）
8. 重启服务
   ——原文附注："注意留存补丁记录及备份"
```

**对照：官方取日志的流程（用友智能服务云 helpcenter，A 级）**

```
1. 点页面上的【日志】按钮，把两个日志级别改成 debug
2. 点 clear 清空
3. 手工复现一次报错
4. 把日志页面的内容复制粘贴到 txt
   ——后台日志：先把 nclogs/server 下所有日志备份，复现一次，再把它们全部上传
```

**判读**：第 8 步"注意留存补丁记录及备份"和第 4 步"复制粘贴到 txt"是全篇最值钱的两句话。
**前者说明"回滚"靠人记性，后者说明"取日志"靠人搬运。** 这两步都不该由人做。

### 2.4 猜：不报错的坑

| 现象 | 真实根因 | 来源 | 可信度 |
|------|---------|------|--------|
| `ORA-00942 表或视图不存在` | 元数据发布了但表没建，**不是代码问题** | lpqz / 多方一致 | B+ |
| 保存后子表全是空 | 子表外键未回填（引用属性没标必输） | kwkr（AI 站，但机制合理） | C，需实测 |
| 同一单据换个组织，字段值"消失" | `md_class_field.share_flag` 共享级别配错，**不报任何错** | hqwc（AI 站） | C，需实测 |
| 开发环境字段正常、客户现场看不见 | 角色字段权限，不是元数据 | hqwc | C，需实测 |
| 发布元数据报 `ORA-00001 (PK_MD_BIZITFMAP)` | 拷贝接口时留下多余 source 记录，得手工 delete | CSDN 103913904 | A |
| 前端改了不生效，404 not found | 前端不自动重编，要改 `config.json` 的 `buildEntryPath` 再 `npm run build` | CSDN 141650049 | A |
| 节点打开了但"不支持该业务操作" | 没跑 deploy 工具部署 | 同上 | A |

**判读**：这张表就是上一轮说的"报错 → 根因 → 动作"映射库的原料。
但注意：**A 级的两条（PK_MD_BIZITFMAP、前端不重编）是确定性的，可以直接做成规则；C 级三条必须先在真实环境验证再写进代码**，
否则我们就是在复刻 AI 污染。

## 3. 三条反直觉发现

### 3.1 编辑器不是战场，NC 语义才是

两个竞品都选择**寄生在 IntelliJ 社区版**上，而不是自己做编辑器（一个明确写了"基于 IntelliJ IDE 社区版实现"）。
他们赢的点从来不是补全、跳转——那是 IDEA 免费的——而是：

- `Client` 不能调 `private` 端代码（NC 特有的分层约束，标准 IDE 不检查）
- `hotwebs` / `modules` 目录与 `NCHOME` 的实时同步
- 多模块 + 循环引用（Eclipse 不支持，IDEA 存疑但插件作者专门做了"真正的多模块"）
- `NCCAction` 搜索（按请求路径反查鉴权文件和类文件）

**含义**：我们要抢的不是"谁补全更好"，是"**谁知道 NC 的规矩**"。这条判断上一轮已经写了，本轮拿到了一手证据。

### 3.2 UAP Studio 的四条结构性缺陷，正好是"工作台"的产品定义

竞品作者的原话，值得逐条拆：

| # | 原话 | 本质 | 我们的位置 |
|---|------|------|-----------|
| 1 | "UAP Studio 在项目创建时一个项目代表 NC 中的一个模块。客开通常涉及多个模块……这样导出补丁还需要手动修改" | 工程模型 ≠ 交付模型 | ✅ 我们是"打开一个工作区，多个模块"，已对 |
| 2 | "如果当前项目中 java 文件数量多的情况下 UAP Studio 就非常卡顿" | 大工程性能 | ⚠️ 我们有 jdt.ls，但大工程索引速度待实测 |
| 3 | "出现相互引用的情况，Eclipse 又不支持循环引用，这样开发非常麻烦" | 模块循环依赖 | ✅ 我们 `compile_order` 按依赖倒序，但**循环依赖怎么处理没验过** |
| 4 | "客开人员通常接触多个项目。不同项目的 NC 版本又不同。这就要求我们切换不同版本的 UAP Studio，非常麻烦" | **多项目多版本共存** | ❓ 我们是单工作区，**多项目切换要重开窗口吗？** |

第 4 条是本次调研里**唯一一条我们没对标过的需求**，而且它直接对应"客开顾问同时跑 3 个项目"的真实工作形态。

### 3.3 开发者常常不在自己的机器上

> "在客户现场没有 IDE 调试条件的时候，日志就是唯一的眼睛，有没有埋好点直接决定排查效率。" —— CSDN 164417178（B+）

这条把 §2.3 里"mstsc 远程打补丁"的流程串起来了：**他们是在客户的跳板机/远程桌面上干活**。
这带来一个必须回答的问题：

- 如果 NCForge 只能装在自己电脑上，那"现场救火"这个最强场景**根本用不上**；
- 反向的机会：**能读远程 `NCHOME` 的能力**（SSH / 共享盘 / 远程日志），比再多本地功能都值钱。

目前代码里只有本地路径白名单，没有远程通道。**这是形态级缺口，不是功能缺口。**

## 5. 对我们的含义

### 5.1 能赢的三块（按确定性排序）

| 块 | 依据 | 现状 |
|----|------|------|
| **补丁应用 / 回滚** | §2.3 八步手工流程 + 用友官方把它当卖点 + 竞品 YDS 有 | 缺（只有出包） |
| **VO ↔ 表 ↔ 字段 双向查** | §2.2 两个独立竞品都做了这个功能，说明是每日高频 | 半有（正向有字典，反向缺） |
| **报错 → 根因 映射库** | §2.4，且 AI 污染让"搜"这条路失效 | 缺 |

### 5.2 别碰的

- **编辑器基本盘**（补全/跳转/重构）：竞品都寄生 IDEA，说明这块不值得自研。
- **"AI 问答窗口"**：§1 证明机器生成的答案已经在污染这个领域，再加一个生成答案的入口只会加重不信任。
  要做就做**确定性映射 + 跳转**，不做自由问答。

### 5.3 需要先回答的三个问题（都不写代码）

1. **形态**：现场没有 IDE，我们是本地应用。要不要做远程 NCHOME 读取（SSH/共享盘）？
   不做，就放弃"救火"这个最强场景；做了，安全模型要重做（现在只有本地路径白名单）。
2. **多项目多版本**：一个工作区只能开一个工程，客开顾问同时跑三个项目怎么办？
   这是竞品明确列出的痛点，我们还没对标。
3. **循环依赖**：竞品说 Eclipse 不支持循环引用导致"开发非常麻烦"。我们的 `compile_order` 按依赖倒序排，
   真出现环会怎样？没验过。
