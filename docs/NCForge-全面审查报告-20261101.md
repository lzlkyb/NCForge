## 0. 结论总览

| 级别 | 数量 | 构成 | 定义 |
|---|---|---|---|
| **P0** | 3 | — | 可造成数据被覆盖/丢失，或界面结论与事实相反且用户会据此做决定 |
| **P1** | 28 | 架构 6 + 功能 12 + 交互 7 + 性能 3 | 明确功能错误、反馈断链、明显违反自家约定，需排期 |
| **P2** | 13 | — | 体验毛刺、可访问性、性能隐患、文案与动效细节 |
| 合计 | 44 | — | — |

**总体判断**：单个功能的实现质量仍然很高（虚拟滚动、分帧、单飞闸、三层只读、原子写、回合式取消都是真的）。问题集中在三个结构性的地方：

1. **「文件页」同时是「全局页面宿主」**——一个组件承担两个职责，代价是首屏空白、懒加载失效、错误边界粒度失效、页面表三处漂移（A1）。这是本轮最值得动的一处架构。
2. **状态订阅粒度全部是「整仓快照」**——没有一处 selector。编译日志每 80ms 刷一次，就带动整棵文件树、标签条、所有隐藏页面重渲染（A2 / D1 / D2 / A4 / A5）。
3. **异步回包普遍没有「我这一趟还作数吗」的判定**——切工作区、切连接、翻页、打开文件、冲突选版都存在先发后至覆盖，其中冲突选版会覆盖用户没选过的文件（P0-1）。

其余是反馈层的老毛病：15 处把 Rust 英文错误原样弹给用户（A6）、错误 toast 3.5 秒消失且不可选中（C2）、危险操作在命令面板里绕过确认（C1）。

## 1. P0（建议本周内修）

### P0-1　冲突文件的「选了哪一版」跨文件残留：会不问自取地覆盖另一个文件

- 位置：`components/svn/ConflictPane.tsx:29` `const [choice, setChoice] = useState<Choice | null>(null);`
  ＋ `components/svn/RightPane.tsx:101` `<ConflictPane file={file} … />`（**没有 `key`**）
- 现象：左栏选冲突文件 A → 点「用作最终内容」（按钮变「已选作最终内容」）→ **不点「已解决」**，直接点左栏的文件 B。于是 B 的面板一打开就显示「已选作最终内容」，「已解决」立刻可点。点下去会用 B 的 `.mine` / `.rN` 覆盖 B 的工作副本、删掉临时文件——而用户从未对 B 做过选择。
- 根因：React 复用同一个 `ConflictPane` 实例（`file` 变化不卸载），`choice` 是组件内 state，没有跟随文件重置。
- 影响：单条命令内的**不可逆数据覆盖**，且事后只有 `.ncforge-resolve-<时间戳>` 备份能救。冲突解决本来就是用户最紧张的场景。
- 修法：`<ConflictPane key={file.path} … />`（最省事），或 `useEffect(() => setChoice(null), [file.path])`。补一条单测：换 `file` 后按钮文案回到「用作最终内容」。

### P0-2　语句正在执行时可以关掉标签或切换连接，结果与错误全部静默蒸发

- 位置：`lib/dbActions.ts:68-83` `requestCloseTab`（全函数无 `tab.running` 判断）、`lib/dbActions.ts:57-65` `switchConn`（同）
- 现象：执行一条 30 秒的 `update`（自动提交连接）→ 立刻点标签上的 ×。没有任何拦截或确认，标签消失；语句仍在库里跑完并**提交**；`execOne` 后续的 `patchTab` / `appendOutput` 落到已删除的标签上，被静默丢弃。用户既看不到结果，也不知道到底改没改；切连接同理（还会顺手 `releaseSlot`）。
- 根因：`runStatements` 自己用 `tab.running` 拦住了重入（`:154`），但**退出路径没有对称地检查**。项目已有取消能力（`db_cancel` + 原子位），这里没接。
- 影响：写入类是真实的数据影响，读取类是「以为跑崩了」重复执行。
- 修法：`requestCloseTab` / `switchConn` 在 `tab.running` 时先弹确认「正在执行，关闭将失去结果（语句仍会在库里跑完）」，确认后先 `dbApi.cancel` 再关。同一条守卫抽成 `guardRunning(tab, reason)`。

### P0-3　结果页的「自动提交 / 手动提交」读的是另一条会话，与同屏黄条互相矛盾

- 位置：`components/db/ResultPanel.tsx:20` `const autoCommit = rtOf(tab.connId).tx?.autoCommit ?? true;`（用于 `:69`「自动提交模式，已生效」/「手动提交模式…」）
- 现象：连接默认自动提交 → 工具条点「手动提交」（切的是**这个标签的会话槽**）→ 执行 `update`。上方 `TxBar` 黄条说「未提交事务：1 条写语句」，结果页却写「自动提交模式，已生效」。用户据此关掉应用，改动作废。
- 证据：`lib/dbStore.ts:500-508` 明确写着「槽各自独立事务：primary 的结果写回连接，槽的写回标签」——`if (slot) patchTab<SqlTab>(tabId, { tx: r.tx }); else setTx(connId, r.tx);`。`TxBar` 因此走 `override` 读 `tab.tx`（`TxBar.tsx:30`），只有 `ResultPanel` 读错了对象。
- 根因：`dbStore.ts:325` 的注释已经把这条契约写清楚了（「槽的事务状态存在标签上，不在连接的 `rt.tx` 里」），`ResultPanel` 是漏改的那一处；`?? true` 兜底又把「读不到」变成「已提交」。
- 修法：`const tx = tab.slot ? tab.tx : rtOf(tab.connId).tx`，`autoCommit` 缺失时按连接 `info.autoCommit` 算，不要 `?? true`。补单测：手动模式 + 槽执行 → 文案必须是「手动提交模式」。

## 4. 性能（D 组）

### D1　编译日志每 80ms 刷一次，带动整棵未 memo 的文件树

- 位置：`hooks/useModuleCompile.ts:60` `setCompileLog((l) => appendLog(l, batch));`（`LOG_FLUSH_MS = 80`，`:13`、`:65`）
- 链路：`lib/workspaceSession.ts:186-188` 返回整份快照 → `FilesTab.tsx:61-73` 一次性解构 10 个字段 → `useTreeLoad.ts:14` 也订阅 `{ tree }` → `components/workspace/TreeRow.tsx:12/59` 两个行组件**都没有 `React.memo`**（全仓仅 `Header.tsx` / `SideNav.tsx` 用了 memo）→ `FileTree.tsx:168` 每次渲染重建全部行元素。
- 现象：编译期间每 80ms 一次广播，FilesTab、FileTree、每一条目录/文件行、TabStrip、EditorStatus 全部重渲染。展开几千文件时是肉眼可见的掉帧。
- 修法（按性价比排序）：① `compileLog / compiling / compileResult` 拆成独立小 store，只让 BottomPanel 订阅；② `TreeRow` 加 `memo`（props 全是原始值，容易生效）；③ 文件树本身还没有虚拟滚动（`grep scrollTop` 只命中 `ResultGrid`），大工程建议引入（见第 5 节）。

### D2　`resolve_safe_path` 在 async 命令体里做同步 `canonicalize`

- 位置：`security/path.rs:39/48`；调用点 `commands/compile_cmds.rs:152`、`local_history_cmds.rs:25`、`workspace_cmds.rs:34/179`、`patch_cmds.rs:148`、`svn_cmds.rs:289` 六处直接在 async 体内调用（`db_cmds.rs:1489` 已经包了 `spawn_blocking`）。
- 现象：网络盘/机械盘上一次 `canonicalize` 可达数百毫秒，而 tokio worker 数 = CPU 核数，几个路径校验就能把整个 IPC 层堵住。
- 修法：把该函数标记为阻塞（命名 + 文档），调用点统一进 `spawn_blocking`，或提供内部已包 `spawn_blocking` 的 async 版本。

### D3　`resources_status` 是同步命令，在主线程做磁盘 IO

- 位置：`commands/resource_cmds.rs:56` `pub fn resources_status(`（`:60` 读状态 JSON、`:68` 对每个包 `is_dir()`）
- 现象：Tauri 2 里非 async 命令跑在主线程。前端每次挂载都调 → UI 线程被同步盘查阻塞，窗口短暂无响应。
- 修法：改 `async` + `spawn_blocking`（同文件 `ensure_resources_async` 已是范式）。
