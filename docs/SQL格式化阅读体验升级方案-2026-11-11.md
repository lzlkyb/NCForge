# SQL 格式化阅读体验升级方案

## 问题与实测

用户提供的 NC / Oracle 多层分页查询，原文 3 行，最长一行 1938 字符。当前生产格式化使用 `sql-formatter` 的标准展开策略，得到 100 行，最长一行 101 字符。

将现有 `expressionWidth` 从 50 改成 120 后，仍然是 100 行、最长 101 字符。该参数主要影响括号内表达式能否内联，不控制 SELECT 字段列表及主子句的整体换行。

当前体验问题：字段逐项竖排，SELECT / FROM / WHERE 与其后的短内容分离，多层分页包装进一步增加高度。业务查询需要持续滚动才能同时查看字段、关联和筛选条件。设置页的预览只有一条两字段简单查询，无法暴露这些问题。

## 推荐决策

新增两种排版方式：**阅读优先**作为默认，**结构展开**保留当前行为。推荐方式按查询结构组织，字段列表按行宽装入多个完整字段，短子句保持同一行；复杂关联、条件分组、子查询和 CASE 继续体现层级。

目标行宽默认 120 字符，每级缩进 2 空格。关键字大小写继续使用用户现有偏好。行宽以可配置的固定值计算，避免窗口大小变化导致同一 SQL 生成不同文本；窄窗口的视觉折行继续由编辑器控制。

## 排版规则

| 对象 | 阅读优先规则 |
| --- | --- |
| SELECT 字段 | 多个完整字段放入一行，接近行宽时在逗号后折行。字段、别名、函数调用作为整体，避免逐词拆开。字段顺序与表达式保持原样。 |
| 短主子句 | `select * from (`、`from bd_project`、`where rownum_ > 0` 保持简洁；不能把完整长查询压成一个超宽行。 |
| JOIN / ON | 短 JOIN 与单个 ON 条件同一行；多个 ON 条件、复杂表达式或超宽内容另起续行。 |
| WHERE | 首个条件与 WHERE 同行，顶层 AND / OR 按条件换行；短括号分组保持完整，长分组按逻辑边界展开。保留原始括号与逻辑顺序。 |
| IN / 函数 | `not in ('5', '6')`、`nvl(dr, 0)` 这类短表达式保持一行，长候选列表按宽度换行。 |
| 子查询 | 保留嵌套边界，每级缩进 2 空格；分页壳的短 SELECT 和行数限制紧凑展示，内部业务查询分段阅读。 |
| CASE / UNION / CTE | 按语义分支或查询边界展开，避免为了减少行数挤掉结构。 |
| 注释、字符串、提示、参数 | 保留原文和归属。行注释结束必须保留换行；长字符串或标识符允许超过目标宽度，不能拆开 token。 |
| 空行 | 默认不在每个子句之间插空行；独立语句之间沿用用户现有设置。 |

不改变分页写法，不删除子查询、条件或括号，不替换成 WITH，不调整连接类型、别名、字段及其顺序。

## 用户这条 SQL 的拟议效果

以下是前期人工编排的目标样例，得到 **42 行、最长 103 字符**。该样例已经校验 token 序列，原文与样例只有空白差异；未执行 SQL。最终已实现的算法得到 **39 行、最长 120 字符**，完整输出见 `.codex-artifacts/sql-reading-final.sql`；人工样例保留作设计过程对照。

```sql
select * from (
  select row_.*, rownum rownum_ from (
    select project_code, project_reportname, institution_code, project_name, type_name,
      administrative_levelname, application_provincename, addressname, nconstructionarea,
      state_name, pk_project, ordermethod, planmodel, planpriority, pk_group, pk_org,
      pk_workcalendar, pk_projectclass, application_province200, administrative_level
    from (
      select * from (
        select distinct institution_code, PROJECT_name, PROJECT_CODE, bd_project.pk_project,
          bd_project.ordermethod ordermethod, bd_project.planmodel planmodel,
          bd_project.planpriority planpriority, bd_project.pk_group pk_group, bd_project.pk_org pk_org,
          bd_project.pk_workcalendar pk_workcalendar, bd_project.pk_projectclass pk_projectclass,
          application_province200, administrative_level, project_reportname, type_name,
          e.name administrative_levelname, d.name application_provincename, r.name addressname,
          bd_project.pk_projectstate, pk_duty_org, bd_project.dr dr, bd_project.pk_eps,
          bd_project.def1 nconstructionarea, e.state_name state_name
        from bd_project
        left outer join bd_region r on r.pk_region = bd_project.address
        left outer join bd_projectclass p on p.pk_projectclass = bd_project.pk_projectclass
        left outer join md_enumvalue e
          on e.value = bd_project.administrative_level
          and e.id = '1d0dbab7-07af-48d9-94f5-70bdb0e944b5'
        left outer join bd_defdoc d on d.PK_DEFDOC = bd_project.application_province200
        left outer join pm_projectstate e on bd_project.pk_projectstate = e.pk_projectstate
        where bd_project.enablestate = 2
          and bd_project.administrative_level not in ('5', '6')
      )
    )
    where 11 = 11
      and pk_project in (
        select pk_project from pim_set_information_h
        where nvl(dr, 0) = 0
          and ctrantypeid = '1001A810000001UJ5S79'
          and fstatusflag = 1
      )
      and (pk_projectstate <> '~' and pk_projectstate is not null
        and pk_duty_org = '0001U110000000000VBF')
      and (pk_eps = '1001A110000000FBCHC0')
    order by project_code
  ) row_ where rownum <= 500
)
where rownum_ > 0
```

## 设置与操作

- 设置页首先展示“排版方式：阅读优先 / 结构展开”和“目标行宽：120 字符”，保留缩进、大小写和方言。现有 expressionWidth 放到高级选项，改名为“括号内表达式宽度”，避免误解为整篇宽度。
- 预览提供“简单查询 / 多表关联 / NC 分页查询”三种示例，并支持粘贴自己的 SQL。并排比较格式化前后，显示行数与最长行，内容只用于预览。
- 工具栏主按钮与快捷键使用当前排版方式。格式化菜单里沿用“选中 / 当前语句 / 整个脚本”的范围操作；排版方式单独分组，不与范围混在同一串菜单项里。
- 保留一次撤销恢复原文、选中范围保护、格式化期间版本变更保护，以及脚本里坏语句保留原文的原有行为。
- 既有大小写、缩进、方言等偏好不被覆盖；未配置过排版方式时采用阅读优先。用户可切回结构展开。

## 实施路径与验收

1. **先实现布局规则**：保留现有公开方言格式化入口，在其已展开的子句、字段和嵌套边界上做受控布局。用词法保护检查字符串、注释、括号和完整表达式；禁止用正则批量删换行，不依赖库的私有 AST；无法可靠处理的结构保留展开结果。
2. **统一接入**：新增排版方式与目标行宽偏好，SQL 编辑器、选中范围、单语句、脚本兜底及设置预览都通过同一格式化入口，避免预览与实际输出不同。
3. **补齐预览与测试**：用用户这条 SQL 作为回归样例，再覆盖 JOIN、混合 AND/OR、CASE、函数、窗口函数、注释与 Oracle 提示、绑定变量、长字符串、CTE、UNION、多语句脚本。

验收点：

- 用户提供的分页查询在默认阅读样式下接近本稿 42 行效果，不再强制一字段一行；同时保持清晰的子查询、关联和条件边界。
- 输出与输入的 token 序列一致，允许用户明确选择的关键字大小写变化。复杂注释、字符串、参数不能被拆坏。
- 第二次格式化与第一次结果相同，不发生布局反复变化。
- 目标行宽为软限制，不拆分超长 token；缩窄编辑器窗口不改变生成文本。
- 选中格式化不修改选区外文本；撤销一次恢复本次修改；解析失败保持原文并给出提示。

## 成熟工具对照与技术路线

2026-11-11 使用同一份原始 NC 分页查询对照。测试依赖仅安装于 `.codex-artifacts/sql-format-research/`，没有加入应用依赖或改动锁文件。处理时长是此机器一次本地调用的观察值，不代表跨机器基准；行数也不是唯一质量指标。

| 工具 / 配置 | 行数 | 最长行 | 观察耗时 | 原样 token / 幂等 | 结论 |
| --- | ---: | ---: | ---: | --- | --- |
| 当前 sql-formatter 15.9.0 | 100 | 101 | — | 本轮对照原文 | 方言基础保留，默认布局需改善 |
| prettier-plugin-sql-cst 0.25.1，SQLite，120列，collapse，关闭规范化和补分号 | 77 | 107 | 83ms | 是 / 是 | 不提供 Oracle 方言；Oracle `(+)` 和层次查询额外试例解析失败，不能替换本应用引擎 |
| SQLFluff 4.5.0，Oracle，layout rules，exclude LT09，fill，require implicit indents，120列，2空格 | 35 | 119 | 2915ms | 是 / 是 | 字段填行可借鉴，但原始多层分页展开后局部层级不清；Python运行时和此条处理延迟不适合当前桌面快捷格式化 |
| shandy-sqlfmt 0.32.0，polyglot，120列 | 85 | 119 | 33ms | 否 / 是 | 标识符大小写也变化，且仍大量竖排字段；与保留现有文本习惯不符 |
| sqlparse 0.6.1，reindent，wrap_after120，compact，2空格 | 39 | 162 | 18ms | 是 / 是 | 多字段填行有效，但深层悬挂对齐占宽，最长行仍162；不足以直接替代现有方言布局 |

DataGrip 根据官方文档核验配置能力，未在本机运行，不给它编造行数或耗时。其 `Same line`、`Wrap if long`、`Collapse short statements`（可限定子查询）、独立 JOIN / ON / WHERE 设置，说明“整篇行宽 + 按结构折行”比单纯调括号表达式宽度更合适。

SQLFluff 文档还明确：`list_wrapping = fill` 仅对超宽列表断行，**不会主动收拢既有列表换行**；SELECT 需禁用 LT09 才不强制逐项一行。因此本应用不能把当前100行输出再交给 fill 就期望收拢。自己的受控布局必须主动合并完整字段，再根据固定宽度分配新行。

最终采用原方案的改进版：保留 sql-formatter 的方言和错误处理，补一层有明确安全边界的阅读布局；短 SELECT/FROM 收拢、字段按宽度填行、FROM 子查询只增加一级标准缩进、JOIN条件和WHERE逻辑按边界保留；结构展开仍可选。不引入 Prettier / Python 生产运行时。
