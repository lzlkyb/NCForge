> 日期：2026-11-11 初稿，2026-11-12 三版，2026-11-13 补落地情况　状态：**P1 已落地，P2 起未做**

## 0. 已确认的决策（2026-11-12）

| # | 决策 | 理由 |
|---|---|---|
| 1 | 目标是**让用户更方便地审查代码**，审查单位是需求（= 一个补丁） | 一个会话可能做几个需求 |
| 2 | **需求名 = 补丁名去掉日期**：`[问题清单号_]改动内容描述`，出包时再拼 `_YYYYMMDD.zip` | 与 nc-patch-pack 包名规范、`previewZipName` 一致 |
| 3 | **改动全集 = SVN 改动列表**；变更日志只用来「认领」和「解释」 | SVN 列表天然包含 AI 工具改的、AI 用脚本改的、人手改的；未认领 = SVN 列表里没人认领的文件，是完整的 |
| 4 | cc-bridge 只记录（`changeSet` + `reason` + 前后哈希 + 备份），需求的改名、认领、出包、关闭都存在 NCForge | 桥保持开放、无状态 |
| 5 | 写文件带 `reason`（一句话原因），审查时显示在改动块旁 | 审查不用回对话里翻 |
| 6 | 不做影子 git、不做「先审后落盘」 | 前者和「备份 + SVN BASE」重复且要同步 SVN；后者打断边改边编译、热替换 |
| 7 | **两种审查方式都做，用户自己切换**：方案一「审查改动」里按需求分组、逐文件审；方案二新增「按需求审查」视图、整个需求连续审。两者共用同一份已审状态 | 用户偏好不同，不替用户选（2026-11-12 设计稿对比后定） |
| 8 | 未认领改动的按时间分段由 NCForge 按变更日志的 `at` 自己算，默认间隔 5 分钟，可调；cc-bridge 不输出分段 | 分段只用于展示，放使用方更灵活 |

命名（2026-11-12 改）：不写项目 CLAUDE.md（其他用户机器上没有），也不做 cc-bridge 约定目录。模型只靠 cc-bridge 服务说明里的通用规则取名（同一需求同名、先用 `change_sets` 查已有名字），名字不规范由 NCForge 兜底：新名字自动建需求，用户可改名或合并进已有需求（旧名变别名），出包时补丁名以 NCForge 里的需求名为准。

## 2. 方案

### 2.1 数据

- **读变更日志**：Rust 侧按 `seq` 续读，只留工作区内的条目，**读到就把条目和备份内容存进 NCForge 自己的存储**（复用本地历史）。这样不依赖桥的 30 天保留期，也顺带补上「AI 写入前没快照」的缺口。
- **需求表**（每个工作区一份，存 config 目录）：名字、别名（改名前的名字，模型用旧名写的条目照样归这里）、状态（进行中 / 已关闭）、出包记录（zip 名 + 时间，可多次）。变更日志里出现新名字就自动建一条。
- **名字兜底**（不预先约束模型取名）：需求卡片上可「改名」「合并到…」；与已有需求名很像的新名字（规则同 cc-bridge 的疑似敲错判定）直接提示合并。合并后旧名进别名，之后用旧名写的条目自动归到新需求。
- **文件归属** = 变更日志里的 `changeSet` + 在 NCForge 里手改时的「当前需求」+ 人工认领。只对 SVN 改动列表里的文件有意义；文件提交到 SVN 后自然从审查里消失。
- **改动块级归属**（混改提示与原因显示的基础）：对每个文件，把「SVN BASE → 各次 AI 写入前后 → 当前」这一串版本逐段对比，追踪当前每一行是哪一步引入的（类似 blame），得到「这一行属于哪个需求、原因是什么」。
  - 某一步的「写后内容」取自下一次写入的备份（哈希对得上时）或当前文件。中间有人动过、又没留下内容时，先查 NCForge 本地历史，查不到就把那一段标「来源不明」，不硬猜。

### 2.2 界面（先出设计稿）

**需求审查页**
- 左栏：进行中的需求（名字、文件数、未审块数、是否出过包）+ 「未认领」。
- 选中需求后两种视角：
  - **上线视角（默认）**：该需求的文件逐个对比 SVN BASE，即补丁上线后真正生效的改动。复用 `SvnDiffEditor` / `MultiFileDiffPanel`。
  - **过程视角**：AI 每一步改了什么、`reason` 是什么；可「对比本需求改之前」。
- 改动块旁显示原因（来自引入这些行的那一步的 `reason`）。
- **混改提示**：同一文件里属于别的需求的改动块标黄，写「属于需求 Y」——NC 补丁整类替换，出这个包会把 Y 的改动一起带上线。
- **已审按改动块落盘**：AI 再改后只有变了的块要重审；提供「只看上次审完之后的新改动」。
- 「未认领」：SVN 列表里不属于任何需求的文件，按时间分段（NCForge 按改动时间自己算，默认 5 分钟），可勾选「归入需求 X」。
- **两种审查方式**（设计稿 `design/按需求审查-P1-设计稿-2026-11-12.html`）：方案一 =「审查改动」列表加「按模块 / 按需求」分组，逐文件审；方案二 = 顶部视图切换加「按需求审查」，左栏需求卡片、右侧整个需求的文件连续滚动对比（审完自动折叠、顶部可跳文件）。两者读同一份数据、共用已审状态，在一处审过另一处也算审过。
- 页内直接「出包」：跳补丁页并带入名字与文件。

**状态栏「当前需求」**：在 NCForge 里手改保存的文件归到当前需求；未选则进未认领。

**补丁页**：
- 「从需求带入」：名字填进补丁名，只勾该需求的文件（文件列表仍来自 SVN，只是预先勾选）。
- 出包前拦三类：混改文件、还有未审块、AI 改完后有人动过（当前哈希 ≠ 最后一次 `after`）。都是提示确认，不硬拦。
- 出包成功记出包记录；之后该需求又有改动时提示「出包后又改了 N 个文件」。
- 补丁名框里改名（如补清单号）时询问是否同步改需求名（旧名自动变别名）。

cc-bridge 没装 / 没开 / 版本旧时：需求审查页照样可用（靠当前需求 + 人工认领），只是没有原因和过程视角。cc-bridge 的变更日志**默认关闭**（2026-11-12 定）：读不到日志目录或长时间没有新记录时，审查页顶部提示「在 cc-bridge 设置 › 备份与审计里开启变更日志，并让 AI 客户端重新连接」（并进 P1）。

## 5. 已确认的界面细节（2026-11-12）

1. 变更日志里出现过需求名或用户建过需求后，第一次自动切到「按需求」分组，之后记住用户选择。
2. 改动块标注默认显示，「显示设置」里可关。
3. 「已审并看下一项」文案不改；按需求分组时只标当前需求的块，悬停提示写明。
4. 第一次进版本控制默认落在「审查改动」，之后记住上次的视图。
