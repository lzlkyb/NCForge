# 搜索内容包（Content Pack）· 开发清单与实测记录

> 2026-11-08。目标：把「内容搜索」从「每次查询重新走目录 + 逐个 open + 整份解码」改成「查一份常驻的内容快照」，
> 让首次与再次搜索都进 100ms 级，且**不需要用户改系统设置、不需要管理员权限、不新增常驻进程**。

## 1. 问题与基线（本机实测，工作区 `C:\work\aier\newar`）

| 项 | 实测 |
|---|---|
| 目录 / 目录项 / 文本候选 | 10 316 / 34 154 / 8 255（73.1 MB） |
| 只 readdir 走全树 | 0.93 ~ 1.37 s |
| 走树 + 逐文件 stat | 2.2 ~ 4.3 s |
| 冷缓存逐个读这 8 255 个文件 | **97.0 s（11.75 ms/个）** |
| 热缓存再读一遍 | 1.5 s（0.18 ms/个） |
| 在 74.3 MB 拼接文本上扫一个词 | **18.6 ~ 28.6 ms** |

结论：慢的不是匹配算法，是 **8 255 次 open**（实时防护逐个拦）和**每次重走目录**。
冷/热差 65 倍说明瓶颈在 I/O 形态，不在 CPU。

## 2. 同类实现对照（2026-11-08 核对）

| 项目 | 做法 | 对我们的可借鉴点 |
|---|---|---|
| `zeux/qgrep` | 全库 LZ4 压缩内容包（~5x）+ 每 chunk 4-gram Bloom（约语料 0.4%），chunk 级增量 | **与本方案同构**：内容可以存，但要有分块、要能只换坏块 |
| IntelliJ `TrigramIndex` | 磁盘 trigram 倒排 + 未保存文档的内存增量索引 | 查询先求候选、再逐文件确认；未保存内容必须单独一层 |
| `google/codesearch`、`sourcegraph/zoekt` | trigram 倒排，索引与内容分离 | 索引体积通常是语料 30%~100%，74 MB 场景不划算 |
| Cursor（2025） | 稀疏 n-gram，postings 顺序写盘、只 mmap 哈希查找表 | 索引不存正文；查询二分找 offset |
| ripgrep / VSCode / Zed | 不建索引，每次扫（VSCode 拉 ripgrep 子进程） | 冷启动同样受 open 成本拖累；本机不适用 |

**同类实现都不把明文常驻内存**：qgrep 存 LZ4 压缩包、IDEA/zoekt/Cursor 存倒排索引（只存指针）。
我们这里反过来——**不压缩、常驻 74 MB 明文**。这是有意的偏离，理由见 §3.0（实测解压比扫描贵十倍），
不是没查就自己发明。

## 3. 设计

### 3.0 为什么最后没压缩（实测推翻初版判断）

初版打算用 LZ4 分块压缩（74.3 MB → 18.5 MB，4.0x），理由是想省磁盘与首次读盘。实现完实测：

| 方案 | 磁盘 | 单线程整库扫描 | 说明 |
|---|---|---|---|
| LZ4 分块（18.5 MB） | 18.5 MB | **~580 ms**（解压 536 ms + 扫描 45 ms） | 解压比它省下的活贵十倍 |
| 不压缩（74.3 MB） | 74.3 MB | **~12 ms** | 只做切片 + memmem |

搜索是「每改一次关键词就跑一次」的高频操作，580 ms 里 92% 是重复解压同一份数据。
换成不压缩：**查询 12 ms**，代价是磁盘多 55 MB、进程多驻留 74 MB 文本。
用「磁盘 + 内存」换「每次查询的 CPU」，在这个场景是明显划算的——也让「首次与再次一样快」成立。

### 3.1 文件布局（`{config_dir}/search-pack/`）

| 文件 | 内容 |
|---|---|
| `pack.bin` | 顺序拼接的 UTF-8 文本块（1 MB/块），实测 74.3 MB |
| `pack.idx` | JSON：`{version, root, built_at, bin_len, chunks[], files[], skipped}`；`files` 存 `path/size/mtime/chunk/off/len` |

- 版本号不符 / root 不符 / `bin_len` 对不上 / 块越界 → 直接当没有包，重建（自愈，不弹错）。
- `pack.idx` 里的 `files` 同时是「转到文件」与「全部替换」的文件清单来源。

### 3.2 建包

1. 走树规则**与现有搜索完全一致**：`SKIP_DIRS`、`SKIP_EXTS`（`has_binary_ext`）、`MAX_SEARCH_BYTES = 4 MB`、前 8 KB 含 NUL 视为二进制。
2. 内容按 `workspace::decode_lossy` 解码成 UTF-8（GBK 一并归一），追加到当前块；块满 1 MB 就换块。
3. 文件按相对路径排序后分组，保证同一份工作区反复建包得到同样的块划分（增量才有意义）。
4. **增量**：旧表里某个块的全部文件 `size + mtime` 都没变 → 直接搬旧块字节，不重读；
   否则只重读这一块涉及的文件。整包写临时文件后原子替换（`atomic_file`）。
5. 建包在后台线程跑，带 `building` 去重；期间搜索走磁盘路径。
6. **排除包目录自身**：配置目录被指到工作区内时，不能把 `pack.bin` 当源码收进来。

### 3.3 查询

- 每块零拷贝切片得到每个文件的 `&str`（包内保证合法 UTF-8）。
- 纯文本 + 区分大小写 + 非整词时，先用 `memchr::memmem` 做**整文件快速否决**，未命中不切行。
- 切行与高亮仍走现有 `Matcher::spans` / `clip_with_ranges`，`SearchOutcome` 契约不变，前端零改动。
- 块级并行（`std::thread::scope`，上限 8），块内文件顺序扫，结果按 `(路径, 行号)` 排序，与磁盘路径一致。
- 范围（`dirs`）与掩码（`include`）在**包内按相对路径过滤**，不重新走树。

### 3.4 未保存内容（overlay）

搜索语料 ≠ 磁盘内容：正在编辑的文件有未保存改动。前端（`lib/searchOverlay.ts`）把 dirty 的
Monaco model 作为 `overlay: [{path, text}]` 传上来，后端**先用 overlay 扫、再从包里跳过这些路径**。
单文件超 200 KB 或累计超 4 MB 的不传。

### 3.5 新鲜度

- 文件监听 `watcher` 的 flush（任何 `pending` 变更，不只 `.java`）调 `content_pack::mark_dirty()`，
  静默 1.5 s 后做一次增量重建。
- 工作区切换 / 包 root 不匹配 → 下一次搜索触发重建，期间回落磁盘路径。

## 6. 不做（明确留到以后）

- trigram / 稀疏 n-gram 倒排索引：语料 ≤ 300 MB 时收益不抵复杂度。
- 压缩存储：实测解压成本是扫描的 10 倍，已否决（见 §3.0）。
- Bloom 过滤器：整包扫描只有 12 ms，没有可省的。
- 把所有工程拼成**一个**共享包：按工程根各一份（见 §7），便于单独失效与增量重建。

## 7. 第二轮：把「还有 4 条没优化完」补齐（当日 12:xx）

| 档位（全量 8 225 文件） | 一轮 | 二轮 | 说明 |
|---|---|---|---|
| 区分大小写，无命中 | 13.0 ms | 13 ms | 已有 memmem 预筛 |
| **忽略大小写（界面默认），无命中** | **337.5 ms** | 待测 | 一轮完全没预筛，逐字节 `eq_ignore_ascii_case` |
| 忽略大小写，常见词 | 81~92 ms | 待测 | 命中 200 条就停，只扫 1/6 |
| 忽略大小写 + 整词 | 113~133 ms | 待测 | 同样没有预筛 |
| 正则 | 900~1121 ms | 待测 | 每文件逐行 `find_iter`，8225×N 次调用开销 |

### 7.1 预筛扩到所有纯文本档（T8）

`Matcher::quick_needle()` 换成 `Prefilter`：
区分大小写走 `memmem`；忽略大小写走 `memchr2` 找首字节的两种大小写变体，再逐位
`eq_ignore_ascii_case` 验证（与 `plain_spans` 同为只折 ASCII，多字节 UTF-8 不动）。
**整词也放行**——「子串必须出现」是命中必要条件，与边界判定无关。
两条路径（包 / 磁盘）都接上 `file_may_match()`；新增单测「逐行有命中 ⇒ 预筛不得判否」。

### 7.2 正则走整文件预判，而不是抽字面量（T9）

原计划用 `regex-syntax` 抽必要字面量。改走更保守的做法：编译同一模式的 `(?m)`
版本，在**整个文件文本**上先 `is_match` 一次，没有就跳过逐行切分。
逐行扫描时 `^` / `$` 是行边界，`(?m)` 才能保持等价；`\A` / `\z` / `\Z` / `(?-m)`
锚的是整段文本，一律**放弃预判**，宁可慢也不漏结果。单测守着「中间行的 `^class` 不许被否决」。

在此基础上加 `regex-syntax` 抽**必需字面量**（`required_literals`），用 memmem 再挡一层：
`Seq` 是「至少出现一个」的并集，一个文件里所有字面量都不出现就必然无命中。
HIR 必须用与 `RegexBuilder` 相同的大小写标志解析——忽略大小写是 Unicode 折叠
（`ſ`↔`s`），字节层 ASCII 预筛会静默漏结果。集合变成无限集、字面量过长/过短、
含前后顾或绝对锚点，一律返回 `None` 不预筛。**区分大小写的正则从 ~500–1100 ms
降到 ~25–50 ms**；忽略大小写且模式是长 ASCII 单词时集合会膨胀成无限集，
只能退回整文件 `(?m)` 预判，仍是本轮唯一有感知的残余（见 §7.5）。

### 7.3 多根：依赖工程也各有一份包（T10）

- 目录 `{config_dir}/search-pack/<根键 FNV-1a>`；0.2.0 的单根布局在首次同根访问时
  自动搬进子目录，省掉升级后重新读 8 千个文件的两分钟。
- 状态从单 `Option<Arc<Pack>>` 改成 `根键 → Arc<Pack>` + LRU；**内存上限 320 MB**、
  磁盘最多 8 份子目录（按 `pack.idx` mtime 淘汰，跳过内存里还加载着的）。
- 建包走单线程**串行队列**，多个依赖工程同时 `ensure` 不会并发抢磁盘；
  `ensure_primary` 只登记文件监听盯着的那个根，改文件只重建它。
- `search_projects` 在循环前为所有工程排队：第一次「全部工程」搜索付一次建包成本，
  之后每根都是毫秒级。

### 7.4 首次建包期给用户一句人话（T11）

`search_pack_status` 前端接入（`lib/searchPackStatus.ts` → `SearchTab` 细条提示），
从契约 `ALLOW_UNUSED` 里移出。轮询只在「没建好 / 队列非空」时存在，建完自停；
窗口不可见一律停（`useAppHidden`），换工作区与每次搜索各唤醒一次。
提示写明「本次搜索仍逐个读文件、建好自动变快、无需任何操作」，不让人以为又慢回去了。

- 0.2.0 老布局在首次加载时自动搬进 `search-pack/30523d19bf56dd9a/`，**没有重新读盘**；
  `packed_roots: 1` 与真机目录都已核对。
- 正确性：`预筛不漏命中`（7 组词 × 大小写/整词组合）、`正则预判不漏行首锚点`、
  `正则字面量预筛不漏命中`（8 个模式 × 两档大小写）、`legacy_pack_is_adopted_into_root_dir`、
  `pack_and_disk_agree`（8 组选项包/磁盘逐条相同）、`SearchTab` 组件 17 例（含 2 例提示条）。
- 唯一残余：**忽略大小写的长 ASCII 正则**仍是 0.5~0.7 s（dev 构建）。原因是 Unicode

  trigram 索引或给正则专门建 n-gram，按当前语料规模不划算。release 构建会明显更快。
