# 补丁应用/回滚 与 日志归因 方案设计

> 日期：2026-11-01　依据：**本机 `D:\ncc\1909home` 实测**（非文档推断）+ 三个真实补丁 zip 解包
> + `ierp/bin/logger-config.properties` 原文。凡标「实测」的都可复验，命令附在 §8。
>
> 两个功能都属于"部署闭环 / 现场救火"，与三期元数据无依赖。

---

## 0. 一页结论

| 项 | 补丁应用 / 回滚 | 日志归因 |
|----|----------------|---------|
| 现状 | 只有出包（`patch_build.rs`），**应用与回滚全靠手工解压** | **零**（现有"日志"是我们抓中间件 stdout，不是 NC 的 nclogs，见 §1.6） |
| 关键实证 | zip 带统一 `replacement/` 前缀，**去掉前缀即 1:1 落到 HOME 根** | 1909 是 `nclogs/server/*-log.log`，**44 个条目（42 个 .log + 2 个子目录）**，5MB×20 轮转 |
| 最大坑 | 覆盖后**必须重启才生效**；回滚要防"人手又改过" | 日志是 **GBK**，按 UTF-8 读全是乱码；堆栈行不带前缀 |
| 估时 | ≈ 5.5 人日 | ≈ 6 人日 |
| 依赖 | 复用 `patch_view::Section` / `target_dir` 做逆映射 | 复用 `nc_home.rs` 定位 HOME |

**两个意外收获**（直接改变设计）：

1. **`callid` 就是 traceId**（`1793352946225-8333`），跨 logger 可把所有日志按一次请求串起来。
   归因不需要猜关联，NC 自己给了。
2. **`warningsql-log.log` 自带性能数据**：`msg` 尾部带 `|costtime=17||rownum=5284||defcol1=…|`。
   也就是说"慢 SQL 定位"不用我们算执行计划，**NC 已经把耗时和影响行数记好了**，排序即可。

## 1. 实证：这台机器上的真实形态

### 1.1 补丁 zip 的结构（实测三个真包）

`D:\AItool\aiwork\_patchcmp\new_patch.zip`、`eyeinvoice-perf\async\backup_patchzip_*.zip`、
`_esign3\old_auth_patch.zip` 结构一致：

```
<描述>_<年月日>.zip
├── CHANGES.md                      ← 放 zip 根
├── <若干>.sql                      ← 放 zip 根，**不自动执行**
└── replacement/                    ← 统一前缀
    ├── modules/<模块>/classes/<包路径>/X.class + X.java
    ├── modules/<模块>/META-INF/classes/<包路径>/…
    ├── modules/<模块>/client/classes/<包路径>/…
    ├── modules/<模块>/hyext/classes/…            ← 实测 arap 就是这层
    ├── modules/<模块>/META-INF/*.upm
    └── hotwebs/<应用>/…
```

**`replacement/` 到 HOME 是纯前缀剥离，去掉即 1:1**：

```
replacement/modules/arap/client/hyext/classes/nc/ui/arap/actions/X.class
        ↓ strip "replacement/"
D:\ncc\1909home\modules\arap\client\hyext\classes\nc\ui\arap\actions\X.class
```

这与出包侧 `patch_view::target_dir()` 生成的是同一套路径，所以应用侧**不需要另写一套规则**，
把 `target_dir` 反过来用即可——这也是不引入"两套映射对不上"风险的关键。

### 1.2 HOME 落位实测

| 段 | 实测存在的目录 | 计数 |
|----|--------------|------|
| public 本体 | `modules/<m>/classes` | 245 个模块 |
| public hyext | `modules/<m>/hyext/` | 含 hyext 的共 **51 处** |
| private | `modules/<m>/META-INF/classes` | 有 |
| client | `modules/<m>/client/classes`、`client/hyext/` | 有 |
| hotwebs | `hotwebs/nccloud/{WEB-INF,resources,html}` 等 | 10+ 应用 |

注意：`modules/arap/hyext/` 下只有 `lib`，**没有 `classes`** —— 说明 hyext 层是按需才建 `classes`，
应用补丁时要能**自己创建目标目录**，不能假设它存在。

网上流传的 `$NC_HOME/nclog/run.log` + `err.log` 是 **NC57/NC65** 的。1909 实测：

轮转参数来自 `ierp/bin/logger-config.properties`：

```properties

warningsql.size.maxSize=5MB
warningsql.size.maxIndex=20
warningsql.pattern=$$callid=%X{serial}  $$thread=[%t] $$userid=%X{user} $$ts=%d{yyyy-MM-dd HH:mm:ss} $$msg=%m %n

```

🔴 **结论：不要把目录和文件名写死。** 这张 properties 就是权威映射表
（logger → 文件路径 + 轮转方式 + 字段集），NC65/BIP 换了版本它也在。
归因侧做成"读 config 得清单"，比硬编码 44 个文件名活得久。

### 1.4 日志行格式（实测原文）

```
$$callid=1793352946225-8333 $$thread=[http-bio-80-exec-2] $$host=127.0.0.1 $$userid=#UAP# \
  $$ts=2026-10-30 17:35:47 $$remotecall=[nc.login.bs.INCLoginService] $$debuglevel=ERROR  \
  $$msg=BusiCenterManageImpl:getBusiCenterVOsFromDB begin
```

四条硬约束：

| 约束 | 实测证据 | 影响 |
|------|---------|------|
| **GBK 编码** | `defcol1=�򿪽ڵ�-ҵ��Ԫ`（UTF-8 读出来是乱码） | 必须按 GBK 解码，否则中文全废 |
| **CRLF** | `cat -A` 显示 `^M$` | 不能用"只按 `\n` 切"的写法漏掉 `\r` |
| **堆栈行不带前缀** | `\tat nc.bs.framework.server.AbstractContainer.register(...)` | 记录 = 1 条 `$$` 行 + N 条裸行 |
| **`debuglevel` 不可信** | `$$debuglevel=ERROR` 但 msg 是 `###udapte table success` | **不能按 level 过滤/着色判严重性** |

实际异常块长这样（首行记录后跟裸行）：

```
$$callid= $$thread=[Thread-14] … $$msg=info: module=mmbcm-scm component=deviceregister, error at D:\ncc\1909home\modules\mmbcm-scm\META-INF\accessright.upm
nc.bs.framework.exception.DuplicateException: Detail Message: deviceregister
	at nc.bs.framework.server.AbstractContainer.register(AbstractContainer.java:92)
	at sun.reflect.GeneratedMethodAccessor33.invoke(Unknown Source)
```

两个可利用点：

- `msg` 里含 **HOME 绝对路径**（`D:\ncc\1909home\modules\mmbcm-scm\...`）→ 归因结果可直接跳转到文件。
- 本机日志里已出现 `DuplicateException: deviceregister`，说明"组件重复注册"是真实高频问题，
  应该进规则表第一批。

### 1.5 慢 SQL 有现成数据源（实测）

`warningsql-log.log` 的 msg 尾部自带三个字段：

```
… from org_orgs where pk_group = ( … )|costtime=11||rownum=44618||defcol1=裸开节点-业务单元|
```

- `costtime` = 毫秒（11ms、17ms 这种小值也会记，阈值由 NC 侧控制）
- `rownum` = 影响行数
- `defcol1` = 业务描述（GBK 中文）

→ "慢 SQL 定位"不需要解析执行计划，**按 costtime 排序取 TOP N** 即可。
这比我们自己去 `db_stats` 抓 stats 更接近现场真实入口。

### 1.6 澄清：现有"日志"不是这个

`server.rs` 的 `log_path()` 指向 `{config_dir}/logs/middleware.log`，
内容是**我们自己 spawn 中间件时抓的 stdout**，用来判断"启动失败原因"。
与 NC 自己的 `nclogs/` 是两个东西。

→ 日志归因是**新增**，不是改造。两者不合并：一个看"我们怎么起的"，一个看"NC 内部发生了什么"。

## 2. 补丁应用 / 回滚

### 2.1 目标与非目标

**做**：
- 选一个补丁 zip → 校验 → 预演（列出将覆盖/新增哪些文件）→ 应用 → 台账 → 提示重启
- 台账里一键回滚任意一次已应用的补丁
- 冲突检测：目标文件在应用前已被人改过 / 已被别的补丁改过

**不做**：
- 不执行 zip 根目录的 `.sql`（只列出"待手工执行 N 个"，附路径）
- 不做 jar 内类替换（我们的补丁只出目录文件）
- 不做"打补丁到远端服务器"（无 SSH，超出范围）
- 不做 `_src.jar` 双产物

### 2.2 数据模型

台账落 `{config_dir}/patch_applied.json`（跟设备走，不进 HOME，不污染产品目录）：

```jsonc
{
  "version": 1,
  "records": [{
    "id": "uuid",
    "patchName": "开票优化_20261030",
    "zipPath": "D:\\...\\开票优化_20261030.zip",
    "zipSha256": "…",            // 同一份包重放能被识别
    "ncHome": "D:\\ncc\\1909home",
    "appliedAt": "2026-10-30T15:14:00+08:00",
    "files": [{
      "rel": "modules/eye/classes/nccloud/vo/eye/portal/EyeInvoiceTaskVO.class",
      "before": { "existed": true, "backup": "…/20261030T151400/files/0.bin", "sha256": "…" },
      "after":  { "sha256": "…" }
    }],
    "sqlFiles": ["pu_eyeinvoicetask.sql"],
    "rolledBackAt": null
  }]
}
```

`before.sha256` 与 `after.sha256` 两个哈希是关键：**回滚时靠它判断"有没有人在中间动过手"**。

### 2.3 应用流程

```
1. 选 zip → 读条目（不解压全文）
2. 校验（任一不过即中止，不落任何文件）
   - 每个条目必须以 replacement/ 开头，否则报"不是 NC 补丁包"
   - 剥前缀后按 patch_view::Section 判段，非法段（不认识的第一级目录）拒绝
   - 路径必须无 ".."、非绝对、无盘符（防穿越）
   - 模块目录不存在 → 标记"新模块"（黄），不拒绝但要在预演里显眼
   - 文件名大小写原样保留（HOME 可能在 Linux 上）
3. 预演列表：覆盖 N / 新增 M / 新模块 K / SQL S（只显示，不动盘）
4. 用户确认 → 开始
   - 目标文件存在则先备份到 {config_dir}/patch_apply/<id>/files/<序号>
   - 原子写（写 .tmp → rename），复用 atomic_file.rs
   - 单文件失败即停，已写的按台账回滚（半成品不能留）
5. 记台账
6. 结束提示：① 有 S 个 SQL 待手工执行；② 服务在跑 → 提示需重启生效
```

### 2.4 回滚流程

```
1. 从台账选一条
2. 逐文件比对当前 sha256 与记录的 after.sha256
   - 一致 → 直接还原 before
   - 不一致 → 标"已被修改"，默认**不覆盖**，要用户逐个勾选
3. before.existed=false 的 → 删除（不是还原）
4. 删除目录只在"回滚后为空"时尝试，失败忽略
5. 台账标 rolledBackAt（不删记录，保留审计）
```

### 2.5 边界与硬坑

| 坑 | 处理 |
|----|------|
| **覆盖 class 不会自动生效** | 应用完必须提示重启；不做"静默假装生效" |
| 服务在跑时覆盖 jar | 我们的包不含 jar，但校验阶段若发现 `.jar` 条目 → 拒绝并说明"服务停止后再试" |
| 同一补丁重复应用 | 用 `zipSha256` + `ncHome` 判重，提示"已应用过，是否重放" |
| 两个补丁改同一文件 | 应用第二个时 `before.sha256` 与第一个的 `after.sha256` 比对，不一致 → 提示"被 <补丁名> 改过" |
| 回滚链断裂 | A 装了、B 装了、先回滚 A → 拒绝，提示"需先回滚 B"（栈式） |
| HOME 被换成另一份 | 台账记 `ncHome`，不匹配时只警告不阻止（现场常换 home） |

## 3. 日志归因

### 3.1 目标与非目标

**做**：
- 自动发现日志文件（读 `logger-config.properties`，回退到目录探测）
- 解析成结构化记录（callid / thread / userid / ts / logger / msg / 堆栈）
- 按规则判"这是什么问题 + 大概原因 + 该看哪里"
- 按 callid 把一次请求跨 logger 的日志串起来
- 慢 SQL 榜（costtime 排序）

**不做**：
- 不做全文检索式日志浏览器（工程搜索已经有了，别重复）
- 不做实时 tail 的通用终端（`ServicesTab` 已有专用面板）
- 不接大模型（规则是确定的，接模型只会把确定性丢掉）
- 不改 `logger-config.properties` 的 level（改配置是现场运维动作，要人确认）

### 3.2 文件发现

```
优先：<home>/ierp/bin/logger-config.properties
      解析 <logger>.file → 展开 ${server} = "server"（实测 server 目录就是它）
      解析 maxSize / maxIndex / .time
回退：目录探测 <home>/nclogs、<home>/nclog、<home>/ierp/nclog
只读：当前文件 + 最近 R 个轮转（默认 R=3）
排序：按 mtime 倒序，默认只看最近改过的 5 个文件
```

🔴 不能全量扫：180 个文件、单文件 10MB，全读会卡死 UI 且没必要。

### 3.3 解析器（Rust 侧）

放在 `src-tauri/src/nc_log.rs`，只回传"记录"不回传原文：

```rust
pub struct LogRecord {
    pub file: String, pub line_no: u32,
    pub ts: Option<String>,          // 2026-10-30 17:35:47
    pub call_id: Option<String>,     // = traceId
    pub thread: Option<String>,
    pub user_id: Option<String>,
    pub remote_call: Option<String>, // 类名，能直接跳源码
    pub level: Option<String>,       // 只展示，不用于过滤
    pub msg: String,
    pub stack: Vec<String>,          // 续行（裸行）
    pub cost_ms: Option<u64>,        // warningsql 的 costtime
    pub rows: Option<u64>,
}
```

解析要点（全部来自 §1.4 实测）：

1. 按字节读，`encoding_rs::GBK` 解码（**先试 UTF-8 严格解码，失败再 GBK**，因为少数 logger 可能被配成 UTF-8）
2. 行切分兼容 `\r\n` / `\n`
3. 以 `$$` 开头 = 新记录；**其余非空行 = 上一条记录的续行**
4. `$$k=v` 用 `$$` 切段再取首个 `=`；值里可能含 `=`（SQL 里全是），所以**只切第一个 `=`**
5. `msg` 是最后一段且可能跨多行——`$$msg=` 之后到行尾全算 msg
6. `remotecall=[类名]` 去掉方括号，直接作为"跳转源码"的入参
7. `warningsql` 的 `|costtime=(\d+)|` 用后缀正则抽

### 3.4 归因规则表（第一版 12 条，全部有实测/社区证据）

| 触发 | 判定 | 给用户的动作 |
|------|------|-------------|
| `ORA-00942` | 表/视图不存在 → **多半是元数据发布了但表没建**，不是代码错 | 一键查 `all_tables` 有无该表；跳元数据体检（三期） |
| `ORA-00001` | 唯一约束冲突 → 复制单据/并发写 | 显示约束名，定位到表 |
| `ORA-01000` | 游标超限 → 游标没 `close` | 提示"每 N 次复现"的用法（有前科：第 298 次） |
| `ORA-01652/01653` | 临时表空间/表空间不足 | 给 DBA 命令，不自动执行 |
| `ClassNotFoundException` | 类路径缺 jar | 跳"依赖闭包"看该类归属模块 |
| `NoSuchMethodError` | 编译期/运行期两个版本 | 提示查同名类的两份来源（newar vs pm 有 18 处前科） |
| `DuplicateException … deviceregister` | 组件重复注册（`.upm` 重复） | **本机日志实测存在**；跳 `.upm` 所在 META-INF |
| `OutOfMemoryError: Java heap space` | 堆不足 | 指向 VM 参数配置 |
| `OutOfMemoryError: Metaspace/PermGen` | 类加载泄漏（反复重部署补丁） | 提示"补丁重启次数" |
| `ORA-01001` / `ORA-01008` | 嵌套游标/绑定变量 | 关联到 P0 路由那套（refcursor） |
| `PLS-00707` / 自定义函数 | PL/SQL 兼容 | 提示走 Java 桥兜底 |
| 前端 `charindex` / `找不到元数据文件` | 数据源混用（SQLServer + Oracle） | 提示查 `ncchome` 数据源配置 |

规则表落**数据文件**（`resolve/nc_log_rules.json` 或 Rust 常量表），不写死在分支里——
加规则不该改逻辑代码。

### 3.5 按 callid 串联

这是最省力也最有价值的一步：用户在 `nc-log.log` 看到一条异常，点"追踪这次请求"
→ 拿 callid → 在所有 logger 里捞同 callid 的记录 → 按 ts 排序 → 出一条时间线：

```
14:59:41  [http-bio-80-exec-7]  nc        → 进入 XXService
14:59:41  [http-bio-80-exec-7]  metadata  → 加载实体 md_class
14:59:41  [http-bio-80-exec-7]  warningsql→ costtime=127 rownum=44618
14:59:42  [http-bio-80-exec-7]  nc        → ORA-00942
```

只扫当前 + 最近轮转，且 callid 前缀是 epoch 毫秒 → **可以先按时间窗口把文件筛掉**（只读 ts 落在
该毫秒 ±5 分钟内的文件），避免全量读。

### 3.6 UI 形态

放在哪：`ServicesTab` 旁边加一个 **"NC 日志"** 页签（不放数据库页，也不塞进工程搜索）。

```
┌ 日志源 ──────────────────────────────┐
│ [全部] [nc] [sql] [warningsql] [pfxx] …  ← 从 logger-config 生成
│ 时间范围: [最近 1 小时 ▾]   等级: 全部   [只看异常]
├──────────────────────────────────────┤
│ ⚠ ORA-00942 表或视图不存在        15:35:47  nc-log.log:12   [看栈] [追踪] [跳元数据]
│ ⚠ DuplicateException deviceregister 15:23:47 nc-log.log:1    [看栈] [跳 .upm]
│ 🐢 select pk_org…  costtime=1274ms  14:59:41 warningsql:3557 [看SQL] [复制到SQL窗口]
├──────────────────────────────────────┤
│ 详情：message / 栈 / 同 callid 时间线   │
└──────────────────────────────────────┘
```

两个细节：
- 慢 SQL 那条的"复制到 SQL 窗口"直接接到现有 `DbTab`（我们有 SQL 编辑器，这是别人没有的顺滑点）。
- `remotecall=[类名]` 和 msg 里的绝对路径 → 双击直接开文件；这是"日志 → 代码"的桥。

## 4. 两个功能的共用底座

| 复用点 | 现状 |
|--------|------|
| HOME 定位 | `nc_home.rs` 按内容识别，直接用 |
| 段/落位映射 | `patch_view::{Section, target_dir, parse_path}`，应用侧反向用 |
| 原子写 + 备份 | `atomic_file.rs`、`svn_backup.rs` 的范式 |
| 大文件/编码 | `encoding_reg.rs` 有编码判定经验；**`encoding_rs 0.8` 已在 Cargo.toml 里**，不用加依赖 |
| 归因展示范式 | `compile_diag.rs` 的 `{outcome, message}` 结构可沿用 |

---

## 5. 落地顺序与工作量

建议**先日志归因，再补丁应用**（虽然补丁应用收益更大）。理由：
日志归因是纯读操作，风险低、当天就能看到东西；补丁应用要写产品目录，一旦有 bug 是"把现场搞坏"，
需要更充分的夹具测试。且日志归因能顺带把 `nc_home` 的日志路径探测补上，补丁应用不依赖它。

| 批 | 内容 | 估 |
|----|------|-----|
| L1 | `nc_log.rs`：读 logger-config → 文件清单；GBK/CRLF/续行解析器；单测用真日志切片当夹具 | 2.5 d |
| L2 | 规则表 + 归因 + callid 串联 | 1.5 d |
| L3 | "NC 日志"页签 UI + 跳转（源码 / .upm / SQL 窗口） | 2 d |
| P1 | `patch_apply.rs`：zip 校验 + 逆映射预演（只读，不改盘） | 1.5 d |
| P2 | 应用（备份 + 原子写 + 台账）+ 回滚 + 冲突检测 | 2.5 d |
| P3 | 补丁页签的"已装补丁"列表 + 应用/回滚对话框 | 1.5 d |

合计 **约 11.5 人日**，L1~L3 与 P1~P3 之间无依赖，可分段验收。

> 批次标号说明：本文的 L1~L3 / P1~P3 是**批次编号**，不是优先级档位。
> 两个功能的优先级档位见《P0-P1能力补齐-总体规划》——它们同属 P0。

## 7. 明确不做

| 不做 | 理由 |
|------|------|
| 自动执行补丁里的 `.sql` | 数据变更不可逆，必须人确认 |
| 打补丁到远程服务器 | 无 SSH 通道，且现场通常就是本机 |
| 通用日志终端 / tail -f | 已有专用面板，重复建设 |
| 改 `logger-config.properties` 的 level | 运维动作，改错会把日志打爆 |
| 按 `debuglevel` 过滤判严重 | 实测该字段不可信（§1.4） |
| 用大模型做归因 | 规则确定，接模型只会引入不确定性 |
