## 0. 结论先行

1. **功能面已经够宽，缺的主要是「信任」和「几个收口」。** 编辑、重构、调试、热替换、SVN、数据库、补丁、日志、UPM/元数据都已有实现，
   台账里真正「缺」的只剩零星几条。要替代 IDEA / Eclipse，不是再堆功能，而是让开发者**敢**把一整天的活放在这里做。
2. **信任的第一块基石是「和 Eclipse 的结果一致」。** 今天实测 31 个模块、6030 个可比文件，发现并修了 4 类误报
   （全限定类名、继承链、`ant/lib`、单文件编译看不到新兄弟类）。这说明**编译这一层此前并没有被系统地对过账**——
   同类问题大概率还藏在「代码智能（jdt.ls）」「运行（类路径）」两条线上，它们和 ecj 编译是**三套各自解析类路径的引擎**。
3. **建议分三档推进：**
   - **A 档「对齐且可证明」**（约 8–10 d）：把今天的临时对比脚本做成常驻回归、补齐三套引擎的一致性、修几个已知的静默坑。
   - **B 档「日常顺手」**（约 8–10 d）：新建类模板、客户端一键重启、运行配置、提交前检查、提取参数等，补完日常动作。
   - **C 档「NC 独有的赢面」**（按需，约 6–8 d）：多语资源查询、模块依赖检查、接口/元数据联动，这是 IDEA 和 UAP Studio 都没做好的地方。
4. **不建议做**：内置终端、测试运行器、结构化搜索替换、Profiler 等（台账 §4 已裁剪，触发条件未出现）。

## 2. A 档：对齐且可证明（先做，优先级最高）

### A1　把「与 Eclipse 对账」变成常驻回归　〔2 d〕　✅ 已完成 2026-11-10

> **落点**：`desktop/src-tauri/tests/eclipse_parity_live.rs`（`#[ignore]` 真机回归）+ `tests/fixtures/eclipse_parity_baseline.txt`（白名单）。
> **运行**：`node scripts/rust-gate.mjs test --test eclipse_parity_live -- --ignored --nocapture`；只跑部分模块用 `PARITY_MODULES=aim,gl`。
> **实测**：全量 33 个模块、7267 个源文件、可比对 6057 个，耗时约 9 分钟；差异 2 条（均为 `ic` 里 NCForge 自产的过期 class，已写入白名单并注明原因）。
> **反向验证**：临时去掉 `ant/lib` 后，回归对 `uapbs` 报出差异并失败；恢复后通过。
> **与原计划的差别**：对比逻辑直接写在 Rust 测试里（不另起 node 脚本），避免两套实现漂移；只编 `ModuleLayout` 源根（不含 `src/test`，与生产一致），所以不再有「YBTest 漏报」这类探针盲区。

- **现状**：今天的对比靠一个临时探针测试 + `cmp_eclipse.py`（在 `D:\AItool\aiwork\nc-workbench-m0\`），用完就删，不进仓库，也不会随改动自动跑。
- **做法**：
  1. 抽成仓库内的 `#[ignore]` 集成测试（沿用 `tests/*_live.rs` 的做法）：循环模块 → 整模块编译 → 输出 JSON；
  2. 对比逻辑写成脚本放 `desktop/scripts/`，口径固化（只比非 import 的缺失符号；Eclipse 干净而我们报错 = 误报；Eclipse 过期/混有 NCForge 自产 class 要剔除；见记忆 `reference_ncforge_vs_eclipse_compile_cmp`）；
  3. 基线冻结：把「当前已解释的差异」写成白名单（今天只剩 3 条），新增差异即失败。
- **验收**：改 `compile.rs` / `nc_index.rs` / `eclipse_cp.rs` 后，一条命令得到「误报 0 / 漏报 0 / 白名单外差异 0」。
- **要注意**：探针要传 `.classpath` 的源根，否则回落 `public/client/private`，会漏掉 `src/test`（今天 `YBTest` 就是这么来的）。

### A2　三套引擎的类路径一致性　〔3 d〕 ✅ 容器对照已完成（2026-11-10）；三方逐文件对比未做

- **落地说明**：反编译 `nc.uap.mde` 插件（`CoreUtility.getClasspathEntry` / `ClasspathComputer`）拿到每个容器的真实规则：
  `computeJarsInPath` 只扫下一层（不递归）、排除 `_src/_doc`、收 `.zip`；`computeStandCP` = extension → var → **hyext** → classes → resources → lib；
  模块三容器顺序是「全部模块 public → 全部 client（uap* 先）→ 全部 META-INF」。
  实测对比（`tests/eclipse_containers_live.rs`，两个 `#[ignore]` 测试）发现并修掉三处偏差，现在 jar 集合与同名类先命中顺序都与 Eclipse 零差异：
  1. `framework`/`middleware` 递归收录，多收 32 个 `framework/mwconfig` jar + 6 个 `middleware/was|wls/*/fwejb.jar` + 2 个 `_doc` jar（Eclipse 看不到，引用它们的类在 Eclipse 里是编译错），漏收 `external/lib` 的 1 个 `.zip`；
  2. 模块 jar 按模块分组排列，跨模块同名类谁先命中和 Eclipse 不同（**5974 个类**，例：guava-18、jackson-2.8、bcprov-1.57 被 baseapp/META-INF 抢先）；改为按容器分组；
  3. `stand_cp`（客户端启动类路径用）漏了 `hyext`（189 个 `*/hyext/lib` 二开覆盖 jar）。
- **容器对照表**：

| 容器 | Eclipse 取法 | 我们 | 结论 |
|---|---|---|---|
| Ant_Library | `standCP(ant)` | `ant/lib` 最后追加 | 覆盖；位置偏离（Eclipse 排最前）——实测与其它 jar 无同名类，结果等价 |
| Product_Common_Library | `standCP(NC_HOME, external)` | `lib` + `external/lib` | 覆盖 |
| Middleware_Library | `middleware` 下一层 jar | 同 | 覆盖（已修为不递归） |
| Framework_Library | `framework` 下一层 jar | 同 | 覆盖（已修） |
| Module_Public/Client/Private | 各模块 `standCP(m)` / `(m/client)` / `(m/META-INF)` | `classpath_jars` 模块段 | 覆盖（已按容器分组） |
| Module_Lang_Library | `langlib` 下一层 jar | 未收 | **有意偏离**：1568 个 jar 共 0 个 class（纯语言资源），编译用不到 |
| Generated_EJB | `ejb` 及其子目录 jar | 未收 | 本机 NC home 没有 `ejb` 目录，无内容（如现场有再补） |

- **已知未对齐（有意保留）**：① Eclipse 给 Private/EJB/Middleware 容器加了访问规则（Forbidden/Discouraged），我们的 ecj 不带规则，对「不该引用」的类不会报错（Eclipse 只是警告/错误级别由设置决定，未验证）；
  ② `FIELD_EX_MODULES`（Eclipse 工作区变量）排除的模块我们读不到；③ client 容器里「当前模块」排前面，索引层不知道当前模块；
  ④ `module_class_dirs`（散类目录）仍按模块分组，共 160 个目录/406 个 class，跨模块同名冲突未比对；⑤ 同目录内 jar 排序沿用早期实测的「大写全路径」（与反编译出的 `compareToIgnoreCase` 不同，但实测无类受影响）。
- **未做**：原计划的「5–8 个文件三方（编译 / jdt.ls / Eclipse 产物）逐一对比」——jdt.ls 影子工程和 ecj 共用 `select_jars` + `classpath_jars` 顺序（代码层面已一致），但 jdt.ls 真机诊断没跑。

**A2 原计划原文**（保留对照）：

- **背景**：ecj 编译（`compile.rs` 按 import 挑 jar）、jdt.ls 代码智能（影子工程，`lang.rs`/`shadow.rs`）、中间件/客户端启动（`launch.rs`）
  各有一份类路径逻辑。今天发现的 4 类误报，在编译这条线上修了；`select_jars` 是 jdt.ls 侧的挑 jar 入口，已一并带上前两类，**但没有实测过**。
- **做法**：
  1. 选 5–8 个有代表性的文件（含今天暴露的 `LabeldeptLoadingPlugin`、`WarSysEquipImpl`、`IniStorage`、`SaleImpl`），分别拿「编译问题列表」「jdt.ls 诊断」「Eclipse 产物」三方对比；
  2. 差异归因到类路径来源（jar 挑选 / 类目录顺序 / 容器是否包含），统一到 `nc_index` + `eclipse_cp` 这一个真源；
  3. 排查「ant/lib」这类**整容器遗漏**：把 Eclipse 的 9 个库容器（`Ant_Library`、`Product_Common_Library`、`Middleware_Library`、`Framework_Library`、`Module_Public/Client/Private/Lang_Library`、`Generated_EJB`）逐个对照我们 `classpath_jars` 的覆盖，缺的补、有意偏离的写清楚。
- **验收**：上面几个文件三方结论一致；容器对照表落文档，每个容器标「覆盖 / 有意偏离（原因）」。

### A3　文件索引与外部改动联动　〔0.5 d〕 ✅ 2026-11-10 已落地

- **落地说明**：watcher 批次新增 `filesChanged`（只有文件集变化——新建/删除/改名，或丢事件要求全量重扫——才为真；改内容、`.class`、`.svn` 不算）。
  后端 `Batcher::flush` 直接调 `search::mark_list_dirty()`，前端收到 `fs-changed` 后 `invalidateFileIndex()`；
  `list_files_cached` 遇到脏标记**绕过内存与磁盘缓存真扫**（顺带修了旧 bug：失效只清内存，随后读到的还是旧的磁盘缓存）。
  测试：`watcher::文件集变动才标记_files_changed`、`search::文件集变动后下次取清单必须真扫`。**未做**真机验证（外部建文件→界面搜到）。

**A3 原计划原文**（保留对照）：

- **现状**：`fileIndex.ts` 靠 `invalidateFileIndex` 主动失效；watcher（`notify`）只刷文件树，不通知索引。
  外部工具（SVN 更新、AI、手工拷贝）新建的文件进不了「转到文件」，TTL 5 分钟、磁盘缓存 24 小时。
- **做法**：watcher 收到创建/删除/重命名事件时，合并后调 `search_invalidate_files`；只对「文件集变化」失效，内容修改不触发。
- **验收**：外部新建一个文件，3 秒内「转到文件」能搜到。

### A4　产物目录遮挡与「改了不生效」　〔1.5 d〕 ✅ 2026-11-10 已落地（方案有调整，未做端到端验证）

- **根因**（实测确认）：newar 的模块没有自己的 `.classpath`，工作台把它们编到 `<模块>/classes`；但根 `.classpath` 里有 40 条 src
  把产物写到 `out/<模块>`（riart、gsp、purp、pu、uapbd、baseapp）或默认的 `out/bin`（pubapp、ia 等）。运行用的类路径只按根
  `.classpath` 拼，所以工作台编出的 `<模块>/classes` 根本不在类路径上——改了代码重启也不生效，热替换报「被遮挡」。
- **落地（与原方案的差异）**：原计划「检测 + 用户二选一（输出指向 out / 清理旧产物）」。改输出目录会碰清单/增量编译/清理里「产物必须在模块目录内」
  的安全假设（`safe_join`、重解析点检查、`output_rel`），而「清理旧产物」要删 Eclipse 的文件，都不划算。所以改为**自动排序**：
  `eclipse_cp::push_outputs` 对「没有自己 `.classpath` 且输出不是 `<模块>/classes`」的模块，把 `<模块>/classes` 排在它对应的 Eclipse 产物目录之前。
  工作台编过的类优先、没编过的回落到旧产物，不删任何文件。服务页「被遮挡」告警同步改了：列出遮挡来源目录，
  说明 out/ 旧产物造成的遮挡重启后即可生效（原文案写「重启解决不了」），并给出「重启服务」按钮。
- **限制 / 风险**：① 第一次编译某模块前它的 `<模块>/classes` 不存在，已在运行的 JVM 类路径里没有它，所以该模块的「首次」改动仍需重启；
  ② 在 Eclipse 和工作台之间来回编同一模块时，工作台旧产物会压过 Eclipse 较新的类，切换工具后建议先在工作台重编该模块；
  ③ 源码里删掉的类如果还留在 Eclipse 的 `out/` 里仍会被加载；④ **没做端到端验证**（真的对 riart 改方法体、重启、看到生效），只有单测和真机目录顺序。

**A4 原计划原文**（保留对照）：

- **现状**：`riart`、`gsp` 的类实际从 Eclipse 旧的 `newar/out/<模块>/` 加载，工作台编出的类被 agent 报「被遮挡」，**重启也不生效**。
  痛点调研里「改完不生效且不报错」是最高频事故，这是同一类。
- **做法**：编译/热替换前检测「运行用的类目录 ≠ 编译输出目录」，在界面明确提示（哪个模块、遮挡它的目录），并提供「把输出指向 out 目录」或「清理旧产物」两个动作，二选一由用户确认。
- **验收**：对 riart 的一个类改方法体，要么生效，要么界面明确告诉用户原因与处理办法。

### A5　Eclipse 把 UTF-8 文件按 GBK 编的差异　〔1 d（调研）+ 视决策〕

- **现状**：newar 有 53 个 UTF-8 源文件没登记到 Eclipse 偏好，Eclipse 把其中的中文字符串编成乱码；NCForge 逐文件探测编码，编出来是对的。
  同一份代码两个工具产物不同，线上用哪个编的就是哪个行为。**线上补丁是否乱码未核实。**
- **做法**：先核实线上补丁里这些类的字符串常量；再由用户决定「以谁为准」（见 §6 决策 2）。

## 6. 需要你拍板的决策

1. **「替代」的范围**：是「替代 Eclipse（UAP Studio 级的 NC 开发）」，还是「Eclipse 与 IDEA 都不再打开」？
   后者会把 B6（超大文件）、更完整的重构、格式化提到更高优先级。
2. **UTF-8 / GBK 以谁为准**（A5）：A. 以 NCForge 为准（编出来正确，但与 Eclipse 产物不同）；B. 以 Eclipse 为准（保持字节一致，包括乱码）；
   C. 两边都标出这 53 个文件，由人逐个决定。我倾向 C，再根据线上核实结果收敛到 A。
   **2026-11-11 用户决定：A**，并加「出补丁时提示」（核查结果见 A5 核查报告）。
3. **热替换要不要做「动态挂载」**（B3 批 F）：不做则只有「由工作台启动的 NC」才能热替换；做则可挂到已运行的 JVM，
   代价是需要 JDK、增加一条权限路径。当前用户都从工作台启动，建议**不做**，等出现「附着到别人启动的服务」的诉求再评估。
4. **排期**：我的建议顺序是 **A1 → A3 → A2 → A4 → B1 → B3 → B5 → B2 → A5 → C1/C2**，即先让「对得上」可证明，再补顺手度。

## 7. 风险与边界

- **对比基线本身不干净**：Eclipse 的 `out/` 里混有 NCForge 自己产的 class；Eclipse 只在整个类变成问题类型时才把 import 级报错一起嵌进 class。
  A1 的脚本已把这两点做进口径，但**任何新基线都要先过这两关**。
- **A2 会动类路径真源**（`nc_index` / `eclipse_cp`），影响编译、调试、启动三处。必须先有 A1 的回归网，再动。
- **B1 脚手架要写用户源码**：遵守「方案确认前不动代码」「GBK+CRLF 无损」的既有规则，新建文件的编码/换行按所在工程的现有风格探测，不能默认 UTF-8 + LF。
- **本机实测的限制**：没有登录账号，登录后的真实业务界面类没测过热替换；客户现场（无 IDE）场景没有实地验证。
