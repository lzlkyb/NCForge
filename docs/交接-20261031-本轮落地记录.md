## 1. 数据库：REF CURSOR + 隐式结果集（commit `791571e`）

### 1.1 为什么这件事以前判成「2–3 天的协议补全」

首轮探针给出的现象是：`dbms_sql.return_result` 在 19c 上服务端确实下发 TTC 27 号消息，客户端
报 `UnknownTtcMessageType(27)`；而 `open :1 for` 报 `PLS-00707`。当时判断需要新增两条协议路径。

实际动手后只有一条是真缺：

| 形态 | 首轮判断 | 实际根因 | 现状 |
|---|---|---|---|
| `dbms_sql.return_result`（隐式结果集） | 「要补协议」 | 消息分发表不认 27 号 | **已通**，界面能看到行 |
| 嵌套游标列（`cursor(select …)`） | 「要补协议」 | 上游 `check_for_statement_error` 判断顺序 bug | **已通** |
| `open :1 for …`（OUT 绑定） | 「要补协议」 | `BindParameters` 只有输入值，真要补 OUT 绑定 | **仍不通** |

### 1.2 块 a：一处 8 行的上游修复（vendor 补丁三）

`vendor/oracledb/src/response/mod.rs`：`Response::check_for_statement_error` 里
「ORA-01403 当正常结束」的判断原本排在「关闭游标」之后。嵌套游标在 **describe 阶段**服务端会带
01403，于是父游标被 piggyback（`TTC_RPC_CLOSE_CURSORS`）关掉，子游标连带失效 ⇒ 取子游标行
`ORA-01001`。

修法：01403 判断提前 `return`，不落到关游标分支。

**走过三条弯路，都证伪了，别再重走**：①「换 EXECUTE 取行」（`TTC_RPC_FETCH` 本来就能用）；
②「describe 少读字节」；③「消息字段写错」。

**因果倒置的更正**：python-oracledb thin 全走 EXECUTE，是因为它**没实现 FETCH**，不是协议不允许
FETCH。这条搞反过一轮，直接影响了成本估算（2–3 天 → 1.5 天）。

### 1.3 块 b：TTC 27 号隐式结果集（vendor 补丁四，~200 行）

字节布局（抓包核对过）：

```
ub4  结果集个数
每个结果集：
  ub1  SQL 文本长度 N
  N    SQL 文本（不解析，跳过）
  …    describe 正文
ub2  cursor_id
```

三个坑，每条都有反向验证：

1. **`from_cursor_response` 不能复用**——它读的 1 字节是「嵌套游标列」的固定值，27 号那里是
   真长度，必须 `advance(N)` 跳文本。
2. **`ExecResult` 必须实现 `Drop` 归还子语句**——`CachedStatement` 没有 `Drop`，不归还就漏会话
   游标。反向验证：关掉归还后 **第 298 次** 撞 `ORA-01000`（`open_cursors` 默认 300）。
3. **`FetchMessage` 不需要实现 27 号**——fetch 响应不带它（默认 `not_implemented` 是对的）。

### 1.4 块 c'/d：引擎摊多结果集 + 前端小标签

- `db_rust.rs::implicit_sets()`：把隐式结果集摊成 `sets`，**顶层仍保留第一个结果集** ⇒
  排序 / 复制 / 导出 / `guessTable` 一行没改。
- 前端 `ResultEntry.sets` + `ResultPanel` 的「结果集 1 / 2…」小标签，切换用 `key={at}` 重挂表格，
  避免串筛选与选中状态。

**限制（写进界面提示，不是静默截断）**：隐式结果集**不支持「加载更多」**——`Session` 只有一个
游标槽，多结果集留哪个都是猜。所以每张表一次取 `max_rows`，取满标 `hasMore`，让用户调大重跑。

### 1.5 为什么不把 `Caps.refcursor` 翻成 `true`

能力位代表「整条路能跑」。现在 `dbms_sql.return_result` 与嵌套游标列通了，但 `open :1 for` 要
OUT 绑定，仍然 `PLS-00707` ⇒ 只有一半，不能翻。**改这块必须同步** `db_engine.rs` 的 `Caps`、
`db_rust.rs` 模块文档、验收清单 H 组、CHANGELOG。

### 1.6 真机验收（19.3.0.0.0 @ `10.200.22.144:1521/aier260824`，需 VPN）

- `tests/db_refcursor_probe.rs`：**R1–R11 全绿**（R6 是块 a 的门禁，R7 防普通 fetch 回归，
  R8/R9/R10 覆盖 1 个 / 2 个 / 0 行结果集，R11 连跑 400 次盯泄漏）。

## 2. 类路径：`.classpath` 成为唯一真源（commit `290110a`）

### 2.1 为什么批次 1 和批次 3 一起做

方案里的批次 1 原本标「最便宜的一刀，只改目录枚举」。动手时发现它的漏点二、三
（「兄弟扫描只跟 `.classpath` 声明」「顺序按 `.classpath` 而非字典序」）**必须解析 `.classpath`**，
拆开等于同一个解析器写两遍。于是先建完整版 `eclipse_cp.rs`，批次 1 只换数据来源。

结果仍然只换了两个函数的数据来源：`project_class_dirs`、`module_class_dirs`；
`compile.rs` / `shadow.rs` / `launch.rs` 三处调用**零改动**。

### 2.2 `eclipse_cp.rs` 的四条规则（每条一个单测）

| 规则 | 为什么必须这么写 |
|---|---|
| `src` 条目缺 `output=` 时回落 `kind="output"` | 该行在文件**末尾**，必须两遍扫描；漏了会少整个输出目录 |
| 同一 output 被多条 src 共享要去重 | `newar` 223 条 src → 35 个目录，不去重类路径会重复膨胀 |
| `path="/X"` 三路解析：目录名 → `.project` 的 `<name>` → `.metadata/.projects/X/.location` | `newar/.project` 自称 `ar`，只按目录名匹配会失败；顺序写反也失败 |
| `exported="true"` 才递归传递 | `EyePortal` 有 95 个类只能经 `pm → newar` 拿到；无视它会多收不该收的目录 |

无 `.classpath` 的老工程走 `legacy_roots`：模块 `classes` → `out/*` → **`bin`** → 兄弟目录。
`bin` 是新增补扫的（`pm/bin` 的 339 个 class 以前从没进过类路径）。

### 2.3 D6：六段散类目录 + jar 段序

`nc_index.rs` 的 `MODULE_CLASS_DIRS`（私有 const）六段，按 public → client → private：
`hyext/classes`、`classes`、`client/{hyext,}classes`、`META-INF/{hyext,}classes`。

`MODULE_JAR_DIRS` 段序同步改成 public → client → private（旧序 client 最前，实测让 1 个类被标准层
抢先）。两份常量（`launch.rs` 一份、`nc_index.rs` 一份）**收敛成一份 `pub const`**——两份各写一套时
改一处漏另一处 = 「编译找得到、启动加载不到」，这类偏差日志里看不出来。

## 4. 勘误：本轮改掉的四个错结论（含我自己算错的）

1. **§2.5 原表「161 目录 / 458 class」是混算值**。那是把各层级 `classes` 一起 `find` 出来的。
   按段分别是 **49/258**，六段合计 **160/406**。
   > 第二次更正：初次统计用 `-path "*/hyext/classes"` 匹配，把 `platform/META-INF/hyext/classes`
   > 同时计进了 public 段和 private 段。段位判断必须用固定层数分别验。
2. **「漏 147 个」应为 148**（406 − 258）。差 1 就是上一条重复计入导致。以 `406 / 258` 为准。
3. **「真库取消 2 秒生效」作废**。实测计算类查询取消 **~182ms**（python thin 对照 76ms，同量级）；
   等待类语句受 19c 服务端 **~3s 块边界**支配（3s/6s/9s，与中断时点无关），python 含 OOB 通道
   也一样 ⇒ 服务端行为，客户端无解。旧结论是 sleep 测试的假象。**结论：不投入。**
4. **「`TTC_RPC_FETCH` 对 ref cursor 不可用」是因果倒置**（见 §1.2）。

## 6. 接手须知（本轮踩到的坑）

- **`docs/` 是快照，不是现状**。任何「未做 / 写死 / 留到 Mx」的结论，动手前先 `grep -rn` 核代码。
  本轮就是被「NC home 写死」「配置导入导出没做」两条过期描述误导过。
- **类路径顺序是行为不是美观**。实测 `pm` 与 `newar` 有 18 个同名类内容不同，字典序会让 newar 赢。
  改 `class_roots` 前先看 `eclipse_cp_live` 的断言。
- **`cargo test` 默认 fail-fast**：lib 单测挂了集成测试根本不会跑。别把「没看到集成测试结果」
  读成通过或失败，修完 lib 必须重跑全量。
- **`cargo fmt --check` 是不可跳过的门禁**。前导空格这类列位置问题 grep 抓不出（只证明行存在，
  证明不了列位置）。本轮又踩了一次。
- **clippy 版本比本地新会挂 CI**（1.96 本地 / 1.99 CI）。`is_none_or` 这类新方法要注意 MSRV。
- **`check_for_statement_error` 那类判断顺序 bug，日志是看不出来的**。改 vendor 必须记 `FORK.md`
  （根因 + 抓包证据 + 验证命令），否则下一个人会重新绕三条弯路。
- 环境：Bash 里 cargo 不在 PATH（`export PATH="$HOME/.cargo/bin:$PATH"`）；vitest 别与 cargo
  重活并行跑（worker 超时会显示 "passed" 但实际没跑，核对测试文件数）。
