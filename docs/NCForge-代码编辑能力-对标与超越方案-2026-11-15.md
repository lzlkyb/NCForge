# 代码编辑能力：对标 IDEA / Eclipse / VS Code 与超越方案

> 日期：2026-11-15
> 范围：代码面（Java / 编辑器 / 工程模型 / 运行调试 / 审查），不含数据库与 SQL。
> 方法：逐条读当前代码取证据（file:line），旧台账冲突时以代码为准；性能数字引既有实测，未实测的标「待实测」。
> 本文取代 `NCForge-能力台账-对标IDEA-20261102.md` 的编辑能力部分（该台账 10 条判定已过期，见 §1）。

## 0. 三句话结论

1. **编辑器基本盘已经过了「能用」线，不是短板。** Monaco 挂了 11 类语言 provider（`src/lib/langProviders.ts` / `langProvidersExtra.ts`），叠 jdt.ls + 11 个自研 Java 类（`src-tauri/jdtls-ext/src/ncforge/jdt/`，其中 9 个 `*Handler`），编辑器动作 12 条命令已绑定（`src/lib/editorActions.ts`）。这轮提交又补上签名改动、结构搜索、字段访问、批量检查、文件模板、粘贴 import。
2. **真正拖后腿的是速度与形态，不是功能清单。** jdt.ls 全量索引 152 秒、单文件编译 1.1 秒里 0.9 秒是 JVM 启动（`docs/NCForge-编译系统-提速与清理重编-方案-2026-11-06.md` §4.1）；多项目多版本、远程 NCHOME 两个形态问题一次都没对标过（`docs/NC开发者痛点-一手材料调研-2026-11-07.md` §3.2/§3.3）。
3. **「超越」要押在能测量的地方。** 功能数量追平 IDEA 必然变重（IDEA 4GB、索引分钟级），与「轻量 + 快」直接冲突。方案因此分两条线：**速度线**（可测量、可超越）+ **NC 语义线**（护城河、竞品抄不走），编辑器功能只补 4 处、明确不做 9 类。

**判断**：这一层不缺功能，缺的是**大文件与高亮预算**（见 §4.3）。

### L2 语言智能（jdt.ls + 扩展）

- provider 覆盖：Completion / Hover / Definition / Reference / Implementation / TypeDefinition / SignatureHelp / CodeAction / FoldingRange / DocumentHighlight / SelectionRange / DocumentFormattingEdit（11 类，`langProviders*.ts`）。
- 自研 Java 类 11 个（`src-tauri/jdtls-ext/src/ncforge/jdt/`）：9 个 handler —— `BatchInspect` / `CompletionMetadata` / `FieldAccess` / `IncludeType` / `ProjectClasspath` / `RefactorWorkbench` / `SignatureWorkbench` / `StructuralSearch` / `TypeHierarchy`；2 个供 handler 复用的辅助类 —— `RefactorWorkspace` / `SignatureSafety`。
- 前端叠了三层增强：`javaCompletion`（+`CompletionMetadataHandler` 拿来源）、`javaEditing`（意图动作）、`javaParameterHints` / `javaLambdaHints`（内联提示，后者管 lambda 与类型标注）。

**判断**：能力面已超过 Eclipse 自带 JDT（Eclipse 没有结构搜索、没有字段访问分析、没有签名安全预检）。与 IDEA 的差距不在「有没有」，在**准确率与响应延迟**——这两项我们一次都没量过。

### L3 工程模型

- `.classpath` 是唯一真源：`eclipse_cp.rs::class_roots`（主工程 `outputs` → 依赖闭包 DFS → NCHOME）。
- 编译单位是整 IProject（`newar` 只有 1 个 `.project`），`compile_order` 按依赖倒序、模块名保大小写、深度 ≥ root+2。
- 多工程依赖链、编译当前模块/全部模块、自动编译（700ms 防抖、按模块分组、一批一次 IPC）。

**判断**：比 Eclipse 强（Eclipse 不支持模块循环引用，竞品作者原话）。但**循环依赖真的出现会怎样，没验过**——这是三个未验证项之一。

### L4 运行与调试

- DAP + java-debug；热替换分 `Target{Server, Client}` 两个 JVM，各一套会话文件/令牌/状态。
- 覆盖率（`java_run/coverage.rs`）、单测 runner、`java_run` 支持 `debug` / `coverage` 两种模式（`src/lib/javaRun.ts:37`）。
- 断点、条件断点、表达式求值、调用栈、变量面板（`DebugPanel.tsx`）、高级调试（`debugAdvanced` + `debug_advanced_cmds.rs`）。

**判断**：这一层已经**超过 Eclipse 默认体验**（双目标热替换是 NC 独有），接近 IDEA 的可用性。差距在「远程 attach」——现在只能本地。

### L5 审查与版本

SVN 全套（增量扫描 + 桥分单元并行 + 流式上屏）、补丁打包、变更时间线、逐块接受/驳回、已审标记、本地历史、change shelf。这块是**明确超越**产品（IDEA 的 SVN 插件功能少得多，且不做 NC 补丁口径）。

### L6 NC 语义（护城河）

元数据字典（`md_dict`）、BMF 实体画布、补丁生成/应用（`patch_build.rs`）、NC 日志解析（`$$k=v` + `$$callid`）、热替换、类路径闭包、数据字典正反向。

**判断**：这层竞品（IDEA 插件、UAP Studio）**结构上做不到**——它们的宿主 IDE 不认识 NC 的规矩。

## 4. 五目标的量化口径（没数就不算目标）

### 4.1 轻量

| 对象 | 当前 | 对照（公开分发口径，非本机实测） |
|---|---|---|
| **安装包（NSIS，压缩后）** | **~8 MB**（外置资源后；v0.1.0 是 63.8 MB，`resource_pack.rs` 头部有据） | IDEA ~4 GB 安装后；Eclipse ~700 MB；VS Code ~400 MB 安装后 |
| 应用本体 | 24 MB（`nc-forge.exe`，未压缩，含前端 12 MB `dist`） | — |
| 外置资源（首次使用下载） | ~64 MB（jdtls 54 + ecj 6.7 + svnkit 3，按版本 + SHA-256 分发，内容不变不重下） | — |
| 全量磁盘占用 | **~90 MB** | IDEA 是它的 40 倍 |
| 代码规模 | 前端 15.7 万行 / 1581 文件；Rust 10.7 万行 / 181 文件 | — |

⚠️ 对外口径必须写清：**8 MB 是安装包，不是全量占用**。jdtls / ecj / svnkit 走 `resource_pack.rs` 外置下载（这条设计让自动更新不用每次重下 59 MB 不变内容），首次用完整功能后磁盘约 90 MB。讲「8 MB 比 IDEA 轻 500 倍」是成立的，讲「装上就只有 8 MB」不成立。

### 4.2 速度

同日同 fixture 实测两次，**两个数都列**（单次数会被冷热伪造出收益）：

| 指标 | 写方案时 | 首测 | 复测 | 目标 | 测法 |
|---|---|---|---|---|---|
| 单文件保存 → 出 class | 1.1 s（池化前旧数） | 33 ms | **31 ms** ✅ | **< 0.4 s** | `单文件编译_p50`：预热 3 次 + 20 次取中位数 |
| 1–5 文件增量编译 | < 3 s（未复核） | 未接探针 | **未接探针** | < 1.5 s | 改 3 个文件计时 |

| 冷启动到可编辑 | **未实测** | 未测 | **未测**（通道已通） | < 2 s | 打包版 stderr → `--boot-log` |

## 5. 方案

### A 档：速度线（能真正超越，先做）

| 编号 | 项 | 做法 | 收益 | 成本 |
|---|---|---|---|---|
| **A0** | ✅ 建性能基线 | 5 个指标打点（冷启动、索引、单文件编译、补全 p50、大文件打开），写进 `scripts/perf-baseline.mjs`，CI 不跑但本地一键出表 | 之后所有优化可判定 | 1 |
| **A1** | ✅ 常驻 ecj worker | 一个 JVM 加载 ecj 反复接任务；空闲超时退出；配置变更重启；内存上限可配。先做 `-XX:TieredStopAtLevel=1` + `UseSerialGC` 的参数实验再定 | 1.1 s → **0.4 s** | 3 |
| **A2** | 索引提速 | 三条并行试：① `.svn` 排除已做，再加 `hotwebs` 等产物目录排除；② workspace 缓存持久化（jdt.ls 支持 `initOptions` 里的 data dir 复用）；③ 索引期间 UI 全功能可用（现在是否阻塞未验） | 152 s → **< 60 s** | 3 |
| **A3** | 启动分段 | 首屏可编辑 > 目录树 > 索引 > 诊断，四段各自出进度；索引在后台时状态栏给一行「代码智能 63%」 | 感知启动时间 | 2 |
| **A4** | 大输入保护 | 文件 > 5000 行或 > 2 MB 时降级（关 hover/补全，只留高亮）；模块 > 80 个时先索引主工程再补依赖 | 避免「一打开就卡死」 | 2 |

### B 档：NC 语义线（护城河，竞品抄不走）

| 编号 | 项 | 依据 | 成本 |
|---|---|---|---|
| **B1** | 循环依赖实测 + 兜底 | 竞品原话「Eclipse 不支持循环引用」；我们 `compile_order` 遇环的行为未验。先造一个最小环，看是死循环、报错还是静默错序，再决定是报警还是按 SCC 缩环编译 | 1（探针）/ 3（兜底） |
| **B2** | 多项目多版本共存 | 调研里唯一没对标过的需求。最小做法：工作区切换不走「重开窗口」，而是按「工程 + NC 版本档位」存独立的索引/类路径/会话槽；同一进程内切换 | 3 |
| **B3** | VO ↔ 表 ↔ 字段双向 | 调研的确定性第二块（两个竞品都做了）。正向（字段→VO）有，反向（VO→表→字段栅格）缺 | 2 |
| **B4** | 报错 → 根因映射 | 调研的确定性第三块。确定性映射 + 跳转（不做自由问答）：ORA 错误码 / NC 异常栈 → 已知原因 + 定位到文件行 | 2 |

### 明确不做（守轻量）

AI 补全/问答、插件市场、主题导入、Profiler、UML/依赖图、HTTP Client、集成终端、Git 后端、CodeLens 装饰、彩虹括号、自定义检查规则 DSL、检查抑制管理界面。

## 6. 需要你拍板的 4 件事

1. **「超越」的对外口径**：按 §3.3 六条讲（NC 语义 + 速度），还是继续按「IDEA 功能表对齐度」讲？前者能赢，后者永远差 30 项。
2. **A1 常驻 worker 值不值**：它要引入一个长驻 JVM（内存 +200~400 MB），换来 0.7 秒/次。按每天保存 200 次算省 2 分钟，但会让「轻量」标签变模糊。做还是不做？
3. **B2 多项目多版本要不要现在做**：成本 3，但它是竞品明确列出的痛点，也可能是我们唯一能拉开「顾问同时跑 3 个项目」场景的地方。
4. **C4/C1 先验后做**：这两项可能 jdt.ls 早就给了，我们只差一个开关。要不要先花半天验，再决定是否立项？

## 7. 风险与验证方式

| 风险 | 触发条件 | 应对 |
|---|---|---|
| 常驻 worker 的内存换速度不划算 | A0 量出来单文件编译实际 p50 > 1.5 s 且每天保存次数高 | 先做参数实验，再决定是否上 worker |
| 索引提速卡在 jdt.ls 内部 | 排除目录 + 缓存复用都做了仍 > 100 s | 转「分段可用」，不追求缩短总时长 |
| 多项目切换破坏类路径真源 | `.classpath` 唯一真源被多版本档位撕开 | 档位只存「索引与类路径的快照」，真源仍是 `.classpath` |
| 功能继续膨胀导致启动变慢 | 启动路径新增同步 IO 或全量扫描 | 加一条门禁：`main` 启动路径禁止同步扫盘（可测） |

**每项交付前必须自测**：A 档给出前后对比表（同一机器同一工程）；B 档给出「没有这个功能时用户怎么做」的对照；C 档给出「入口在哪、按什么键、按了之后发生什么」三句话。
