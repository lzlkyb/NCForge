1. **jdt.ls 0.57 确实不下发「加 `@SuppressWarnings`」** —— 这一条原判成立，自研无意义（服务端没有这个提案）。

## 1. 证据链（服务端实现，逐层）

### 1.1 问题位置**只**来自客户端传入的 diagnostics

`CodeActionHandler.getCodeActions`（反编译第 120 行）：

```java
IProblemLocationCore[] locations =
    CodeActionHandler.getProblemLocationCores(unit, params.getContext().getDiagnostics());
```

🔴 **没有任何「按 range 反查服务端自己那份诊断」的逻辑。**  locations 完全由 `context.diagnostics` 决定。

### 1.2 空数组 ⇒ 立即返回空列表

`QuickFixProcessor.getCorrections`（反编译第 67-70 行）：

```java
public List<ChangeCorrectionProposal> getCorrections(IInvocationContext context,
                                                    IProblemLocationCore[] locations) {
    if (locations == null || locations.length == 0) {
        return Collections.emptyList();     // ← 这里
    }
    ...
    while (i < locations.length) { ... this.process(context, curr, resultingCollections); }
}
```

`process` 是一个 **121 个 `case` 的 switch**（按 `IProblem` id 分发）。locations 为空 ⇒ 一次都不进 ⇒ 零提案。

### 1.3 我们的调用点传的就是空数组

`desktop/src/lib/langProvidersExtra.ts:136-144`：

```ts
const res = await ask<LspCodeAction[]>("textDocument/codeAction", ctx, {
  range: { ... },
  // 不传诊断：jdt.ls 的 quick fix 主要按 range 反查它自己那份诊断，
  // 传一份可能过期的诊断列表反而会把修复过滤掉。
  context: { diagnostics: [] },
});
```

🔴 **注释里那句「jdt.ls 主要按 range 反查它自己那份诊断」与二进制实现不符**，是这条 bug 的认知来源。range 只用来构造 `InnovationContext`（第 113-115 行），**不参与 quickfix 的问题定位**。

### 1.4 suppress 本身确实没有

- `QuickFixProcessor` 全文无 `suppress` / `unchecked` / `rawtypes` 字样
- `jdt.ls.core` 与 `jdt.core.manipulation_1.14.0` 两个 jar 的字符串池里搜不到任何 `SuppressWarnings*`

⇒ **0.57 版本没有这个提案，自研 quickfix 也补不出服务端的语义**（要自己判 problem id 与抑制目标，等于重写 JDT 的 correction 层）。

### 4.2 🔴 真机对照为什么没跑通（不是本改动的问题）

`code_action_diag_live` 卡在「90 秒内 jdt.ls 没解析出符号」。**做对照组证明是环境问题**：

| 既有 live 测试 | 本机结果 |
|---|---|

三个测试同症状 ⇒ 本机 jdt.ls **不导入临时 Eclipse 工程**，只创建兜底 `jdt.ls-java-project`（`.metadata/.log` 实证）。

排查中已排除的假设（都实测过，不是推测）：
- 缺 `initialized` 通知 → 补上后 `ServiceReady` 能到了，但工程仍不导入；且 `semantic_tokens_live` **本来就有**这一步却同样红

- 工程 XML 形态 → 改成与 `java_completion_live` 完全同构（单行 `.project` + `render_classpath` + `src/demo/`）仍不导入
- OSGi bundle 缺失 → `config.ini` 引用的 jar 逐个核对，**都在**

**结论**：环境侧问题，待单独定位。本轮**不假装验证过**。

### 4.3 原始立案说明（保留）

**G3-b【P1】Java quickfix 通道被空诊断数组堵死**

- 落点：`desktop/src/lib/langProvidersExtra.ts:143` 的 `context: { diagnostics: [] }`
- 修法方向：把 Monaco 当前 model 的 markers（`monaco.editor.getModelMarkers`）转成 LSP Diagnostic 传下去，**只传与 range 相交的那些**，并保留 `code` / `source` 字段（服务端按 problem id 匹配，`code` 丢了等于没传）
- 🔴 **风险点（原注释担心的那个，是真的）**：诊断过期会让服务端按旧 problem id 找错位置。所以必须
  1. 只取当前 model 版本的 markers（`model.getVersionId()` 已有的抢号机制可复用）
  2. 过滤到 range 相交
  3. 拿不到 `code` 的 marker 不传（自定义诊断混进去会污染匹配）
- **结案前必须做的实测**：真实 jdt.ls 会话里造一个有 quickfix 的错误（如缺分号），对照「传诊断」与「传空」两次 `textDocument/codeAction` 的返回条数。**没有这个对照就不算修好**。
- 与并发会话无重叠（对方在 Rust 侧 `crash.rs` / `diagnostics.rs`，本项在前端 LSP  provider）

**不做**：自研 `@SuppressWarnings` quickfix（服务端无此语义，自研等于重写 JDT correction 层，命中「结构性劣势不追」）。
