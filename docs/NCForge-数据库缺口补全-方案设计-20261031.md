## 1. 缺口一：REF CURSOR

### 1.1 根因（比原来记的更靠前）

原来的记录是「实测 `PLS-00707`，不支持」。往协议层挖了一层，真正的原因不是「不支持
REF CURSOR 这个类型」，而是**整个驱动没有 OUT 绑定**：

- `vendor/oracledb/src/bind_params.rs:32` — `BindParameters` 只有 `Slice(&[&dyn ToDbValue])`，
  全是**输入值**，没有任何「这个绑定是 OUT」的表达。
- `vendor/oracledb/src/messages/execute.rs:65` — `write_bind_params` 只写输入值。
- `vendor/oracledb/src/messages/execute.rs:337` — `self.statement.set_bind_directions(resp)`
  说明驱动**能从服务器响应里读回绑定方向**，但本地没有对应的声明入口——这条只对
  `dbms_output.get_line` 那种「服务端强制的 OUT」有用，用户声明的 `:rc` 一律按输入发出去。
- 于是 `open :rc for select ...` 里的 `:rc` 被当成一个普通输入绑定（NULL），Oracle 收到
  这个组合只能拒绝——`PLS-00707` 就是这一步的产物，不是「游标类型不被支持」。

**这条根因很重要**：它决定了「补 REF CURSOR」不是补一个类型，而是补一条能力轴（OUT 绑定）。
工作量比「加个枚举分支」大一个量级。

**上游调研已确认协议层完全支持，缺的只是 API**（2026-10-31 查证）：

- `vendor/oracledb/src/constants.rs:343-344` — `TTC_BIND_DIR_INPUT = 0x20` /
  `TTC_BIND_DIR_OUTPUT = 0x10` **两个常量已经定义好，全仓无人使用**（和 `_MARKER_TYPE_BREAK`、
  `_TTC_MSG_TYPE_IMPLICIT_RESULTSET` 一样是「写了没人用」）。说明 bind 元数据里本来就有
  方向字段，只是没开放给调用方。
- 上游 `oracle/rust-oracledb` **没有任何 open issue 涉及 REF CURSOR / OUT 绑定**
  （`gh api repos/oracle/rust-oracledb/issues?state=open`，#63/#62/#60/#58/#56/#54/#52/#50/
  #47/#46/#45/#44/#43/#41/#40/#39/#34/#31/#25/#24/#23/#20/#18/#6/#3 无一提及），
  最新 release 仍是 `v26.0.0-beta.5`（2026-10-28，正是我们锁的版本）——**上游短期不会做**。
- 但**协议可行、且有官方参考实现**：python-oracledb thin 模式（v26.1.0）已支持
  `callproc()` 的 SYS_REFCURSOR OUT 参数（其 issue #169、#600 都是 thin ref cursor 的修复记录）。
  具体做法见 `src/oracledb/impl/thin/messages/execute.pyx`：
  - `params = [info for info in params if info.bind_dir != TNS_BIND_DIR_OUTPUT and not info._is_return_bind]`
    ——reexecute 时**过滤掉纯 OUT 绑定**（对照我们 vendor 的 issue #17 复现路径）；
  - `if stmt._sql_bytes is None: ERR_INVALID_REF_CURSOR` —— REF cursor 的 statement
    **没有 SQL 文本**，靠 `bind_dir` 声明。

### 1.2 一个现成的线索

`vendor/oracledb/src/messages/execute.rs:102` 已经把
`TTC_EXEC_FLAGS_IMPLICIT_RESULTSET` 置进 exec flags 了，而
`vendor/oracledb/src/constants.rs:206` 的 `_TTC_MSG_TYPE_IMPLICIT_RESULTSET = 27`
**带下划线前缀、全仓无人引用**——典型的「开了开关、没实现消息处理」。

这意味着存在一条比 OUT 绑定短得多的路：Oracle 12c+ 的隐式结果集
（`dbms_sql.return_result(rc)`），客户端只要处理消息类型 27 就能拿到结果集，不需要声明
任何 OUT 绑定。

### 1.3 方案对比

| 方案 | 做法 | 优点 | 缺点 | 改动量 |
|------|------|------|------|--------|
| **A 隐式结果集** | 实现 `_TTC_MSG_TYPE_IMPLICIT_RESULTSET`（消息 27）解析：读 cursor id + 元数据，复用既有 `Cursor` 做 fetch | 不碰绑定层；驱动已置 flag；fetch 链路可完全复用 | 用户要写 `dbms_sql.return_result`，需要一层自动改写；**12c+ 才有**，11g 无解 | ~200 行 + 真库调试 |
| **B 完整 OUT 绑定** | 给 `BindParameters` 加 OUT 声明 + cursor 类型，`deserialize_return_parameters` 读 cursor id | 一次到位，`open :rc for` 原样可用；11g 也能用；**python-oracledb thin 有同协议实现可逐行对照** | 要把 Cython 的 buffer 逻辑翻成 Rust；会动 `statement.rs` 的绑定元数据；~400-600 行 | 风险最高→**中**（有参考实现后风险显著下降） |
| **C 服务端转 JSON** | 把 `open rc for <select>` 改写成 `dbms_xmlgen`/`json` 输出 CLOB，Rust 取字符串再解析 | 零驱动改动 | 只能覆盖**能被正则认出来的简单形态**；类型精度/CLOB 会失真；多结果集无解 | ~120 行，但脆 |
| **D 自动回落 JVM 桥** | 语句被判为「需要 REF CURSOR」时不报错，这条语句改走同一连接的 JVM 桥 | 成本最低；用户无感；对所有形态都有效 | 这条连接会临时拉起 JVM（内存 + 首次 ~1.5s） | ~~~150 行~~ → **实测 ~420 行**（Rust + Java 桥两侧，见下方勘误） |

> **勘误（2026-10-31 第十一轮，D 已落地）**：原估「~150 行、只改 Rust 侧」**不成立**。
> 前提假设是「JVM 桥天然支持 `open :1 for`」，真库实测被推翻：桥用的是普通 `Statement`，
> `:1` 按输入变量绑成空串，服务端回 `ORA-01008 并非所有变量都已绑定`。所以 D 的真实改动面 =
> **先给桥补上游标 OUT 绑定（`prepareCall` + `registerOutParameter`）**，再加 Rust 侧判定与路由。
> 详细拆分与踩坑见 §13.15。教训：把「另一条实现路径能做」当既成事实，等于把风险藏进估算里。

### 1.4 推荐：D 已落地（P0，2026-10-31），A 已完成（P1），B 仍不做

> 状态：**A（隐式结果集，§13.12~§13.14 前的块 a/块 b）与 D（能力路由，§13.15）都已落地**；
> B（完整 OUT 绑定）仍不做——D 把 `open :1 for` 这条最难的路交给了 JVM 桥，B 只剩
> 「省掉一次 JVM 拉起」的收益，不值得再动驱动绑定层。

理由（写于开工前，保留原判断以便回溯）：

理由：

1. **D 解决的是「体验断裂」，A/B 解决的是「能力缺失」，两者不是同一件事。**
   现在的表现是用户选了 Rust 引擎、写了 PL/SQL、撞一个 PLS-00707，无法自救。D 让这条语句
   自动降级成功执行，是投入产出比最高的一步。
2. **A 的探针已跑完（2026-10-31 晚，19c 真库），关键未知量有答案了**：`dbms_sql.return_result`
   执行后服务端**确实下发** TTC 27 号（隐式结果集）消息，客户端当前报
   `UnknownTtcMessageType(27)`——消息分发表不认这一号，但**连接不受影响**
   （报错后同一会话 `select 1 from dual` 正常；多结果集场景同样只挂在第一个 27 上）。
   所以 A 的改动面 = 分派表加 27 号 + 消息解析 + 暴露 API，协议侧已通，
   且有 python-oracledb thin 26.1.0 的同协议实现可逐行对照。原估 ~200 行没算分派表，
   实际略增；风险从「中」降到「中低」。
3. **B 不做预研就写，很可能写成「能连不能取」。** 绑定元数据、cursor id 回填、fetch 首包
   三处任一处理错，现象都是「查询成功但结果为空」——比报错更难查。

### 1.5 探针设计与实测结果（2026-10-31 晚已跑完，真库 19c）

```
tests/db_refcursor_probe.rs   （#[ignore]，手动带连接信息跑）
  R1: 普通 PL/SQL 带 OUT 绑定 → 记录实际错误码，确认是 PLS-00707
  R2: dbms_sql.return_result(rc) → 观察是收到消息 27、还是协议错误、还是静默空结果
  R3: 多个 return_result → 观察多结果集
```

实测结果（5 个场景全部执行，服务端 19.3.0.0.0）：

| 场景 | 语句 | 结果 |
|---|---|---|
| R1 | `open :1 for select 1 from dual` | `PLS-00707`（根因确认：驱动无 OUT 绑定，占位符按输入发空串） |
| R2 | `dbms_sql.return_result(rc)` | **`UnknownTtcMessageType(27)`** —— 服务端发了 27 号、客户端不认；会话随后可用 |
| R3 | 两个 `return_result` | 同样 `UnknownTtcMessageType(27)`（挂在第一个结果集上） |
| R4 | `open :1 for select ... from all_tables`（真实形态） | `PLS-00707`（同 R1） |
| R5 | JVM 桥对照 | 未设 NC_HOME 跳过（该能力由 K29/K30 覆盖） |

判定（按上表对号入座）：

- **R2 命中「报协议错误」分支** → A 的做法明确：先修消息分发里的 27 号分支
  （`messages/mod.rs` 分派表 + 新消息解析），再复测 R2/R3 能否拿到行。
- 若修完仍拿不到行 → 判 A 不可行，只保留 D；B 是否做由「团队 PL/SQL 里 ref cursor
  使用频率」决定（可以先用现有 `sql_refs` 统计 NC 源码里 `open ... for` 的出现次数）。

### 1.6 自动改写的边界（A 的前置）

只在**能安全识别**时改写，认不出就回落 D：

| 形态 | 处理 |
|------|------|
| `open rc for <select>;` 单个游标 | 改写：`rc` 声明后加 `dbms_sql.return_result(rc)` |
| 多个游标各自 open | 每个都加，按顺序返回多个结果集 |
| 游标从别的包返回（`pkg.f(rc)`） | 不认，回落 D |
| `sys_refcursor` 变量名出现在字符串里 | 误判即失败，宁可回落 |

改写失败时的行为必须是**回落 JVM 桥执行原语句**，不是报错——这条要写进验收。

### 1.7 验收

- 新增探针测试通过（真库 19c）
- K 组补一条 K41（**2026-10-31 第四轮修正**：原写「执行 `open rc for …` 出结果表」，
  那其实是 OUT 绑定形态，现在仍不支持；能验的是隐式结果集）—— **已写进清单（2026-10-31 晚）**：
  Rust 引擎连接上执行 `declare rc sys_refcursor; begin open rc for select * from bd_material;
  dbms_sql.return_result(rc); end;`，出结果表；两个 `return_result` 出「结果集 1 / 2」标签；
  再执行一个 `open :1 for` 形态的块，**接受它报错**（OUT 绑定未做，属已知限制），
  或把引擎切回 JVM 桥后成功返回
  - **2026-10-31 第十一轮更新**：后半句「接受它报错」**已过期**。P0 落地后 Rust 引擎下
    写 `open :1 for …` 不再报 `PLS-00707`，会自动改走 JVM 桥执行并出结果表，输出区留一行
    说明（见 §13.15）。这条验收改为 **K52**：Rust 引擎下 `open :1 for` 形态应出结果 +
    输出区有「改在 JVM 桥的临时会话上执行」提示 + 该语句**不受**本连接事务条支配
- ~~`Caps.refcursor` 在 12c+ 连接为 true、11g 连接为 false（按 `db_info` 版本判断），前端按钮可用性随之变化~~

## 2. 缺口三：取消不是瞬时 —— 探针已判决：**不成立，不投入**（2026-10-31 晚更新）

### 2.1 原担忧与它的来源

FORK.md 记录「真库实测约 2.0 秒取消生效」，据此列为缺口。本轮用黑盒探针复测，
并首次与上游 python-oracledb thin 同场景对照，结论是：**那个 2 秒是测试假象，
取消机制对真实负载是快的**。

### 2.2 实测数据（19c @10.200.22.144，2026-10-31，VPN 下实测）

| 语句类型 | 中断时点 | Rust 侧（我们的补丁） | Python thin 26.1.0 对照（上游未打补丁） |
|---|---|---|---|
| CPU 长查询（`connect by level <= 30000000`，不取消要跑 ~4.4s） | 1s | **1182ms**（取消延迟 ≈182ms） | 总 1077ms，cancel→报错 **76ms** |
| `dbms_lock.sleep(30)` | 1s | 3021ms | 总 3023ms，cancel→报错 2022ms |
| `dbms_lock.sleep(20)` | 50ms / 300ms / 800ms / 1500ms | 3010 / 3004 / 3009 / 3017ms | 3014 / — / — / 3026ms |
| `dbms_lock.sleep(20)` | 3.1s / 4.5s / 5.5s | **6008 / 6014 / 6014ms** | — |
| 行锁等待（`for update` 等别人持有的事务） | 1s / 4s | **3009ms / 6017ms** | — |
| 不中断基线 | `sleep(6)` | 6019ms **成功** | — |

探针设计时的三个假说，全部有答案：

1. **客户端没有 3 秒幻影读超时**：`sleep(6)` 不中断 6.02s 正常返回。探针连接从未设过
   `call_timeout`，`read_timeout` 全程为 `None`（`set_read_timeout` 的全部调用点：
   连接建好时的 `None`、引擎执行时的 timeout+10、pool ping；`transport.rs:520`）。
2. **等待类语句的中断受服务端 ~3s 块边界支配**，块边界在 3s/6s/9s…，与中断请求时点无关：
   - sleep：中断落在 0-3s 内 → 3.0s 返回；落在 3.1-5.5s → 6.0s 返回；
   - 行锁：@1s → 3.0s；@4s → 6.0s。同一条规律，两种等待机制都一样。
3. **3 秒块边界是 19c 服务端行为，不是我们的补丁**：python-oracledb thin 是上游未打
   任何补丁的实现，取消时优先走 TCP urgent data（`_break_external()`，协商支持 OOB 时）、
   否则退回 in-band marker——两条路都不比我们的 in-band 差；实测同场景同样落在 3s
   （cancel@1s → 2022ms 后报 ORA-01013；@50ms → 2963ms；@1.5s → 1526ms，相加都是 3.0s 整）。
   传输层怎么发都一样，瓶颈在服务端等待内部的取消检查粒度。

### 2.3 对产品的含义

- 用户点「停止」取消一条**正在计算的查询**（真实负载）：**~0.2 秒**生效
  （≤100ms 客户端切片 + ~80ms 服务端）。与上游同量级（76ms），无需优化。
- 取消一条**卡在锁/等待上的语句**：最坏 ~3 秒（服务端块边界）。这是 Oracle 19c 的行为，
  JDBC（`Statement.cancel`）与 python-oracledb 完全一样，**客户端无解也不必解**。
- 中断后会话始终可用（每个场景后 `select 1 from dual` 均通过），连接不会被弄死。
- 原「缩短切片」「非阻塞 poll」「做 OOB」三条优化路全部失去前提：切片只贡献 ≤100ms
  且早已不是瓶颈；OOB 经上游对照证明对等待类语句无效。

### 2.4 结论与附带发现

- **缺口三不成立，不投入。** 判据写进 H 组「已知限制」：等待类语句的取消最坏 ~3s
  （19c 服务端块边界，与 JDBC/python-oracledb 一致），避免以后有人重复挖。
- **FORK.md 的「约 2.0 秒取消生效」记录已更正**：那是 interrupt 在 ~1s 时发起、
  恰被 3s 块边界接收的假象（1s + 2s = 整句 3.0s 返回）。真实取消延迟见 2.2 表。
- 附带发现（不影响决策）：我们的驱动把「中断」和「真超时」统一报成
  `CallTimeoutExceeded`，服务端的 `ORA-01013` 在 `reset()` 时被丢弃（python 能拿到）。
  引擎层 `db_rust.rs:72` 已用中性文案「语句已中断（点了停止，或等待超过超时时间）。
  会话仍然可用」覆盖，用户无感知。若将来想把 ORA-01013 透出来，改动点在
  `recover_from_error`/`reset()` 捕获服务端错误包再改抛——属 cosmetic，无产品价值。

## 3. 缺口四：DBA 能力

### 3.1 先把「DBA 能力」拆开，逐项判死刑或立项

原评估列了八项，但团队是 NC 二开、不是 DBA，全做是错的。按「NC 二开真实会遇到的痛」排序：

| 能力 | 判断 | 理由 |
|------|------|------|
| **锁与会话排查** | **做（P1）** | NC 运维头号事故：改一张表卡死、`ORA-00054 资源忙`、找不到是谁锁的。每个二开都会遇到 |
| **长事务 / 回滚段** | **做（P1，可并入上一条）** | 与锁同源，同一个面板多一个 tab |
| **表空间 / 段增长** | 做（P2） | 大表导出/补丁 SQL 前想知道还剩多少空间，低频但有用 |
| **整表 / 大结果集流式导出** | 做（P2） | 现在导出在前端内存里攒 CSV，十万行会顶到几百 MB。真要做是后端流式写文件 |
| **AWR / ASH 报告** | **不做** | 需要 Diagnostic Pack 授权，客户库里基本没买；生成报告还要 `$ORACLE_HOME` 下的脚本 |
| **存储过程调试器** | **不做** | 需要 `DBMS_DEBUG` 授权 + 断点协议，成本远超收益；真调试用 PL/SQL Developer |
| **ER 图** | **不做** | NC 两千多张表，全图不可读；局部图的价值低于「表结构 + 中文名」已有能力 |
| **Schema diff / 数据迁移** | **不做** | 这是另一个产品（如 Redgate），做半套比不做更危险 |

### 3.2 锁与会话面板的设计

**关键决策：只读展示 + 生成语句，不代执行。**

理由：`ALTER SYSTEM KILL SESSION` 需要 DBA 权限，二开账号通常没有；更危险的是
**NC 的生产库杀掉一个会话可能连带打断别人的补丁执行**。所以本工具的定位是「让你 30 秒内
搞清楚是谁锁了、该找谁」，而不是「一键杀」。这也符合已有的设计哲学（写权限交给数据库账号）。

数据来源（全部是普通 SELECT，不需要新能力，两个引擎都支持）：

```
v$locked_object  ─┬─ object_id → dba_objects / all_objects（表名、属主）
                  └─ session_id → v$session（机器、程序、用户名、状态、sql_id）
v$lock           ─ 锁类型（TM/TX）、lmode/request、block/request 关系
v$session        ─ blocking_session、event、wait_class、seconds_in_wait
```

面板形态（沿用现有表页组件，不新写表格）：

- **锁等待树**：`blocking_session → session` 两列缩进，直接看出「谁堵了谁」
- **被锁对象**：表名 + 中文名（`md_column`/`md_table` 已有，复用 `db_schema` 缓存）
- **每行两个动作**：「复制 kill 语句」「复制完整 kill 语句（含 @实例）」，都是复制到剪贴板
- 刷新按钮 + 「最近一次刷新时间」，不自动轮询（DB 页不该偷偷跑查询）

### 3.3 验收

- 在测试库造一个锁（`update` 不提交，另开一连接 `select for update` 同表），面板能出树
- 面板刷新只读 `v$` 视图，不产生任何写语句（可用 `v$session` 里自己的 `sql_text` 反查）
- 两个引擎都能跑（`v$` 视图查询就是普通 SELECT，纯 Rust 引擎没有额外要求）

## 4. 缺口五：SSH 隧道 —— 已否决（2026-10-31）

> **决策：不做。** 团队通过 VPN 接入内网，网络层已可达，数据库 / SVN / NC 服务三条链路在
> VPN 下本来就全通。SSH 隧道与 VPN 解决的是**同一层问题（可达性）**，有 VPN 即无需求；
> 而且 VPN 是更优解——路由级、全协议生效、不用维护隧道生命周期与本地端口。
>
> 下面 4.1~4.4 保留为技术调研留档，**不再执行**。将来若出现「没有 VPN、必须过跳板机」的
> 场景再重新评估；届时按 4.2 的结论选 `russh`，并且要把隧道做成**工作区级**（SVN 提交同样
> 要走这条链路）而不是连接级——只给数据库做，会出现「查询能跑、代码提不了」的半成品。

### 4.1 为什么不能用「系统自带 ssh.exe」

Windows 10+ 有 `ssh.exe`，看起来零依赖。但：

- 密码认证无法自动化（没有 sshpass，`SSH_ASKPASS` 在 Windows 上行为不可靠）；
- 需要管理子进程生命周期、端口探测、异常退出重连；
- 用户机器上未必装了 OpenSSH 客户端功能（Server 版默认有，桌面版要手动开）。

**只能密钥登录**这一条就足以否掉：NC 客户现场给的通常是密码。

### 4.2 方案对比

| 方案 | 依赖 | 优点 | 缺点 |
|------|------|------|------|
| **A `russh`** | 纯 Rust，无 C 依赖 | 跨平台一致；可编程口令/密钥；tokio 生态 | 二进制体积增加（估 1.5-3MB 未压缩）；API 版本变动快，要锁版本 |
| **B `ssh2`（libssh2）** | 需要 C 编译 | 成熟 | Windows 交叉编译链路复杂，与现有「纯 Rust 优先」取向冲突 |
| **C 调系统 ssh.exe** | 零依赖 | 体积不变 | 只能密钥；见 4.1 |

推荐 A。体积代价要正视——项目对安装包 5MB 很敏感，这一项会让安装包涨 30-60%，
**必须先量一下再决定**（用 `cargo bloat` 或直接对比 release 体积）。

### 4.3 设计

**隧道在网络层，与引擎无关**，所以 JVM 桥和纯 Rust 驱动都自动获得这个能力，不需要各写一遍。

```
DbConnConfig 新增：
  ssh: Option<SshConfig> {
    host, port, user,
    auth: Key { path, passphrase_dpapi } | Password { dpapi },
  }
```

连接流程：

1. `db_connect` 前若 `ssh` 存在 → 起隧道：`russh` 连跳板机 → 本地监听 `127.0.0.1:0`
   → 每条进来的连接开一条 `direct-tcpip` 通道到 `目标host:1521`
2. 把 `DbConnConfig.url` 里的 `@目标host:1521` 临时替换成 `@127.0.0.1:<本地端口>`
   —— 只在内存里换，不写回配置
3. 隧道句柄与连接句柄同生命周期：`db_disconnect` 时先关驱动连接再关隧道
4. 隧道起不来 → **明确报错**，不静默直连（静默直连会让人以为隧道生效了，实际走的是明文/被防火墙拦）

凭据：复用 `svn_cred.rs` 的 `Dpapi::protect/unprotect`（`svn_cred.rs:130,143`），
口令与私钥 passphrase 都走 DPAPI，密文不过 IPC 桥（沿用 `config.rs::redacted` 的规则）。

UI：`ConnManualForm.tsx` 增加一个可折叠的「SSH 隧道」区（默认收起，不干扰大多数直连用户），
`db_conn_test` 需要区分「隧道失败」与「数据库认证失败」两类错误文案——这是最容易做错的地方。

### 4.4 验收

- K 组补 K42：配一条需要跳板机的连接，「测试连接」成功；断开后 `netstat` 里本地监听端口消失
- 跳板机口令错 → 提示「SSH 登录失败」，不是「ORA-12541 无监听程序」
- 隧道建立后拔掉跳板机（模拟）→ 查询报错但应用不崩，重连可用
- 安装包体积对比记录进 CHANGELOG

### 8.2 取消探针为什么不用改驱动

客户端切片是 **100ms 固定值**，所以延迟归属可以直接算出来：

- 实测值是 **100ms 的整数倍** ⇒ 客户端轮询造成（`2000 / 100 = 20` 片，严丝合缝）；
- 实测值**不是** 100ms 的整数倍 ⇒ 服务端响应造成（服务端不配合我们的切片）。

这比在 `transport.rs` 里加日志可靠，也不需要为了测量而改动要交付的代码。Rust 探针与
Python 探针跑同一台库、同一条语句、同一个中断时点，两边数字一对比，归属没有歧义。

## 10. 块 a 完成：REF CURSOR 取行修复（2026-10-31）

> 用户批准「先修 R6」。结论：**根因是上游驱动的一个 bug，不是我们原先假设的「协议缺失」**。

### 10.1 排查过程（供以后复用，别重复绕）

| 假设 | 验证手段 | 结果 |
|---|---|---|
| 1. ref cursor 不能走 `TTC_RPC_FETCH`，必须换 EXECUTE | 抓 python thin 的包（`PYO_DEBUG_PACKETS=1`）对照 | **假设不成立**。把 fetch 换成 EXECUTE 照样 ORA-01001 |
| 2. describe 解析少读字节，cursor id 错位 | dump 我方响应原始字节，与 python 抓包逐字节对齐 | **假设不成立**。`4C 01 02 01 01 5C …` 两边完全一致，读出的 cursor id、列名、后续普通列全对 |
| 3. 我方发出的消息体字段写错 | dump `WriteBuffer` 内容与 python op19 对比 | **假设不成立**。除 seq 号外**逐字节相同**（同样的 options、同样的 cursor id 位置） |
| 4. **父游标被驱动提前关闭** | 在 `close_cursor` 打调用栈 | ✅ **命中** |

关键一行日志：

```
[DBG-CLOSE-SRC] sql="select cursor(select 100 as z from dual) as c, 42 as n, 'abc' as s from dual"
                cursor_id=1 cached=true
   4: StatementCache::close_cursor
   5: Client::close_cursor
   6: Response::check_for_statement_error      ← 就是这个
```

同一条 piggyback 包里先发「关闭父游标 1」、再发「fetch 子游标 3」 ⇒ 父一关，子游标连带失效 ⇒ ORA-01001。

### 10.2 根因与修法

`Response::check_for_statement_error`（`desktop/vendor/oracledb/src/response/mod.rs:150`）
把两个判断的顺序写反了：

```rust
// 上游原写法（错）
if db_error.should_close_cursor() {      // 01403 不在白名单里 → true
    client.close_cursor(statement);      // 父游标进待关闭队列
}
if statement.is_query() && db_error.code() == DB_ERR_NUM_NO_DATA_FOUND {
    self.end_of_fetch = true; Ok(())     // 到这里才当「正常结束」忽略
}
```

嵌套游标的 describe 阶段，服务端会随响应带一个 **ORA-01403（no data found）**
（python 抓包里同样有 `ORA-01403: 未找到任何数据`，它是被忽略的）。上游代码在忽略它
**之前**就先把游标登记关闭了。

修法：把 01403 的判断提到前面，命中直接 `end_of_fetch = true` 返回，不碰关闭队列。

**影响面**：所有「查询遇到 01403」的路径都受益，不只是 ref cursor。
普通查询在第一页就取完时也会走到这里 —— 之前同样会误登记关闭，只是下次执行会重新
parse，用户看不出来。

### 10.3 一个重要的事实更正

**`TTC_RPC_FETCH` 对 ref cursor 完全可用**。修好父游标误关之后，原来那行
`FetchMessage`（`ub2 cursor_id` + `ub4 array_size`）一行没改就能取到子游标行。
之前推断的「python thin 全走 EXECUTE 所以 FETCH 不行」是**因果倒置**：
python thin 不发明细 FETCH，是因为它压根没实现这条 RPC，不是因为协议不允许。

⇒ 块 a 的实际成本是 **0（不需要新代码路径）**，而不是原估的 0.5–1.5 天。
本轮的净改动只有一处判断顺序 + 注释。

### 11.2 两个必须记住的坑

**坑一：`from_cursor_response` 不能直接复用。**
它读 1 个字节就进 describe —— 那是**嵌套游标列**的形态，python 侧写的是
`skip_ub1()  # length (fixed value)`，那个字节不代表长度。27 号消息的 `ub1` 是**真长度**，
后面跟 N 字节 SQL 文本，少跳就整体错位（cursor id 也会读错）。所以另写了
`from_implicit_result_response`。

**坑二：`ExecResult` 必须主动归还子语句，否则会话游标漏光。**
`CachedStatement` 本身没有 `Drop`（只有公开的 `Statement` 才在 drop 时归还），
裸的 `CachedStatement` 被丢掉等于把服务端游标留在会话里。所以加了
`impl Drop for ExecResult` 做 drain + `return_statement`。

这条**做了反向验证**（按项目纪律，绿灯测试必须先证明它能红）：
把 Drop 里的归还临时改成空循环后，R11（连跑 400 次不看结果集）第 **298** 次就报
`ORA-01000: 超出打开游标的最大数`（`open_cursors` 默认 300）；恢复后 400 次干净通过。
R11 已改成真断言（`assert!(fail.is_none())`），不是只打印。


`implicit_sets()` 做的事：`res.implicit_resultsets()` → 逐个 `Cursor` 取列、按

**为什么顶层还保留 `columns` / `rows`**：排序、复制、导出、`guessTable` 这些现存逻辑

所以每张表一次取 `max_rows` 行，取满就 `hasMore: true`，前端提示「调大每次取后重跑」。
这条限制是**显式**的，不是静默截断。

`return_on_drop` 会把它还给客户端（探针 R11 / 引擎侧 200 次循环都验过；关掉归还

### 13.4 A0：多标签独立会话（2 d）

**问题**：`db_connect` 一个连接一条会话；前端所有标签共享 `connId`。长查询在执行时持会话锁，
同连接其它标签只能等。

**方案**：会话槽（slot）。后端把「连接」与「会话」拆开：

```rust
// db_engine.rs 之上加一层，不动两个引擎的实现
pub struct SessionPool {           // 每 connId 一个
    primary: SessionId,            // 元数据 / 表页 / 事务条 用，保持现状
    extras: Vec<SessionId>,        // SQL 标签按需创建，空闲 10 分钟回收
}
```

- 命令层：`db_exec` 增加可选 `slot`（缺省 = primary），返回里带 `slot`；
- 前端：`SqlTab` 首次执行时申请 slot，标签关闭时释放；表页/元数据/事务条仍走 primary；
- 事务语义：**slot 各自独立事务**，事务条只反映 primary。SQL 标签上有未提交写入时，
  关标签的确认框针对该 slot（复用 `dbConfirm` 的三选一）；
- 连接数上限：每连接最多 3 个 slot（`open_cursors`、服务端会话数都要留余量），超了排队并提示。

**验收**：标签 A 跑 `dbms_lock.sleep(20)`（或 CPU 长查询），标签 B 同连接查 `select 1 from dual`
必须 < 1 秒返回；关标签 A 弹未提交确认；断开连接时所有 slot 一起断。

### 13.5 A1：锁与会话只读面板（1.5 d）

**定位**：30 秒内回答"谁锁了这张表、在跑什么、找谁"。**只读 + 生成语句，不代执行**
（`ALTER SYSTEM KILL SESSION` 二开账号通常没权限，生产库误杀会打断别人的补丁）。

**数据源**（全部普通 SELECT，两个引擎都支持）：

```sql
-- 阻塞链
select s.sid, s.serial#, s.username, s.machine, s.program, s.status,
       s.blocking_session, s.event, s.wait_class, s.seconds_in_wait, s.sql_id
  from v$session s
 where s.type = 'USER' and (s.status = 'ACTIVE' or s.blocking_session is not null)

-- 锁与对象
select l.session_id, o.owner, o.object_name, o.object_type, l.locked_mode, l.oracle_username
  from v$locked_object l join all_objects o on o.object_id = l.object_id

-- 等锁
select sid, type, lmode, request, block, id1, id2 from v$lock where block = 1 or request > 0
```

**接口**：`db_meta` 新增 kind `sessions`（两边引擎各实现一份，见 13.7 的改动面）。

返回结构（前端只认这个形状，两个引擎必须一致）：

```json
{ "rows": [ { "sid": 12, "serial": 345, "user": "AIER633", "machine": "PC-01",
              "program": "JDBC Thin", "status": "ACTIVE", "blocker": 9,
              "event": "enq: TM - contention", "waitSec": 42, "sqlId": "8k1x…",
              "sql": "update bd_material set …", "locked": ["BD_MATERIAL(TABLE)"] } ],
  "granted": true }
```

`granted: false` = 账号读不到 `v$locked_object`，此时只回 `v$session` 那部分，界面顶部黄条写
「缺 SELECT ON V_$LOCKED_OBJECT 授权，锁信息不可见」并给出授权语句（不代执行）。

**UI**：数据库页顶部新增一个「会话」小按钮 → 右侧抽屉（复用 `HistoryDrawer` 的形态），
表格列：SID / 用户 / 机器 / 状态 / 等待事件 / 等待秒 / 阻塞源 / 锁对象 / SQL 摘要，
每行「复制 SQL」「复制 KILL 语句」两个动作。5 秒自动刷新，可在抽屉里关掉。

**验收**：真库开两个会话，A `update` 不提交、B 同表 `update` ⇒ 面板必须显示 B 阻塞于 A，
且 `v$lock` 的 TM 锁能看到；关掉 A 后 5 秒内消失。

**实测（2026-10-31，19c @ `aier633`，`tests/db_sessions_live.rs` 两条用例全绿）**：

| 观察 | 结果 |
|---|---|
| `granted` | `true`（这个账号能读 `v$locked_object`） |
| 自己这条会话 | 出现在列表里，`sid=1337`、`status=ACTIVE`、字段齐全 |
| **`v$sql` 的 SQL 文本** | **一条都读不到**——连自己刚跑的语句也只有 `sql_id`（`dz7qu3xhmvu1v`），文本是空串 |
| 别人在跑长查询 | 另一条连接跑 ~9s 的 CPU 查询，1 秒内在面板看到「除自己外的 ACTIVE 会话 0 → 1」 |
| 未覆盖 | `granted:false` 降级（需要一把没有 `SELECT ON V_$LOCKED_OBJECT` 的账号）；TM 锁阻塞（要写表，共用库上不写） |

> **`v$sql` 读不到不是 bug，是必须预留的分支**：普通账号通常只有 `SELECT_CATALOG_ROLE` 的部分列，
> `v$sql` 只回自己的游标（实测连自己的都不回）。所以面板在 SQL 文本为空时显示 `sql_id`，
> 鼠标悬停说明「这个账号读不到 SQL 文本」——<b>不能显示成空白让人以为没有语句</b>。

> 没验**——下次有人切到 JVM 桥发现面板空，先看这里。

### 13.6 A2–A5

**A2 Autotrace（0.75 d）**：`db_exec` 在持会话锁的同一段里，执行前后各读一次
`v$mystat`（`db block gets` / `consistent gets` / `physical reads` / `execute count`），
差值放进返回的 `stats`。普通账号一般可读；读不到 → `stats: null` + 前端不显示该行。
额外成本是每条 SQL 两次往返（~1 ms 级），比"查不出为什么慢"便宜得多。

**A3 排序口径（0.5 d）**：现状是客户端对**已取到的行**排序（`viewOrder`），用户会误以为全表
有序——这是"看起来对、实际骗人"的缺陷。改法两条：①底栏常驻提示「排序/筛选只作用于已取
N 行」；②表头右键「用此列重排并重查」⇒ 包一层 `select * from (原SQL) order by c dir`，
仅在单条 SELECT 时可用，非 SELECT 时禁用并说明。

**A4 流式导出（1 d）**：现在 `toCsv` 在前端内存拼整表，十万行几百 MB。改成后端命令
`db_export_file`：游标边读边写临时文件（CSV/TSV/INSERT 三种），完成后返回路径由前端
`downloadText` 之外的系统保存框落盘；带进度事件（每 5000 行一次）。内存峰值从 O(行数) 降到 O(1)。
> 与 A1 的耦合：导出走独立 slot，避免占住主会话。

**A5 XPLAN 树（0.75 d）**：现有 `explain` 已取到 `depth/cost/rows`，前端 `PlanView` 只按平表
渲染。改成按 depth 缩进的树 + 每节点显示 `cost/rows`；再加「保存计划」与「与上次对比」
（同 SQL 两次执行 diff，用于验证加索引前后）。

- `commands/db_cmds.rs` 里 `MAX_SLOTS = 3`、`SLOT_IDLE = 600s`；槽登记表是
  `OnceLock<Mutex<HashMap<String, Instant>>>`，`slot_key(id, slot)` 只接受 ≤2 位纯数字槽名，
  其余直接拒（防前端传 `../x` 之类的键打到别的连接上）。
- 四条命令都加了 `slot: Option<String>`：`db_exec` / `db_more` / `db_tx` / `db_cancel`。

  primary 与全部槽一起 commit/rollback，一个失败不中断其余，返回第一个错误。
- 前端 `dbStore.ensureSlot()` 首次执行时申请，失败**退回 primary 并写一条输出提示**
  （不能让用户以为后端卡了）；遇 `slot-gone` 自动重开重试一次（用户不该被要求「再点一次运行」）。
- 事务状态分家：槽的结果写 `tab.tx`（`patchTab`），primary 的仍写 `setTx(connId)`。

- 退出确认的多会话合并放在后端 `quit_cmds::merge_sessions`：同连接多条会话按 id 归并，

前端拿不到就不画条。**改 explain 返回类型时别只看后端编译过没过。**

**A4 的边界（写进验收，不是缺陷）**：
- 强制开一条独立会话导出，避免吃掉 primary 的游标；开不出会话直接报错，不降级。
- 上限 `STREAM_MAX_ROWS = 2_000_000`，超出置 `truncated: true` 并在界面标注——

**事务边界是这次的核心设计**：`db_import_rows` 自己 `connect_args(..., false, engine)` 开一条
**独立会话**（键 `__import:{连接id}:{seq}`），从不借用用户 primary 会话。原因不是洁癖：用户
很可能正开着一条 SQL 标签、里面有没提交的改动；导入如果用同一会话，一次 `commit` 会把他的
改动一起提交，一条 `rollback` 会连带丢掉。代价是导入期间连接上多一条会话（槽位上限 3 是
按 `连接id#N` 计的，`__import:` 前缀不占槽）。

**每批（200 行）自成事务**：成功即 `commit`，`skip_errors=false` 遇错整批 `rollback` 并返回
`committed:false`，前端看到就停下不再发后续批。所以「中途崩了」的现场是：前面若干批已提交、
当前批整体没有——这一点在向导里明说（「每批 200 行自成事务」），不做假的全有全无承诺。

**为什么复用 `sql_export::literal`**：两个引擎的 `exec` 都只收 SQL 文本（没有绑定参数这条路），
字面量只能拼。既然「导出 INSERT」已经有一份处理 NULL / 日期 / 数字 / 引号转义的实现，导入就必须
用同一份——否则同一个值导出去再导回来会长得不一样（典型：日期、`''` 与 NULL）。

**行号换算是唯一"错了不报错"的点**：文件第 1 行是表头 ⇒ 第 i 条数据在文件第 i+2 行。分批之后
每批起点都要 +2。算错的后果不是崩溃，而是用户拿着「第 5 行」去 Excel 里找不到问题。所以这块
从组件里拆成纯函数 `planImport`，配 6 条单测，并做了反向验证（把 `start + 2` 改成 `start + 1`
⇒ 2 红；恢复即绿）。

   全量会把别人未提交的代码一起格式化）。

### 13.14 B 档 B4 实施记录：片段库 + 历史全文检索（2026-10-31 晚，B 档收工）

**存储选 localStorage 而不是后端/配置文件**：片段是「我自己的备忘」，跨机器同步的需求远小于

### 13.15 P0 能力路由实施记录：`open :1 for …` 自动降级到 JVM 桥（2026-10-31 第十一轮）

| 项 | 状态 | 落点 |
|---|---|---|
| 桥补上游标 OUT 绑定 | ✅ | `db-bridge/NcDbBridge.java`：`prepareCursorCall` + `registerOutParameter` |
| 形态判定 | ✅ | `db_engine.rs`：`refcursor_need()` → `RefcursorNeed::{OutBind, CursorWithoutResultSet}` |
| 语句级路由 | ✅ | `commands/db_cmds.rs::exec_via_java`（`JavaFallback` 结构体） |
| 兜底会话「不占槽、不假装提交」 | ✅ | `#java` 后缀键 + 执行后 `ping` 探未提交写入 → `rollback` 报 `fallback-tx` |
| 结果与提示同形 | ✅ | `dbApi.ExecFallback` → `dbStore` 输出区一行说明 |
| 真库回归守卫 | ✅ | `tests/db_refcursor_probe.rs::R5_对照_JVM桥能跑`（断言版，`#[ignore]`） |

**最大的收获是估算被证伪，不是代码。** 开工前的前提是「桥梁天然支持 `open :1 for`，只改 Rust
侧认一下就路由过去」。第一版跑真库直接吃 `ORA-01008 并非所有变量都已绑定`——桥用普通
`Statement.execute` 执行，`:1` 被当输入变量绑成空串。也就是说 **D 的成本一半在 Java 侧**，
而且这部分不做，「路由」就是「把 PLS-00707 换成 ORA-01008」。所以顺序被强制改成：
**先让桥自己能跑，再谈路由**。

#### 桥侧四个坑（每个都只报一个错，但都不是它说的那个意思）

1. **必须 `prepareCall`，不能 `prepareStatement`**：`open :1 for …` 的 `:1` 是游标 **OUT** 参数，
   普通语句表达不了，要 `registerOutParameter(1, OracleTypes.CURSOR)`。
2. **`oracle.jdbc.OracleTypes` 不能 import**：桥的 classpath 只有 JDK 标准库
   （`build-bridge-jar.mjs` 里 `cp: []`，靠运行时由 NC 的驱动 jar 兜）。改用反射取
   `OracleTypes.CURSOR`，取不到退回历史值 **`-10`**。
   `java.sql.Types.REF_CURSOR` 那条路走不通——NC 自带 ufjdk 是 **Java 7**，没有这个常量，编译就报「找不到符号」。
3. **PL/SQL 块的结尾分号不能去掉**：`prepareCursorCall` 里保留原文（去掉立刻
   `PLS-00103 出现符号 end-of-file`）。普通 SQL 的尾分号依旧由 `normalize` 处理，两条路不要合并。
4. **`ResultSetMetaData` 必须在游标关闭之前读**：重构 `readRows` 时先 `page()` 后读列名，
   直接 `ORA-17009 关闭的语句`（`page()` 取完行会 `closeCursor()`）。现在拆成
   `columnsJson(md)` / `pageOf(rs, cols, maxRows)` 两个静态纯函数，调用顺序写死在 `readRows` 里。

重打 jar：`node scripts/build-bridge-jar.mjs db` → 5 class / 26.5 KB。

#### Rust 侧判定：只认能安全识别的形态

`refcursor_need(sql)` 先 `strip_literals`（逐字节去掉 `'…'` / `--` / `/* */` 并转小写），
再按 word boundary 扫 `open`：

- `open :N for` → `OutBind`（必然 `PLS-00707`）
- 有 `sys_refcursor` 且 `open <标识符> for`，但**既无** `return_result` 也无 `fetch` → `CursorWithoutResultSet`
  （语句能过，但客户端拿不到行，等于白跑）
- 其余一律 `None`，交给原引擎按原文报错

认不出就不动，是刻意的：误判会把一条本来能跑的语句推到另一条链路上，报错更难懂。
另有第二道网——Rust 引擎执行报 `PLS-00707` 时也兜一层（注释里写明「判定没覆盖到的形态，
比如游标从包里返回」），两条路都失败就把**两个原因一起**给用户，用户至少知道我们试过什么。

#### 兜底会话的三条纪律（改这块前必读）

1. **不占会话槽**：键是 `{引擎键}#java`，`live_slots` 只认纯数字后缀（≤2 位），
   所以它不出现在「会话」列表里，也不会顶掉用户的 3 个槽。
   `split_slot_key` 先 `strip_suffix("#java")` 再切 `#N`，否则 `c1#2#java` 会被解析成
   连接 `c1#2`——单测钉了这两条（`java_key("c1")` / `java_key("c1#2")`）。
2. **不做假的无感**：结果里带 `fallback: {engine:"java", reason}`，`dbStore` 在输出区写
   「这条语句改在 JVM 桥的临时会话上执行：… 它不受本连接「事务」条管理」。
   悄悄换引擎执行、界面什么都不说，是更难查的那类问题。
3. **绝不静默提交**：执行后 `ping` 一次，看 `tx.statements > 0` 就 `rollback` 并报 `fallback-tx`。
   兜底会话与主会话是两个事务，绝不能让一条「顺手写成」的 UPDATE 留在别人的会话里。

连带清理：`db_disconnect` / `db_slot_release` / `sweep_idle_slots` 都要顺带
`drop_bridge(java_key(...))`，否则桥进程会挂到应用退出。

#### 真库验证（19c @10.200.22.144:1521/aier260824，`aier633`）

|---|---|
| 单游标 `open :1 for select table_name from all_tables where rownum<=3` | 3 行，`kind:"rows"`；随后 `select 1 from dual` 正常（会话不坏） |
| 两个游标 | 第一个进顶层（`A=1`），其余进 `sets[0]`（`B="x"`），与 Rust 引擎同形 |
| 取满再取 | `rowCount:3 hasMore:true` → `more` 再 3 行 |
| `R5` 回归守卫（断言版） | 全绿 |
