# NCForge 热替换：方案设计

> 日期：2026-11-06　状态：方案稿，待确认（确认前不改代码）
> 取代：`NCForge-多期规划-方案设计-20261027.md` §5.1 阶段 5（估 1 d）、`P0-P1能力补齐-总体规划-20261101.md` §4 P1-4 批次 B（JDI redefine）
> 目标：改完 Java 方法体并保存后，运行中的 NC 服务（以及 NC 客户端）**秒级**用上新代码，不重启；做不到时**明确说做不到**，并给一键重启。

---

## 0. 结论先行

1. **原计划「走 java-debug 的热替换」在本仓走不通。** java-debug 0.32.0 的
   `JavaHotCodeReplaceProvider` 靠 jdt.ls 工作区构建产生的 class 变化来触发，
   而我们刻意关了 jdt.ls 构建（`lsp.rs:281` `autobuild.enabled=false`，影子工程
   `shadow.rs:33` 双保险，红线是「禁止 jdt.ls 写用户文件」）。这条红线不该为热替换破例。
   另外，影子工程的 classpath 不保证完整，它编出来的 class 可能带「Unresolved compilation
   problem」桩方法，推进 NC 会把能跑的代码换成会抛异常的代码。
2. **推荐路线：自带一个极小的 Java agent（`-javaagent`），用 `Instrumentation.redefineClasses`
   推送 ecj 产物。** 字节来源与磁盘上的 class 完全一致（就是自动编译写进 `<模块>/classes`
   的那份），**不依赖调试会话**，没开调试也能热替换；与 JDWP 可同时存在。
3. **原文档的头号风险「NC 8 段 BootstrapClassLoader 下 redefine 很可能不成立」大概率是
   误判。** `redefineClasses` 按 `Class` 对象工作，与是哪个加载器无关；Eclipse 里调 NC
   时方法体热替换本来就能用。真正要处理的是「同名类被多个加载器各加载一份」和
   「运行的那份不是工程产物（被 `hyext/classes` 补丁遮蔽）」。这两点仍要 spike 实证，不当结论。
4. **能力边界照 JVM 原生 HotSwap：只能改方法体。** 增删字段 / 方法、改签名、改继承、
   新增 lambda（会多一个合成方法）都会失败 —— 失败时整批不生效，报原因并提示重启。
   DCEVM / HotswapAgent 这类结构性热替换要换团队的 ufjdk，**不做**。
5. **工期约 6 d**（spike 0.5 d + 实现 5 d + 验收 0.5 d），不是原计划的 1 d。

## 2. 先 spike（0.5 d，go / no-go）

用工作台启动 NC 中间件（develop 模式），再用 Arthas 附加，**不写任何产品代码**：

| # | 类的位置 | 验证 |
|---|---|---|
| S1 | 工程 public 段（如 newar 某个 BS 实现类） | `sc -d` 看加载器与 `codeSource`；改方法体里一个字符串常量 → ecj 编译 → `redefine` → 接口行为真变了 |
| S2 | 工程 private 段（`META-INF/classes`，模块加载器） | 同上；重点看是否有两个加载器各加载一份 |
| S3 | nccloud 的 action 类（webapp 委托链） | 同上 |
| S4 | NC 客户端 JVM（JStarter 启动）里的 UI 类 | 同上；确认客户端类来自工程 `client/classes` 还是下载缓存 |
| S5 | 反例：给类加一个方法 | 必须报 `UnsupportedOperationException`，且旧代码继续可用 |
| S6 | 断点所在方法被替换后 | 断点还在不在、需不需要重新下发 |

**通过条件**：S1–S3 至少两项行为真变；S5 失败可控。
**不通过**：只做「改完一键重启」，不做热替换；本方案其余部分作废。

## 3. 路线比较

| 路线 | 机制 | 优点 | 问题 | 结论 |
|---|---|---|---|---|
| **A. 自带 agent** | 启动参数加 `-javaagent:ncforge-hotswap.jar`，agent 在 127.0.0.1 开端口，收到类名后读磁盘 class 调 `Instrumentation.redefineClasses` | 不依赖调试；字节就是 ecj 产物；能看到每个同名类的加载器与来源 | 需要启动参数（开关）；要自写约 300 行 Java | **推荐** |
| B. jdt.ls 扩展里调 java-debug 的 VM | 在 `ncforge-jdt-ext.jar` 注册命令，取当前调试会话的 `VirtualMachine.redefineClasses` | 不改启动参数 | 只在调试会话里可用；依赖 java-debug 内部类，升级即碎 | 备选，不做 |
| C. 开 jdt.ls autobuild 让 java-debug 自己热替换 | 原生 HCR | 代码最少 | 违反「jdt.ls 不写用户文件」红线；影子工程编出的类可能带错误桩 | **否决** |
| D. Arthas `redefine` | 每次 attach Arthas | 零开发 | 重、慢、要额外进程，体验差 | 仅用于 spike |
| E. DCEVM / HotswapAgent | 换 JVM | 能改结构 | 要替换团队 ufjdk；1.8.0_202 无现成可信构建 | **不做** |

## 4. 推荐方案（路线 A）

### 4.1 组成

```
保存 → 自动编译（已有，ecj → <模块>/classes）
     → 收集本次产出的 class（主类 + 内部类 Foo$*.class）
     → Rust 热替换客户端 ──TCP 127.0.0.1 + 令牌──▶ NC JVM 内的 ncforge-hotswap agent
                                                     │ getAllLoadedClasses 按类名匹配
                                                     │ 核对 codeSource 是否就是这个 classes 目录
                                                     └ redefineClasses（同一批原子）
     ◀── 逐类结果：已替换 / 未加载（下次加载即新）/ 被遮蔽 / 失败(原因)
```

### 4.2 agent（`resources/hotswap/ncforge-hotswap.jar`，Java 8，用随包 ecj 编）

- `premain`：起一个守护线程，`ServerSocket` **只绑 127.0.0.1**，端口由工作台分配。
- 鉴权：agent 参数只传一个**令牌文件路径**（在工作台配置目录下），agent 读文件拿令牌；
  令牌不进命令行，避免出现在进程列表里。
- 请求：`{token, classes:[{name, file}]}`；agent 自己读 `file` 的字节（同机，无需传字节）。
- 匹配：`getAllLoadedClasses()` 按类名过滤；对每个命中看
  `getProtectionDomain().getCodeSource().getLocation()`：
  - 来源就是请求里那个 classes 目录 → 纳入本批 redefine；
  - 来源是别处（如 `hyext/classes` 补丁、NC home jar）→ **不替换**，报「被 X 遮蔽」。
    这比悄悄替换更有用：它直接解释了「为什么我改的代码不生效」。
- 一批类一次 `redefineClasses`（JVM 保证整批成功或整批失败），失败把异常类型和消息原样返回。
- 未加载的类：不处理，报「未加载，首次使用时即为新代码」。
- agent 只用 JDK 自带类，不依赖 NC 任何 jar；不加载用户类、不做反射调用。

### 4.3 启动参数

- `middleware_vm_args` / `client_vm_args` 增加可选 `-javaagent:...=<令牌文件路径>`。
- 服务页启动配置加「允许热替换」开关，**默认开**（只绑回环 + 令牌；与 JDWP 不同，它不能执行任意代码，
  只能把磁盘上 classes 目录里的类换进去）。是否默认开见 §8 第 1 条。
- 已在跑、但启动时没带 agent 的 JVM（包括 Eclipse 或脚本启动的 NC）：用 Attach API **不重启直接挂上**（2026-11-06 已定）。
  由工作台用目标 NC 的 ufjdk（`lib/tools.jar`）起一个短命进程调 `VirtualMachine.attach(pid).loadAgent(jar, 令牌文件)`；
  agent 同时实现 `premain` 与 `agentmain`，MANIFEST 开 `Can-Redefine-Classes`。按 `nc.server.location` 找进程，重复挂载幂等（先试连令牌端口）。

### 4.4 工作台侧

- 新模块 `hotswap.rs`（纯逻辑 + 测试）与 `commands/hotswap_cmds.rs`。
- 挂点：自动编译 / 手动编译**成功之后**；编译有 error 时不推送。
- 设置：热替换 自动 / 手动 / 关。手动时状态栏出「有 N 个类待热替换」按钮。
- 结果展示：状态栏 chip「已热替换 3 个类」；有失败时弹一次可关的提示，带「重启服务」按钮。
- **运行代码与磁盘不一致**的状态要持久提示：一旦有失败或被遮蔽，服务页标「运行中的代码不是最新」，
  直到下次重启清除。不假装成功。
- 调试联动：替换成功后，对该源文件重新下发 `setBreakpoints`（S6 结论决定是否必须）。

### 4.5 不会生效的改动（界面上要写明）

| 改动 | 原因 | 怎么办 |
|---|---|---|
| 增删字段 / 方法、改签名、改父类或接口 | JVM HotSwap 限制 | 重启 |
| 新增 lambda / 匿名类导致编号变化 | 会新增合成方法或改类名 | 重启 |
| 静态初始化块、静态字段初值 | 类已初始化，不会重跑 | 重启 |
| `static final` 常量 | 已被调用方内联 | 重编调用方或重启 |
| 正在执行的那一帧 | 旧帧继续跑旧代码，下次调用才是新的 | 重新触发调用 |
| `.upm`、UIF2 xml、Spring xml、BMF 元数据 | 不是类 | 重启 / 客户端重新打开节点 |

## 5. 风险

| 风险 | 等级 | 应对 |
|---|---|---|
| spike 显示 NC 某些段的类无法替换 | 中 | §2 go / no-go；只对通过的段开放，其余报「此类所在位置不支持热替换」 |
| 同名类多份，替换错对象 | 中 | 只替换 codeSource 与编译输出目录一致的那份；其余只报告 |
| 编译写 class 时 NC 恰好去加载，读到半个文件 | 低 | 核对 ecj 输出是否原子；不原子则改为同目录临时文件 + 改名 |
| 本地端口被其他进程连 | 低 | 只绑回环 + 令牌文件；只接受 classes 目录内的文件路径 |
| 自动替换让人误以为改了结构也生效 | 中 | 失败必提示 + 「运行中代码不是最新」常驻标记 |
| ecj 与 Eclipse 编出的字节布局不同（内部类编号） | 低 | 编译参数已与 Eclipse 对齐（jdt.core 3.17 + `-preserveAllLocals`） |

## 7. 验收

- S1–S4 四类位置各改一个方法体：保存后 3 s 内行为改变，无需重启。
- 加方法 / 加字段 / 加 lambda：明确报失败与原因，旧代码继续正常；服务页出现「不是最新」标记，重启后消失。
- 制造遮蔽（`hyext/classes` 放同名旧类）：报「被遮蔽」，不替换。
- 没开热替换开关启动的服务：提示需重启，不报错、不卡。
- 调试中替换：断点仍能命中新代码。
- 安全：从回环以外连不上；无令牌 / 错令牌 / classes 目录外的路径一律拒绝。
- 编译失败时不推送任何类。
