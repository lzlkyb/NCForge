## 1. 主线 A：结果页写回是表页写回的降级副本

同一次「改数据并写回」，表页走 `useTableSave`，SQL 结果页走 `useResultSetEdit.save`。两条路径应有的安全设施，后者少了四样：

| 设施 | 表页 `useTableSave.ts` | 结果页 `useResultSetEdit.ts` |
|---|---|---|
| 并发守卫 | `:47` `operationActive("db."+dbTxKey(connId))` | **无** |
| 任务进度（可取消/可观测） | `:55` `beginOperation(dbTaskSpec(...))` + `:67` `task.update` | **无** |
| 成功后重新读库 | `:124` `await load()` | **无** |
| 冲突详情面板（原值/新值/当前值） | `:71-89` `setConflict` + `setConflictValues` | **只 toast 一句** |

### A-1【P1】连按两次 Ctrl+S 会重复 INSERT（已复读验证）

- 证据：`hooks/useSaveShortcut.ts:21` 把 Ctrl+S 直接接到 `save`；`hooks/useResultSetEdit.ts:194-255` 的 `save` 没有任何 in-flight 判据（`saving` 只在 `:200` 之后用于禁用 UI，不再检查）。表页同位置有 `operationActive` 早退（`useTableSave.ts:47`）。
- 触发：结果页改了 1 行新增 → 连按两次 Ctrl+S（第一次还在 `await confirmProdWrite` / 逐条 `execBound`）→ 两个循环都跑一遍 → 同一行插两次。
- 修复方向：`save` 首行加 `if (saving || operationActive(...)) return;`，并把写回登记进 `operations`（顺带获得进度条与取消）。

### A-2【P1】DELETE 写回成功后，行原地复活（已复读验证）

- 证据：`useResultSetEdit.ts:243` 对 `delete` 也调 `drafts.restoreRow(change.row)`；`useRowDrafts.ts` 的 `restoreRow` 对真实行是 `deleted.filter(r => r !== row)`，即**撤掉删除标记让行回到普通显示**。表页同样调用 `restoreRow`，但表页紧接着 `await load()` 重新查询，行自然消失（`useTableSave.ts:124`）。
- 触发：结果页点行号列 `−` → Ctrl+S → 行又变回普通行、值还在。用户以为没删掉，再删一次 → 写回报「该行已被其他人删除」。
- 修复方向：删除成功后不再 `restoreRow`，而是把该行标记为「已写回删除」（视觉置灰/隐藏），或在提示里明确「结果集是快照，请重新执行确认」。

### A-3【P1】重新执行 SQL 静默丢弃未写回改动（已复读验证）

- 证据：`lib/dbActions.ts:59-183` 的 `confirmDiscardEdits` 覆盖了切换标签、恢复标签、新建控制台、打开表页、打开字典、切换连接、关闭标签 **7 个入口**，唯独没有「重新执行」。而 `useResultSetEdit.ts:62-71` 只要 `rows` 换了一套就 `setChanged(new Map())` + `resetDrafts()`。
- 触发：改了三格没保存 → 手顺按下 Ctrl+Enter 重跑 → 改动无声消失，界面没有任何提示。
- 修复方向：执行入口在 `dirty` 时先问一句（复用 `confirmDiscardEdits` 文案），或在结果替换前保留改动并提示「原结果有 N 处未写回改动」。

### A-4【P2】大选区粘贴是 O(n²) 内存（已复读验证）

- 证据：`useResultSetEdit.ts:152` 的 `onEditMany` 在循环内逐格调用 `update`，而 `update`（`:90`）每次都 `new Map(current)` 全量复制；粘 5000 格 = 5000 份 Map。`GridEdit` 接口本就支持整批返回（`onEditMany` 可以在一次 setState 内完成）。
- 修复方向：`onEditMany` 改为单次 `update(next => { for (...) writeCell(...) })`。

### A-5【P2】表页与结果页的失败文案、部分成功口径两套

- `useTableSave.ts:104-120` 会区分「前 N 条已自动提交/仍在未提交事务」并强制回读；`useResultSetEdit.ts:221-227` 只说「已停止写回」。同一次部分失败，用户在两处看到的严重程度不同。

## 2. 主线 B：防护写在调用点，不在执行通道上

### B-1【P0】表数据可以搬到自己身上，追加模式直接翻倍（已复读验证）

- 证据：`commands/db_transfer_rows_cmds.rs:113-146` 只校验 `plan.pairs` 非空与 LOB 列，**没有校验 `req.from` 与 `req.to` 是同一张表**；前端 `TransferRowsDialog.tsx:44-62` 的目标 schema / 表名是两个自由输入框，`ConnPicker` 允许选当前连接。
- 触发：表页 →「表操作」→ 搬运行数据 → 目标 schema 与表名都填成源表 → 追加 → **原行数 ×2**，全程无确认、无回滚。
- 修复方向：后端在 `read_columns` 前比对 `(connId, owner, table)`，相同即 `Err("源和目标是同一张表")`；前端同表时禁用「追加」。

### B-2【P1】`.sql` 文件回放绕过危险语句二次确认（已复读验证）

- 证据：危险判定只在组件层 —— `SqlConsole.tsx:105-111` 调 `dangerousStatements` 后 `askDanger`；`lib/dbActions.ts:436` 的 `runStatements` 内部只有 `confirmProdWrite`（生产库确认），没有危险语句闸门；`lib/scriptReplay.ts:103` 直接调 `runStatements`。
- 触发：回放一个含无 WHERE `delete from t;` 的脚本 → 不弹「整表删除」确认，直接执行。
- 修复方向：把 `dangerousStatements` 闸门下沉到 `runStatements`（或 `runStatements` 增加 `confirmed` 令牌参数），组件层只负责画对话框。这也是「一次判定、处处生效」的唯一解。

### B-3【P1】`WHERE 1=1 AND 1=1` 绕过整表更新拦截（已复读验证）

- 证据：`lib/sqlDanger.ts:87-92` 的 `tautology` 要求条件 token 恰好 3 个（`1 = 1`）。`1=1 AND 1=1` 是 7 个 → 不命中 → 判为「有条件」，放行。
- 触发：`update po_order set n=1 where 1=1 and 1=1;` 静默执行。SQL 生成器用 `where 1=1` 起头的习惯让这条路很容易被踩到。
- 修复方向：按布尔连接词拆分条件组，全部为恒真才算「无有效条件」；至少让 `WHERE 1=1 AND …`（后续条件也恒真）与 `WHERE 1=1` 同判。

### B-4【P1】导出/搬运全量取数没有内存上限（已复读验证）

- 证据：`commands/db_export_cmds.rs:34` `PAGE = 5000`，`:256` 起循环把每页 `rows` 全量 `into` 一个 `Vec<Vec<String>>`；同时走的是 `execFull`（`:256` 注释「CLOB 给到 1M」），`db_rust.rs:53` `CLOB_MAX = 1MB`。最坏一页 5000 行 × 1MB = 5GB 常驻。
- 触发：导出带 CLOB 附件字段的大表（或宽表 + 大 varchar2），进程 OOM 或长时间无响应，且用户看不到进度。
- 修复方向：导出改为「取一页 → 边写文件边释放」，行缓冲设上限；搬运已有分批（`batches`），导出应同口径。

## 3. 主线 C：中文输入法在网格里被吃掉首字母

### C-1【P1】`ResultGrid` 的非编辑态「打字即编辑」没判 `keyCode === 229`（已复读验证）

- 证据：`components/db/ResultGrid.tsx:216-217`：
  ```ts
  if (!editing && sel && edit && e.key.length === 1 && e.key !== "Enter" && !e.ctrlKey && ... 
      && !e.nativeEvent.isComposing && edit.canEdit(sel.c, sel.r)) { e.preventDefault(); typeInto(e.key); }
  ```
  项目自己的判据是 `lib/utils.ts:161` 的 `isImeComposing(e) = e.isComposing === true || e.keyCode === 229`，注释写明「Safari 的 keydown 在组词中 `isComposing` 恒为 false 但 keyCode 会变成 229」。同族的 `GridCellEditor.tsx:43` 就是两个都判。
- 触发：网格单元格聚焦（非编辑态）→ 用拼音输入法打第一个字母 → 网格 `preventDefault` 抢走按键并进入编辑，输入法不弹窗，格子里出现一个拉丁字母。
- 影响：**中文用户在结果网格里无法用输入法输入中文**，只能先双击进编辑再打字。
- 修复方向：`ResultGrid.tsx:217` 换用 `!isImeComposing(e.nativeEvent)`。

### C-2【P2】db 侧 5 处仍是手写 `isComposing`，与统一工具口径不一

`DbDocTabs.tsx:61`、`DbObjectFinder.tsx:63`、`PasswordResetDialog.tsx:91`、`SchemaChip.tsx:123`、`ResultSource.tsx:31`（另有 `hooks/useFileSave.ts:108` 不在 db 域）。这些只影响 Enter/Esc，风险低于 C-1，但同一问题在仓库里有两种写法，下次改必然再踩。

## 4. 主线 D：结果集生命周期的边角

### D-1【P1】向上滚动时目标行被 sticky 表头遮住（已复读验证）

- 证据：`components/db/ResultGrid.tsx:144-148`：
  ```ts
  if (y < el.scrollTop) el.scrollTop = y;                       // 向上：不扣表头
  else if (y + h > el.scrollTop + height - HEAD_H) ...          // 向下：扣了表头
  ```
- 触发：用 ↑ 键或 `reveal()` 向上跳（例如从第 500 行跳回第 20 行），目标行正好落在表头下方被压住，用户看到的是「跳过去了但看不见」。
- 现有测试没有覆盖向上分支：`ResultGrid.test.tsx:62` 只断言向下时的 `506*30-200+44`。
- 修复方向：向上分支改 `el.scrollTop = Math.max(0, y - HEAD_H)`。

### D-2【P2】结果集内存上限触顶后，提示文案指向「重新查询导出」，但导出本身也受同一上限

`lib/dbResultBudget.ts:9` 的 `RESULT_LIMIT_NOTICE` 与 B-4 的导出无上限组合起来，用户被告知「重新查询导出」，而导出同样有截断/内存风险。

### E 主线：连接配置的保存靠「手工列举字段」

`dbApi.save` 有 3 个调用点，两个传完整对象（`{...c}` / `input()`），一个（`dbActions.ts:279` 拖拽改分组）手工列了 14 个字段，漏了 `keepAliveSec` 与 `initSql`；而后端 `DbConnInput` 对这两个字段的缺省语义是「重置为默认」（`:150-153`），不是「保留原值」。于是**用户拖一下连接改分组，之前配好的保活间隔和 `ALTER SESSION` 启动脚本就没了**，没有任何提示。细节见 §5.6 N-1。

这类缺陷的根治办法不是补一行，而是把「部分更新」的语义固定下来：`dbApi.save` 只接受完整 `DbConn`，或后端改成 `Option<T>` + `unwrap_or(原值)`。
