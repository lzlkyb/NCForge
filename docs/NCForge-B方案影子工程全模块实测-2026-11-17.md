# B 方案（影子工程链全部源码模块）实测结论

> 2026-11-17 · 为 Task #93 提供决策数据。**只回答「B 要花多少代价、换来什么」，不改 A 方案已上线的事实。**
> 承 `docs/NCForge-跨模块跳转工作区优先-2026-11-17.md`（A 方案）。

## 1. 为什么要补这个实测

`NCForge-代码编辑能力-对标与超越方案-2026-11-15.md` 里的 **152 s** 是**全工作区**口径，
而生产只链当前模块。**只链一个模块跑多久，从未单独量过。**

没有这个基线，「链全部 53 个模块会不会太慢」就无法判定 —— 只能说「行业都这么做」。
行业实践只说明 B 可行，不说明 B 在这个工作区、这台机器上**可接受**。

   （53 + jdt.ls 兜底的 `jdt.ls-java-project`），证明多 project 真的生效了。

## 4. 结论

### 4.1 B 的代价是这个量级

| | single → flat | single → multi |
|---|---|---|
| jdt.ls 导入耗时 | 16.1 s → 128.8 s（**8.0 倍**） | 16.1 s → 280.2 s（**17.4 倍**） |
| 到 ServiceReady | 46.4 s → 154.1 s（**3.3 倍**） | 46.4 s → 305.6 s（**6.6 倍**） |
| 峰值内存 | 921 → 996 MB（+8%） | 921 → 1079 MB（+17%） |
| 影子重建 | 19 s → 11 s | **19 s → 554 s（9 分钟）** |

内存不是瓶颈（都约 1 GB），**时间才是**：multi 每次冷启动多等约 4.3 分钟，
外加 9 分钟重建影子工程。

### 4.2 flat 比 multi 又便宜又简单，而且同样拿到收益

- flat 导入 128.8 s vs multi 280.2 s（**multi 贵 2.2 倍**）
- flat 造影子 11 s vs multi **554 s**（multi 要为 53 个模块各跑一遍 `shadow::generate`）
- 两者跨模块 definition **都落到源码**（同一个 `DeliveryVO.java`）

multi 贵的原因：53 个 project 每个都要建 Eclipse 工程模型、跑一次配置解析；
而且为了让 ic 解析到 so 的源码，还要写 **468 条工程间引用**
（`<classpathentry kind="src" path="/nc-forge-so"/>`）—— 见 §5.1。

### 4.3 与历史 152 s 的关系

历史那个 152 s 是**全工作区**口径，本次 flat 组 128.8 s、multi 组 280.2 s
与之同量级。**历史数字不是孤证，本次数据与它一致**；此前缺的是 single 基线，
现在是 16.1 s。三者放一起才看得出「全量导入比现状贵一个数量级」。

### 4.4 对 A / B 决策的影响

- **A（已上线）**：零成本解决用户报的跨模块跳转。本次实测同时**客观复现了那个 bug** ——
  single 组 jdt.ls 自己对 `DeliveryVO` 的 definition 就是 `jdt://` 字节码。
  这证明 A 不是「绕过了问题」，而是补上了 jdt.ls 在当前工程模型下**结构上给不出的东西**。
- **B 的收益面比 A 宽**：不止跳转，跨模块补全、诊断、类型层次、引用查找都会变准。
- **B 的代价是 8～17 倍导入耗时**。按这个数据，B 不应作为默认形态全量上线。

**建议**：B 暂不实施，Task #93 保留为「待评估」。若将来要做，
按 §5 的改动面评估，并优先考虑 **flat 而非 multi**（更便宜、更简单、收益相同）。

## 5. B 若实施，真实改动面（本次新探明）

### 5.1 必须写工程间引用，否则 B 不生效

第一版 multi 探针**没有**工程间依赖，结果 ic 的 `.classpath` 里躺着
`out/so`（class 目录，第 41 行），工程引用排在第 191 行 ——
Eclipse 按 classpath 顺序解析，**字节码赢**。跨模块跳转仍然落到字节码。

那不是 B 不行，是探针没建模。补上「把 `<module>/classes` 与 `out/<module>`
都换成工程引用」之后，同一个 `DeliveryVO` 立刻解析到源码。

🔴 这条对生产是硬要求：**只建 junction 不够，必须同时把被链模块的 class 目录
从 classpath 里撤掉**，否则陈旧字节码会继续压过源码 —— 正是用户报的那个 bug。

### 5.2 `lang.rs` 的 URI 映射要从「一对前缀」改成「N 对前缀」

`LangSession` 现在只存一对（`real_prefix` ↔ `shadow_prefix`），且
`shadow_uri_of` 直接拒绝不在当前模块内的文件（`文件不在当前代码智能模块内`）。
B 之后每个模块一个 junction，需要：

- `LangSession` 持 `Vec<(real_prefix, shadow_prefix)>`；
- `shadow_uri_of` 先判断真实路径属于哪个模块（**最长前缀优先**）；
- `to_server` / `from_server` / `swap_path_fields`（DAP）依次应用全部前缀对。

⚠️ 有真实隐患：现有测试 `swap_prefix_only_touches_string_heads` 明确钉住
「同名前缀的另一个模块不能被误换」（`gl` vs `gl2`）。53 个模块里
`ic` / `ia` / `ia`-类前缀碰撞要按最长优先处理，且多对依次替换时
**不能把上一步的输出再喂给下一步**。

### 5.3 `shadow.rs` 的链接与清扫

`sweep_shadow` 现在按「当前模块」摘旧链；B 之后要维护 53 条，
且 MEMORY-lang.md 记的「影子工程只有一个 junction」契约作废。
`ensure_link` 的 `.orphan-<UTC>` 备份展开逻辑仍适用，但数量级变大。

### 5.4 一个已知风险：跨模块同全限定名

全量索引 7942 个类型里，**只有 1 个**全限定名跨模块重复
（`nc.ui.so.pub.findprice.FindSalePrice` 同时在 `medsoprc` 与 `so`）。
flat 形态把 53 个源根塞进同一个 project，这一个重复会变成 duplicate type；
multi 形态有 project 隔离，不受影响。这是 flat 相对 multi 唯一的劣势。
