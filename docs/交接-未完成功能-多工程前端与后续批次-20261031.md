### 1.2 命令语义（前端照着写 UI 就行）

```
linked_projects(root?: string) -> LinkedGraph
  root 不传 = 用配置里的 workspace_root；传了 = 「预演」（切换工作区前先看依赖链，
  不必先改配置——切过去再切回来 jdt.ls 要重建索引，是有代价的）。
  工作区没选 / 目录不存在时返回 Err（中文可读消息）。

set_linked_overrides(overrides: {action,target,dir?}[]) -> LinkedOverrideConfig[]
  全量替换 + 落盘（update_config 串行写）。返回落盘后的列表——前端据此刷新，
  不要信本地状态。坏条目（动作不认识 / add 缺 dir / 其它缺 target）**整体拒绝**，
  不静默跳过：保存路径上的静默丢弃会让用户以为存上了，改半天不生效还找不到原因。
```

### 1.3 数据结构（serde camelCase，与 `lib/linkedProjects.ts` 已对齐）

```
LinkedGraph  { primary, primaryRoot, workspace, projects[], extraDirs[],
               projectDirCount, ncHomeDirCount, totalDirCount, notes[] }
LinkedProject{ name, root|null, origin, depth, exported, classDirs[],
               disabled, hasClasspath }
```

- `name` 取 `.classpath` 里 `/X` 的写法（**不是** `.project` 自称名——`newar` 自称 `ar`，
  界面要能和 Eclipse 对得上号）。
- `origin` ∈ `primary / classpath / legacy / front`；`legacy` = 没读到 `.classpath` 走老启发式。
- `root = null` = `.classpath` 里写了但磁盘上找不到，界面要显示出来。
- `disabled = true` 时 `classDirs` 为空但**条目保留**——为了让用户看得见「它被剪掉了」。
- `notes` 是解析异常与覆盖动作的说明，**必须显示**：它是「为什么我改的类没生效」的
  唯一界面线索。
- 覆盖三语义：`disable` = 整个工程不参与，**连同它往下传递的依赖一起剪掉**（连带剪枝）；
  `front` = 排到主工程之后、其它依赖之前（标 `origin="front"`，主工程不可排前，后端保护）；
  `add` = 追加不在任何工程里的类目录 / jar（`dir` 必填，后端校验存在性并写进 notes）。

### 3.1 D4 的落地口径（2026-10-31，与设计文档 §3.5 有两处偏差）

**偏差一：全量「产物比源码旧」不挂在编译流程里，改成按需命令。**
设计写的是「编译前提示」，实测之后必须改：真机 `C:\work\aier` 三工程整树扫描
**8.3~25.9 秒**（三次实测 8.3 / 21.8 / 25.9，同一台机器、同一批工程；12k 个 `.java`、
13k 个 `.class`、149k 个目录条目；release 与 debug
基本一样，也不是 `metadata` 的锅——纯 `read_dir` 遍历同样 9 秒，本机目录枚举约
7~15k 条目/秒）。挂在每次编译后等于每次白等十几秒。
⇒ 拆成两层：

| 层 | 触发 | 成本 | 覆盖什么 |
|---|---|---|---|
| 按类归因（`compile_diag::uncompiled_diagnostics`） | 编译**失败**时自动 | 每个命中 1 次 stat | 有源码没产物 / 工程被停用 / **这个类**的产物比源码旧 |
| 全量新旧（`compile_diag::stale_diagnostics`，命令 `check_artifacts`） | 用户点「工程关联」页的「检查产物」 | 8~22 s | 整个工程的产物比源码旧 / 一个产物都没有 |

**偏差二：诊断与 `Problem` 分开，不混进错误数。**
`CompileResult.diagnostics: Vec<Diagnostic>`（`kind` = `uncompiled` / `disabled` /
`stale-class` / `stale` / `no-output`）。ecj 原文**照旧保留**，诊断只是追加一条可读结论。
界面上是「问题」列表里不可点的多行行（源码在关联工程里 = 工作区之外，点开会被
`security::path` 挡住，所以显示路径而不是做成链接）。

**落地清单**：`src/compile_diag.rs`（8 单测）、`compile.rs`（`CompileResult.diagnostics`
+ 失败时调归因并逐条写进编译输出）、`commands/linked_cmds.rs::check_artifacts`、
`tests/compile_diag_live.rs`（`#[ignore]`，断言 `pm` 不被误判成 `no-output`、扫描 < 30 s）、
前端 `lib/compile.ts`（`CompileDiagnostic`）、`lib/linkedProjects.ts::checkArtifacts`、
`workspace/BottomPanel.tsx`（诊断段）+ `BottomPanel.test.tsx`（3 条）。

**「检查产物」按钮（2026-10-31 补做）**：`hooks/useArtifactCheck.ts`（序号挡竞态 /
结果带签名判过期 / 记实际耗时）+ `components/linked/ArtifactCheck.tsx`（独立卡，放在依赖链
之后）+ `components/linked/artifactKind.ts`（行内徽章与结果列表共用的文案表）。
三条行为约定：① 结果**同时**进列表和依赖链行内徽章（否则用户要在两处对照）；② 覆盖表有未
保存草稿时按钮禁用——检查读的是**已落盘**的配置，拿草稿去检查会得到对不上的结论；③ 依赖链
变了（保存覆盖表 / 切工作区）**保留结论但标过期**，不直接清空——用户刚等完十几秒，清空等于白等。

## 5. 坑（接手前读完再动手）

1. **`docs/` 是快照不是现状**。任何「未做 / 写死 / 留到 Mx」的结论，动手前 `grep -rn` 核代码——
   本轮已被「NC home 写死」「配置导入导出没做」两条过期描述误导过。
2. **类路径顺序是行为不是美观**。实测 `pm` 与 `newar` 有 18 个同名类内容不同，字典序会让
   newar 赢。改 `class_roots` 前先看 `eclipse_cp_live` 的断言。
3. **覆盖表是全量替换语义**（§1.2），UI 的保存策略必须照 §2.3 来。
4. **`get_config` 出口是 snake_case，`set_linked_overrides` 入口是 camelCase**
   （`OverrideInput` 有 `rename_all`）。两边命名不一致是既有设计，别「顺手统一」。
5. **`cargo test` 默认 fail-fast**：lib 单测挂了集成测试根本不会跑。别把「没看到集成
   测试结果」读成通过或失败。
6. **未提交**：整个多工程批次（后端 + `linkedProjects.ts`）都在工作区。
   按 R5，等明确说「提交」再 commit；提交前双 feature 口径门禁重跑一遍。
