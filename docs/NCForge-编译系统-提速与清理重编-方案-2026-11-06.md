# NCForge 编译系统：又快、又好、又准，以及“清理缓存重新编译”

- 日期：2026-11-06
- 范围：`desktop` 的 ecj 编译链路、类索引、构建结果与相关 UI
- 目标：补齐 IDE 级的 **Clean / Rebuild / 重建索引** 能力，并把“保存后自动编译”从“能编”推进到“编得对、编得全、编得快”
- 本文只做方案，不改代码

---

## 0. 结论先看

现在的编译链路不是“缺一个清理按钮”，而是缺三层基础设施：

1. **构建状态账本**：不知道上次编了哪些源文件、产出了哪些 class、用的哪套 classpath。没有它，清理不敢删、增量不敢跳、结果不可信。
2. **统一的构建引擎**：`compile_module` / `compile_file` / `compile_all_modules` 各写一套输出目录、结果合并和失败语义，清理/重编只能继续在外面打补丁。
3. **依赖与失效规则**：模块全量重编、单文件编译不传播签名变化、配置变了也不失效。没有依赖图，“快”和“准”只能二选一。

建议分三批：

- **P0（先让“能清、能重编、不误删”）**：构建清单 + 安全清理 + 清理并重编本模块/全部 + 按模块的结果账本。
- **P1（再让“增量可信”）**：模块级跳过、变更文件编译、反向依赖与 ABI 变化传播、删除源文件后的旧 class 清理、配置变化自动全量。
- **P2（最后让“更快”）**：类索引预热与持久化 seed、常驻 ecj worker、独立模块有界并行、外部改动（SVN 更新/脚本生成）触发构建。

**不做**：用 jdt.ls 的 `buildWorkspace` 替代 ecj（实测全量 150.7 秒、autobuild 12 分 22 秒）；每次保存整模块/整工作区编译；递归删除带 junction 的目录；自动删源码、配置、SVN 元数据或 NC 安装目录。

## 1. 现状审计

### 1.1 已经有的能力

| 能力 | 现状 | 证据 |
|---|---|---|
| 保存后自动编译 | 有。700ms 防抖，按模块分组，一批一次 IPC | `desktop/src/lib/autoCompileQueue.ts`、`autoCompileRun.ts`、`useFileSave.ts` |
| 手动编译模块/全部 | 有。按依赖顺序，失败即停 | `commands/compile_cmds.rs:245`、`:520` |
| 取消编译 | 有。40ms 轮询杀掉 ecj 子进程 | `compile.rs:538-548`、`compile_cmds.rs:508` |
| 类索引磁盘缓存 | 有。按 jar 的 size+mtime 复用，8 线程扫描 | `nc_index.rs:load_or_build` |
| 单文件编译 | 有。约 1.1 秒，其中 JVM 启动约 0.9 秒 | `docs/NCForge-自动编译-调研与方案-20261104.md` §4.1 |
| 编译诊断 | 有。有源码没产物、产物比源码旧、工程停用 | `compile_diag.rs` |
| 代码智能缓存重建 | 有。`lang_regenerate` 停 jdt.ls、删模块缓存、重启 | `commands/lang_cmds.rs:697-733` |
| 工作区文件监听 | 有。但只用于刷新文件树，且**刻意忽略内容修改** | `watcher.rs:5-10`、`:57` |

### 1.2 缺口清单

| 缺口 | 现状 | 后果 |
|---|---|---|
| 清理/重编命令 | 全仓没有 compile clean/rebuild；`main.rs:246-249` 只有 compile_module/file/all/cancel | 用户遇到“产物不对/旧类残留”只能手动删目录 |
| 产物清单 | 没有。编译只 `create_dir_all` 输出目录，不知道写了哪些 class | 不敢自动清，删除源文件后旧 class 永远留着 |
| 模块级增量 | 没有。`files: None` 时 `collect_sources()` 收集整个模块 | 改一个方法体也要全模块重编，模块动辄 2000+ 文件 |
| 跨文件签名传播 | 没有。保存只编当前文件，引用方仍是旧字节码 | 改方法参数/继承关系，运行期才炸 |
| 配置失效 | 没有构建状态，自然没有“`.classpath` 改了要全量” | 改了 classpath/覆盖表/NC home，仍按旧产物判断 |
| 结果账本 | `CompileResult` 没有 `modules` 字段，手动编译开始就 `setCompileResult(null)` | 编译一个模块会把其它模块的历史错误抹掉；取消后树标记全消失 |
| 全部模块失败隔离 | `compile_all_modules` 在第一个失败模块 `break` | 后面独立模块的错误一条都看不到 |
| 输出目录 | 三处硬编码 `<模块>/classes`（`compile_cmds.rs:292/485/618`） | `.classpath` 输出是 `bin`/`out/x` 的工程会写到错位置 |
| 源码根 | 只认 `src/public|client|private`（`compile.rs:28`） | `.classpath` 里额外 src 条目不会被编译 |
| 类索引刷新 | 进程内 `CACHE` 只按 NC home 命中（`compile_cmds.rs:115-143`） | 运行中新增/替换 jar，仍用旧索引 |
| seed jar 持久化 | 只在内存 `Caches.seeds` | 重启后整编又要多跑几轮补 jar |
| 外部改动编译 | 文件监听只认增/删/改名，不认内容变更 | SVN 更新、脚本生成、外部编辑器保存的源码不会自动编 |
| 常驻编译进程 | 每次编译起一次 JVM | 单文件 1.1 秒里 0.9 秒是启动 |
| 并行模块编译 | 没有 | 多模块全编是串行的 |

### 1.3 六个会直接导致“编得不准”的问题

1. **全部模块失败即停**  
   `compile_cmds.rs:645-647` 在第一个 `error_count > 0` 的模块 `break`。后面的模块不是“没问题”，而是“没编”。用户看到的错误集是不完整的。

2. **手动编译开始就清空结果**  
   `useModuleCompile.ts:125`：`if (!mergeFiles) setCompileResult(null)`。取消或异常时上一轮结果已经没了，文件树/标签/状态栏只能显示“没有错误”，这是假绿。

3. **编译一个模块替换所有模块的结果**  
   `CompileResult`（`compile.rs:43-62`）没有模块维度；`useModuleCompile.ts:141` 直接 `setCompileResult(merged)`。模块 A 编完，模块 B 的历史错误从问题面板消失。

4. **单文件编译不更新模块级信息**  
   `compile_cmds.rs:490-493` 明确写了“不写回模块 seed、不投送”。这本身有道理，但没有别的账本记录“这个文件的产物已更新”，后续模块增量无从判断。

5. **产物目录与 `.classpath` 可能不一致**  
   `compile_cmds.rs:292/485/618` 都写死 `<模块>/classes`；而 `compile_diag.rs:13-15` 已经承认真实产物目录来自 `.classpath`，可能是 `out/x` 或 `bin`。写错目录时，编译“成功”了，启动却加载旧类。

6. **类索引没有显式失效入口**  
   进程内 `CACHE` 只比较 `nc_home`；磁盘缓存按 jar stat 复用。用户在 NC home 里换了 jar，当前进程可能一直用旧 `by_class`，直到重启。IDE 的 “Invalidate Caches” 正是解决这类“看起来毫无道理”的编译错误。

## 2. 对标：IDE 到底做了什么

| IDE / 功能 | 官方行为 | 对我们的启示 |
|---|---|---|
| IntelliJ 自动构建 | 保存文件或空闲时触发自动构建 | 自动构建是默认，但不是唯一入口 |
| IntelliJ Rebuild Project | 清空整个输出目录、删除构建缓存、从头构建（[官方文档](https://www.jetbrains.com/help/idea/compiling-applications.html)） | “清理 + 全量”是一个明确动作，不混在普通编译里 |
| IntelliJ Invalidate Caches | 删除所有工程的缓存文件，重开时重建；与 rebuild 是两件事（[官方文档](https://www.jetbrains.com/help/idea/invalidate-caches.html)） | 类索引缓存与产物清理必须分开 |
| Eclipse Java Builder | 单个 Java 文件保存时增量构建（[官方文档](https://help.eclipse.org/latest/topic/org.eclipse.jdt.doc.user/concepts/concept-java-builder.htm)） | 增量单位是“受影响的编译单元”，不是“整个模块” |
| Eclipse Clean / Build Automatically | Project > Clean 选择要清理的工程；Build Automatically 保存后重建修改过的文件（[Project 菜单参考](https://help.eclipse.org/latest/topic/org.eclipse.jdt.doc.user/reference/ref-menu-project.htm)） | Clean 是“清输出”，Build Automatically 是“保存后增量”，两者配合 |
| VS Code Java | `Java: Force Java Compilation` 手动触发工作区编译；`Java: Rebuild Projects` 全量构建；`Java: Clean Java Language Server Workspace` 清语言服务器缓存并重载（[扩展说明](https://marketplace.visualstudio.com/items?itemName=redhat.java)、[官方 FAQ](https://code.visualstudio.com/docs/java/java-faq)） | “清构建缓存”和“清语言服务器缓存”要分成两个命令 |

四条共同结论：

1. **自动构建是默认，但 Clean / Rebuild 永远保留**，因为“状态坏了”需要一个人工出口。
2. **清理是分级、可解释的**：清输出、清构建缓存、清语言服务器缓存不是同一个按钮。
3. **增量依赖依赖图**，不是“按时间戳猜”。Eclipse 能秒级增量，靠的是常驻 builder + 工程依赖图。
4. **构建结果要有稳定宿主**。IDE 的 Problems / Build 面板不会因为点了一次编译就丢掉其它模块的错误。

## 3. 目标设计

### 3.1 三层职责

```
Build State（账本）  →  Build Engine（计划/执行）  →  Surfaces（树/标签/面板/状态栏）
  上次编了什么            这次该编什么、怎么清          用户看到什么、能点什么
```

不要让命令层继续各自算输出目录、各自合并结果。新增一个纯逻辑的 `build_state`（可单测，不依赖 tauri）和一个薄的 `build_cmds`（只做参数解析、锁、事件推送）。

### 3.2 构建状态账本

**位置**：应用配置目录下，按工作区分桶，不写进工作副本。

```
<config_dir>/build/<workspace-key>/
  <module>.bin          # 该模块的构建清单（紧凑二进制，带 magic/version）
  <module>.summary.json # 可选，给人看的小摘要（耗时/错误数/上次成功时间）
```

`workspace-key = hash(canonical workspace root)`，避免切换工程互相覆盖。

**必须记录**：

- schema 版本、工作区根、模块名
- 输出目录（可能多个）与每个源根的归属
- 源文件清单：相对路径、size、mtime、内容哈希（可选）、package、本次产出的 `.class`（含 `$` 内部类）、ABI 指纹
- classpath 指纹：有序 jar 列表（路径+size+mtime）、NC home、覆盖表、`.classpath` 内容、源根、编码规则
- 编译器指纹：ecj jar 哈希、java 路径/版本、编译参数
- 本次结果：成功/失败、错误数、耗时、resolved jar id、构建时间
- 上次成功构建时间（用于“产物是否可信”）

**写入规则**：只在编译结束后写；先写临时文件再 rename；读取时 magic/version 不对、内容截断、路径越界一律当“没有清单”，记一行日志后走全量。清单是优化，不是正确性前提。

**失效规则**：下面任一项变化，直接把该模块标记为“需要全量”，不允许增量：

- `.classpath` 内容变化
- 覆盖表（linked overrides）变化
- NC home 变化
- 有序 jar 集合变化（新增/删除/替换）
- 源根或输出目录变化
- ecj / java 版本变化
- 编码规则变化

### 3.3 命令与语义

新增统一构建命令，旧命令保留为薄封装（避免任务链/前端入口全改）：

| 命令 | 语义 | 清产物 | 清类索引 | 清构建清单 | 编译范围 |
|---|---|---|---|---|---|
| `build_module(mode)` | 编译本模块；`auto` 先尝试增量，条件不满足回落全量 | 否 | 否 | 更新 | 本模块 |
| `build_all(mode)` | 按依赖顺序编译全部模块；独立模块失败不阻断 | 否 | 否 | 更新 | 全部 |
| `clean_module` | 只清本模块**清单里记录过**的 class | 是 | 否 | 删除 | 不编译 |
| `rebuild_module` | `clean_module` + 全量 `build_module` | 是 | 否 | 重建 | 本模块 |
| `clean_all` | 清全部模块清单里的 class | 是 | 否 | 删除 | 不编译 |
| `rebuild_all` | `clean_all` + 全量 `build_all` | 是 | 否 | 重建 | 全部 |
| `reindex` | 清 `class-index` + 进程内 CACHE + seed，下一次编译重建 | 否 | 是 | 删除 | 不编译 |
| `clean_tmp` | 清理 `tmp/ecj-*.args` 等崩溃残留 | 否 | 否 | 否 | 不编译 |
| `cache_info` | 返回索引/清单/临时文件的大小、jar 数、上次构建时间 | 否 | 否 | 否 | 不编译 |

**概念对照**（UI 文案直接用这套，避免用户把“清缓存”理解成一键全删）：

| 用户熟悉的说法 | 本项目对应 | 清什么 | 绝不清什么 |
|---|---|---|---|
| IntelliJ Rebuild Project | 清理并重编全部 | 产物 + 构建清单 | 源码、`.classpath`、SVN、NC home |
| IntelliJ Invalidate Caches | 重建类索引 | `class-index` + 内存索引 + seed | 编译产物（默认） |
| Eclipse Clean | 清理产物 | 清单里的 `.class` | 源码、配置、NC home |
| Eclipse Build Automatically | 保存自动编译 + 空闲增量 | — | — |
| VS Code Clean JLS Workspace | 重建代码智能索引 | jdt.ls 模块缓存 | 编译产物、源码 |

**“修复编译”一键入口**（高级，需要确认）：
`reindex` → `clean_module` → 全量 `build_module`。
它不包含“重建代码智能索引”，因为 jdt.ls 全量重建实测 152 秒起步，把它塞进编译修复会让用户以为编译卡死。

### 3.4 安全删除规则

这是本方案最容易出事的地方，规则必须先定死：

1. **只删清单里记录过、且确实位于声明输出目录下的 `.class`**。每个路径做 canonicalize + 前缀校验；不在输出目录内的直接拒绝并报告。
2. **不删输出根目录**。只删文件和空包目录（自底向上 `read_dir` 确认空）。输出根保留还有一个关键原因：`eclipse_cp::push_outputs` 只收录存在的目录；如果 clean 把根删了，`compile_all` 的依赖顺序和 classpath 会丢条目。清理后必须仍能从 `.classpath` 解析出完整的输出布局。
3. **不跟随 junction / 符号链接**。`symlink_metadata` 判断；路径任一层是重解析点就拒绝该路径并报告。绝不使用 `remove_dir_all` 删工作区里的目录。
4. **没有清单时**：按源码映射推断可删集合——只删能对应到 `src/{public,client,private}` 下某个 `.java` 的 `.class`（含 `Outer$*.class`）；无法映射的 class 不删，列在报告里让用户自己判断。这样第一次清理也有用，又不会误删手工放进 `classes` 的第三方类。
5. **服务运行中**：清理前检测 NC 服务是否在跑。在跑就警告并给两个选项：“先停止服务再清理”或“仅清理，不停止（可能影响运行中的服务）”。不自动停服务。
6. **SVN 版本化的产物**：如果输出目录下检测到 `.svn`，提示“这些 class 可能被版本控制，清理后会显示为删除”；仍按清单删除，但不碰 `.svn`。
7. **失败即停**：删除过程中遇到锁定/权限错误，停止并报告已删数量与失败路径，不要继续“尽量删”。
8. **清理后状态可解释**：账本标记为 `cleaned`，UI 显示“已清理 N 个 class，尚未编译”，而不是“成功”。

### 3.5 增量与依赖

增量的前提是“知道谁依赖谁”，否则就是拿正确性换速度。分三步：

**第一步：模块级跳过（最安全、收益立刻可见）**

- 每次构建后记录模块输入指纹。
- `build_all` 先算每个模块的指纹；没变化的模块直接跳过，日志写“未变化，跳过”。
- 任一输入失效（见 3.2）→ 全量，不跳。

**第二步：变更文件编译 + 删除源清理**

- 对比清单，得到新增/修改/删除的源文件。
- 新增/删除/重命名：默认全模块编译（新类可能被任何同包/通配 import 引用，保守）。
- 只修改内容：先编变更文件；如果 ABI 指纹没变，结束。
- 全量或增量成功后，按新清单删除“上次有、这次没有”的产物；删除发生在**成功之后**，失败不动旧产物。

**第三步：ABI 变化传播 + 反向依赖**

- 源码级 ABI 指纹：public/protected 的类、方法、字段、继承/实现关系，去掉注释/字符串/泛型细节后归一化。先覆盖 NC 常见的 Java 8 语法；record/注解处理器等未覆盖语法一律按“ABI 可能变了”处理。
- 反向依赖索引：从每个源文件提取 package、显式 import、通配 import、声明的父类型、同包类型引用，构建 `FQCN -> 引用它的源文件`。通配 import 按包建边，宁可多编，不可漏编。
- ABI 变了 → 把引用方加入待编集合；引用方自己 ABI 再变 → 继续传播。深度/数量超阈值（例如超过模块源文件 30%）→ 直接全模块，避免“增量比全量还慢”。
- 索引不完整（首次、清单损坏、配置变了）→ 全模块。
- **单文件自动编译仍保留**：保存后先给 1 秒内的快速反馈；空闲 2~3 秒后再跑一次“受影响文件”的增量构建，把签名变化补上。这是 IDE “save/idle 自动构建”的等价物，必须有可见开关（默认开、可关、本机持久化）。

### 3.6 结果账本

- `CompileResult` 增加 `modules: ModuleBuildResult[]`，每项带模块名、状态（`ok|failed|blocked|skipped`）、错误/警告数、耗时、输出目录、是否清理过。
- 前端会话增加按模块的结果表；现有 `compileResult` 作为派生视图保留，避免一次改爆所有消费者。
- **开始构建时不清空上一轮结果**：只置 `buildingModules`。成功替换对应模块；失败替换对应模块并保留错误；取消/异常保留上一轮，另加一条“本轮已取消/失败”的横幅。
- `build_all`：A 失败后，把 A 的传递依赖方标为 `blocked`，继续编译与 A 无关的分支。最终结果包含“失败 + 被阻断 + 成功 + 跳过”，问题面板能把“没编”与“编了有错”分开。
- 工作区切换时丢弃旧结果，沿用现有 `root` 校验。

这同时是上一份“树/标签资源级标记”方案的前提：结果账本不稳，标记就会假消失。

### 3.7 产物目录与源码根

- 从 `.classpath` 解析每个 src 条目的 output 和工程默认 output；没有声明时回落 `<模块>/classes`。
- 一个模块有多个 output 时，按 output 分组各跑一轮 ecj（`-d` 只能一个目录），共享 jar 集合与源文件读取；日志写清“3 组输出”。
- 源码根以 `.classpath` 的 src 条目为准；没有 `.classpath` 时回落 `src/{public,client,private}`。`src/test` 默认排除，先不改变现有行为；如果发现 NC 工程依赖 test 产物，再单独开关。
- 编译、启动、语言服务必须共用同一套布局解析。新增一致性测试：同一 fixture 下，编译输出目录集合必须是启动 classpath 的子集，否则测试失败。
- 旧输出目录（例如配置从 `classes` 改到 `bin`）不自动删；账本记录旧路径，UI 提示“旧目录仍有 N 个 class，可清理”，由用户决定。

### 3.8 快

按收益排序：

1. **类索引预热**：工作区打开后在后台建索引，而不是等第一次保存。当前首次保存会 `index-cold` 跳过（`compile_cmds.rs:441-455`），预热能直接消掉这个空窗。默认开，可关。
2. **seed jar 持久化**：把每模块上次的 resolved jars 写进账本，重启后整编少跑几轮“按报错补 jar”。
3. **JVM 启动参数实验**：单文件 0.9 秒是启动。先量 `-XX:TieredStopAtLevel=1`、`-XX:+UseSerialGC`、`-Xshare:auto` 对单文件/整模块的影响，再决定是否按模式分参数；不要直接写死。
4. **常驻 ecj worker**：一个 JVM 加载 ecj，反复接收构建任务；空闲超时退出，配置变化重启，内存上限可配。目标把保存到出 class 从约 1.1 秒降到 0.4 秒级。复杂度高，放 P2。
5. **独立模块有界并行**：按拓扑层分组，只并行互不依赖、输出不重叠的模块。默认并发 2，低内存机器可设 1；开发机有过重负载蓝屏记录，不做无上限并发。
6. **结构化进度**：`build-start/progress/end` 事件，面板与状态栏能显示“3/12 模块、当前模块、已用时”，而不是只有滚动日志。

### 3.9 UI

- 编译输出面板标题栏：主按钮仍是“编译”；旁边下拉：
  - 重新编译本模块
  - 清理并重编本模块
  - 清理全部产物并重编
  - 重建类索引
  - 清理编译临时文件
- 文件树模块节点右键：编译模块 / 清理并重编模块 / 清理产物。
- 命令面板新增：`build.cleanModule`、`build.rebuildModule`、`build.cleanAll`、`build.rebuildAll`、`build.reindex`、`build.cleanTmp`。
- 设置 → 维护（或“任务与构建”新卡片）：
  - 缓存占用：类索引、构建清单、临时文件
  - 上次成功构建时间
  - 自动编译开关（保存/外部改动/空闲增量分别可关）
  - “重建编译环境”危险按钮，二次确认
- 确认框必须写清：影响哪些模块、将删除多少个 `.class`、哪些目录、不会删除什么。没有清单时显示“可识别 N 个 / 未识别 M 个（不会删除）”。
- 状态栏构建 chip：`空闲 / 编译中 3/12 / 2 个模块失败 / 上次成功 10:32`；点击打开编译输出。
- 代码智能的“重新生成影子工程”保持独立入口，不和编译清理混在一起。

## 4. 分期

### P0：能清、能重编、不误删（先做）

交付：

1. `build_state`：清单读写、指纹、失效规则、原子写、损坏回退。
2. `ModuleLayout`：从 `.classpath` 取输出目录/源根，回落 `classes`。
3. `clean_module` / `clean_all`：清单删除、无清单的源码映射删除、junction/越界/锁定保护、dry-run 报告。
4. `rebuild_module` / `rebuild_all`：清理 + 全量编译；保留输出根，保证 compile_order 不丢。
5. 结果账本：`modules` 字段、前端按模块合并、开始不清空、取消保留。
6. `compile_all` 失败隔离：失败模块的依赖方标 `blocked`，独立分支继续。
7. UI：面板下拉、树右键、命令、确认框、状态栏。
8. 测试：清单、清理安全、输出布局、结果合并、失败隔离。

退出标准：

- 能在真实工作区清理一个模块/全部并重编；源码、配置、NC home 零改动。
- 删除源文件后，成功重建会清掉对应旧 class；失败时旧产物不动。
- 取消重编后，上一轮结果和树标记仍在。
- 清理后 `compile_all` 的模块顺序与清理前一致。

### P1：增量可信

交付：

1. 模块级跳过（指纹未变不编）。
2. 变更文件编译；新增/删除/重命名默认全模块。
3. 成功后的旧产物清理。
4. 反向依赖 + ABI 指纹；超阈值回落全量。
5. 单文件保存 + 空闲增量双阶段（开关可见）。
6. 配置变化自动全量；错误日志说明原因。
7. seed 持久化；类索引按 home 分文件。
8. 外部 `.java` 内容变更监听（独立事件，不与文件树刷新混用），批量防抖。

退出标准：

- 只改方法体：模块增量只编 1 个文件；引用方不受影响。
- 改 public 方法签名：引用方自动重编；无旧 class 残留。
- 改 `.classpath`/覆盖表/换 NC home：下一次构建自动全量，日志给出原因。
- 外部 SVN 更新后，模块标记 dirty，按开关触发一次批量构建。

### P2：更快

交付：

1. 类索引预热（工作区打开即后台建）。
2. JVM 参数按模式调优，保留基准数据。
3. 常驻 ecj worker（空闲退出、配置变化重启、内存上限）。
4. 独立模块有界并行（默认 2）。
5. 结构化构建进度与历史（最近 N 次构建报告）。
6. 缓存占用统计与“未跟踪 class”报告。

退出标准：

- 单文件保存 p50 目标 < 0.8s（worker 后 < 0.5s），以真机实测为准。
- 1~5 个文件变更的模块增量 < 3s（不含首次索引）。
- 并行 2 个模块不触发内存/磁盘异常；可一键降为 1。

## 5. 验收矩阵

| # | 场景 | 预期 |
|---|---|---|
| 1 | 清理本模块 | 只删清单内 `.class`；源码/配置/NC home 不变；输出根保留；报告删除数量与失败路径 |
| 2 | 清理全部 | 各模块独立清理；一个失败不阻断其它模块；报告汇总 |
| 3 | 无清单首次清理 | 只删能映射到源码的 class；未识别 class 列出且不删 |
| 4 | 清理后重编全部 | 模块顺序与清理前一致；输出根存在；全部模块都被编译或明确标记 skipped |
| 5 | 删除源文件后重建 | 对应 `.class` 与内部类被清；其它文件产物不动 |
| 6 | 重编失败 | 报告“已清理、重建失败”；不把部分产物说成成功；旧结果按规则保留 |
| 7 | 取消重编 | 上一轮结果、树标记、问题面板不变；日志写明取消 |
| 8 | 模块 A 失败 | A 依赖方标记 blocked；独立 B/C 继续编译并报错；问题面板不把“没编”当“无错” |
| 9 | 改方法签名 | 空闲增量重编引用方；引用方产物时间戳更新；无旧 class |
| 10 | 改 `.classpath` | 自动全量；写入新输出目录；旧目录提示可清理 |
| 11 | 换 NC home / 换 jar | 类索引失效并重建；构建用新 jar；不出现“旧索引找不到类” |
| 12 | 重建类索引 | 内存 CACHE、磁盘索引、seed 全清；下一次编译显示扫描进度；不会静默跳过保存 |
| 13 | 输出目录是 junction | 清理拒绝并解释；junction 目标目录零改动 |
| 14 | 清单损坏/截断 | 忽略清单、走全量、不崩溃；日志可定位 |
| 15 | 工作区切换中构建结束 | 旧结果丢弃；新工作区不被污染 |
| 16 | 服务运行中清理 | 警告；选择停止/不停止；锁定文件失败时报告具体路径 |
| 17 | 输出目录在 SVN 下 | 提示版本控制风险；只删清单内 class；不碰 `.svn` |
| 18 | 并发保存/重编 | 同一时刻只有一轮写产物；后到者排队或明确拒绝；无参数文件互覆盖 |

## 6. 不做项与触发条件

| 不做 | 原因 | 什么时候重新考虑 |
|---|---|---|
| 用 jdt.ls `buildWorkspace` 替代 ecj | 实测 import 152 秒、全量 autobuild 12 分 22 秒；每次启动重建 workspace | jdt.ls 能做到秒级增量导入，且输出能写进 NC 的 `<module>/classes` |
| 每次保存整模块/整工作区编译 | 模块 2000+ 文件，一次几十秒；编辑器会卡死 | 增量图和常驻 worker 落地后再评估“空闲整模块” |
| 每次改动清理产物 | 会把正常增量变成全量，且运行中服务可能缺类 | 不重新考虑 |
| 自动删源码/配置/SVN/NC home | 不可逆且超出编译职责 | 永不 |
| 递归删除含 junction 的目录 | 会沿链接删到用户源码（影子工程已有教训） | 永不 |
| 自动在启动/失败时 clean all | 用户没要求，且可能破坏正在运行的服务 | 不重新考虑 |
| 用 javac 替换 ecj | ecj 与 Eclipse 产物/参数已对齐；换编译器要重做编码、错误解析、jar 选择 | ecj 无法支持目标 Java 版本时 |
| 编译工作区外的关联工程 | 当前 `CompileEnv` 只有一个 `project_root` | 关联工程也纳入工作区模型后 |
| 把“重建代码智能索引”并入编译清理 | jdt.ls 重建 152 秒起步，语义也不同 | 不重新考虑；保持两个入口 |
| 无确认的一键全删 | 与“安全删除”冲突 | 永不 |

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 清理时服务正在运行，class 被占用 | 检测服务状态；删除失败逐文件报告；提供“停止服务后重试” |
| 输出目录含手工放置的 class | 默认只删清单/源码映射内的；未识别 class 只报告不删 |
| 反向依赖近似导致漏编 | ABI 不确定、新增/删除源、索引不完整一律全模块；通配 import 按包过度连边（宁可多编） |
| 清单过大（每模块数千源文件） | 紧凑二进制；只存必要字段；损坏即全量；不把清单放进工作副本 |
| 并行编译内存/磁盘压力 | 默认并发 2，可设 1；只在独立模块间并行；不并行共享输出目录的模块 |
| 常驻 worker 泄漏/占内存 | 空闲超时退出；配置变化重启；内存上限；状态栏可停止 |
| 清理后输出根消失导致依赖顺序丢失 | clean 永不删输出根；`compile_order` 改用 `.classpath` 声明而不是“目录存在” |
| 外部改动监听风暴（SVN 更新） | 防抖 + 按模块合并 + 单次批量构建；与文件树刷新事件分离；可关闭 |
| 改输出目录后旧 class 仍在旧路径 | 账本记录旧路径，UI 明确提示；不自动删 |

## 8. 建议的开工顺序

1. **先做账本和布局**：`build_state` + `.classpath` 输出/源根解析 + 结果 `modules` 字段。没有这一步，清理和增量都不安全。
2. **再做清理/重编**：`clean_module/clean_all/rebuild_*` + 安全删除 + UI。这是用户当前最直接的诉求。
3. **然后做索引入口**：`reindex`、`cache_info`、预热、seed 持久化。先解决“换 jar 之后越编越怪”。
4. **最后做增量**：模块跳过 → 变更文件 → 反向依赖/ABI → 空闲增量。每一步都要保留“条件不满足就全量”的退路。
5. **P2 再碰 worker/并行**：先把正确性和可解释性做稳，再拿启动时间开刀。

## 9. 水平定位：这是主流 IDE 基线，不是行业顶尖

先给结论：**按这份方案做完 P0/P1，在 NC 这类遗留 Java 工作台里算靠前；放到 IntelliJ / Gradle / Bazel 这一档，还不是顶尖。**

| 对标对象 | 它的核心做法 | 本方案的位置 |
|---|---|---|
| Eclipse JDT | 保存文件后按资源增量构建；输出目录 + 问题标记 | P0/P1 能追平，并在结果账本、清理安全性、输出目录一致性上更好 |
| IntelliJ IDEA | 增量构建只编变化类并递归编依赖；有独立构建进程与持久化缓存；后台自动构建（[官方文档](https://www.jetbrains.com/help/idea/compiling-applications.html)、[External Builder API](https://plugins.jetbrains.com/docs/intellij/external-builder-api.html)） | P2 的 worker + 反向依赖能接近“形状”，但缓存成熟度、语言特性覆盖、长期稳定性还差一档 |
| Gradle | 任务输入/输出快照、增量编译、compile avoidance：依赖方 ABI 兼容就不重编（[增量构建](https://docs.gradle.org/current/userguide/incremental_build.html)、[Java 插件](https://docs.gradle.org/current/userguide/java_plugin.html)） | P1 的源码级 ABI + 反向依赖是近似版；Gradle 用 classpath ABI 快照，精度更高，且有本地/远程构建缓存 |
| Bazel | 动作图 + action cache + 内容寻址存储；输入、命令、环境变量共同决定 action key（[Remote caching](https://bazel.build/remote/caching)） | 不在一个维度。我们没有 hermetic 输入、没有跨分支/跨机器缓存、没有沙箱与远程执行 |

差距主要在五个地方：

1. **依赖图精度**：我们 P1 用 package/import/同包引用 + 源码级 ABI 指纹，宁可多编。Gradle 用 classpath ABI 快照，能准确区分“ABI 兼容的改动”和“必须重编的改动”；Bazel 的 action key 更是内容寻址。要做到顶尖，得读 class 文件级 ABI，而不是猜源码。
2. **缓存层级**：本方案只有“模块清单 + 类索引”，没有跨工作区/跨分支可复用的构建缓存。IntelliJ 有持久化构建缓存，Gradle/Bazel 有本地和远程缓存。
3. **执行模型**：本方案是 IDE 内嵌构建，P2 才上常驻 worker 和有界并行；IntelliJ 有独立构建进程，Gradle 有 daemon，Bazel 有沙箱化 worker 与远程执行。
4. **可复现性**：我们没有 hermetic 输入、没有 classpath 归一化、没有“同一输入产出完全一致”的验证。Bazel 的核心价值就在这里。
5. **可观测性**：本方案是日志 + 进度；顶尖构建系统有构建事件协议、每 action 的缓存命中/失效原因、构建扫描。BSP 这类标准就是为了让 IDE 和构建工具解耦（[BSP](https://build-server-protocol.github.io/)）。

为什么**不建议**在这个产品上追 Bazel 级：

- NC 工程没有可靠的构建描述，classpath 大量来自 NC home、`.classpath`、覆盖表和隐式约定；做 hermetic 动作图等于先重建一套 NC 构建系统，成本和风险都远超收益。
- 用户当前的痛点是“清不干净、编不准、看不出状态”，不是“跨机器复用构建缓存”。
- 正确目标不是“理论最强”，而是“在这个 7000+ jar、2000+ 文件/模块、Java 8 的环境里，比 Eclipse 默认链路更准、比裸 ecj 更省心”。

如果要往“顶尖”再走一步，优先级最高的不是更多按钮，而是两件事：

1. **class 文件级 ABI + 精确依赖图**，并用“增量结果 == 全量结果”的差分测试做门禁。
2. **本地内容寻址构建缓存**（源码 + classpath + 编译器参数做 key），先服务分支切换和重复构建，不碰远程执行。
