### 1. 重构重新基准化磁盘冲突，覆盖外部修改

位置：[refactorWorkbench.ts:57](D:/AItool/winapp/nc-workbench/desktop/src/lib/refactorWorkbench.ts:57)，核心57–61行；关联 `useExternalReload.ts:24` 和 `workspace_edit.rs` 的预检。

触发：打开Java文件并产生未保存编辑；Eclipse或外部工具再修改同一磁盘文件；在工作台执行重命名、改签名等重构并应用。

模型有未保存内容时外部刷新正确地保持旧模型，但重构只比较服务端快照与模型。它把后来读取的新磁盘内容和mtime直接设为 `expectedText/expectedMtimeMs`，使后端预检接受这次覆盖，而写入正文仍由旧模型计算。预览只显示模型差异，没有提示即将覆盖的外部改动。

实际函数内存探针确认：旧模型含 `local`，磁盘含 `external`，准备计划成功返回 `expectedText=external`、`text=local`。新磁盘内容可能进入历史，但需要手工找回，不能代替冲突保护。

建议：对有模型的文件核对标签保存的磁盘基线；发现外部变动先解决冲突，不能默默将其作为合法写入基线。

### 2. 参数改名捕获原字段引用，代码仍能编译但结果改变

位置：[SignatureWorkbenchHandler.java:173](D:/AItool/winapp/nc-workbench/desktop/src-tauri/jdtls-ext/src/ncforge/jdt/SignatureWorkbenchHandler.java:173)，核心173–177行；参数校验129–140行只检查参数彼此重名。

原代码：

```java
class C {
    int value = 10;
    int m(int x) { return value + x; }
}
```

把参数 `x` 改为 `value`，当前AST替换更新旧参数引用，却不处理原字段引用，生成 `int m(int value) { return value + value; }`。`m(5)` 从15变成10，编译器不会报错。

证据：直接核对生产AST绑定替换逻辑；对其对应的转换前后最小样例，用本机Java8实际编译执行，两个版本均编译成功，输出分别为15和10。本次没有重新调用真实JDT重构服务，生成形状来自生产替换逻辑。

建议：检查新参数名的作用域绑定冲突；拒绝冲突，或为原字段引用加正确的接收者限定。

### 3. 恢复缺失文件时漏备份仍存在的未保存正文

位置：[changeShelf.ts:27](D:/AItool/winapp/nc-workbench/desktop/src/lib/changeShelf.ts:27)，27–29行；关联 `prepareShelfRestore` 第23行和 `applyWorkbenchPlan` 模型替换/标记已保存。

触发：已有旧副本的文件在磁盘上被外部删除，但打开的编辑器仍有更新的未保存正文；用户恢复旧副本。

恢复计划读取了当前模型正文，但因磁盘不存在、`expectedMtimeMs=null`，该文件被排除恢复前备份。本地历史也跳过此项。应用随后用旧副本覆盖模型并标为已保存；用户关闭标签不会遇到未保存提示，新正文没有持久恢复副本。与窗口承诺“恢复前的当前编辑内容会另存为一份副本”不符。

实际函数内存探针确认：计划 `beforeText=NewerUnsaved`、写入 `OlderShelf`；没有调用 `change_shelf_create`。

建议：缺失磁盘文件但模型仍存在时也先持久保存当前正文，或阻止恢复直到用户处理该内容。

## P2：功能缺陷

### 4. 泛型特化实现被覆盖成接口类型变量

位置：[SignatureWorkbenchHandler.java:162](D:/AItool/winapp/nc-workbench/desktop/src-tauri/jdtls-ext/src/ncforge/jdt/SignatureWorkbenchHandler.java:162)，162–165行。

触发：`interface I<T>{void m(T value,int n);}` 与 `class C implements I<String>{public void m(String value,int n){}}`；从接口仅重排参数。

所有关联声明都采用窗口传入的接口类型文本，导致实现被改为 `m(int n,T value)`，而C没有声明T。本机Java8核验原样例编译通过、对应转换后编译失败；生产AST第164行确实无条件覆盖关联参数类型。本次真实JDT未复跑此样例。

建议：未改变的参数类型保留各关联方法的实际类型；需要改变时执行正确的泛型替换和合法性检查。

### 7. 注解中的命名参数导致漏字段，生成构造器不能编译

位置：[javaModel.ts:370](D:/AItool/winapp/nc-workbench/desktop/src/lib/javaModel.ts:370)，370–372行。

触发：类中有 `@SuppressWarnings(value = "unchecked")` 方法，其后紧跟 `private final String token;` 和 `private int value;`，原构造器正确初始化token。

`head.includes("=")` 把注解方法当成字段初始化，保留方法头并吞掉后面的首个字段。构造器生成只识别value，新增构造器不初始化final token；getter、toString等也漏字段。

实际当前/HEAD基线模型对比探针：基线字段 `[token,value]`，当前 `[value]`。

建议：剥离注解或按声明层解析赋值符号，不能以整个方法头是否含等号判断字段初始化。

### 8. 从nc-library文档跳出后，后退无法返回

建议：统一识别支持的虚拟URI，按对应虚拟打开入口恢复历史。

### 9. 主JVM退出后持续输出的子进程使运行任务无法停止

位置：[java_run.rs:323](D:/AItool/winapp/nc-workbench/desktop/src-tauri/src/java_run.rs:323)；关联348–361行。

触发：main启动继承stdout的子进程后退出，子进程持续以短于40ms的间隔输出。

`completed` 已有值后取消和总超时检查被跳过；两秒管道等待期限只在 `recv_timeout` 超时分支检查。持续输出使该分支一直不执行，即使输出已截断也一样。任务一直占用单飞槽，停止按钮只设置取消标志，不能结束此状态。

证据：生产循环和 `java_run_cancel` 调用链核对；本次未启动真实子进程复现。

建议：完成后的绝对等待期限仍在每轮检查，并保留取消/子进程清理能力。
